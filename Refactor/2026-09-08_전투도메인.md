### ① A~G 묶음 (52개 파일)

#### 2-1) 최적화 측면 용이성 — 점검 완료

점검 대상: A~G 전 파일. 특히 매 틱 실행되는 성능 민감 로직(`BattleSimulationLoop.Tick`, `BattleCharacterUnit.Tick`, `MoraleWaveCoordinator.Update`, `LinearScanUnitSpatialQuery`)을 집중 확인.

**문제점 없음.** 이 도메인은 프로젝트에서 가장 성능 민감한 영역(매 틱 실행)인데도 최적화 근거가 코드 주석에 이미 명시적으로 남아있다:
- `LinearScanUnitSpatialQuery`/`BattleCharacterUnit` 자체가 "지금 규모(아군 최대 16, 적 3~5)에서는 O(n)으로 충분, 커지면 공간 분할로 교체(OCP)"라고 스스로 문서화 - 실제로 `sqrMagnitude`로 `sqrt` 호출을 필요한 쌍에서만 수행하는 등 세부 최적화도 이미 돼 있다.
- `BattleCharacterUnit`의 타겟 고정(스티키 타겟팅)은 "매 프레임 O(n) 재탐색을 피하기 위한 의도된 선택"이라고 명시 - 타겟이 죽거나 재탐색 트리거(피격 등) 조건에서만 재탐색.
- `BattleSimulationLoop.Tick`의 `enemyTargets` 재구성(매 틱 `List` 새로 생성)은 유일하게 매 틱 할당이 있는 지점이지만, 규모(최대 18)를 명시하고 "무시할 만하다"고 스스로 인정 - 실측 없이도 타당한 판단.
- 테이블 자산 조회(`CharacterStatsTableAsset.TryGetEntry` 등)는 선형 탐색이지만 전투 시작/유닛 생성 시점(1회성)에만 호출되고 엔트리 수도 작아(직업 3종/적 타입 3종) 문제 없음 - `RoleGroupTacticsCatalogAsset` 등 이미 검증된 패턴과 동일.
- `InMemoryUnitConditionRepository`는 `Dictionary`/`HashSet` 기반 O(1).

**교차 확인**: 처음 발견하는 기준이라 대상 없음.

#### 2-2) SOLID 원칙 준수 여부 — 점검 완료

**문제점 1 — 재사용(DRY): 테이블 자산 5개가 동일한 "키로 엔트리 찾기" 선형 탐색을 각자 구현**
- `CharacterStatsTableAsset.TryGetEntry`, `EnemyStatsTableAsset.TryGetEntry`, `EnemyEncounterCompositionTableAsset.TryGetEntry`, `CharacterStringsTableAsset.TryGetLabel`, `EnemyStringsTableAsset.TryGetLabel` 5개 메서드가 전부 "`foreach entries; 키 필드 일치하면 entry/label 반환; 없으면 실패 반환`"이라는 동일한 로직을 타입만 바꿔 반복한다.
- `TacticsPanel.IndexOfOption`(§6 공통 추가분에서 이미 제네릭 1개로 통합한 사례, `adae71b`)과 완전히 같은 성격의 중복 - 제네릭 `TryGetEntry<TEntry, TKey>(entries, key, keySelector, out entry)` 헬퍼 하나로 통합 가능하다.
- 참고: `H`/`I` 묶음(Tactics/)의 `RoleGroupTacticsCatalogAsset.TryGetEntry`도 같은 패턴을 쓰는 것으로 보인다(공통 §6 점검 때 이미 확인) - 이 묶음(A~G)에서 헬퍼를 만들면 H/I 점검 때 그 인스턴스에도 재사용할 수 있다.

**교차 확인**: 최적화(2-1)와 충돌 없음 - 테이블 조회는 이미 "빈도 낮음(설정 시점 1회)이라 선형 탐색이 성능상 문제없다"고 확인했고, 이번 SOLID 지적은 성능이 아니라 코드 중복이 문제라 서로 다른 관점.

#### 2-3) 확장성 측면 및 하드코딩 여부 — 점검 완료

**문제점 1 — `TableEnemyTypeCompositionProvider.AllTypes`가 `EnemyType` enum의 전체 값 목록을 하드코딩으로 복제**
- `TableEnemyTypeCompositionProvider.cs` 줄 18: `private static readonly EnemyType[] AllTypes = { EnemyType.Marauder, EnemyType.Monster, EnemyType.Adversary };` - `EnemyType` enum(`Marauder=1`/`Monster=2`/`Adversary=3`)의 값 목록을 그대로 다시 나열한다.
- 지금은 정확히 일치하지만(3개 vs 3개), `EnemyType`에 새 값이 추가되면 `AllTypes`를 함께 고치는 걸 잊어도 **컴파일은 통과하고 그 타입은 조용히 인카운터 무작위 선택 후보에서 영원히 빠진다** - CLAUDE.md가 경계하는 "컴파일은 통과하되 런타임에 조용히 깨지는" 유형의 하드코딩.
- `Enum.GetValues(typeof(EnemyType))`로 대체하면 enum과 항상 동기화된다 - 다만 캐스팅 비용/배열 순서가 선언 순서에 의존한다는 트레이드오프가 있어 수정안 단계에서 실익 대비 비용을 따진다.

**교차 확인**: 최적화(2-1)·SOLID(2-2)와 충돌 없음 - 이번 건은 다른 파일/관심사(enum 값 목록 동기화)다.

#### 3. 수정안 도출 (① A~G 묶음)

**수정 O — `TableEntryLookup`(제네릭 헬퍼) 신설, 테이블 자산 5개에 적용**
(SOLID 문제점 1 해결)

- `Core/Battle/TableEntryLookup.cs`(internal static) 신설: `TryFind<TEntry, TKey>(IReadOnlyList<TEntry> entries, TKey key, Func<TEntry, TKey> keySelector, out TEntry entry)` - `EqualityComparer<TKey>.Default`로 비교(`TacticsPanel.IndexOfOption` 수정 때와 동일 접근).
- `CharacterStatsTableAsset`/`EnemyStatsTableAsset`/`EnemyEncounterCompositionTableAsset.TryGetEntry`는 `TableEntryLookup.TryFind(entries, key, e => e.Xxx, out entry)` 한 줄로 축소.
- `CharacterStringsTableAsset`/`EnemyStringsTableAsset.TryGetLabel`은 엔트리 자체가 아니라 `.Ko` 필드만 꺼내야 해서 완전한 한 줄은 아니지만, 내부 `foreach` 선형 탐색은 `TableEntryLookup.TryFind` 호출로 대체하고 엔트리에서 `ko`를 꺼내는 2~3줄만 남긴다.
- 이 헬퍼는 H/I 묶음(Tactics/) 점검 때 `RoleGroupTacticsCatalogAsset.TryGetEntry` 등 유사 패턴에도 재사용할 수 있다(그 묶음 점검 시 별도 판단).

**수정 P — `TableEnemyTypeCompositionProvider.AllTypes`를 `Enum.GetValues`로 대체**
(확장성 문제점 1 해결)

- `private static readonly EnemyType[] AllTypes = { EnemyType.Marauder, EnemyType.Monster, EnemyType.Adversary };` → `private static readonly EnemyType[] AllTypes = (EnemyType[])Enum.GetValues(typeof(EnemyType));`
- `using System;`은 이미 파일에 있다. 현재 enum 값과 정확히 일치해 동작 변화 없음 - 앞으로 `EnemyType`에 값이 추가/제거돼도 이 배열이 자동으로 따라간다.

#### 4. 통합 점검 (① A~G 묶음)

- **최적화**: 수정 O·P 둘 다 설정 시점(전투 시작/유닛 생성 1회) 호출부라 런타임 프레임 비용과 무관 - 오히려 O는 `foreach` 탐색 로직 자체는 그대로라 성능 영향 없음, P는 `Enum.GetValues`가 배열을 매번 새로 할당하지만 `static readonly`로 1회만 호출되므로 무관.

- **기준 간 상충 여부**: 없음 - 수정 O(`TableEntryLookup` 신규 + 5개 파일)와 수정 P(`TableEnemyTypeCompositionProvider` 1개 파일)는 겹치는 파일이 없다(`TableEnemyTypeCompositionProvider`도 수정 O로 `TryGetEntry` 호출부가 바뀔 순 있으나, 그 클래스 자체는 `TryGetEntry`를 정의하지 않고 호출만 하므로 무관 - 실제로 `TryGetEntry`를 정의하는 건 `EnemyStatsTableAsset`/`EnemyEncounterCompositionTableAsset`이다).

### ② H 묶음 (~48개 파일: 타겟선택/포지셔닝/추격정책/자기보존/적인식/활동반경/프로필조립)

#### 2-1) 최적화 측면 용이성 — 점검 완료

점검 대상: H 전 파일. 매 틱 실행되는 조율자(`FrontlineFormationCoordinator`, `RangedSurroundCoordinator`)와 인식 추적기(`EnemyRecognitionTrackerBase`)를 특히 집중 확인 - 이 도메인에서 가장 복잡하고 성능 민감한 로직이다.

**문제점 없음.** A~G보다도 한 단계 더 철저하게 최적화 근거가 문서화돼 있다:
- `FrontlineFormationCoordinator`/`RangedSurroundCoordinator`는 매 틱 실행되는 군집화(Union-Find)·기하 계산·교차 판정 전체에 걸쳐 **10개 이상의 재사용 버퍼**(`unionFindParent`/`clusterPool`/`protectionCandidateBuffer`/`recognizedUnionBuffer` 등)를 필드로 미리 만들어두고 매 틱 `Clear()` 후 재사용한다 - "§12.8과 같은 이유로 매 틱 새 List/Dictionary를 할당하지 않는다"는 동일 원칙이 코드 전체에 일관되게 적용됨.
- `EnemyRecognitionTrackerBase.recognizedBuffer`도 같은 패턴 - "재할당을 피하기 위한 최적화 결정"이라고 명시.

- 나머지(타겟 셀렉터 7종/포지셔닝 전략 6종/추격 정책 5종/자기보존 4종/인식 추적기 3종/활동반경 3종)는 전부 단일 순회 O(n) 이하의 짧은 순수 계산 클래스로, 할당·폴링 문제 없음.

**교차 확인**: 처음 발견하는 기준이라 대상 없음.

#### 2-2) SOLID 원칙 준수 여부 — 점검 완료

**문제점 1 — 재사용(DRY): `FrontlineFormationCoordinator`와 `RangedSurroundCoordinator`가 `ContainsReference`/`ComputeAveragePosition` 정적 헬퍼를 바이트 단위로 중복 구현**

- `ComputeAveragePosition(IReadOnlyList<IDamageable> units)`: 두 클래스 모두 "0개면 zero, 아니면 위치 합/개수" 동일 구현.

**교차 확인**: 최적화(2-1)와 충돌 없음 - 이번 지적은 코드 중복이 문제이지 성능이 아니다(두 메서드 다 이미 O(n) 그대로 유지해도 최적화 결론과 상충하지 않음).

#### 2-2) SOLID 원칙 준수 여부 — 점검 완료

**문제점 1 — 재사용(DRY, 묶음 경계 초월): `BattleTestFieldLayout`(J)이 A~G에서 이미 점검을 마친 `BattleFieldLayout`(카테고리 E, 프로덕션)과 사실상 같은 코드**

#### 2-3) 확장성 측면 및 하드코딩 여부 — 점검 완료

**문제점 1 — `BattleTestSpawnPointReservations.Composition`이 `EnemyType` 3종을 이름 있는 필드로 하드코딩**
- `Composition` 구조체가 `int Marauder`/`int Monster`/`int Adversary` 3개 필드로 타입별 개수를 저장하고, `GetCount(EnemyType type)`도 이 3개를 나열한 `switch`(기본값 0)로 조회한다.

**교차 확인**: 최적화(2-1)·SOLID(2-2)와 충돌 없음.

## 5. 후속 처리 — SOLID 문제점 2(배틀 테스트 로스터 중복) 완료 (2026-09-21)

- **설계(설계 28번, 4결정 모두 추천안 확정)**: (1) 통일 식별자 `BattleTestUnitKind`(진영 + 정수 종류값, enum 변환은 이 구조체 한 곳에 격리), (2) 진영별 차이를 `IBattleTestSide` 구현체 2개(아군/적)가 흡수 — 로스터, 사기/파동 인스턴스, 기본 스탯 조회, 미리보기/전투 유닛 생성, (3) 팔레트 아이콘은 직렬화 필드 3개 유지 + `Kind` 조회 프로퍼티만 추가(씬 재저장/인스톨러 수정 없음), (4) 적 구성 편집/스폰 포인트 예약/적 로스터 비움 이벤트는 범위 제외. 로스터는 클래스 1개, 인스턴스는 진영별 2개(항목 Id는 진영별 0부터).
