## 2. 기준별 순차 점검 (문제점 식별만)

### 2-1) 최적화 측면 용이성 — 점검 완료

점검 대상: A~C 전 파일(1단계 누락분 포함).

**문제점 없음.** 이 씬 전용 코드는 대체로 규모가 작은 디버그/에디터 전용 데이터(지도 위 도시·경로)를 다루는데, 이미 CLAUDE.md 최적화 컨벤션을 잘 따르고 있다:
- `SceneUIRoot.TryGetElement`(공통 §0에서 이미 확정) 기반 조회 외에, `InMemoryTripCityRepository`/`InMemoryTripRouteRepository`가 각각 `Dictionary<int, TripCity>`/`HashSet<(int,int)>`+인접 목록으로 O(1) 추가/삭제/조회를 제공한다. `IsReachable`의 BFS도 자체 주석대로 "디버그 지도 규모(도시 수십 개 이하)"라는 명시적 전제 하에 적절한 선택.
- `TripMapInteractionCoordinator.RefreshLinesForCity`는 전체 노선이 아니라 `routeRepository.GetConnectedCityIds(cityId)`(인접 목록)만 순회 — 드래그 중 매 프레임 호출되는데도 전체 스캔을 피한다.
- `MoveCityDragBehavior`/`DrawRoadDragBehavior`의 `OnDragUpdate`(포인터 이동마다 호출)는 좌표 변환 1회 + 필드 갱신뿐, 할당이나 순회가 없다.
- `TripMapView`/`HubUIController`/`TripPanel` 전부 이벤트/콜백 기반(`OnScroll`, `onClick`, `sceneRevealSignal.SceneRevealed` 등)이고 `Update()` 폴링이 없다.
- 마커/연결선(`TripDebugCityMarkerView`/`TripDebugRoadLineView`)은 `CreateMarker`/`CreateLineInstance`에서만 `Instantiate`하고, 이후 삭제 시점(저장소 이벤트)에만 `Destroy` — 매 프레임 재생성 없음.

**교차 확인**: 처음 발견하는 기준이라 대상 없음.

### 2-2) SOLID 원칙 준수 여부 — 점검 완료

**문제점 1 — 재사용(DRY): "씬에서 SceneUIRoot 찾기" 보일러플레이트가 6개 파일에 거의 그대로 중복**
- `HubUIController.RegisterHubUI`, `TripPanel.RegisterTripUI`(이상 Hub 전용, 이번 라운드 대상), `HubFormationPanel.RegisterFormationUI`, `FieldFormationPanel.RegisterFieldFormationUI`, `TacticsPanel.RegisterTacticsUI`, `FieldUIController.RegisterFieldUI`(이상 §6 공통 추가분에서 이미 처리된 파일들, `adae71b`) 총 6곳이 다음과 동일한 ~12줄 블록을 반복한다:
  ```csharp
  var scene = SceneManager.GetSceneByName(SceneNames.Xxx);
  if (!scene.IsValid()) { Debug.LogWarning(...); return; }
  SceneUIRoot sceneUIRoot = null;
  foreach (var rootObject in scene.GetRootGameObjects())
  {
      sceneUIRoot = rootObject.GetComponentInChildren<SceneUIRoot>(true);
      if (sceneUIRoot != null) break;
  }
  if (sceneUIRoot == null) { Debug.LogWarning(...); return; }
  ```
- 씬 이름과 경고 문구만 다르고 로직은 완전히 동일 - 다른 컨텍스트에서 찾기 로직 자체가 바뀌면(예: 다중 루트 오브젝트 최적화) 6곳을 전부 손으로 고쳐야 한다.
- **근본 원인**: 이 6개 메서드는 전부 `HubUIWiring.Wire`/`FieldUIWiring.Wire`가 호출하는데, 그 두 Wire 메서드는 이미 씬이 로드된 시점에 실행되면서도 `SceneUIRoot`를 직접 조회하지 않고 각 `RegisterXxxUI(...)` 호출부에 맡긴다 - 정작 "이 씬의 `SceneUIRoot`"는 `Wire` 호출 시점에 한 번만 구하면 충분한 값인데 소비자마다 각자 다시 구하는 구조.
- 발견 경위: Hub 전용 코드(`HubUIController`/`TripPanel`)의 SOLID 점검 중 동일 패턴을 목격하고 전체 프로젝트에서 검색해 §6에서 이미 처리된 파일에도 같은 코드가 있음을 확인했다(공통 §6은 그 라운드 시점엔 Formation/Tactics 서브시스템 "내부 로직"만 봤고 이 씬-조회 보일러플레이트는 그때 놓쳤다).

**교차 확인**: 최적화(2-1)와 충돌 없음 - 최적화 관점에서도 이 중복은 콘텐츠 씬 로드마다(Hub 3회, Field 2회) 같은 탐색을 반복하는 낭비이지만, `GetRootGameObjects()` 순회가 씬 로드 시 1회뿐이라 심각도는 낮다(주된 문제는 SOLID/DRY).

### 2-3) 확장성 측면 및 하드코딩 여부 — 점검 완료

**문제점 1 — §1 D항목(씬 전환 커튼 캔버스 값 미검증) 검증 결과: 실제로 어긋남을 확인**
- Bootstrap 라운드에서 "미검증 자리표시자"로 이월했던 값을 이번에 Hub.unity/Field.unity의 실제 `CanvasScaler`와 대조했다.
- `ManagerHierarchyInstaller.EnsureSceneTransitionCurtain`(줄 227~230): `referenceResolution=(1920,1080)`, `screenMatchMode=MatchWidthOrHeight`, `matchWidthOrHeight=0.5`.
- `Hub.unity`(줄 16441~16443)/`Field.unity`(줄 8501~8503) 콘텐츠 씬 `CanvasScaler` 실측값: `referenceResolution=(800,600)`, `screenMatchMode=0`(MatchWidthOrHeight, 모드 자체는 일치), `matchWidthOrHeight=0`. **두 콘텐츠 씬은 서로 일치하지만, 커튼의 하드코딩 값과는 해상도·matchWidthOrHeight 둘 다 다르다.**
- 영향: 화면 해상도가 800×600 기준 비율에서 벗어날수록(특히 세로 비중이 큰 해상도) 커튼의 UI 스케일링 기준이 콘텐츠 씬과 달라져, 씬 전환 시 커튼이 화면 전체를 못 덮거나 슬라이드 연출 위치가 콘텐츠와 어긋나는 시각적 결함으로 이어질 수 있다(코드 주석이 예견했던 "§12 남은 이슈"가 실제로 존재함을 확인).
- `sortingOrder`는 문제 없음 - 커튼(100)이 콘텐츠 씬(0)보다 항상 위에 그려지도록 의도적으로 높였고 실측도 그와 상충하지 않는다.

**교차 확인**: 최적화(2-1)·SOLID(2-2)와 충돌 없음 - 별개 파일/관심사(`ManagerHierarchyInstaller`의 Canvas 설정값 vs 씬 조회 중복).

## 3. 수정안 도출

### 수정 J — `SceneUIRootLocator` 신설 + `HubUIWiring`/`FieldUIWiring`이 씬당 1회만 조회해 하위 컴포넌트에 전달
(SOLID 문제점 1 — DRY 해결. **Bootstrap 매니저 오브젝트 정리 포함**: `HubUIWiring`/`FieldUIWiring`은 `ManagerHierarchyInstaller.WireUIManagerPanels`가 `UIManager` GameObject에 부착하는 Bootstrap 산하 컴포넌트라, 이 둘의 배선 책임 경계를 바로잡는 것 자체가 Bootstrap 매니저 오브젝트 정리에 해당한다.)

- **신설**: `Core/UI/SceneUIRootLocator.cs` — `public static class SceneUIRootLocator { public static bool TryFind(string sceneName, out SceneUIRoot sceneUIRoot) }`. 기존 6곳의 "씬 조회 → 루트 오브젝트 순회 → SceneUIRoot 탐색" 로직을 그대로 옮기고 경고 로그도 유지한다. `EditorUIBuilder`가 Editor 인스톨러들의 공용 저수준 유틸리티인 것과 같은 자리에, 런타임 어셈블리(`Core/UI/`)용으로 둔다.
- **`HubUIWiring.Wire`**: 맨 앞에서 `SceneUIRootLocator.TryFind(SceneNames.Hub, out var sceneUIRoot)` 1회 호출, 실패 시 즉시 반환(로그는 헬퍼가 남김). 이후 `hubUIController.RegisterHubUI(sceneUIRoot, uiManager, sceneRevealSignal)`, `formationPanel.RegisterFormationUI(sceneUIRoot, ...)`, `tripPanel.RegisterTripUI(sceneUIRoot, ...)`, `tacticsPanel.RegisterTacticsUI(sceneUIRoot, ...)`로 전달.
- **`FieldUIWiring.Wire`**: 동일하게 `SceneUIRootLocator.TryFind(SceneNames.Field, ...)` 1회 호출 후 `formationPanel.RegisterFieldFormationUI(sceneUIRoot, ...)`, `tacticsPanel.RegisterTacticsUI(sceneUIRoot, ...)`, `fieldUIController.RegisterFieldUI(sceneUIRoot, ...)`로 전달.
- **6개 소비자 시그니처 변경** (내부 씬 조회 블록 삭제, `SceneUIRoot sceneUIRoot`를 첫 매개변수로 받음 — `TacticsPanel`/`HubFormationPanel`/`FieldFormationPanel`은 더 이상 `string sceneName`을 받지 않아도 된다. 왜냐하면 씬 조회가 사라지고 넘겨받은 `sceneUIRoot`만 쓰면 되기 때문):
  - `HubUIController.RegisterHubUI(SceneUIRoot sceneUIRoot, IUIManager uiManager, ISceneRevealSignal sceneRevealSignal)`
  - `TripPanel.RegisterTripUI(SceneUIRoot sceneUIRoot, IUIManager uiManager, IGameManager gameManager, IFormationReader formationReader, ITripInfoProvider tripInfoProvider, ISceneRevealSignal sceneRevealSignal, ITripCurrentLocationReader currentLocationReader, ITripDestinationAssigner destinationAssigner)`
  - `HubFormationPanel.RegisterFormationUI(SceneUIRoot sceneUIRoot, ICaravanRosterProvider rosterProvider, IFormationRepository repository, IUnitConditionRepository conditionRepository, IUIManager uiManager)`
  - `FieldFormationPanel.RegisterFieldFormationUI(SceneUIRoot sceneUIRoot, ICaravanRosterProvider rosterProvider, IFormationRepository formationRepository, IUnitConditionRepository conditionRepository, IFieldFormationActivityRepository activityRepository, IUIManager uiManager)`
  - `TacticsPanel.RegisterTacticsUI(SceneUIRoot sceneUIRoot, ITacticsRepository repository, IUIManager uiManager)`
  - `FieldUIController.RegisterFieldUI(SceneUIRoot sceneUIRoot, IUIManager uiManager, ISessionState sessionState, IEncounterManager encounterManager, IBattleController battleController, IBattleResultSource battleResultSource, IDefeatConsequenceSource defeatConsequenceSource, IBattleSimulationEvents battleSimulationEvents, IGameManager gameManager, ISceneRevealSignal sceneRevealSignal, IUnitConditionRepository unitConditionRepository, ITripCurrentLocationRepository currentLocationRepository, ITripDestinationAssigner destinationAssigner, IFieldFormationActivityRepository fieldActivityRepository)`
- 동작은 기존과 동일 - 실패 조건(씬/`SceneUIRoot` 못 찾음)이 이제 `Wire()` 진입점 하나로 합쳐질 뿐, 원래도 같은 씬을 6곳이 각자 조회해 항상 같은 성패를 냈으므로 관찰 가능한 동작 변화 없음.

### 수정 K — 씬 전환 커튼 `CanvasScaler` 값을 Hub/Field 콘텐츠 씬 실측값으로 정정
(확장성 문제점 1 해결)

- `ManagerHierarchyInstaller.EnsureSceneTransitionCurtain`의 `scaler.referenceResolution`을 `(1920,1080)` → `(800,600)`으로, `scaler.matchWidthOrHeight`를 `0.5f` → `0f`로 변경. `screenMatchMode`(`MatchWidthOrHeight`)는 이미 일치해 그대로 둔다.
- 코드 주석(줄 214~216 "미검증 자리표시자")을 "Hub.unity/Field.unity 실측값과 대조해 확정됨(2026-09-08, Docs/Refactor/2026-09-08_Hub.md §2-3)"으로 갱신 - 향후 콘텐츠 씬 해상도 설정이 다시 바뀌면 이 주석이 대조 필요성을 다시 알려준다.

## 4. 통합 점검

- **최적화**: 수정 J·K 둘 다 Editor 전용 코드(K)이거나 씬 로드 시 1회만 실행되는 배선 로직(J)이라 런타임 프레임 비용과 무관 - 오히려 J는 중복 탐색을 6회→2회로 줄여 최적화 방향과도 부합.
- **SOLID**: 수정 J가 2-2에서 식별한 DRY 문제를 직접 해소한다. 새로 만든 `SceneUIRootLocator`가 단일 책임(씬 이름 → SceneUIRoot 조회)만 가져 SRP 위반 없음.
- **확장성/하드코딩**: 수정 K가 2-3에서 확인한 실측 불일치를 해소한다. 수정 J는 향후 콘텐츠 씬이 추가돼도(`ContentSceneId`에 새 값 + 새 `XxxUIWiring`) 씬 조회 로직을 다시 복붙할 필요 없이 `SceneUIRootLocator.TryFind`만 호출하면 되므로 확장성도 개선.
- **기준 간 상충 여부**: 없음 - 수정 J(8개 파일: 신규 1 + `HubUIWiring`/`FieldUIWiring`/6개 소비자)와 수정 K(`ManagerHierarchyInstaller.cs` 1개 파일, 그것도 J가 손대지 않는 다른 메서드)는 겹치는 파일이 없다.
- **결론**: 수정안 J·K가 세 기준을 모두 만족하며 서로 충돌하지 않는다. 통합 점검 통과.

- Unity 에디터를 직접 열어 플레이 테스트하는 회귀 확인은 컨벤션에 따라 이번 단계에 포함하지 않는다. **사용자 확인 필요**: `Tools > Game > Build Bootstrap Scene`(또는 필요 시 Hub/Field 씬 각각 재실행) → 씬 저장 → Hub/Field UI 전체(상단 버튼/정비창/방향성 지시/상행 준비) 정상 동작 확인, 씬 전환 시 커튼이 화면을 제대로 덮는지(특히 창 크기/해상도를 바꿔가며) 확인.

## 6. 수정 K 정정 — 회귀 발견·재수정 (2026-09-08)

사용자가 실전 확인 중 Hub↔Field 전환 시 검은 커튼과 콘텐츠 사이에 빈 화면이 보이는 회귀를 발견(스크린샷 확인). 원인 조사 결과 §2-3 점검이 불완전했음이 드러났다:

- §2-3에서는 Hub.unity/Field.unity CanvasScaler의 `referenceResolution`/`matchWidthOrHeight`만 확인하고 **`uiScaleMode`(스케일 모드 자체)를 확인하지 않았다**. 실측 결과 Hub/Field 콘텐츠 캔버스는 `uiScaleMode=0`(`ConstantPixelSize`, `scaleFactor=1`) - `referenceResolution`/`matchWidthOrHeight` 필드는 이 모드에서 아예 무시된다.
- 수정 K는 커튼을 `ScaleWithScreenSize` 모드로 그대로 둔 채 `referenceResolution`만 800x600으로 맞췄다 - 실제로는 `SceneTransitionEffectController.PlayTransition`이 콘텐츠 캔버스(1:1 픽셀 단위)의 `contentRoot.rect.width`를 커튼의 `anchoredPosition`에 그대로 대입하는데, 커튼이 여전히 `ScaleWithScreenSize`라 그 숫자가 커튼 자신의 scaleFactor(1920x1080 화면 기준 2.4배)로 다시 배율돼 슬라이드 시작 위치가 화면 폭보다 훨씬 크게 밀려났다 - 콘텐츠가 다 빠져나간 뒤에도 커튼이 아직 화면에 들어오지 않아 빈 화면이 노출됐다.
- 이전(1920x1080/matchWidthOrHeight=0.5)에 문제없었던 이유: 그 referenceResolution이 테스트 해상도(1920x1080)와 우연히 정확히 일치해 scaleFactor가 항상 1이 나왔을 뿐 - 처음부터 스케일 **모드** 자체가 콘텐츠 씬과 달랐던 잠재 결함이었고, 이번 해상도 값 변경으로 그 결함이 드러난 것이다.

**재수정**: `EnsureSceneTransitionCurtain`의 `scaler.uiScaleMode`를 `ConstantPixelSize`로, `scaler.scaleFactor`를 `1f`로 변경(`referenceResolution`/`screenMatchMode`/`matchWidthOrHeight`는 이 모드에서 무의미해 제거). 이제 커튼·Hub·Field 세 캔버스가 전부 "1 canvas unit = 1 화면 픽셀"로 고정돼 해상도가 바뀌어도 어긋나지 않는다. `dotnet build Game.Core.Editor.csproj` 오류 0건 확인.

**교훈**: CanvasScaler를 다른 캔버스와 "맞춘다"고 할 때는 `referenceResolution`/`matchWidthOrHeight` 같은 세부값 이전에 `uiScaleMode` 자체가 같은지부터 확인해야 한다 - 모드가 다르면 세부값을 아무리 맞춰도 무의미하다.
- **사용자 확인 필요**: Unity에서 `Tools > Game > Build Bootstrap Scene` 재실행 → 씬 저장 → Hub↔Field 전환 시 커튼-콘텐츠 사이 빈 화면이 사라졌는지 확인.
