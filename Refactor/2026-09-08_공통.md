## 2. 기준별 순차 점검 (문제점 식별만)

### 2-1) 최적화 측면 용이성 — 점검 완료

점검 대상: A~G 전 파일. DI 인프라(`DependencyManager`)와 대부분의 매니저(`UIManager`, `GameManager`, `SceneLoader` 등)는 `Dictionary` 기반 O(1) 조회, 초기화 시 1회 수집, 이벤트 기반 반응 등 CLAUDE.md 최적화 컨벤션을 그대로 따르고 있다. `SessionStateTracker.Update()`는 시간 누적 타이머라 정당한 `Update()` 사용(입력 폴링이 아님).

**문제점 1건 식별**: `InMemoryFieldFormationActivityRepository.cs`(F 카테고리)
- `TryGetActivity`/`IsSlotReserved`/`IsUnitBusy`(줄 34~41)가 `List<FormationActivity>`에 대해 LINQ `FirstOrDefault`/`Any`(선형 탐색 + 람다 클로저 할당)를 쓴다. `Cancel`/`RedirectMove`도 `FindIndex`로 선형 탐색.
- CLAUDE.md 최적화 컨벤션("ID 조회는 `Dictionary<string, T>`로 O(1) 처리, `panelsById`/`elementsById` 사례")과 이 프로젝트에 이미 확립된 패턴에 어긋난다.
- 심각도: 낮음 — 활동 개수가 배치 상한(카테고리당 5개, 기획 11번)으로 항상 작아 체감 성능 영향은 없다. 다만 일관성 관점에서 지적 대상.

### 2-2) SOLID 원칙 준수 여부 — 점검 완료

**문제점 1 — ISP: `IDependencyRegistrar`가 쓰기/읽기를 분리하지 않음**
- `IDependencyRegistrar`(`Core/Dependency/IDependencyRegistrar.cs`)가 `Register`(쓰기)와 `Resolve`/`TryResolve`(읽기)를 한 인터페이스에 묶어 제공한다. `IManagedComponent.RegisterSelf(IDependencyRegistrar)`는 쓰기만, `ResolveDependencies(IDependencyRegistrar)`는 읽기만 필요한데도 항상 전체 인터페이스를 받는다.
- CLAUDE.md가 이미 명시한 ISP 사례(`IFormationReader ← IFormationRepository`)와 같은 종류의 문제.
- **파급력 경고**: 이 인터페이스는 프로젝트의 모든 `IManagedComponent` 구현체(전역 매니저 8개 + 저장소 8개 + 향후 추가분)가 예외 없이 쓰는 핵심 기반 인터페이스라, 분리 시 변경 범위가 전역적이다. 수정안 단계에서 실익 대비 비용을 반드시 따져야 한다.

**문제점 2 — ~~DIP/OCP: EncounterManager가 전략을 직접 new로 생성~~ (2-3 점검 중 정정: 위반 아님)**
- ~~`EncounterManager.cs` 줄 19의 `new RandomEncounterRule()`이 `BattleManager`의 sibling 컴포넌트 패턴과 어긋난다~~ — `RandomEncounterRule.cs`의 클래스 주석을 확인한 결과, 이는 **의도된 설계**였다: "같은 GameObject에 `FixedEncounterRule`이 추가되면 `GetComponent<IEncounterRule>()`로는 어느 쪽인지 구분할 수 없어 이 방식을 택했다"(설계 05번 §4). `BattleManager`의 마커 인터페이스(`IRequiresXxx`) 방식과 달리 `IEncounterRule`은 구분 수단이 없어 순수 C# 객체로 직접 소유하는 쪽을 선택한 것 — SOLID 위반이 아니라 문서화된 트레이드오프.
- 잔여 관찰(새 위반 아님, 참고용): 그래도 규칙을 교체하려면 `EncounterManager` 소스 수정이 필요하다는 확장성 제약 자체는 남아있으나, 설계 문서가 이미 인지·수용한 사항이라 이번 점검의 신규 발견 사항으로 잡지 않는다.

**문제점 3 — 재사용(DRY): `ManagerHierarchyInstaller.EnsureSiblingComponent`가 `EditorUIBuilder.GetOrAddComponent`와 중복**
- `ManagerHierarchyInstaller.cs` 줄 168~172(`EnsureSiblingComponent<T>`)와 `EditorUIBuilder.cs` 줄 120~124(`GetOrAddComponent<T>`)의 구현이 완전히 동일하다(`GetComponent<T>() ?? Undo.AddComponent<T>()`).
- CLAUDE.md 씬 편집 컨벤션("여러 인스톨러가 공유하는 저수준 조립 로직은 EditorUIBuilder로 뽑는다", "기존 것을 재사용할 수 있는지 먼저 확인") 위반 — 다른 모든 인스톨러(`FieldUIInstaller`, `HubSceneInstaller`, `FormationUIBuilder` 등)는 이미 `EditorUIBuilder.GetOrAddComponent`를 쓰고 있어 `ManagerHierarchyInstaller`만 별도 재구현한 상태.

**문제점 4 — SRP: `ManagerHierarchyInstaller.BuildManagerHierarchy()`가 다수의 무관한 도메인을 한 메서드에서 처리**
- 줄 30~166(약 137줄) 단일 메서드가 핵심 매니저 생성, UI 패널/Wiring 배선, 씬 전환 커튼 구성, 배틀 테이블 자산 배선, 태틱스/트립 데이터 배선, 8개 데이터 저장소 생성, DI 배열 동기화까지 순차 인라인으로 처리한다.
- 하위 `Wire*`류 private 메서드로 일부는 쪼개져 있으나, 최상위 오케스트레이션 자체가 서로 무관한 여러 도메인(전투 데이터/UI/태틱스/트립)을 한 흐름에 나열한 구조 — **이번 사용자가 지적한 "책임성 분산 + 비직관적 구조"의 코드 레벨 원인이 이것**(1단계 정보수집에서 확인한 씬 하이어라키의 평면 구조는 이 메서드 구조를 그대로 반영한 결과).

**최적화(2-1) findings와의 교차 확인**: 충돌 없음 — `InMemoryFieldFormationActivityRepository`의 List/LINQ 이슈와 위 4건은 서로 다른 파일/메서드로 독립적이다.

**문제점 1 — 자산 경로 문자열이 여러 파일에 중복 하드코딩됨(단일 소스 오브 트루스 없음)**

## 3. 수정안 도출

사용자 요청: "Bootstrap에 무분별하게 신설된 Manager 오브젝트 정리"를 핵심으로, 2단계에서 식별된 문제 전체를 종합.

### 수정 A — `ManagerHierarchyInstaller.BuildManagerHierarchy()` 도메인별 분리 + 데이터 저장소 8개를 UIManager 산하로 재배치
(SOLID 문제점 4 해결, 최초 사용자 지적 사항 해결)

- 현재 137줄 단일 메서드를 도메인별 private 메서드로 분리:
  - `BuildCoreManagers(root)` — 초기 정리(EventSystem 잔재/Missing Script 제거) + 핵심 매니저 8개 생성.
  - `WireGameManagerDependents(gameManager)` — `SceneLoader`/`SessionStateTracker` 부착.
  - `WireBattleManagerDependents(battleManager)` — `LiveBattleSimulationRule`/`PlaceholderDefeatConsequenceRule` 부착 + 테이블 자산 배선.
  - `WireUIManagerPanels(uiManager)` — 기존 8개 sibling 패널/Wiring 컴포넌트 부착(로직 변경 없음, 위치만 이동).
  - `BuildUIManagerDataRepositories(uiManager)` — **저장소 8개를 `root.transform`이 아니라 `uiManager.transform`을 부모로 생성**(`EditorUIBuilder.GetOrCreateManager<T>(uiManager.transform, name)`). 하이어라키가 `Managers/UIManager/{8개 저장소}`로 바뀌어, 1단계 정보수집에서 지적한 "누구 소관인지 알 수 없는 평면 구조"가 해소된다.
  - `BuildManagerHierarchy()` 본체는 위 메서드들을 순서대로 호출하고 마지막에 `SyncManagedComponents`만 수행하는 짧은 오케스트레이터로 축소.
- 씬 재실행 안전성: `EditorUIBuilder.GetOrCreateManager`는 이름 기준 `Find`로 기존 오브젝트를 찾으므로, 기존 씬(저장소가 root 평면에 있는 상태)에서 재실행하면 **root에 남은 옛 오브젝트를 못 찾고 uiManager 밑에 새로 생성**해 root에 중복이 남는다. 별도 정리 로직 필요: `BuildUIManagerDataRepositories` 시작부에서 `EditorUIBuilder.DestroyChildIfExists(root, 저장소이름)`로 루트에 남은 옛 오브젝트를 먼저 제거한 뒤 `uiManager.transform` 밑에 새로 생성한다(8개 전부 동일 처리).

### 수정 B — `EnsureSiblingComponent<T>` 제거, `EditorUIBuilder.GetOrAddComponent<T>`로 통일
(SOLID 문제점 3 해결)

- `ManagerHierarchyInstaller`의 `EnsureSiblingComponent<T>` 사설 메서드와 그 8개 호출부를 전부 `EditorUIBuilder.GetOrAddComponent<T>` 호출로 교체하고, 사설 메서드는 삭제.

### 수정 C — `SyncManagedComponents` 배열을 "핵심 매니저"/"데이터 저장소" 두 배열로 명시적 분리
(확장성 문제점 3 완화)

- 기존 하나의 인라인 배열을, `coreManagers`(순서 의존 — 기존 주석 그대로 유지)와 `dataRepositories`(순서 무관) 두 개의 명명된 지역 배열로 나누고 `coreManagers.Concat(dataRepositories).ToArray()`로 합쳐 전달.
- 순서 제약이 "배열 중간의 주석"이 아니라 "배열 자체의 경계"로 드러나, 향후 매니저 추가 시 실수로 순서를 흩트릴 위험이 줄어든다(런타임 assert 등 추가 장치 없이 구조만으로 완화 — 과설계 지양).

### 수정 E — `InMemoryFieldFormationActivityRepository`: unitId 조회에 Dictionary 병행 구조 도입
(최적화 문제점 1 해결)

- `List<FormationActivity> activities`는 그대로 유지(`Update()`의 역순 순회, `ActiveActivities`/`ForceCompleteAll` 등 순서·스냅숏 의존 로직을 건드리지 않기 위해).

(SOLID 문제점 1 — ISP 해결)
- 기존 `IFormationEditingHandler`에서 Field 전용 3개 멤버(`IsUnitReserved`, `HandleRedirectMove`, `GetActiveActivities`)를 새 인터페이스 `IFormationActivityHandler`(internal)로 분리해 낸다. 나머지(`GetDisplayLayout`/`HandlePaletteDrop`/`HandleGridMove`/`HandleRemove`/`ResizeGrid`)는 Hub/Field 공통이라 기존 인터페이스에 남긴다.

**수정 H — `TacticsPanel.IndexOfOption` 6개 오버로드를 제네릭 1개로 통합**
