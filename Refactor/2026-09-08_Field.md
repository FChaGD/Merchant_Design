## 2. 기준별 순차 점검 (문제점 식별만)

### 2-1) 최적화 측면 용이성 — 점검 완료

점검 대상: A~C 전 파일(21개).

**문제점 없음.** Field는 전투 뷰(월드 오브젝트)가 많은 유닛을 다루는 성능 민감 영역이지만 이미 CLAUDE.md 최적화 컨벤션을 철저히 따르고 있다:
- `BattleBackgroundGridView`: 타일을 매 전투 `Destroy`+`Instantiate`하지 않고 풀로 관리(`ConfigureField`).
- `BattleViewPresenter`: 유닛 뷰는 전투 시작마다 `Instantiate`(빈도 낮음 - 프레임당 아님), Field 배치 시간 유령(`BattlePendingReinforcementView`)만 매 틱 갱신되는데 get-or-create 풀 사용.
- `BattlePlaceholderSprite`/`BattleGaugeSprite`: 스프라이트를 `??=`로 지연 생성 후 모든 인스턴스가 공유(텍스처 재생성 없음).
- 입력(드래그팬/휠줌)은 전부 `IDragHandler`/`IScrollHandler` 콜백(`BattleFieldInputForwarder`) - `Update()` 폴링 없음.
- `Update()`를 쓰는 곳은 정확히 2곳뿐이고 둘 다 이벤트로 대체 불가능한 정당한 사유가 코드 주석에 명시돼 있다: `BattleCharacterUnitView.Update`(유닛이 매 틱 계속 이동하므로 위치 추종 필요), `BattleHealthGaugeView.Update`(HP 재생이 이벤트 없이 매 틱 조금씩 바뀌는 값이라 `OnDamaged`만으로 못 따라감) - 둘 다 이 프로젝트에서 이미 확립된 "연속 변화값은 Update() 허용" 예외 패턴과 일치.

**교차 확인**: 처음 발견하는 기준이라 대상 없음.

### 2-2) SOLID 원칙 준수 여부 — 점검 완료

**문제점 1 — 재사용(DRY): `FieldTransitionCurtainView`가 `SceneTransitionCurtainView`(Bootstrap, `Core/Game/`)와 `Show`/`FadeOut` 로직이 완전히 동일**
- 두 클래스 다 `[SerializeField] CanvasGroup canvasGroup` 하나만 갖고, `Show()`(`SetActive(true)` + `alpha=1f`)와 `FadeOut(coroutineRunner, duration, onComplete)`(`SlideTransitionTimeline.Run`으로 `alpha`를 1→0 페이드 후 `SetActive(false)`+콜백)이 바이트 단위로 동일하다. 차이는 `SceneTransitionCurtainView`만 `SetAnchoredPosition`을 추가로 노출한다는 점뿐(Hub↔Field 슬라이드용 - `FieldCameraController`는 대신 `(RectTransform)transitionCurtain.transform`을 직접 캐스팅해 써서 이 메서드가 없어도 동작한다).
- 두 커튼이 서로 다른 GameObject/스코프(Bootstrap 영속 vs Field 콘텐츠 씬)에 있어야 하는 이유는 각 클래스 주석에 이미 잘 설명돼 있지만, 그렇다고 "페이드 인/아웃" 로직 자체까지 두 번 구현할 이유는 없다 - 순수 로직(`Show`/`FadeOut`)을 공용 헬퍼나 베이스로 뽑아 재사용할 수 있다.

**문제점 2 — 재사용(DRY, 경미): `BattleCharacterUnitView`/`BattleProtectedUnitView`의 `FlashWhite()` 코루틴이 사실상 동일**
- 둘 다 "피격 시 흰색으로 즉시 바꿨다가 0.1초 뒤 원래 색으로 복원"하는 동일 로직이다(`BattleCharacterUnitView`만 복원 조건에 `&& unit.IsAlive`가 추가로 붙어 사망 틴트를 덮어쓰지 않게 하는 차이만 있음). `HandleDamaged` 이벤트 배선도 동일 패턴(`unit.OnDamaged += HandleDamaged; ... StartCoroutine(FlashWhite())`).
- 심각도는 낮음(문제점 1보다 작은 중복, 로직도 5줄 내외) - 통합하려면 두 View의 공통 베이스 클래스나 별도 컴포넌트(`BattleHealthGaugeView`처럼 자식으로 붙이는 방식)가 필요해 문제점 1보다 리팩토링 비용이 크다.

**교차 확인**: 최적화(2-1)와 충돌 없음 - 이번 두 건은 다른 파일/관심사(커튼 페이드 로직 중복, 피격 플래시 코루틴 중복)이며 프레임당 비용과는 무관.

### 2-3) 확장성 측면 및 하드코딩 여부 — 점검 완료

**문제점 1 — `BattleFieldWorldCameraView`/`OrthographicCameraZoomController`(Field 소유 클래스)에 배틀 테스트 씬 전용 확장이 누적됨**
- 두 클래스 다 "C. 전투 뷰"로 Field 소유 코드로 분류했지만, 실제로는 배틀 테스트 씬(3단계 계획 밖)만을 위한 멤버가 여럿 섞여 있다: `ConfigureZoomRange(zoomInRatio, zoomOutRatio, clampToField)`(줄 56~60), `ScreenToWorld`(줄 45), `CurrentOrthographicSize`/`CurrentSize`(줄 49, 50), 생성자의 `zoomOutRatio`/`clampToField` 매개변수(`OrthographicCameraZoomController.cs` 줄 19~26).
- 코드 주석 7곳이 전부 "배틀 테스트 씬 전용", "Field 씬은 이 값을 바꿀 방법이 없어 영향 없음"이라고 명시적으로 인정하고 있다 - Field 입장에서는 죽은 코드 경로(`zoomOutRatio≠1`, `clampToField=false`)를 항상 함께 짊어지는 구조.
- OCP 관점: 배틀 테스트 씬이라는 두 번째 소비자를 위해 기존 클래스를 "확장"이 아니라 "수정"(새 생성자 오버로드 추가, `ConfigureZoomRange`로 컨트롤러 자체를 교체)으로 대응했다. 클래스를 상속하거나 별도 데코레이터로 배틀 테스트 전용 동작을 분리했다면 Field 쪽 클래스는 더 단순했을 것.
- 심각도: 낮음~중간 - 현재는 죽은 분기가 방어적으로 잘 격리돼 있어(기본값이 Field 동작과 동일) 실질적 버그 위험은 없지만, Field 코드베이스를 읽는 사람이 "왜 Field 카메라가 클램프 해제/줌아웃 비율 같은 옵션을 갖고 있는지" 파악하려면 배틀 테스트 씬의 존재까지 알아야 한다.

**교차 확인**: 최적화(2-1)·SOLID(2-2)와 충돌 없음 - 이번 건은 다른 파일/관심사(카메라 컨트롤러의 소비자 확장 방식)이다.

## 3. 수정안 도출

### 수정 L — 커튼 페이드 로직을 공용 유틸리티로 추출
(SOLID 문제점 1 해결)

- `Core/UI/CanvasGroupCurtainFader.cs`(internal static) 신설: `Show(GameObject, CanvasGroup)`과 `FadeOut(MonoBehaviour coroutineRunner, GameObject, CanvasGroup, float duration, Action onComplete)` 두 정적 메서드로 두 클래스의 동일 로직을 통합. `SlideTransitionTimeline`(이미 `Core/Game`/`Core/UI/Field` 양쪽에서 쓰이는 공용 유틸리티)과 같은 자리에 둔다.

### 수정 M — 피격 플래시 코루틴을 공용 헬퍼로 추출
(SOLID 문제점 2 해결)

- `Core/UI/Field/Battle/BattleHitFlash.cs`(internal static) 신설: `Run(SpriteRenderer bodyRenderer, Color flashColor, Color restoreColor, float durationSeconds, Func<bool> canRestore = null)` — `canRestore`가 null이면 항상 복원(기본값), `BattleCharacterUnitView`는 `() => unit.IsAlive`를 넘긴다.
- `BattleCharacterUnitView.FlashWhite`/`BattleProtectedUnitView.FlashWhite`는 `StartCoroutine(BattleHitFlash.Run(bodyRenderer, FlashColor, baseColor, HitFlashSeconds, ...))` 호출로 축소.

### 확장성 문제점 1 — 보류(사용자 판단 필요)

`BattleFieldWorldCameraView`/`OrthographicCameraZoomController`의 배틀 테스트 전용 확장은 이번 라운드에서 수정하지 않을 것을 권한다:
- "고치는" 방법은 두 가지뿐인데 둘 다 비용이 크다 - (a) 배틀 테스트 씬용 클래스를 별도로 복제하면 지금 없앤 SOLID 문제(DRY)가 다시 생기고, (b) 줌/클램프 동작을 전략 객체로 주입 가능하게 재설계하면 이번 라운드 범위를 넘는 아키텍처 변경이 된다.
- 지금 상태는 죽은 분기가 기본값으로 안전하게 격리돼 있어(Field는 절대 그 분기를 안 탐) 실질적 버그 위험이 없다 - 가독성 문제일 뿐이라 과설계를 피하는 게 낫다는 판단.
- 사용자가 그래도 정리를 원하면 별도 요청으로 설계 단계부터 다시 논의한다.

## 6. 후속 처리 — 확장성 문제점 1(배틀 테스트 전용 카메라 확장) 완료 (2026-09-20)

§3에서 "비용이 크다"며 보류했던 항목을 사용자 요청으로 다시 다뤘다. 이번엔 "복제(a)"도 "전략 객체 재설계(b) 전체"도 아닌, **축별 정책을 조합하는 방식**(방향성 지시 구조와 동일 패턴)으로 풀었다.

- **문제 재확인**: 프로덕션에서 호출되지 않는 배틀 테스트 전용 멤버(줌 아웃 배율, 전장 밖 이동 허용, 설정 메서드)가 줌 컨트롤러 생성자 인자/분기로 섞여 있었다. 한 클래스가 정반대 규칙을 조건 분기로 품고, Field에서 설정 메서드를 부르면 규칙이 조용히 깨지는 구조였다.
- **설계(설계 27번, 사용자 확정)**: 축 2개(줌 범위/이동 범위)만, 정책은 상태 없이 읽기 전용 상태 묶음을 받음, 조합은 코드 프리셋(enum)+팩토리(데이터 자산 아님), 주입 진입점은 뷰의 프리셋 적용 메서드 1개. 화면→월드 변환/현재 크기 조회는 순수 조회라 뷰에 유지.
