# 2026-08-26 공통 코드 점검

대상: DI(`Dependency/`), 게임/씬 흐름 코어(`Game/`), 입력(`Input/`), UI 패널 프레임워크(`UI/` 루트),
공용 UI 유틸리티(`UI/Common/`), 에디터 공용 설치 유틸리티(`Editor/`), 부트스트랩 재진입 가드,
캐러밴 편성/용병 데이터 계층(`UI/Formation/`, `Battle/Stats/` 중 Hub·Field 양쪽에서 소비되는 부분).

## 1. 최적화 점검

문제점 없음. ID 조회는 전부 Dictionary 기반 O(1), 요소 수집은 씬 로드당 1회, 입력 반응은 이벤트/콜백
기반이라 CLAUDE.md 최적화 규칙을 준수하고 있었다. `UIManager`가 씬 재진입마다 `RegisterFormationUI`/
`RegisterTripUI`를 반복 호출하는 구조라 이벤트 구독 누적 가능성을 의심해 다운스트림까지 확인했으나
실제 누적은 없었다(리스너는 `RemoveAllListeners` 후 재등록, 좌표계 이벤트는 매번 새 인스턴스 구독).

## 2. SOLID 점검

**`UIManager`의 SRP/DIP 위반.** `HandleSceneLoaded`가 씬 이름별로 분기해 최대 8개 인자를 조립하며
4개 패널/컨트롤러를 배선하는 씬별 UI 조립(composition root) 책임까지 겸했다. 이 때문에 "공통" 프레임워크
클래스인 `UIManager`가 `IBattleController`/`IBattleResultSource`/`IDefeatConsequenceSource`/
`IBattleSimulationEvents`처럼 Field 전투 도메인에만 속하는 인터페이스를 무조건 알아야 했다.

## 3. 확장성/하드코딩 점검

**콘텐츠 씬 식별자가 5곳에 흩어져 있었다.** `ContentSceneId` enum, `SceneNames` 상수, `SceneLoader
.ToSceneName()` 스위치문, `UIManager.HandleSceneLoaded`의 if/else 분기, `BootstrapSceneInstaller
.ContentScenePaths` 배열 — 콘텐츠 씬이 하나 늘 때마다 이 5곳을 각각 고쳐야 했다. 대조적으로
`DebugBootstrapReentryGuardInstaller.GetContentScenePaths()`는 Build Settings에서 동적으로 읽어와
이 문제가 없었다(이미 프로젝트 안에 있던 올바른 패턴).

## 4. 수정안 및 통합 점검

SOLID·확장성 문제가 `UIManager.HandleSceneLoaded` 한 곳에서 교차해, 아래 구조로 함께 해결했다.
최적화 기준은 애초에 문제가 없어 이 변경이 그 기준을 해치지 않는지만 확인했다(딕셔너리 조회는
ResolveDependencies 1회 + 씬 전환 시에만 발생, 매 프레임 비용 없음).

- `IContentSceneUIWiring`/`IPanelRegistrar` 인터페이스 신설, `HubUIWiring`/`FieldUIWiring` 구현체 신설
  — 씬별 배선 책임과 Battle 도메인 지식을 `UIManager` 밖으로 분리(SRP/DIP 회복).
- `UIManager`는 `GetComponents<IContentSceneUIWiring>()`로 수집한 뒤 씬 이름→`ContentSceneId` 파싱 →
  딕셔너리 조회로 위임만 한다. 새 콘텐츠 씬 추가 시 `UIManager` 자체는 더 이상 수정 대상이 아니다.
- `ContentSceneId`를 유일한 식별자 출처로 삼았다. `SceneNames` 상수는 `nameof(ContentSceneId.Xxx)`로
  정의해 enum과 항상 같은 값을 갖도록 컴파일 타임에 강제(클래스 자체를 지우는 대신, 기존 호출부
  8곳을 건드리지 않는 최소 변경으로 "정의가 어긋날 수 없게" 만드는 방향을 택함 — 애초 수정안의
  "SceneNames 제거"에서 구현 단계에 실익 대비 변경 범위를 고려해 조정).
  `SceneLoader.ToSceneName()` 스위치문은 `id.ToString()`으로 대체(enum 멤버 이름 = 씬 이름 불변식).
  `IGameManager.RequestSceneTransition`은 `string` 대신 `ContentSceneId`를 받아 호출부의 문자열
  오타 가능성을 제거했다. `BootstrapSceneInstaller.ContentScenePaths`는 `Enum.GetValues`로 계산한다.
- 부수: `IUIPanel.cs`를 `UI/Formation/`에서 `UI/` 루트로 이동(GUID 보존을 위해 `git mv`로 `.meta`도 함께 이동).

## Formation UI 추가분

Hub 씬 코드 분류 과정에서 `FormationPanel`(및 하위 뷰들)과 `FormationUIBuilder`(Editor)가 Hub·Field
양쪽에서 재사용된다는 사실을 뒤늦게 확인해 공통 추가분으로 점검했다. 대상: `FormationPanel`,
`IFormationPanel`, `FormationGridView`, `FormationPaletteView`, `FormationInfoPanelView`,
`FormationSlotView`, `FormationUnitIconView`, `FormationLayout`, `FormationUnitKind`,
`FormationUIElementIds`, `FormationGridDebugView`(에디터 전용), `FormationUIBuilder`(Editor).

### 1. 최적화 점검

**CLAUDE.md 최적화 규칙("슬롯/아이콘 렌더링은 매번 Destroy+Instantiate하지 않고 get-or-create로
재사용") 위반.** `FormationPanel.Open()`마다 `FormationGridView.RebuildSlots()`(슬롯 전체)와
`FormationPaletteView.SetRoster()`(팔레트 아이콘 전체)가 파괴 후 재생성됐고, `FormationGridView
.RenderSlot()`도 슬롯 점유 아이콘이 바뀔 때마다(드래그마다) 파괴 후 재생성했다.

### 2. SOLID 점검

**`FormationPanel`의 SRP.** 드래그/드롭 배치 판단 로직(스왑/이동/취소, 약 90~100줄)이 UI 바인딩·조율
책임과 섞여 있었다. 같은 그룹의 `TripPanel`은 비교 가능한 복잡도의 로직을 `TripMapInteractionCoordinator`
로 이미 분리해뒀는데 `FormationPanel`만 분리돼 있지 않아 그룹 내 일관성이 깨져 있었다.

### 3. 확장성/하드코딩 점검

문제점 없음.

### 4. 수정안 및 통합 점검

- `FormationGridView.RebuildSlots()`: 슬롯 개수(`SlotCount`)가 이전과 같으면 파괴 후 재생성 대신
  기존 슬롯에 콜백만 다시 바인딩. 실제로 개수가 바뀔 때(디버그 리사이즈)만 전량 재생성.
- `FormationGridView.RenderSlot()`: 슬롯에 아이콘이 이미 있으면 파괴하지 않고 `Bind`/`SetHandlers`
  재호출 + `SetActive`로 재사용. 없을 때만 `Instantiate`.
- `FormationPaletteView.SetRoster()`: 아이콘 개수 변화분만 생성/파괴하고 나머지는 재바인딩.
- `FormationDragCoordinator` 신설(순수 C#, `TripMapInteractionCoordinator`와 같은 성격) — 드래그 세션
  상태(고스트/드래그 중 유닛/원본 슬롯)와 배치 판단 로직을 이전. `currentLayout`/`unitsById`는
  `FormationPanel`이 계속 소유하고 호출마다 인자로 전달(디버그 리사이즈로 `currentLayout`이 교체돼도
  항상 최신 값을 참조하기 위함, 내부에 캐시하지 않음).
- 세 재사용 변경 모두 매번 `Bind`/`SetHandlers`로 상태를 완전히 덮어써 최종적으로 보이는 결과는
  이전과 동일하다(순수 최적화, 기능 변경 없음 — 사용자 확인 거침). 통합 점검: SOLID 분리는 로직
  위치만 옮길 뿐 파괴/재생성 방식에 관여하지 않아 최적화 효과를 그대로 유지한다.
