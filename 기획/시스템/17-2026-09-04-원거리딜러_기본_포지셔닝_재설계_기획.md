# 원거리딜러 기본 국소적 포지셔닝 재설계 기획

작성일: 2026-09-04

## 1. 배경

battle 브랜치 실전 검증 중 "원거리딜러가 전투 시작부터 완전히 정지해 있다"는 현상이 보고됐다. 원인을 추적한 결과:

- 원거리딜러 역할군의 국소적 포지셔닝 기본값(카탈로그 0번째 항목)이 **자리 사수**(`LocalPositioning.Stationary`)다 — 사거리와 무관하게 항상 제자리를 반환해 절대 접근하지 않는다(설계상 의도된 동작).
- 적 스폰 거리(대형 반경 + 10m 여유, `BattleFieldLayout`)가 원거리딜러 기본 사거리(Archer 기준 6m)보다 훨씬 커서, 인식 지연(1초) 뒤 처음 고르는 타겟이 사실상 항상 사거리 밖에서 시작된다.
- 추적 판정 기본값(`PursuitPreset.OffensiveJudgment`)의 재탐색 트리거는 "자기 위치가 활동 반경을 벗어났는가"를 신호로 쓰는데, 자리 사수는 정의상 절대 움직이지 않으므로 이 신호가 성립할 수 없다 — 재탐색 안전장치가 무력화된다.

**결론**: 코드 결함(버그)이 아니라, "자리 사수"(이동하지 않음)와 "OffensiveJudgment"(이동을 전제로 한 재탐색 판정) 두 축이 조합될 때 생기는 설계 사각지대다. 각 축은 그 자체로는 정상 동작한다. 다만 이 조합이 원거리딜러의 **기본값**이라, 결과적으로 원거리딜러가 별도 방향성 지시 조정 없이는 전투에 사실상 참여하지 못한다 — 사용자 확정: 버그 수정이 아니라 **기본값 재설계**로 대응한다.

## 2. 목표

원거리딜러 역할군의 국소적 포지셔닝 기본값을 자리 사수에서 **접근 공격**으로 바꾼다 — 사거리 밖이면 타겟에 접근하고, 안이면 멈추는 동작. 이러면 위 §1의 사각지대(자기 위치가 활동 반경을 벗어나지 않아 재탐색이 안 걸리는 문제)도 자연히 해소된다 — 접근하는 유닛은 실제로 위치가 바뀌므로 `isOutsideRadius` 신호가 정상적으로 성립한다.

## 3. 핵심 결정 (사용자 확정, 2026-09-04)

- **새 기본값의 동작**: 기존 전열 돌격형(`ChargePositioningStrategy`)과 완전히 동일한 로직 — "거리 > 사거리면 타겟 위치로 접근, 아니면 제자리". 새 알고리즘을 고안하지 않고 이미 검증된 로직을 원거리딜러 역할군에도 적용한다(클래스를 공유할지 별도로 감쌀지는 설계 단계에서 결정).
- **명칭(사용자 확정, 2026-09-04)**: "접근 공격". `LocalPositioning` enum에 새 값으로 추가한다(기존 전열 `Charge`=1을 원거리딜러 카탈로그에 그대로 노출하지 않음 — 역할군마다 별도 값을 쓴다는 기존 관례 유지, §2.1 컨벤션).
- **enum 정수 재배정(사용자 확정, 2026-09-04)**: 접근 공격이 `LocalPositioning`의 첫 정수(1)를 갖도록 기존 값을 전부 한 칸씩 민다.

  | 값 | 기존 | 변경 후 |
  |---|---|---|
  | 접근 공격(신규) | - | **1** |
  | Charge(돌격형) | 1 | 2 |
  | Blocking(저지형) | 2 | 3 |
  | Stationary(자리 사수) | 3 | 4 |
  | Surround(포위) | 4 | 5 |
  | Disperse(산개) | 5 | 6 |

  이 값들은 `Assets/Table/Tactics/RoleGroupTactics.xlsx`(`RoleGroupPositioningOptions`/`PositioningStrings` 시트)에 이미 저장된 데이터 Id이기도 하다 — 전열(RoleGroup 1)의 Charge/Blocking 행도 포함해 **기존에 저장된 모든 관련 행을 새 번호로 함께 수정**해야 한다(§5 참고). 원거리딜러만의 변경이 아니라는 점을 제작 단계 착수 전 재확인할 것.
- **자리 사수(Stationary) 처우**: 삭제하지 않는다. 원거리딜러가 선택 가능한 옵션으로 계속 남긴다(후방 고정 저격수 등 의도적으로 쓰고 싶을 수 있음) — 다만 카탈로그 기본값(0번째)에서는 제외한다. 자리 사수를 플레이어가 직접 선택했을 때는 §1의 사각지대(재탐색 안 걸림)가 여전히 남는다는 점을 문서에 남겨, 향후 "왜 정지형이 가끔 안 움직이냐"는 재질문을 방지한다 — 사용자가 능동적으로 고른 트레이드오프로 취급.
- **적용 범위**: 원거리딜러(RoleGroup 2) 역할군에만 적용. 전열의 돌격형/저지형, 원거리딜러의 포위/산개는 무변경.

## 4. 남은 미정 사항 (설계 단계에서 확정)

- **클래스 재사용 방식**: `ChargePositioningStrategy`와 로직이 완전히 같은 "접근 공격"을 별도 클래스로 만들지, 내부적으로 위임/공유할지 — 두 갈래 모두 근거가 있어 설계 단계에서 판단 필요.
  - **(a) 클래스 공유**: `PositioningStrategyFactory`가 새 enum 값도 기존 `ChargePositioningStrategy`로 매핑. 코드 중복 0, 수정 지점 1곳. 다만 "전열 돌격형"과 "원거리딜러 접근 공격"이 물리적으로 완전히 결합돼, 나중에 둘 중 하나만 다르게 조정하고 싶어지면 그때 분리해야 한다.
  - **(b) 별도 클래스**: 새 클래스를 만들되 지금은 내부 로직이 `ChargePositioningStrategy`와 동일(복제 또는 내부 위임). 이 프로젝트가 지켜온 "enum 값 하나 = 전용 클래스 하나" 명명 관례와 일관되고 두 역할군이 나중에 갈라져도 서로 영향 없음. 다만 지금 시점엔 실질적으로 새로 하는 일이 없는 얇은 클래스가 하나 생긴다.
  - CLAUDE.md 제작 규칙의 "기존 것을 확장해 재사용할 수 있는지 먼저 확인"과 이 프로젝트의 "enum=전용 클래스" 관례가 서로 다른 답을 가리키는 지점이다.

## 5. 테이블(엑셀) 반영 준비 상태 — 확인 완료

`RoleGroupTacticsTableImporter`(`Assets/Scripts/Editor/`)가 `Assets/Table/Tactics/RoleGroupTactics.xlsx`를 읽어 `RoleGroupTacticsCatalog.asset`/`RoleGroupTacticsStringsTable.asset`을 채우는 파이프라인이 이미 갖춰져 있다 — **이번 추가에 임포터 코드 변경은 필요 없다**, 데이터(워크북 행)만 갱신하면 된다.

- **카탈로그 순서(1순위) 문제는 enum 정수 크기와 무관하다**: `GroupByRoleGroup`이 각 역할군의 옵션을 `RoleGroupPositioningOptions` 시트의 **`SortOrder` 컬럼**으로 정렬하고, 그 순서가 곧 카탈로그 리스트 순서(=0번째가 기본값)가 된다. 접근 공격을 1순위로 만드는 건 이 행의 `SortOrder`를 가장 작게 주면 되고, §3의 enum 정수 재배정과는 독립적인 문제다.
- **제작 단계에서 실제로 갱신해야 할 워크북 행**(§3 표의 번호 변경 반영):
  - `PositioningStrings` 시트: 기존 Id 1~5 행 전부 새 번호로 수정, 신규 `Id: 1, Ko: "접근 공격"` 행 추가.
  - `RoleGroupPositioningOptions` 시트: RoleGroup 1(전열)의 Charge/Blocking 행, RoleGroup 2(원거리딜러)의 Stationary/Surround/Disperse 행 — `OptionId`를 전부 새 번호로 수정. 원거리딜러 행에 신규 `RoleGroupId: 2, OptionId: 1, SortOrder: <최소값>` 행 추가.
  - 수정 후 `Tools > Game > Table > Import Role Group Tactics` 재실행 → 에셋 자동 반영.
- 이 워크북은 `.gitignore` 대상이 아니라 커밋되는 실제 데이터 파일이므로(content 브랜치 엑셀화 작업 결과물), 제작 단계에서 직접 열어 편집해야 한다 — 코드만으로는 채워지지 않는다.
