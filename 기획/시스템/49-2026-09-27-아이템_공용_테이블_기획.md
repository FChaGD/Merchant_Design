## 1. 배경

33번은 교역품·전투 장비·전투 소모품·상단주 개인 물품을 카테고리별 워크북 4개로 나누고, 공통 열(Id, IconPath, 이름)을 워크북마다 따로 두었다. 48번에서 가격과 설명을 추가하게 되면서 같은 열을 워크북마다 반복해서 관리해야 하는 문제가 생겼다. 또 판매 품목과 판매가가 마을마다 달라질 예정이라, 아이템 한 개에 여러 행이 딸리는 데이터를 담을 자리가 필요하다.

변경 전 열 구성:

| 워크북 | 데이터 시트 | 스트링 시트 |
|---|---|---|
| TradeGoods | Id, FootprintWidth, FootprintHeight, IconPath | Id, Ko |
| Equipment | Id, IconPath | Id, Ko |
| Consumable | Id, IconPath | Id, Ko |
| PersonalItem | Id, IconPath | Id, Ko |

## 2. 범위

- 포함: 아이템 테이블의 분류 체계, 각 테이블의 열, 기타 아이템 카테고리 신설, 마을별 판매 데이터의 자리, 무결성 검사 규칙, Placeholder 값.
- 제외: 마을별 판매 품목·판매가 차별화 로직(테이블 자리만 만든다), 카테고리별 전용 열(장비 스탯, 소모품 효과 등)의 내용, 매각가 규칙, 시세 변동, 평판에 따른 가격 증감.

## 3. 확정 사항 (사용자 결정, 2026-09-27)

### 3.1 테이블 6종 분리

네 카테고리가 공유하는 내용은 공용 테이블로 관리하고, 테이블은 아래 6종으로 나눈다.

| | 데이터 | 세부 데이터 | 스트링 |
|---|---|---|---|
| **공용** | 공용 데이터 테이블 | 공용 세부 데이터 테이블 | 공용 스트링 테이블 |
| **카테고리별** | 카테고리별 데이터 테이블 | 카테고리별 세부 데이터 테이블 | 카테고리별 스트링 테이블 |

| 종류 | 정의 | 행 |
|---|---|---|
| 데이터 | 아이템 하나에 값이 하나뿐인 속성 | 아이템당 1행 |
| 세부 데이터 | 다른 기준(마을 등)과 조합될 때마다 값이 달라지는 속성 | 아이템당 0~N행. 속성 하나당 시트 하나 |
| 스트링 | 표시용 문자열(이름, 설명) | 아이템당 1행 |

- 공용은 모든 카테고리의 아이템에 해당하는 속성, 카테고리별은 그 카테고리 아이템에만 해당하는 속성이다.
- **무결성 규칙**: 모든 열은 값이 반드시 있다(빈칸 없음). 일부 아이템에만 값이 있는 속성은 열로 두지 않고 세부 데이터의 행으로 표현한다(행이 없음 = 해당 없음).
  - 예외: IconPath는 아이콘 에셋이 들어오기 전까지 빈칸을 허용한다.
- 지금 열이 없는 카테고리별 테이블도 머리글(Id)만 둔 시트로 미리 만든다.

### 3.2 가격

- **판매가는 공용 데이터 테이블의 필수 열(Price)로 관리한다.** 모든 마을에서 이 가격으로 판매한다.
- 마을마다 판매 품목과 판매가가 달라질 예정이다. 그 차이(마을별 판매 여부, 마을별 판매가)는 공용 세부 데이터 테이블에 둔다. 판매가를 마을별 판매 테이블의 열로 두면 행마다 빈칸이 생기므로 세부 데이터로 분리하는 것이다.
- **마을별 차별화는 아직 구현하지 않는다.** 세부 데이터 시트는 머리글만 만들고 로직에서 쓰지 않는다. 실제 로직은 모든 마을에서 테이블에 등록된 판매 대상 아이템을 공용 데이터의 판매가로 판다.

### 3.3 교역품 구분 (일반 품목 / 특산품)

- 교역품 데이터 테이블에 일반 품목과 특산품을 구분하는 열을 둔다.
- 무역품 구매는 일반 품목을, 특산물 구매는 특산품을 판다. 시설은 이 구분으로 정해지므로 판매 데이터에 시설 열을 두지 않는다. 한 품목을 두 시설에서 동시에 팔 수는 없다.

### 3.4 기타 아이템 카테고리 신설 — 골드 상자

- 골드 상자는 판매 대상이 아니다. 교역품 카테고리에 두면 "등록된 교역품을 모두 판매"하는 규칙에 걸리므로, **기타 아이템 카테고리를 새로 만들어 그곳에서 관리한다.**
- 골드 상자는 지금처럼 교역품/전리품 그리드에 놓인다(31번 §3.4). 카테고리가 바뀌어도 보관 위치는 바뀌지 않는다.

### 3.5 문자열·값

| 항목 | 값 |
|---|---|
| 설명(모든 아이템) | "아이템 설명 텍스트" |
| 골드 상자 이름 | "골드 상자" |
| 아이콘 | 에셋이 들어오기 전까지 빈칸 |

## 4. 테이블 구성

```
Assets/Table/Item/
  Item.xlsx           ← 공용
  TradeGoods.xlsx     ← 교역품
  Equipment.xlsx      ← 장비
  Consumable.xlsx     ← 소모품
  PersonalItem.xlsx   ← 개인 물품
  Misc.xlsx           ← 기타(신설)
```

각 워크북은 데이터 / 세부 데이터 / 스트링 시트를 가진다(세부 데이터는 속성마다 시트 하나).

| 테이블 | 열 | 비고 |
|---|---|---|
| 공용 데이터 | Id, Category, IconPath, Price | Category: 교역품/장비/소모품/개인물품/기타. IconPath만 빈칸 허용 |
| 공용 세부 데이터 — 마을별 판매 | ItemId, CityId, Price | 머리글만. 로직 미사용(§3.2) |
| 공용 스트링 | Id, Ko(이름), DescKo(설명) | |
| 교역품 데이터 | Id, FootprintWidth, FootprintHeight, TradeKind | TradeKind: 일반/특산 |
| 기타 데이터 | Id, FootprintWidth, FootprintHeight | 골드 상자가 교역품 그리드에 놓이므로 크기가 필요 |
| 장비·소모품·개인 물품 데이터 | Id | 머리글만. 크기는 1×1 고정(33번 §3.3 정정) |
| 모든 카테고리별 세부 데이터·스트링 | Id(세부 데이터는 ItemId) | 머리글만 |

- 마을별 판매 세부 데이터의 CityId는 상행 지도 테이블(`TripCityMap.xlsx`)의 도시 Id(정수, 현재 1~10)를 참조한다.
- 마을별 판매 여부를 행의 유무로 표현할지, 판매 여부와 판매가를 별도 시트로 나눌지는 차별화를 구현할 때 확정한다.

## 8. 설계 단계로 넘길 기술 과제

- 임포터 구조: 공용 워크북을 먼저 읽고 카테고리 워크북을 Id로 결합해 카테고리별 아이템 정의를 만드는 흐름. 카테고리별 아이템 테이블 자산과 조회 계약을 유지할지, 공용 자산으로 합칠지.
- 세부 데이터 시트를 읽는 공통 방식(지금은 머리글만 있는 시트를 오류 없이 넘기는 것까지).
- 기타 카테고리 신설: 골드 상자를 교역품 테이블에서 기타 테이블로 옮긴 뒤에도 교역품 그리드 저장소가 골드 상자를 찾고 지갑 연동을 유지하는 방식.
- 아이템 정의에 설명을 추가하는 방식. 가격은 판매 목록 조회 계약(마을 Id + 시설 Id → 품목과 판매가 목록)으로 노출하고, 가격이 필요 없는 소비자에게 노출하지 않는다(ISP). 지금 구현은 마을 Id를 받되 무시하고 전 마을 동일 목록을 돌려준다.
- 시설 → 판매 대상(카테고리 + 교역품 구분) 매핑의 위치. 시설 목록은 코드 상수(`TownFacilityCatalog`)에 있다.
- 이 변경은 `system` 브랜치에서 만든 아이템 테이블 코드(기획 33~36번)를 `ui` 브랜치에서 고친다. 이후 브랜치 병합 시 `ui`→`develop`→`system` 순서.

## 9. 남은 미정 사항 (후속)

- 마을별 판매 품목·판매가 차별화 로직과 세부 데이터 시트 구성.
- 매각가 규칙.
- 시세 변동, 평판에 따른 가격 증감.
- 재고(마을별 판매 수량 제한).
- 카테고리별 전용 열(장비 스탯, 소모품 효과, 개인 물품 세부 분류).
- 이름 외 언어(영문 등) 열.
