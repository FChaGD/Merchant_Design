## 1. 배경

`Docs/세션 인계/battle.md` §9.1의 미결 항목 "정비창 배치가 전투에 미치는 실제 영향"·"재배치(정비창 변경) 중단 시나리오 — 재배치 소요시간 시스템 자체가 없음"을 해소하기 위한 기획. 정비창(Formation) UI에 **배치 소요시간**과 **실시간 이동** 개념을 도입해, 상행 중 재배치가 "즉시·무비용"이 아니라 실제 시간이 드는 행동이 되게 한다.

**조사로 확인한 전제 3가지**(이번 기획 범위를 결정한 근거):

1. **적용 범위는 Hub가 아니라 Field(상행 중)에 한정된다**(사용자 확정). Hub에서의 최초 출발 전 배치는 기존처럼 즉시 적용을 유지한다. 정비창 UI는 이제 "공용 기반 + Hub 전용/Field 전용 분리" 구조로 나뉜다(사용자 확정, §3 참고).
2. **새 시각 요소(반투명 고스트/타이머/경로)는 전부 정비창(Formation) UI 화면(기존 그리드) 안에서만 렌더링된다** — Field 필드 월드 공간에 새 상시 캐릭터 시각화를 만들 필요는 없다(사용자 확정). 배치/이동의 실제 진행(타이머 감소, 이동 거리 누적)은 **정비창 UI를 열지 않아도 백그라운드에서 계속 진행**되고, 패널을 다시 열면 그 시점 상태를 반영해 보여준다.
   - **예외(사용자 확정, 2026-09-05 실전 검증 중 추가)**: 위 원칙은 "상행 이동 중" 배치에 해당하고, **전투가 이미 시작된 상태**에서 §3.2의 "전투 중 신규 소환"이 진행 중인 경우는 다르다 — 이때는 정비창 UI를 열 수 없으므로(전투 뷰로 전환됨), 대신 **전투 뷰의 전장에도** 반투명 유령(고스트)+잔여시간을 표시한다(§9.1 참고). "이동 중" 필드 월드에는 여전히 상시 시각화를 만들지 않는다 — 이 예외는 "전투 중"에만 한정된다.
3. **현재 `FormationPanel`은 "적용(Apply) 버튼을 눌러야만 반영, 닫으면 미적용분 폐기"** 구조다(`FormationPanel.cs` 클래스 요약 주석, `HandleApply`/`repository.Apply(...)`). 이번 기획의 유닛 추가/이동/제거는 각 행동이 **개별적으로 즉시 반영**되고 백그라운드에서 진행돼야 하므로, 이 Apply-버튼-일괄-반영 모델과 정면으로 충돌한다 — Field 전용 배치 UI는 이 모델을 쓰지 않는다(§3.1).

## 2. 목표

정비창(Field, 상행 중)에서 유닛을 추가/이동/제거할 때 실제 시간 비용이 들게 해서, "배치가 전투에 미치는 실제 영향"에 실질적인 트레이드오프(언제 재배치를 시도할지, 인카운터 타이밍과 맞물려 리스크를 감수할지)를 만든다.

## 3. 확정 사항 (사용자 스펙, 2026-09-05)

### 3.1 아키텍처 방향 (사용자 확정)

- 기존 배치 UI(`FormationPanel` 등)를 재활용하되, **공용 기능을 뿌리로 삼아 Hub 전용/Field 전용으로 분리**한다. Hub는 기존 "로컬 편집 + Apply 버튼" 모델을 그대로 유지, Field는 "행동 즉시 반영 + 백그라운드 진행" 모델을 새로 쓴다. 구체적인 분리 지점(클래스 상속/합성 여부)은 설계 단계에서 결정한다(§5).
- Field 배치 UI에서 유닛을 추가/이동/제거하면 **그 즉시** 반영 대상 상태(타이머 시작, 이동 시작 등)가 바뀐다 — Hub처럼 별도 Apply 버튼으로 모아서 반영하지 않는다.
- 타이머/이동 진행은 정비창 UI 패널이 닫혀 있어도 계속된다. 패널을 열면 그 시점의 경과 상태(잔여 시간, 이동 중이면 현재 보간 위치)를 그대로 그려준다.

### 3.2 유닛 추가

- 신규 유닛(로스터에서 팔레트로 드래그해 빈 슬롯에 배치)은 배치 완료까지 소요시간이 든다.
  - 캐릭터(전사/궁수/방패병): 소요시간 **짧음**(구체 수치는 §6 테스트값으로 설계 단계에서 정함).
  - 마차/시설: 소요시간 **김**(캐릭터보다 확연히 긺, 구체 수치는 동일하게 §6).
- 소요시간 진행 중 인카운터가 발생하면 타이머가 **일시정지**되고, 전투가 시작되면 다시 **재개**된다(정지 상태가 전투 워밍업 시간만큼 그대로 보존).
- 전투 도중 타이머가 다 되면(0에 도달하면), **그 즉시 전투 현장에 유닛이 소환**된다 — 배치 완료를 전투 끝까지 미루지 않는다. (전투 시뮬레이션이 시작 시점 1회 스냅샷으로 고정되는 현재 구조와 정면 충돌 — 설계 단계 핵심 과제, §5.2)
- 전투가 종료되면 타이머는 다시 일시정지 상태로 전환되고, 이동 뷰로 복귀해 상행 이동이 재개될 때 다시 타이머가 진행된다.
- 전장에 배치될 위치(정비창 UI 그리드의 해당 슬롯)에 반투명 배치 표시 + 잔여 시간 텍스트를 표시한다(§1의 전제 2 — 정비창 UI 화면 안에서).
- **패배(도주 제외: 궤주/포로/사망) 시**: 진행 중이던 배치는 **그 시점에 완료로 처리**된다(사용자 확정, 2026-09-05 — 타이머 값과 무관하게 즉시 완료, 리셋이 아님). **도주**는 전투 승리와 동일하게 처리한다 — 기존 `FieldEncounterFlowCoordinator.ShowDefeatConsequence`의 `DefeatConsequence.Flee` 분기(Victory와 동일하게 `TransitionToMovement`+`sessionState.Resume`)가 이미 이 규칙과 일치하므로, 이번 기획은 그 흐름에 "타이머 재개"만 얹으면 된다(§5.3 참고 — 나머지 Rout/Captured/Death 분기의 기존 동작 자체는 무변경).

### 3.3 유닛 이동 (이미 배치된 유닛의 위치 변경)

- 유닛은 실시간으로 기존 위치에서 새 배치 위치로 이동한다(즉시 스왑이 아니다).
- 출발지·도착지 두 지점에 각각 유닛 반투명 아이콘을 표시한다.
- 도착지 아이콘은 드래그로 실시간 재조정 가능 — 도착지가 바뀔 때마다 출발지-도착지 사이에 경로선을 다시 긋는다. 이 경로는 **다른 유닛이 이미 점유한 배치 그리드 슬롯을 피해서** 그어진다(구체 알고리즘은 설계 단계, §5.4).
- 유닛은 그 경로를 따라 이동하고, 도착지에 도달하면 배치가 최종 완료되며 출발지·도착지·경로 표시를 제거한다.
- 이동 도중 인카운터가 발생하면 이동이 **중단**되고, 그 시점(경로 중간 어딘가)의 위치에 그대로 유닛이 생성된다 — 즉 배치 슬롯 좌표가 아닌 **임의의 연속 좌표**가 전투 시작 위치가 될 수 있다(기존 "슬롯 인덱스 → HomePosition" 구조를 확장해야 함 — 설계 단계 핵심 과제, §5.2).
- 전투 종료 후 처리는 결과에 따라 갈린다(사용자 확정, 2026-09-05):
  - **승리 또는 패배+도주**: 중단된 지점부터 도착지까지 이동이 **그대로 이어서 진행**된다(애니메이션 재개, §3.2의 "타이머 재개"와 대응되는 규칙).
  - **패배(도주 제외: 궤주/포로/사망)**: 이동이 **그 즉시 완료로 처리**되고, 유닛이 도착지에 즉시 재배치된다(애니메이션 재생 없이 스냅, §3.2의 "그 시점에 완료 처리"와 대응).

### 3.4 유닛 제거

- 마차: 대열에 **최소 1개**가 항상 남아 있어야 한다 — 1개만 남았을 때는 그 마지막 1개를 제거할 수 없다(2026-09-07 사용자 확정: 시설은 이 제한에서 제외 — 시설은 0개까지 자유롭게 제거 가능).
- 시설: 최소 개수 제한 없음 — 0개가 되어도 제거를 막지 않는다(2026-09-07 확정).
- 캐릭터: 소요시간 없이 **즉시** 대열에서 제거된다.
- **배치/이동 진행 중(타이머 미완료)인 유닛을 제거하면**(사용자 확정, 2026-09-05): 진행 중이던 타이머/이동이 **즉시 취소**되고, 그 유닛은 로스터의 가용 개체로 즉시 복귀한다(다시 배치에 쓸 수 있음).

## 4. 이 기획이 건드리지 않는 것

- Hub에서의 최초 출발 전 배치(기존 즉시 적용 + Apply 버튼 모델 무변경).
- 전투 판정 자체(승리/패배, 도주/궤주/포로/사망 확률 등, `BattleResult`/`DefeatConsequence`) — 이번 기획은 그 결과를 "소비"만 할 뿐 판정 로직 자체는 바꾸지 않는다.
- 정비창 배치 상한(카테고리당 5개, 기획 11번) — 무변경, 그대로 전제.
- 마차/시설의 "1개 이상 유지" 규칙 자체의 존재 여부(이미 로스터/배치 상한 기획에 함축된 전제로 취급 — 이번 기획은 "제거 시점의 제약"만 새로 규정).

## 5. 설계 단계로 넘길 사항

1. **Field 전용 배치 상태 저장소**: 정비창 UI가 닫혀 있어도 타이머/이동이 계속 진행되려면, 그 상태(어떤 유닛이 배치/이동 중인지, 시작 시각/경과 시간, 목표 위치)를 UI 컴포넌트가 아니라 Bootstrap 상주 객체(예: `InMemoryFormationRepository`와 같은 성격의 신규 저장소)가 들고 있어야 한다. `FormationLayout`(현재는 "슬롯→유닛Id" 스냅샷 하나만 표현)을 확장할지, 병행하는 새 타입을 만들지 설계 단계에서 결정.
2. **전투 중 신규 유닛 소환**: `LiveBattleSimulationRule.BuildAllies()`가 전투 시작 시 1회만 호출되어 `allies` 리스트가 그 이후 고정되는 현재 구조(`Docs/세션 인계/battle.md`의 조사 결과 참고)를 확장해, 진행 중인 시뮬레이션에 유닛을 늦게 추가하는 경로가 필요하다. `BattleSimulationLoop`/`IPausableBattleSimulation` 등 관련 인터페이스 영향 범위 확인.
3. **임의 연속 좌표 스폰**: 이동 중 인카운터로 중단된 유닛은 슬롯 좌표가 아닌 임의 위치에서 전투를 시작해야 한다 — `FieldPositionLayout.ComputeAllyPosition(column, row, ...)` 기반의 현재 스폰 좌표 계산을 확장해야 함.
4. **경로 회피 알고리즘**: "다른 유닛의 배치 그리드를 피해서" 경로를 긋는 구체적인 방식(그리드 A* 등) — 정비창 그리드가 이미 열/행 인덱스 구조이므로 그리드 기반 경로탐색이 자연스러운 선택지로 보이나 확정은 설계 단계에서.
5. **Hub/Field 배치 UI 공용 기반 분리**: `FormationPanel`을 그대로 둔 채 Field 전용 서브클래스/합성 객체로 확장할지, 공용 로직(팔레트 계산, 그리드 렌더링 등)만 뽑아 별도 클래스로 추출하고 Hub/Field 각각의 조율자를 새로 만들지 — CLAUDE.md의 "기존 것을 재사용" 원칙과 "패널=화면 단위 조율자" 명명 관례를 함께 고려해 설계 단계에서 결정.
6. §3.2/§3.4의 구체 소요시간 수치(테스트값) 확정.

## 6. 남은 사항

- §5.6의 구체 소요시간 수치(테스트값)는 설계/제작 단계에서 정한다.

## 9. 전투 중 신규 소환 유령의 전장 표시 (사용자 확정, 2026-09-05 실전 검증 중 추가)

**계기**: 실전 검증 중 사용자가 "전투 시작 전에 배치될 자리에 반투명 캐릭터+타이머가 보여야 하는데, 아무것도 없이 뿅 배치된다"고 보고. 확인 결과 사용자가 기대한 표시 위치는 §1 전제 2에서 확정한 "정비창 UI 화면 안"뿐 아니라 **전투 뷰의 전장**도 포함하는 것이었다 — 단, 추가 확인 결과 이 전장 표시는 **전투가 이미 시작된 상태**(§3.2 "전투 중 신규 소환")에 한정된다. 상행 이동 중(전투 시작 전) 필드 월드에 상시 시각화를 만드는 것은 여전히 범위 밖이다 — 애초에 그 시점엔 전투 뷰(`BattleWorldRoot`) 자체가 생성되지 않아 표시할 대상이 없다.

**결정 사항**: 전투가 진행 중일 때, 아직 완료되지 않은 Adding 활동(§3.2) 각각에 대해 그 목표 슬롯의 전장 좌표에 반투명 유령(캐릭터 도형 + 잔여 초 텍스트)을 표시한다. 실제로 합류하면(전투 중 신규 소환) 유령을 치우고 진짜 유닛으로 교체한다. 마차/시설은 애초에 전투 중 합류를 지원하지 않으므로(§4 범위 밖) 유령 대상에서 제외한다.

**설계는 25번 §6.3에 추가 반영**.
