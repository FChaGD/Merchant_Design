## 1. 배경

25번 문서 §6, 31번 문서 모두 "개별 아이템 데이터"를 명시적으로 범위 밖에 남겼다. 현재 `IInventoryItemDefinition`은 주석에 "실제 아이템 데이터 시스템이 없어 최소 계약만 정의한다"고 적혀 있고, 유일한 구현체인 `GoldBoxItemDefinition`은 골드 상자 하나만을 위한 특수 클래스다. 인벤토리 저장소(`PlaceholderTradeGoodsInventoryRepository` 등)는 이미 `IInventoryItemDefinition` 인터페이스로만 아이템을 다루도록 설계돼 있어, 실제 아이템 데이터 시스템을 얹을 자리는 이미 마련돼 있다.

## 2. 범위

- 4개 카테고리(교역품/전리품, 장비, 전투 소모품, 상단주 개인 물품) 아이템 데이터에 **공통으로 적용될** 테이블 스키마와 Id 체계를 확정한다.
- 카테고리별로 다른 세부 필드(장비 스탯 체계, 소모품 효과 종류, 개인 물품 세부 분류 등)는 범위 밖 — 카테고리별 후속 세션에서 다룬다.
- 개별 아이템 목록(실제 품목명/수치)은 범위 밖.
- 아이템 장착/사용/소모 시 효과가 게임플레이에 어떻게 반영되는지(전투 스탯 반영, 소모품 효과 발동 등)는 범위 밖 — "정의 데이터 + 카탈로그 조회"까지만 다루고, 효과 적용 로직은 후속 세션 대상(사용자 확정).
- 아이템 UI/조작경로(구매·장착·사용 화면, 진입 버튼 등)는 범위 밖 — 프론트엔드 단계에서 별도 진행(사용자 확정, "백엔드 기초 완료 후 프론트엔드로 이어간다").

## 3. 확정 사항 (사용자 스펙, 2026-09-23)

### 3.1 Id 체계 — 문자열 슬러그

아이템 Id는 정수(enum 정수값 기반, 14번 문서 §6 v2 방식)가 아니라 **문자열 슬러그를 그대로 PK로 쓴다**(예: `"iron-sword"`, `"healing-potion"`). 이미 `GoldBoxItemDefinition.Id => "gold-box"`가 이 형태다.

**14번 문서의 정수 Id 방식과 다르게 결정한 이유**: 14번 §6.2가 정수 Id를 택한 근거는 "그 enum이 게임 로직 분기에도 쓰여(`TargetSelectorFactory` 등의 `switch`), Id 용도가 공짜로 얹힌다"는 것이었다. 아이템은 `PlaceholderTradeGoodsInventoryRepository` 등이 `IInventoryItemDefinition` 인터페이스로만 다루고 종류별 코드 분기가 없으며, 캐릭터 직업(3종)처럼 고정된 소수 집합이 아니라 계속 늘어나는 콘텐츠 카탈로그다. 정수 Id를 쓰면 아이템 추가마다 C# enum 멤버 추가+재컴파일이 필요해지는데, 아이템에는 그 대가로 돌려받을 이득(코드 분기 재사용)이 없다. 문자열 슬러그는 시트에 행만 추가하면 끝난다.

**Id 안정성 규칙(운영 규칙으로 명시)**: 슬러그 자체가 Id이므로, 한 번 부여한 슬러그 문자열은 표시명이 바뀌어도 그대로 유지한다. §3.3에서 표시명을 별도 String 시트로 분리해두므로, 이름을 바꿀 일이 생겨도 슬러그(Id)를 건드릴 필요가 원천적으로 없다.

### 3.2 테이블 파일 구성 — 카테고리별 워크북 분리

```
Assets/Table/Item/
  TradeGoods.xlsx
  Equipment.xlsx
  Consumable.xlsx
  PersonalItem.xlsx
```

저장소가 이미 카테고리별로 별도 클래스(`PlaceholderTradeGoodsInventoryRepository` 등 4종)로 나뉘어 있고, 14번 문서 §2가 세운 "편집 주기·담당자가 다르면 파일도 분리한다" 원칙과 일치한다.

### 3.3 공통 Data/String 시트 스키마

카테고리마다 각자의 워크북 안에 최소 아래 공통 컬럼을 가진 Data 시트 하나 + String 시트 하나를 둔다(카테고리별 추가 컬럼은 후속 세션에서 확장).

**Data 시트 공통 컬럼**

| 컬럼 | 타입 | 비고 |
|---|---|---|
| Id | string (PK) | 문자열 슬러그. 시트 내 중복 금지 |
| IconPath | string | 아이콘 에셋 경로. 임포터가 `AssetDatabase.LoadAssetAtPath<Sprite>`로 로드 |

**FootprintWidth/FootprintHeight는 공통 컬럼이 아니다(2026-09-23 정정)**: 사용자 확인 결과 아이템마다 크기가 달라지는 카테고리는 교역품/전리품(골드 상자 포함)뿐이고, 장비/전투 소모품/상단주 개인 물품은 전부 1×1로 고정이다. `TradeGoods.xlsx`의 Data 시트에만 `FootprintWidth`/`FootprintHeight` 컬럼을 두고, 나머지 3개 워크북은 이 컬럼 자체가 없다 — 임포터가 코드에서 1×1을 못 박는다(런타임 `IInventoryItemDefinition.FootprintWidth/Height`는 카테고리 무관하게 항상 존재해야 하는 값이라, 데이터 출처만 "테이블" vs "코드 상수"로 갈린다).

**String 시트 공통 컬럼**

| 컬럼 | 타입 | 비고 |
|---|---|---|
| Id | string (PK, FK → Data 시트 Id) | |
| Ko | string | 표시명(한국어) |

14번 문서 §6.1의 "문자열/수치 분리(Data 시트 vs String 시트)" 원칙을 그대로 재사용한다 — `IInventoryItemDefinition.DisplayName`에 해당하는 텍스트를 Data 시트에서 분리해 §3.1의 Id 안정성 규칙을 구조적으로 보장한다.

### 3.4 골드 상자도 예외 없이 테이블 데이터를 따른다

현재 `GoldBoxItemDefinition`(internal 클래스)은 `FootprintWidth => 1`/`FootprintHeight => 1`을 C# 코드에 하드코딩하고 있다. §3.3 결정(그리드 크기는 테이블에서 온다)에 따라 골드 상자도 `TradeGoods.xlsx`의 한 행이 되어야 한다 — Id/FootprintWidth/FootprintHeight/IconPath/표시명 전부 테이블에서 읽고, `IPlayerCurrencyWallet` 연동 같은 **행동(behavior)만** `PlaceholderTradeGoodsInventoryRepository`가 Id로 식별해 특수 처리한다(§3.1의 "코드 분기 없음" 원칙과 상충하지 않음 — 분기 대상이 여러 카테고리가 아니라 "이 특정 아이템 하나"이므로 이미 있는 Id 문자열 비교로 충분하다). 설계 단계에서 `GoldBoxItemDefinition` 클래스를 제거하고 테이블 기반 정의로 대체할지, 아니면 저장소가 테이블 조회 결과에 지갑 연동 행동만 얹는 래퍼로 남길지 결정한다(§4에 기술 과제로 추가).

### 3.5 이번에 포함하지 않는 필드

- **가격(매입가/매각가)**: 상점/거래 시스템과 함께 다루는 게 자연스러워 이번 공통 뼈대에서 제외한다. 거래 시스템 기획 또는 카테고리별 후속 기획에서 다룬다.
- **카테고리별 개별 필드**(장비 착용 부위/스탯 보너스, 소모품 효과 종류/수치, 개인 물품 세부 분류 등): 카테고리마다 필요한 도메인 지식이 서로 달라 이번 공통 뼈대 세션에서 함께 다루지 않는다. 각 워크북의 Data 시트에 카테고리 전용 컬럼을 추가하는 방식으로 후속 세션에서 확장한다(14번 §4 정규화 수준 — 1NF~2NF 유지 원칙 재사용).

## 4. 설계 단계로 넘길 기술 과제

- `GoldBoxItemDefinition` 처리 방식 — 테이블 기반 정의로 완전히 대체할지, 저장소가 테이블 조회 결과에 지갑 연동 행동만 얹는 래퍼로 남길지(§3.4).
- 문자열 슬러그 검증 로직 — 정수 Id의 `Enum.IsDefined`(즉시 예외로 드러남)에 대응하는 자체 검증(빈 문자열 금지, 시트 내 중복 Id 금지, 끊어진 FK 참조 감지)을 `TacticsCatalogValidator` 선례를 참고해 설계.
- 런타임 조회 자료구조 — 기존 `TableEntryLookup.TryFind`는 List 선형 탐색(캐릭터 스탯처럼 4종 안팎일 때 문제없음)인데, 아이템은 수십~수백 개로 늘어날 콘텐츠라 `Dictionary<string, TEntry>` 등 O(1) 조회 자료구조가 맞는지 검토(CLAUDE.md 최적화 규칙).
- `IInventoryItemDefinition` 구현체를 테이블 기반으로 교체하는 구체 클래스 설계 — 현재 `PlaceholderXxxInventoryRepository`가 직접 아이템을 생성/소유하는 구조를, 테이블 조회 기반 카탈로그 참조 구조로 바꾸는 인터페이스/DI 설계.
- 아이템 테이블 Import 트리거 — 기존 `Tools/Game/Table/...` 메뉴 인스톨러 패턴(`CharacterStatsTableImporter` 등) 재사용 여부.
- IconPath 파싱 실패 시 처리 — 경로가 비어있거나 에셋을 못 찾을 때 Placeholder 도형 아이콘으로 폴백할지, 즉시 에러로 드러낼지.
