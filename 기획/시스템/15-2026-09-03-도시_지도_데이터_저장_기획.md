## 1. 배경

상행 준비 UI의 지도에는 이미 도시 배치/경로 연결 **디버그 도구**가 있다(기획 03/04번) — 팔레트를 드래그해 도시를 놓고, road-mode에서 도시 간 드래그로 경로를 잇는다. 하지만 이 데이터는 `InMemoryTripCityRepository`/`InMemoryTripRouteRepository`(순수 `Dictionary`/`HashSet`)에만 존재해 **앱을 재시작하면(매 플레이 테스트마다) 전부 사라진다.** 영구 저장 수단이 없다.

기획 02번 §7이 "지역/경로 데이터 모델(지도 좌표 포함)"을 후속 기획 대상으로 이미 명시해뒀다 — 이 문서가 그 후속이다. 목적은 새로운 배치 방식을 만드는 게 아니라, **이미 있는 드래그 배치 결과를 영구 데이터로 저장해 "기본 도시 지도"를 제작**하는 것이다.

## 2. 범위

**저장 대상**: 도시 좌표(Id + `MapPosition`)와 도시 간 경로 연결(무방향 쌍) — 지금 `TripCity`/경로 저장소가 갖고 있는 데이터 그대로.

**저장 대상이 아닌 것**:
- ~~도시 이름/설명 등 표시 정보~~ — **정정(2026-09-03, §8 참고)**: "저장 대상이 아니다"는 "데이터 컬럼 자체를 안 만든다"는 뜻이 아니었다 — 정확히는 "이름/설명을 **입력하는 전용 UI/기능을 별도로 제작하지 않는다**"는 뜻이었다. 데이터 저장은 §8에서 범위에 포함시킨다(엑셀 String 시트로).
- **출발/도착 배정 상태** — `TripOriginDestinationAssigner`가 다루는 건 특정 상행 1회의 런타임 상태지, 지도 자체의 데이터가 아니다. 저장 대상에서 제외.
- **두 도시 간 다중 경로** — 기획 04번이 이미 "지금은 단일 경로만 허용, 정식 다중 경로는 후속"으로 확정해뒀다. 이 저장 기능은 현재 디버그 데이터를 그대로 영구화하는 것이라 그 제약을 그대로 물려받는다.

## 3. 저장 트리거 — 기존 디버그 도구에 버튼 추가

`HubSceneInstaller.BuildTripDebugMapControls`가 이미 배치한 4개 버튼(도시 팔레트, 경로 연결 토글, 도시 전체삭제, 경로 전체삭제) 옆에 **"저장" 버튼**을 추가한다. 클릭하면 현재 지도에 배치된 모든 도시/경로를 하나의 데이터로 스냅샷 저장한다.

저장은 **덮어쓰기**다 — 기존에 저장된 지도가 있으면 그 내용을 현재 배치로 완전히 대체한다(엑셀 임포터의 "재실행해도 안전, 항상 최신으로 덮어씀"과 같은 원칙). 여러 버전을 남기거나 이력을 관리하지 않는다.

### 3.1 기존 UI와 배치 겹침 방지

기존 4개 버튼은 같은 가로 행(상단 0.90~0.97, `SetAnchors` 기준)에 순서대로 0.06~0.12(팔레트) / 0.14~0.30(경로 토글) / 0.32~0.46(도시 전체삭제) / 0.48~0.62(경로 전체삭제)를 차지한다. **저장 버튼은 이 행의 빈 구간(0.62 이후, 예: 0.64~0.78)에 이어 붙여 기존 4개와 겹치지 않게 배치한다.** 정확한 폭/여백은 설계 단계에서 `EditorUIBuilder` 공용 배치 유틸로 확정하되, 반드시 기존 버튼들의 앵커 범위를 침범하지 않는 것을 제약으로 둔다.

### 3.2 "정식 기능 아님" 명시

이 저장 버튼은 **임시 디버깅용 지도 제작 도구**이지, 플레이어가 쓰는 정식 기능이 아니다(기획 03번이 기존 배치 도구를 "정식 게임 콘텐츠가 아니다"로 명시한 것과 동일선상 — 저장 버튼도 예외 없이 같은 분류). 제작 단계에서 다음을 반드시 지킨다:

- 버튼도 기존 3개 디버그 버튼(도시 팔레트 등)과 동일하게 **`#if UNITY_EDITOR` 경계 안**에 둔다 — 정식 빌드에는 버튼 자체가 포함되지 않는다.
- 버튼 라벨/오브젝트 이름에 "저장" 단독이 아니라 임시 도구임이 드러나는 이름을 쓴다(예: 기존 `DebugCityBulkDeleteButton`처럼 `Debug` 접두사를 오브젝트 이름에 붙이고, `TripUIElementIds`에 등록하는 상수명도 `DebugMapSaveButton`류로 통일).
- `DEBUG_FEATURES.md`(저장소 루트)의 기존 디버그 기능 제거 절차 목록에 이 저장 버튼도 함께 등재한다 — 향후 정식 지역 시스템이 생겨 이 디버그 도구 전체를 걷어낼 때, 저장 버튼과 그 배선도 같이 제거 대상임을 놓치지 않기 위함.

## 4. 불러오기 — 씬 진입 시 자동 복원

저장 기능만으로는 "매 플레이 테스트마다 초기화된다"는 원래 문제가 해결되지 않는다 — 그래서 **저장된 데이터를 상행 준비 UI(지도)가 열릴 때 자동으로 불러와 도시/경로를 그대로 복원**하는 것까지 이번 범위에 포함한다. 저장된 지도가 없으면(최초 실행 등) 지금처럼 빈 지도로 시작한다.

불러온 뒤에도 기존 배치/드래그/경로 연결/삭제 상호작용은 그대로 유지된다 — "저장"은 그 시점의 스냅샷을 찍는 것뿐, 편집 기능을 막거나 대체하지 않는다. 즉 작업 흐름은: 지도를 열면 저장된 기본 지도가 나타남 → 드래그로 도시/경로를 추가·수정 → 저장 버튼으로 다시 덮어쓰기 → 반복.

## 5. 이 데이터의 성격 — "임시 디버그 데이터"에서 "기본 지도 데이터"로

기존 디버그 배치 시스템은 기획 03번에서 "실제 지역 시스템이 설계되면 대체·제거 대상"이라고 명시했다. 이 기능이 그 전제를 바꾸지는 않는다 — **배치 방법(드래그)과 도구(에디터 전용 버튼)는 그대로 디버그 성격을 유지**한다. 다만 **저장된 결과물(좌표+연결 데이터)** 은 더 이상 "매번 사라지는 임시값"이 아니라 실제로 게임에 쓰일 "기본 도시 지도"로 취급한다 — 향후 정식 지역 시스템이 이 데이터를 이어받아 쓸 수 있도록, 저장 데이터 자체는 에디터 전용이 아니라 정식 데이터로 관리한다.

구체적으로 이 데이터를 정식 빌드에서도 로드할 수 있게 만드는 방식(현재 `ITripCityRepository`/`ITripRouteReader` 구현체를 어떻게 교체·확장할지, Id 재사용/충돌 방지 등)은 설계 단계에서 다룬다(§6).

## 6. 남은 미정 사항 (설계 단계에서 다룰 것)

1. **선결 조건 - 전체 조회 API 부재**: 저장 버튼은 "현재 배치된 모든 도시/경로"를 순회해야 하는데, 현재 `ITripCityRepository`는 쓰기 전용(`Add`/`UpdatePosition`/`Remove`/`Clear`)이라 도시 목록을 돌려받을 방법이 없다(`DEBUG_FEATURES.md`가 `ITripCityReader.cs`를 언급하지만 실제로는 존재하지 않는 파일 - 문서 드리프트). `ITripRouteReader`도 `HasRoute`/`GetConnectedCityIds`(도시 1개 기준 인접 목록)만 있어 전체 경로 쌍을 얻으려면 도시 목록을 먼저 알아야 한다. 실제 데이터는 `TripMapInteractionCoordinator`의 `private` 필드(`markersByCityId`/`linesByRouteKey`)에만 존재 - 외부에 공개된 조회 경로가 전혀 없다. **설계 단계에서 `ITripCityRepository`/`ITripRouteReader`에 전체 조회 메서드를 추가할지(ISP 원칙상 별도 Reader 인터페이스 분리 - `IFormationReader`/`IFormationRepository` 사례와 동일 패턴), 코디네이터에 조회용 메서드를 새로 열지부터 정해야 한다.**
2. 저장 데이터 포맷 — 이 프로젝트에서 "에디터에서 편집 가능한 데이터"에 이미 쓰이는 ScriptableObject 에셋 패턴(`MercenaryRoleGroupMapAsset` 등)이 유력하나, 정확한 구조/저장 경로는 설계에서 확정.
3. 불러오기가 실제 빌드(플레이어용)에서도 동작해야 하는지, 아니면 에디터/디버그 범위에서만 동작하면 되는지 — §5에서 "정식 데이터로 취급"한다고는 했으나 실제 배선 방식(디버그 리포지토리 재사용 vs 신규 Provider 도입)은 설계 대상.
4. 도시 Id 안정성 — `InMemoryTripCityRepository`는 세션마다 `debug-city-1`부터 순번을 새로 매긴다. 불러온 뒤 새 도시를 추가할 때 기존 Id와 충돌하지 않도록 순번 재개 방식을 설계에서 정한다.
5. 저장 완료 피드백 방식(로그만인지, UI 표시까지 할지) — UI 배치 자체는 §3.1에서 확정.

## 7. 데이터 관리 방식 개정 — 엑셀 테이블화 (2026-09-03)

§1~§6은 전부 설계(19번)·제작을 거쳐 실제로 동작한다 — 도시/경로가 `TripCityMapAsset`(`Assets/Table/Trip/TripCityMap.asset`)에 저장되고, 상행 준비 UI를 열 때 자동으로 복원된다. 그런데 이 방식은 **좌표를 오직 드래그로만** 정할 수 있다 — 저장된 값을 엑셀 등 텍스트/표 형태로 열어 수치를 직접 확인·수정할 방법이 없다. 사용자가 이미 완성된 데이터 테이블 엑셀화(기획 14번, 설계 18번)와 동일한 방식으로 도시 지도 데이터도 관리하고 싶어해, 이 절에서 방식을 개정한다.

### 7.1 결정 사항 요약

1. **드래그 배치와 엑셀 직접 입력을 둘 다 유효한 입력 경로로 유지한다.** 어느 한쪽으로 대체하지 않는다 — 드래그는 시각적으로 위치를 잡을 때, 엑셀은 정확한 수치를 알거나 대량으로 편집할 때 쓴다.
2. **좌표계를 정규화한다**: 지도 **좌측 하단 모서리를 (0, 0)**, **우측 상단 모서리를 (지도 가로 크기, 지도 세로 크기)**로 하는 좌표계를 새로 둔다. 지도 가로/세로 크기는 이미 `HubSceneInstaller.MapContentSize = 2400f`로 고정돼 있다(정사각형 2400×2400) — 새 상수를 만들 필요 없이 이 값을 그대로 기준으로 삼는다.
3. **엑셀 워크북이 두 입력 경로의 단일 진실 소스가 된다** — 데이터 테이블 엑셀화(기획 14번)와 같은 원칙. 드래그 결과("저장" 버튼)도, 엑셀 직접 입력도 최종적으로는 같은 워크북에 반영되고, 상행 준비 UI가 열릴 때 그 워크북(정확히는 그로부터 임포트된 `TripCityMapAsset`)을 읽어 지도에 그린다.

### 7.2 좌표 변환

지도 콘텐츠(`TripMapView.Content`)는 `pivot=(0.5,0.5)`로 중심에 고정돼 있어, 지금 저장된 `MapPosition`(예: `x: 715.39, y: -477.27`)은 **지도 중심 기준**(-1200~+1200 범위, `MapContentSize` 절반씩)이다. 엑셀에서 사람이 보는 좌표는 **좌하단 기준**(0~2400 범위, 음수 없음)이라 상호 변환이 필요하다:

- 저장(콘텐츠 좌표 → 정규화 좌표, 엑셀에 쓸 때): `정규화 = 콘텐츠 + (MapContentSize / 2, MapContentSize / 2)`
- 불러오기(정규화 좌표 → 콘텐츠 좌표, 마커를 그릴 때): `콘텐츠 = 정규화 - (MapContentSize / 2, MapContentSize / 2)`

사람이 엑셀에서 보는 값은 항상 0~2400 범위의 양수라 "지도 왼쪽 아래 구석 근처"인지 "가운데"인지 숫자만 보고도 감을 잡을 수 있다 — 드래그 없이 좌표를 직접 입력해도 대략적인 위치를 예측할 수 있게 하려는 목적.

### 7.3 중대한 제약 — 현재 엑셀 라이브러리는 읽기 전용

데이터 테이블 엑셀화(설계 17번 §2)가 도입한 `ExcelDataReader`는 **읽기 전용**(그 문서에 이미 "MIT, 읽기 전용"으로 명시돼 있음) — xlsx 파일을 파싱만 하지, 새로 쓰거나 셀을 수정할 수 없다. "저장" 버튼이 드래그 결과를 엑셀 파일에 실제로 기록하려면 **쓰기가 가능한 새 라이브러리를 추가해야 한다**(예: ClosedXML - MIT 라이선스, 순수 .NET, 읽기·쓰기 모두 지원하는 후보). 정확한 라이브러리 선정과 통합 방식(Plugins 배치, 의존성 충돌 확인 등 - 이전 `ExcelDataReader` 도입 때 겪은 코드페이지 이슈 같은 게 또 나올 수 있음)은 설계 단계에서 다룬다.

### 7.4 기존 `TripCityMapAsset`/`TripCityMapPersistence`와의 관계

`TripCityMapAsset`(SO)은 그대로 유지하되 **역할이 바뀐다** — 더 이상 "저장" 버튼이 이 에셋을 직접 쓰지 않는다. 데이터 테이블 v1/v2와 완전히 같은 구조로 전환한다:

```
드래그 배치 ──"저장" 버튼──▶ xlsx 워크북 ◀── 사람이 엑셀에서 직접 수정
                                 │
                                 ▼(임포터, 플레이 진입 시 자동 실행)
                          TripCityMapAsset (컴파일된 데이터, 그대로 유지)
                                 │
                                 ▼(EnsureSavedMapLoaded, 그대로 유지)
                        상행 준비 UI 지도에 표시
```

- **"저장" 버튼**: `TripCityMapPersistence.Save`가 더 이상 `TripCityMapAsset`에 `SerializedObject`로 직접 쓰지 않고, xlsx 워크북에 쓴다(§7.3의 새 쓰기 라이브러리 사용).
- **임포터(신규)**: 데이터 테이블 임포터들과 같은 패턴(`Tools/Game/Table/Import ...` 메뉴, `EditorTableReader.ReadSheet` 재사용)으로 xlsx → `TripCityMapAsset`을 채운다.
- **`TableAutoImportOnPlay`에 이 임포터도 추가**한다 — "엑셀에 수치를 입력하면 플레이 진입 시 자동으로 지도에 반영된다"는 요구사항이 정확히 이 메커니즘으로 충족된다.
- **`EnsureSavedMapLoaded`/`TripPanel.Open()` 배선은 변경 없음** — 여전히 `TripCityMapAsset`을 읽을 뿐이라, 이 에셋이 "저장 버튼이 직접 쓴 것"인지 "엑셀 임포터가 채운 것"인지는 소비자 입장에서 차이가 없다.

### 7.5 워크북 위치

기존 SO 에셋이 있던 `Assets/Table/Trip/` 폴더를 그대로 워크북 폴더로 쓴다 — `Assets/Table/Trip/TripCityMap.xlsx`. 도메인별 폴더 관례(기획 14번 §6.3)와 일치.

### 7.6 범위 재확인 — §2와 동일, 매체만 전환

저장 대상(도시 Id+정규화 좌표, 도시 간 경로 Id 쌍)과 저장 대상이 아닌 것(출발/도착 배정, 다중 경로)은 §2에서 이미 확정한 그대로다 — 이번 개정은 "어디에 어떻게 저장되는가"만 바꾼다. (도시 이름/설명은 §2 정정대로 애초에 제외 대상이 아니었다 - §8에서 스키마에 반영.)

### 7.7 남은 미정 사항 (설계 단계)

1. 쓰기 가능한 엑셀 라이브러리 최종 선정과 `Assets/Plugins/`(또는 동일 위치) 통합 방식(§7.3).
2. 정확한 시트/컬럼 스키마(예: `TripCities` 시트에 `Id, X, Y`, `TripRoutes` 시트에 `CityIdA, CityIdB`) - 기존 데이터 테이블 컬럼 명명 관례와 통일.
3. 좌표 변환 로직(§7.2)을 어디에 둘지 - `TripCityMapPersistence`를 그대로 확장할지, 새 임포터 클래스로 분리할지.
4. 엑셀에서 사람이 직접 만든 도시 Id(예: `"seoul"`)와 드래그로 만든 자동 Id(`debug-city-N`)가 섞일 때의 처리 - 기존 §6-4(순번 재개)가 임의 문자열 Id도 이미 허용하므로 충돌 자체는 없으나, 두 출처가 섞인 데이터를 다시 "저장"(드래그→엑셀 덮어쓰기)할 때 사람이 붙인 Id가 유지되는지 확인 필요.
5. `MapContentSize`(현재 `HubSceneInstaller`의 `private const`)를 `Core/Debug/Trip/`(변환 로직이 필요로 함)과 `Editor/`(인스톨러가 씬에 실제로 적용) 양쪽에서 참조 가능한 위치로 옮길지 - 어셈블리 경계 제약(설계 19번 §5와 동일한 종류) 재확인 필요.

## 8. 정정 — 도시 이름/설명 스키마 포함 + Id 정수화 (2026-09-03)

§7까지 기획+설계+제작을 마친 뒤 사용자가 §2의 "도시 이름/설명은 저장 대상 아님" 서술이 오해를 낳았다고 지적했다 — 원래 의도는 "이름/설명을 **입력하는 전용 UI/기능을 새로 만들지 않는다**"는 것이었지, "데이터 컬럼 자체를 안 둔다"는 뜻이 아니었다. 이 절이 그 오해를 바로잡고 범위를 확정한다.

### 8.1 결정 사항 요약

1. **도시 테이블도 다른 데이터 테이블과 같은 원칙으로 Data/String 시트를 분리한다**(기획 14번 §6.1과 동일 원칙) — 좌표(Data)와 이름/설명(String)을 나눈다. 입력 UI는 여전히 안 만든다 - 엑셀에서 직접 채운다.
2. **Id를 "관리 가능한 정수"로 만든다** — 지금 `debug-city-1` 같은 접두사 붙은 문자열 대신, 엑셀/컴파일된 데이터 레벨에서는 순수 정수로 다룬다.

### 8.2 Id 정수화 — 범위와 근거 (2026-09-03 재정정 - 전면 정수화로 확대)

`TripCity.Id`/`ITripCityRepository`/`ITripRouteRepository` 등 **디버그 계층**(`Core/Debug/Trip/`)의 Id는 지금까지 `string`이었다. 이 값은 "정식" 코드(`TripOriginDestinationAssigner`, `ITripOriginDestinationReader`, `ITripOriginDestinationAssigner`, `ITripRouteReader`, `ITripLocationInfo`, `PlaceholderTripLocationInfo` - 전부 `Core/UI/Trip/`, `string` 기반 시그니처)로도 그대로 흘러 들어간다.

처음엔 이 정식 코드가 설계 19번 시점부터 "이 작업 중 손대지 않는다"고 선을 그어둔 영역이라(`DEBUG_FEATURES.md`) 정수화 범위를 엑셀/`TripCityMapAsset` 경계로만 한정하는 절충안을 세웠으나(2026-09-03 최초 결정), **사용자가 재검토를 요청** — 경계에서만 문자열↔정수 변환을 계속 왕복하는 절충안은 당장은 동작해도 향후 유지보수 부담(변환 지점 산재, "이 Id가 지금 string인지 int인지" 매번 확인 필요)이 크다고 판단해 **정식 코드까지 포함한 전면 정수화**로 확정한다. 시간이 걸리더라도 이 편이 낫다는 사용자 판단.

**최종 범위**: 도시 Id를 다루는 모든 계층(디버그 저장소, 정식 출발/도착 배정 상태 머신, 정식 장소 정보 인터페이스, 데이터 테이블)에서 `int`(미배정 상태가 필요한 자리는 `int?`)로 통일한다. `Core/UI/Trip/`의 "정식" 인터페이스 4종(`ITripOriginDestinationReader`/`ITripOriginDestinationAssigner`/`ITripRouteReader`/`ITripLocationInfo`)도 시그니처를 변경 대상에 포함한다 — 설계 19번이 세운 "이 리팩토링은 정식 코드를 안 건드린다"는 경계를 이번 건에 한해 넘는다(그 경계 자체를 폐기하는 게 아니라, 이 특정 변경에서만 예외로 확장).

### 8.3 스키마 확장

- `TripCities`(Data, 기존): `Id(int), X, Y` — 그대로.
- **`TripCityStrings`(String, 신규)**: `Id(int), Name, Description` — `ITripLocationInfo.DisplayName`/`Description`과 같은 구성.
- `TripRoutes`(기존): `CityIdA(int), CityIdB(int)`.

`TripCityMapAsset`에도 대응하는 String 저장 구조(신규 `TripCityStringsTableAsset` 또는 `TripCityMapAsset` 내 리스트 추가 - 설계 단계에서 다른 도메인의 `XxxStringsTableAsset` 패턴과 통일할지 정한다)가 필요하다.

### 8.4 소비자 연동 — 실제 이름/설명 표시

`TripMapInteractionCoordinator.BuildLocationInfo(cityId)`가 지금은 `"디버그 도시 {순번}"`/`"값 없음"`을 그때그때 지어내 `PlaceholderTripLocationInfo`에 채운다(기획 03번 §4.2의 "실제 지역 데이터가 없어 자동 생성 placeholder를 쓴다" 결정). 이제 String 시트에 실제 이름/설명이 있으면 **그 값을 우선 사용**하고, 없으면(예: 갓 드래그 배치해서 아직 이름을 안 붙인 도시) 기존 placeholder 동작으로 폴백한다 - 창작 금지 원칙 유지, 있는 데이터는 실데이터를 쓴다.

### 8.5 남은 미정 사항 (설계 단계)

1. `TripCityMapAsset`의 String 데이터를 별도 SO(`TripCityStringsTableAsset`)로 분리할지, 같은 에셋 안에 리스트로 얹을지.
2. 디버그 계층 Id 값을 `"debug-city-N"`→`"N"`으로 바꿀 때 기존에 이미 저장된 워크북/에셋(§7에서 만든 시드 데이터)을 어떻게 마이그레이션할지(재시드 vs 접두사 제거 스크립트).
3. `BuildLocationInfo`가 String 테이블을 조회하려면 코디네이터가 그 참조를 새로 들고 있어야 한다 - `Bind(...)` 파라미터 추가 지점과 `TripPanel`/인스톨러 배선 변경 범위 확정.
4. Name/Description이 비어 있을 때의 정확한 폴백 문구(기존 `"디버그 도시 N"`/`"값 없음"`을 그대로 쓸지, `"값 없음"`으로 통일할지).
