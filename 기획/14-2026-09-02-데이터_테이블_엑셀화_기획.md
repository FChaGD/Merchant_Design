## 1. 배경

현재 콘텐츠 데이터는 두 갈래로 흩어져 있다.

- **ScriptableObject 에셋 2종**(`MercenaryRoleGroupMapAsset`, `RoleGroupTacticsCatalogAsset`) — 인스펙터에서 리스트를 직접 편집.
- **코드 하드코딩**(`PlaceholderBattleUnitStatProvider`, `PlaceholderEnemyTypeCompositionProvider`) — 기획 08번 §12/§13.1 표를 `Dictionary` 리터럴로 그대로 옮겨놓은 것. 값 하나 바꾸려면 코드를 수정하고 재컴파일해야 한다.

이번 기획은 이 두 갈래를 `Assets/Table/` 아래 엑셀 워크북으로 통합하기 위한 **스키마(시트 구조)와 정규화 수준**을 정하는 것이 목적이다. 임포터 구현, 엑셀 파싱 라이브러리 선정, SO/코드 대체 작업 자체는 이 문서의 범위 밖이며 후속 설계/제작 단계에서 다룬다.

| AttackInterval | float | |

| 컬럼 | 타입 | 비고 |
|---|---|---|
| EnemyType | string (PK/FK → EnemyStats.EnemyType) | |
| CountMin | int | 포함 상한 방식 — 실제 등장 가능한 최소 인원 |

스탯(3.2)과 별도 시트로 분리한 이유: 현재는 적 타입당 구성 규칙이 하나뿐이라 EnemyStats에 열 2개를 얹어도 되지만, 기획 08번 §14.7이 "두목급 변형·타입 선택 가중치·난이도 스케일링"을 잔여 미정으로 남겨뒀다 — 인카운터 구성 규칙이 타입당 1:N(난이도별 프리셋 등)으로 늘어날 여지가 이미 예고돼 있어, 지금부터 "스탯(개체 고유값)"과 "구성 규칙(인카운터 맥락값)"을 별도 시트로 둔다. 현재 코드의 `StatsByType`/`CountRangeByType` 분리와도 대응된다.

### 3.5 축별 옵션 카탈로그 (역할군 → 허용 옵션, 3개 시트)

`TacticsTargetPriorityOptions` / `TacticsPositioningOptions` / `TacticsSelfPreservationOptions` — 3개 시트 모두 동일 구조:

| 컬럼 | 타입 | 비고 |
|---|---|---|
| RoleGroup | string | `Frontline`/`RangedDealer`/`Supporter`/`Assassin` |
| OptionValue | string | 해당 축 enum 이름(예: `Nearest`, `Charge`, `Kiting`) |
| DisplayLabel | string | 드롭다운에 표시할 한국어 라벨 |
| SortOrder | int | 표시 순서. **가장 작은 값이 역할군의 override 초기값**(기획 12번 §2.1 "목록 순서 = 표시 순서 = 초기값") |

한 역할군이 그 축에서 허용하는 옵션 수만큼 행이 반복된다(예: Frontline이 TargetPriority 3개를 허용하면 `TacticsTargetPriorityOptions`에 Frontline 행 3개). Supporter/Assassin은 대응 직업이 없어 세 시트 모두 행이 없을 수 있다 — `TacticsCatalogValidator`가 이미 이 상태를 경고로 잡아내므로, 후속 임포터/검증기 설계에서 동일 규칙을 유지한다.

### 3.6 파티 방침 옵션 카탈로그 (파티 3축, 3개 시트) — 2026-09-02 추가

`TacticsPanel.cs`(§18-45)에 `static readonly (enum, string)[]` 배열 3개로 하드코딩돼 있던 **파티 전체 단위** 방향성 지시 3축(인식방식/활동반경/추격방침) — `RoleGroupTacticsCatalogAsset`처럼 ScriptableObject조차 아니었다. `TacticsTargetPriorityOptions` 등과 같은 "enum값+한국어 라벨" 성격이지만, 역할군별로 갈리지 않는 **파티 전체 단일 설정**이라는 점이 다르다 — `RoleGroup` 컬럼이 필요 없다.

`TacticsRecognitionOptions` / `TacticsRadiusOptions` / `TacticsPursuitOptions` — 3개 시트 모두 동일 구조:

| 컬럼 | 타입 | 비고 |
|---|---|---|
| OptionValue | string | 해당 축 enum 이름(예: `OneSecondDelay`, `TripWide`, `OffensiveJudgment`) |
| DisplayLabel | string | 드롭다운에 표시할 한국어 라벨 |
| SortOrder | int | 드롭다운 표시 순서 |
| IsDefault | bool | 이 축의 기본값 여부 — 시트당 정확히 1행만 `TRUE` |

**§3.5와의 핵심 차이 — `IsDefault`가 별도 컬럼인 이유**: §3.5(역할군 축 카탈로그)는 "표시 순서 첫 항목 = override 초기값" 규칙이 성립했다(기획 12번 §2.1 확정 규칙). 그런데 파티 3축은 그 규칙이 성립하지 않는다 — 현재 코드(각 enum의 XML 주석 + `InMemoryTacticsRepository.DefaultPartySettings`)를 대조하면:

| 축 | 표시 순서(코드 배열) | 실제 기본값 |
|---|---|---|
| EnemyRecognitionType | OneSecondDelay, FiveSecondOrProximity, ProximityOrHit | **OneSecondDelay**(순서상 1번째 — 일치) |
| ActivityRadiusPreset | FormationHold, TripWide, FieldWide | **TripWide**(순서상 2번째 — 불일치) |
| PursuitPreset | Autonomous, HuntToKill, OffensiveJudgment, NoPursuit, HoldPosition | **OffensiveJudgment**(순서상 3번째 — 불일치) |

표시 순서와 기본값이 우연히 한 축(EnemyRecognitionType)에서만 일치할 뿐, 규칙이 아니다. "첫 행 = 기본값"으로 암묵 처리하면 나머지 두 축의 기본값이 조용히 틀어진다 — 그래서 `SortOrder`와 독립된 `IsDefault` 컬럼을 명시적으로 둔다. 현재 기본값 자체는 `InMemoryTacticsRepository.DefaultPartySettings` 코드 상수가 유일한 출처이고, enum XML 주석의 "(기본값)" 표기는 문서일 뿐 실행에 관여하지 않는다 — 이 둘이 서로 다른 값을 갖게 될 위험(코드 두 곳 중복)도 이번에 테이블로 단일화하면서 해소된다.

## 4. 정규화 수준 결정

- **3.1~3.4는 1NF~2NF 수준**으로 충분하다 — 모든 컬럼이 원자값(스칼라)이고, PK 하나에 속성이 직접 종속된다. 반복 그룹이 없어 추가 정규화가 필요 없다.
- **3.5(축별 옵션 카탈로그)가 이번 설계의 핵심 결정**이다. 원본 SO 구조(`RoleGroupCatalogEntry.TargetPriorityOptions` 등)는 역할군 1개당 옵션 리스트(1:N)를 갖는다. 이걸 엑셀로 옮기는 방법은 두 가지:
  - **(채택) 정규화 — 옵션 1개 = 행 1개.** 파싱이 단순 문자열 매칭으로 끝나고(메모리 원칙과 일치), 필터/정렬 등 엑셀 기본 기능을 그대로 쓸 수 있으며, `TacticsCatalogValidator`처럼 "역할군별 옵션 존재 여부"를 행 개수로 바로 검증할 수 있다.
  - **(기각) 비정규화 — 역할군 1행에 옵션을 구분자(`,` 등)로 압축한 컬럼.** 시트 한 줄로 요약되어 얼핏 간결해 보이지만, 임포터가 구분자 파싱 로직을 별도로 가져야 하고, 라벨/순서까지 한 셀에 욱여넣으면(`Nearest:가장 가까운 적,DeepestPenetration:...`) 엑셀에서 오탈자 검증이 사실상 불가능해진다. 기각.
- **PK로 서로게이트 ID 대신 enum 이름 문자열을 그대로 쓴다** — `MercenaryClass`/`EnemyType`/`RoleGroup`/각 축 enum 모두 코드에 이미 존재하는 고정 어휘라, 별도 숫자 ID를 도입하면 코드↔엑셀 간 매핑 테이블이 하나 더 늘어나는 불필요한 간접 계층이 된다.
- **(2026-09-02 추가) §3.6은 그룹핑 키(RoleGroup) 없이 "옵션 1개 = 행 1개"만 적용** — 파티 3축은 역할군처럼 하위 그룹이 없는 단일 설정이라 §3.5의 정규화 이유(1:N 관계 펼치기) 중 "그룹 키" 부분만 빠진다. `IsDefault` 컬럼을 `SortOrder`와 분리한 이유는 §3.6 표 참고 — 이 프로젝트에서 "정규화"란 단순히 관계를 펼치는 것뿐 아니라, 서로 다른 두 개념(표시 순서 vs 기본값)을 하나의 컬럼(행 순서)에 암묵적으로 욱여넣지 않는 것도 포함한다는 선례가 된다.

## 5. 남은 미정 사항 (후속 설계 단계)

1. 엑셀 파싱 라이브러리 선정(예: EPPlus/ClosedXML 등) 및 임포트 트리거 방식(수동 메뉴 vs 에셋 임포트 훅) — CLAUDE.md 씬 편집 컨벤션대로 `Tools/Game/...` 메뉴 인스톨러 형태가 될 가능성이 높으나 확정은 설계 단계에서.
2. 임포트 결과물의 런타임 표현 — 기존 `IBattleUnitStatProvider`/`IEnemyCompositionProvider`/`MercenaryRoleGroupMapAsset`/`RoleGroupTacticsCatalogAsset` 인터페이스를 그대로 두고 내부 구현만 엑셀 기반으로 교체할지, 아니면 인터페이스 자체를 새로 설계할지.
3. `TacticsCatalogValidator`에 대응하는 엑셀 버전 검증기(직업→역할군 매핑 누락, 역할군 옵션 공란 등)의 설계.
4. 엑셀 파일 자체의 버전관리 방침(바이너리 diff 문제) — CLAUDE.md의 `Docs/` gitignore와 별개로, `Assets/Table/*.xlsx`는 Git 추적 대상이 될 텐데 바이너리 파일 diff/충돌 관리를 어떻게 할지.
5. (2026-09-02 추가) §3.6 도입에 따른 후속 설계 항목:
   - `IsDefault`가 시트당 정확히 1행만 `TRUE`인지 검증하는 규칙 — `TacticsCatalogValidator` 확장 대상(§7과 통합할지 별도로 둘지).
   - `InMemoryTacticsRepository.DefaultPartySettings`(현재 코드 상수)와 `TacticsPanel.RecognitionOptions`/`RadiusOptions`/`PursuitOptions`(현재 코드 배열)를 새 테이블 기반 데이터로 교체하는 구체적 방식 — 기존 `RoleGroupTacticsCatalogAsset` 대체 패턴(SO 에셋 새로 만들지, 기존 구조 재사용할지)과 통일할지 결정 필요.

## 6. 스키마 개정 v2 (2026-09-02) — 문자열/수치 분리, 도메인별 폴더, Id 기반 참조

v1(§1~§5, 이미 코드로 구현되어 실제 운영 중)에 사용자가 구조적 개선 3건을 제안했다. 이 절이 현재 유효한 스키마다.

### 6.1 결정 사항 요약

1. **문자열/수치 분리** — 지금까지 `DisplayName`/`DisplayLabel` 컬럼이 수치 데이터 시트에 같이 있었다. 이를 "Data 시트"(수치·Id만)와 "String 시트"(Id→한국어 텍스트만)로 분리한다. 하위 정규화가 필요한 데이터(예: 캐릭터가 스킬을 여러 개 가지는 등 1:N 관계)가 생기면 그때 별도 "세부 Data 시트"를 추가로 허용한다 — 지금 범위(§6.3)엔 해당 사항이 없다.
2. **도메인별 워크북 + 폴더 분리** — 사용자가 지정한 4개 도메인(아군 캐릭터 스탯 / 적 캐릭터 스탯+정보 / 상단 지침 방향성(파티) / 역할군 방향성)별로 폴더와 워크북을 나눈다.
3. **Id 기반 참조** — 데이터 시트가 `MercenaryClass=Warrior` 같은 enum 이름 문자열 대신 **enum에 고정한 정수값**(`Id`)을 저장한다. 이 도메인의 enum 9종(`MercenaryClass`, `EnemyType`, `RoleGroup`, `TargetPriority`, `LocalPositioning`, `SelfPreservation`, `EnemyRecognitionType`, `ActivityRadiusPreset`, `PursuitPreset`) 모두에 명시적 정수값을 박는다(예: `public enum MercenaryClass { Warrior = 1, Archer = 2, ShieldBearer = 3 }`). 이 값이 곧 데이터 시트의 Id다 - 별도 매핑 코드를 두지 않는다(근거: §6.2).

### 6.2 왜 "enum 정수값 = Id"인가 (별도 매핑 체계를 쓰지 않는 이유)

이 도메인의 모든 enum은 두 가지 역할을 겸한다 — **(A) 게임 로직 분기**(`TargetSelectorFactory` 등 전략 팩토리가 switch로 전략 객체를 고름), **(B) 데이터/화면 식별**(테이블 키, 화면 라벨). 사용자가 3번 요청에서 범위를 "UI 출력"으로 명시했으므로, (A)는 그대로 두고 (B)만 쪼갠다:

| 역할 | 담당 | 비고 |
|---|---|---|
| 게임 로직 분기 | enum 그대로 | 전략 팩토리류 무변경 |
| 데이터 테이블 식별자(Id) | **enum의 명시적 정수값** | enum이 식별 책임까지는 계속 담당 - 별도 매핑 레이어 불필요 |
| 화면 텍스트 | enum에서 완전 분리, String 시트에서 Id로 조회 | enum은 텍스트를 전혀 모르게 됨 |

별도 Id 체계(enum과 무관한 서로게이트 Id를 속성/딕셔너리로 관리)를 기각한 이유: 그 경우 "enum과 별개로 관리되는 두 번째 진실 소스"가 새로 생겨, 사용자가 명시한 범위(화면 출력만 분리)보다 더 넓게(식별 책임까지) enum에서 걷어내는 과잉 설계가 된다.

**Id 안정성**: enum 멤버의 **이름**을 바꿔도(`Warrior` → `Fighter`) 명시적으로 박아둔 정수값은 안 바뀌므로 기존 엑셀 데이터가 깨지지 않는다. 정수값 자체를 실수로 바꾸거나 재사용하는 것만 주의하면 된다(코드 리뷰 대상).

### 6.3 폴더/워크북 구성

```
Assets/Table/
  Character/
    CharacterStats.xlsx
      - CharacterStats          (Id, MaxHp, Attack, Defense, MoveSpeed, AttackInterval, Range, MoraleSyncRate)
      - CharacterStrings        (Id, Ko)
  Enemy/
    EnemyStats.xlsx
      - EnemyStats               (Id, MaxHp, Attack, Defense, MoveSpeed, AttackInterval, Range, MoraleSyncRate, HpRegenPerSecond)
      - EnemyEncounterComposition (Id, CountMin, CountMax)
      - EnemyStrings             (Id, Ko)
  Tactics/
    PartyPolicy.xlsx
      - PartyRecognitionOptions  (Id, SortOrder, IsDefault)
      - PartyRadiusOptions       (Id, SortOrder, IsDefault)
      - PartyPursuitOptions      (Id, SortOrder, IsDefault)
      - PartyRecognitionStrings  (Id, Ko)
      - PartyRadiusStrings       (Id, Ko)
      - PartyPursuitStrings      (Id, Ko)
    RoleGroupTactics.xlsx
      - MercenaryRoleGroupMap          (CharacterId, RoleGroupId)
      - RoleGroupTargetPriorityOptions (RoleGroupId, OptionId, SortOrder)
      - RoleGroupPositioningOptions    (RoleGroupId, OptionId, SortOrder)
      - RoleGroupSelfPreservationOptions (RoleGroupId, OptionId, SortOrder)
      - TargetPriorityStrings    (Id, Ko)
      - PositioningStrings       (Id, Ko)
      - SelfPreservationStrings  (Id, Ko)
```

기존 `Assets/Table/CharacterStats.xlsx`/`Tactics.xlsx`(v1)는 이 구조로 대체된다 - 제작 단계에서 삭제하고 새 경로로 이전.

**폴더 분리 근거**: "아군 캐릭터"/"적"/"파티 방침"/"역할군 방침"은 서로 편집 주기와 담당자가 다를 수 있는 완전히 다른 주제라 파일+폴더 모두 분리한다. 반면 역할군 축 3시트(TargetPriority/Positioning/SelfPreservation)나 파티 축 3시트는 항상 함께 편집되는 세트라 워크북 하나 안에 시트로만 나눈다(파일까지 쪼개면 서로 다른 파일을 오가야 해서 오히려 불편해진다 - 사용자가 우려한 "복잡해짐"의 반대 방향).

**String 시트는 enum 타입 1개당 1개**: `RoleGroup` 자체는 화면에 노출되지 않는 내부 분류값이라(§3.5) String 시트가 없다 - 이 결정은 v1과 동일하게 유지. 같은 도메인 파일 안에 서로 다른 enum(예: PartyPolicy.xlsx의 Recognition/Radius/Pursuit)의 Id를 String 시트 하나로 합치지 않는다 - 서로 다른 enum이 같은 정수값을 가질 수 있어(예: `EnemyRecognitionType.OneSecondDelay=1`이면서 동시에 `ActivityRadiusPreset.FormationHold=1`) 합치면 충돌한다. 이건 §4에서 이미 확정한 "OptionValue 시트를 축마다 분리" 원칙의 연장이다.

**교차 파일 참조**: `Tactics/RoleGroupTactics.xlsx`의 `MercenaryRoleGroupMap.CharacterId`는 `Character/CharacterStats.xlsx`의 `CharacterStats.Id`를 가리키는 교차 파일 FK다 - Id가 파일 경계와 무관하게 그 enum 타입 전역에서 안정적인 정수이므로 문제없다.

### 6.4 정규화 재확인

- 모든 Data 시트는 1NF~2NF(원자값, PK 종속)를 유지 - v1과 동일.
- String 시트 분리는 "동일한 텍스트를 여러 곳에 중복 저장하지 않는다"는 표준 정규화 목적과도 부합한다(예: 향후 다른 화면이 같은 캐릭터 이름을 다시 참조해야 할 때 String 시트 하나만 보면 된다) - 다만 이번 프로젝트에 다국어 계획은 없으므로, String 시트에 `Ko` 컬럼 하나만 둔다(다국어가 필요해지면 `En` 등 컬럼을 추가하기만 하면 되는 구조 - 스키마 재설계 불필요).
- "필요에 따라 하위 수치값 테이블 허용"(사용자 1번 결정)은 이번 스키마 범위에는 적용 대상이 없다 - 현재 모든 Data 시트가 이미 플랫(반복 그룹 없음)이기 때문. 향후 캐릭터별 스킬 목록처럼 1:N 관계가 생기면 그때 별도 세부 Data 시트를 추가한다.

### 6.5 남은 미정 사항 (설계 단계)

1. Id 파싱/검증 - `EditorTableReader.ParseEnum<TEnum>`이 이름 문자열 매칭이었는데, 이제 정수 매칭(`(TEnum)Enum.ToObject(typeof(TEnum), id)` 또는 `Enum.IsDefined` 검증 후 캐스팅)으로 바꿔야 한다. 정의되지 않은 Id가 들어오면 즉시 에러로 드러나야 한다(v1의 "조용히 깨지지 않는다" 원칙 유지).
2. String 조회 인터페이스 - `CharacterStatsTableAsset` 등 Data 에셋과 별도로 `CharacterStringsTableAsset`(또는 통합)을 어떻게 나눌지, `IBattleUnitStatProvider`/UI 소비자가 라벨을 조회하는 API 형태.
3. 기존 SO 에셋(`CharacterStatsTableAsset`, `EnemyStatsTableAsset`, `RoleGroupTacticsCatalogAsset`, `PartyTacticsPolicyCatalogAsset` 등)의 `DisplayName`/`DisplayLabel` 필드를 전부 제거하고 새 String 에셋 참조로 교체 - 필드 제거 범위가 넓어 설계 단계에서 영향 파일을 전수 정리해야 한다.
4. 9개 enum에 명시적 정수값을 박는 작업 자체(코드 변경) - 기존 저장된 상행 데이터(`InMemoryUnitConditionRepository` 등 인메모리 상태)는 세션 간 유지되지 않으므로 마이그레이션 이슈는 없다.
5. v1 워크북(`Assets/Table/CharacterStats.xlsx`/`Tactics.xlsx`) 삭제 시점 - v2 임포터가 전부 자리 잡은 뒤 한 번에 정리.
