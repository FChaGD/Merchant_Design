## 1. 배경

마을 화면은 시설 카테고리 4개와 시설 11개를 노출하지만, 어느 마을이 어떤 시설을 제공하는지는 정해지지 않았다. 지금은 임시 구현이 모든 마을에 같은 제공 여부를 돌려준다. 이번 문서는 마을에 **규모**를 두고, 규모로 이용 가능한 시설을 정한다.

## 2. 범위

- 포함: 규모 정의(대도시·도시·촌락), 규모별 이용 가능 시설, 마을별 규모 지정, 데이터 위치.
- 제외: 규모에 따른 다른 차이(판매 품목·가격·후보 수·시설 등급 등), 마을별 시설 예외, 규모 변화(성장·쇠퇴), 규모 표시 UI, 시설 잠금/해금 조건.

## 4. 확정 사항 — 배정·테이블 구성 (2026-09-28)

### 4.1 규모별 시설 배정

포함 관계이므로 시설마다 "처음 이용 가능해지는 규모"(최소 규모) 하나만 정하면 된다. 아래는 추천안 그대로 확정한 기본값이며 인스펙터에서 수정한다.

| 카테고리 | 시설 | 최소 규모(기본값) | 근거(기획 24번 역할) |
|---|---|---|---|
| 시장 지구 | 무역품 구매 | 촌락 | 어디서나 구할 수 있는 물건 — 교역의 기본 |
| 시장 지구 | 특산물 구매 | 대도시 | 사치품·장인 제작품 — 큰 시장에 모임 |
| 시장 지구 | 전당포 | 도시 | 전리품 매각 — 환전 수요가 있는 규모 |
| 주점 지구 | 숙소 | 촌락 | 휴식 — 상행 경로상 최소 기반 |
| 주점 지구 | 용병단 접촉 | 도시 | 용병 고용 — 인력이 모이는 규모 |
| 주점 지구 | 주점 | 도시 | 정보 획득 — 왕래가 있는 규모 |
| 공업 지구 | 잡화 상점 | 촌락 | 전투 소모품 — 기본 보급 |
| 공업 지구 | 마구간 | 도시 | 마차·시설 매매 |
| 공업 지구 | 대장간 | 도시 | 장비 구매 |
| 시청 방면 | 시청 | 대도시 | 퀘스트·은행 — 행정 중심지 |
| 시청 방면 | 상인조합 | 대도시 | 상단 운영 — 행정 중심지 |

결과:

| 규모 | 시설 수 | 노출 카테고리 |
|---|---|---|
| 촌락 | 3(무역품 구매·숙소·잡화 상점) | 시장·주점·공업 지구(시청 방면 없음) |
| 도시 | 8(촌락 + 전당포·용병단 접촉·주점·마구간·대장간) | 시장·주점·공업 지구 |
| 대도시 | 11(전부) | 4개 전부 |

- 특산물 구매는 **대도시로 확정**(사용자 결정). 역할의 "토산품"(지역 특산)을 고려해 촌락·도시에도 여는 경우는 기획상 확장으로만 염두에 둔다 — 규모 기본값 변경 또는 마을별 예외(§6)로 대응.

### 4.2 도시 테이블 3종 구성 (확정)

| 테이블(시트) | 열 | 행 단위 | 기존 시트 |
|---|---|---|---|
| City Data(`CityData`) | Id, X, Y, Scale | 도시 1개 = 1행 | `TripCities` + 규모 열 |
| City String(`CityStrings`) | Id, Name, Description | 도시 1개 = 1행 | `TripCityStrings` |
| City Detail Data(`CityDetailData`) | CityIdA, CityIdB | 경로 1개 = 1행 | `TripRoutes` |

- 한 테이블로 합치지 않는 이유:
  - **스트링 분리**: 수치 데이터와 표시 문자열을 나누는 것이 모든 테이블의 공통 원칙이다(캐릭터·아이템·마차 테이블). 한 도시의 이름을 바꾸거나 번역할 때 수치 행을 건드리지 않는다.
  - **경로는 도시와 1:1이 아니다**: 한 도시에 경로가 여러 개라, 도시 행에 넣으려면 한 칸에 목록("3;4;6")을 적어야 한다. 양방향 중복·오타 검증이 어려워진다. 아이템의 세부 데이터(아이템 × 마을 가격)처럼 "관계 1개 = 1행"이 세부 데이터의 규칙과 맞는다.
  - 규모는 도시와 1:1이라 City Data에 열로 넣는다.
- 디버그 도시 배치 도구는 저장할 때 좌표·경로만 갱신하고 규모 등 다른 열은 보존하도록 바꾼다(설계 과제).

### 4.2-1 규모별 시설·규모 이름 (내부 데이터)

- 시설별 최소 규모(§4.1 배정표)를 코드 기본값으로 두고, 인스펙터에서 시설별로 수정한다.
- 규모 이름(대도시/도시/촌락)은 코드 상수.

### 4.3 마을별 규모 지정 (Placeholder — 디버그 도시 규모는 확정, 나머지 2행은 추천안)

| 항목 | 추천안 | 근거 |
|---|---|---|
| 디버그 도시 10개 | **확정(사용자 지정, 2026-09-28)**: 4번 대도시 / 2·6·7·10번 도시 / 1·3·5·8·9번 촌락 | 값은 테이블에서 자유롭게 수정 |
| 규모가 없는 마을 | 촌락으로 취급 + 임포트 시 경고 | 디버그 도구로 새 도시를 추가하면 규모 행이 없을 수 있음. 가장 작은 규모로 두면 시설이 과하게 열리지 않음 |
| 없는 도시 Id를 가리키는 규모 행 | 임포트 시 경고(무시) | 도시를 지웠을 때 남은 행을 드러냄 |

## 5. 설계 단계로 넘길 기술 과제

- 기존 시설 제공 여부 계약(`ITownFacilityAvailabilityReader`: 마을 Id + 시설 Id)을 그대로 두고 구현만 "마을 규모 ≥ 시설 최소 규모"로 교체. 지금의 인스펙터 체크 목록(시설별 제공 여부)을 시설별 최소 규모 목록으로 바꾸는 방식 검토.
- 도시 워크북 교체(`TripCityMap.xlsx` → `City.xlsx`, 시트 이름 변경)에 따른 임포터·디버그 저장 도구 수정. 디버그 저장 시 규모 열 보존.
- 규모 조회 계약(마을 Id → 규모)을 따로 열지 — 규모를 쓰는 다른 소비자(향후 판매 품목 등)가 생길 때를 대비.
- 시설 Id 목록(`TownFacilityIds`/`TownFacilityCatalog`)과 테이블의 시설 Id 불일치 검증(임포트 시).
- 코드 위치: 시설 제공 여부 계약·카탈로그는 이미 `develop`/`system`에 있다(2026-09-28 동기화). 마을 화면은 `ui` 영역이므로 제작 후 `system`→`develop`→`ui` 반영 필요.
- 새 테이블 자산 → "Play(자동 임포트) → Build Bootstrap Scene" 순서.
