## 1. 배경

33번 문서에서 아이템 Id 체계를 문자열 슬러그로 정하는 과정에서, "기존 `CharacterStats`/`EnemyStats`/`Tactics` 계열 테이블도 같은 체계로 통일하자"는 결정이 나왔다. 기존 테이블은 14번 문서 §6(v2 스키마)에서 "enum에 명시적으로 박은 정수값 = Id" 방식을 이미 확정해 구현·운영 중이었고, 그 근거는 "이 enum들이 전투 AI 등 게임 로직 분기에도 쓰여 Id 용도가 공짜로 얹힌다"(§6.2)는 것이었다 — 아이템처럼 코드 분기가 없는 경우와는 다른 전제였다.

사용자에게 이 차이와 "enum을 완전히 제거하면 전투 AI 분기 로직까지 함께 재설계해야 한다"는 점을 고지했고, 그럼에도 **enum 자체를 제거하고 문자열 기반으로 전체 교체**하기로 확정 답변을 받았다(2026-09-23).

## 2. 범위

- 14번 문서 §6.1에서 정수 Id 대상으로 지정한 enum 9종을 문자열 식별자 체계로 전환한다: `MercenaryClass`, `EnemyType`, `RoleGroup`, `TargetPriority`, `LocalPositioning`, `SelfPreservation`, `EnemyRecognitionType`, `ActivityRadiusPreset`, `PursuitPreset`.
- 대상 테이블(14번 §6.3): `Character/CharacterStats.xlsx`, `Enemy/EnemyStats.xlsx`, `Tactics/PartyPolicy.xlsx`, `Tactics/RoleGroupTactics.xlsx`.
- 이 enum들을 참조해 게임 로직을 분기하는 코드(`TargetSelectorFactory` 등 전투 AI/전술 전략 선택 로직)도 함께 재설계 대상에 포함한다.
- 문자열 슬러그의 구체 표기 규칙, 분기 로직을 문자열 비교로 바꿀지 `Dictionary<string, 전략>` 방식으로 바꿀지, 마이그레이션 순서/단계, 영향 코드 전수 목록, 회귀 검증 계획은 이 문서의 범위 밖 — 설계 단계 대상(§4).

## 3. 확정 사항 (사용자 스펙, 2026-09-23)

- enum 9종을 제거하고 문자열 기반 식별자로 전체 교체한다.
- 14번 문서 §6.1의 나머지 두 원칙(문자열/수치 분리 = Data/String 시트 구조, 도메인별 워크북+폴더 분리)은 그대로 유지한다 — 이번 결정은 "Id를 무엇으로 표현하는가"만 바꾼다.

## 4. 영향 범위 확인 (실측, 2026-09-23)

코드에서 9개 enum 이름을 직접 검색한 결과, 최소 **92개 파일**이 이 중 하나 이상을 참조한다(단순 텍스트 검색 — 실제 컴파일 의존성 그래프 기준 전수 조사는 아님, 아래 확인).

| enum | 참조 파일 수(단순 검색) |
|---|---|
| MercenaryClass | 20 |
| RoleGroup | 20 |
| PursuitPreset | 17 |
| LocalPositioning | 17 |
| EnemyType | 16 |
| SelfPreservation | 16 |
| TargetPriority | 15 |
| ActivityRadiusPreset | 13 |
| EnemyRecognitionType | 12 |

이 수치는 "무엇을 바꿔야 하는지"의 근사치일 뿐, 정확한 영향 범위(어떤 파일이 실제로 `switch`/분기 로직을 갖는지, 어떤 파일이 단순 타입 선언만 갖는지)는 설계 단계에서 파일 단위로 확인해야 한다.

**함께 회귀 검증이 필요한 기존 검증 완료 기능** (메모리 기록 기준, 미확인 — 설계/제작 단계에서 실제 영향 여부 재확인 필요):
- 전투 AI 방향성 지시/전술(12번, 17번 기획) — `RoleGroup`/`TargetPriority`/`LocalPositioning`/`SelfPreservation` 직접 관련.
- 파티 방침(인식방식/활동반경/추격방침) — `EnemyRecognitionType`/`ActivityRadiusPreset`/`PursuitPreset` 직접 관련.
- 원거리딜러 포지셔닝, 자리 사수 복귀 등([[project_ranged_dealer_positioning_redesign]], [[project_stationary_return_to_home]]) — `LocalPositioning` 등에 의존할 가능성.

## 5. 설계 단계로 넘길 기술 과제

- 문자열 식별자 표기 규칙 확정(예: enum 멤버명을 그대로 쓸지 `"warrior"` 같은 별도 슬러그로 새로 정할지).
- 분기 로직 재설계 방식 — `switch(string)` 직접 비교 vs `Dictionary<string, IStrategy>` 등록 방식 중 선택(후자가 OCP 관점에서 유리할 가능성이 높으나 확정은 설계 단계).
- `EditorTableReader.ParseEnum<TEnum>`/`SetEnumValue<TEnum>`(정수 기반)을 대체할 문자열 파싱/검증 유틸리티 설계 — 33번 문서 §4의 아이템용 검증 로직과 공유 가능한지 확인.
- 92개 영향 파일의 실제 분류(단순 필드 타입 vs 분기 로직) 전수 조사.
- 마이그레이션 순서 — enum 9종을 한 번에 바꿀지, 의존성이 적은 것부터 순차 전환할지.
- 회귀 검증 계획 — §4에 나열한 기존 검증 완료 기능들의 재검증 절차.
- 대응 설계 문서(18번 등, v2 스키마 구현 설계) 갱신 필요 여부.

## 6. 위험 고지 (재확인)

이 전환은 이미 구현 완료되고 실전투로 검증된 시스템(전투 AI 타겟팅, 전술 지시, 파티 방침)을 광범위하게 재작성하는 작업이다. 아이템 시스템(33번 문서)과 무관하게 그 자체로 회귀 위험을 지는 별도 작업이므로, 제작 착수 전 설계 단계에서 영향 범위를 확정하고 재검증 계획을 먼저 세운 뒤 진행을 권장한다.
