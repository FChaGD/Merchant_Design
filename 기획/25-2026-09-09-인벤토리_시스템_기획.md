## 1. 배경

24번 문서가 마을 시설 카테고리(시장 지구/주점 지구/공업 지구/시청 방면)와 하위 시설 11개의 역할을 정의했으나, "각 시설에서 실제로 거래되는 품목"이 상단(플레이어 조직) 쪽에서 어떻게 보관·관리되는지는 다루지 않았다(24번 §4 명시). 23번 문서는 재화 상한이 마차 보관 가능량에 연동된다고 정의했지만, 재화 외의 물품(교역품, 장비, 소모품 등)이 같은 구조를 따르는지는 정의된 적이 없다. 이번 기획은 이 공백을 해소한다.

## 2. 범위

- 인벤토리가 다루는 카테고리 구성과 각 카테고리의 정의를 확정한다.
- 각 카테고리 인벤토리의 소유 주체(상단 공용 vs 개별 소지)를 확정한다.
- 마차 보관 가능량(23번 문서)과 각 카테고리 인벤토리의 관계를 확정한다.
- 각 인벤토리의 구체 저장 방식(슬롯 개수제/무게 총합제 등), 슬롯 수·용량 수치, UI 구성, 아이템 데이터(개별 품목 목록/스탯)는 범위 밖 — 후속 세션 대상.

## 3. 확정 사항 (사용자 스펙, 2026-09-09)

### 3.1 인벤토리 카테고리 구성

인벤토리는 하나로 통합하지 않고 용도별로 4종으로 분리한다.

| 카테고리 | 정의 |
|---|---|
| 교역품/전리품 | 무역품 구매·특산물 구매에서 매매하는 상품, 전당포에서 매각하는 상행 전리품 등 "거래용" 물품 |
| 장비 | 대장간에서 구매하는 무기/방어구 등 캐릭터(용병) 장착용 물품 |
| 전투 소모품 | 잡화 상점에서 구매하는, 전투 중 사용/소모되는 아이템 |
| 상단주 개인 물품 | 용병과 별개로 상단주(플레이어) 전용인 물품 일체 — 상단주 전용 장비/액세서리, 스토리·퀘스트 아이템, 상단주에게만 적용되는 소모성 버프/포션을 모두 포함 |

### 3.2 소유 주체

4개 카테고리 모두 캐릭터(용병)별 개별 소지가 아니라 **상단(플레이어 조직) 단위로 관리**한다. 다만 카테고리별로 별도의 인벤토리로 분리 관리한다 — 하나의 통합 목록에서 필터링하는 방식이 아니라, 애초에 별개의 저장 공간이다.

### 3.3 마차 보관량과의 관계

23번 문서의 "재화 상한 = 기본 소지량 + 소유한 모든 마차의 보관 가능량 합계" 구조를 확장한다.

- **마차 보관 가능량은 재화와 교역품/전리품이 공유하는 하나의 자원 풀이다.** 즉 마차 보관 가능량 총합 안에서 재화 보유량과 교역품/전리품 보유량이 함께 자리를 차지한다(구체 계산 방식 — 재화 1단위와 교역품 1단위가 동일한 "무게"로 취급되는지 여부 등은 범위 밖).
- **장비, 전투 소모품, 상단주 개인 물품은 마차 보관량과 무관한 별개의 인벤토리 시스템**이다. 마차를 추가로 확보해도 이 세 인벤토리의 용량은 늘어나지 않는다.

### 3.4 저장 상한

장비/전투 소모품/상단주 개인 물품 3개 인벤토리는 각각 별도의 저장 상한(슬롯 수 등)을 가진다. 상한이 없는(무제한) 인벤토리는 없다. 구체 수치는 밸런싱 영역으로 이번 문서에서 다루지 않는다.

## 4. 이 기획이 건드리지 않는 것

- 장비/전투 소모품/상단주 개인 물품 인벤토리 각각의 저장 상한 구체 수치.
- 저장 방식이 슬롯 개수제인지 무게 총합제인지, 카테고리마다 같은 방식을 쓰는지.
- 마차 보관량 안에서 재화와 교역품/전리품이 정확히 어떤 비율/단위로 용량을 나눠 쓰는지(예: 재화 1당 용량 1 vs 재화는 용량 소모 없이 교역품만 소모 등).
- 각 인벤토리의 UI 화면 구성(마을 시설·정비창 등에서 어떻게 열람/조작하는지).
- 개별 아이템 데이터(품목 목록, 스탯, 아이콘, 획득/구매 경로별 목록).
- 아이템 획득/소모 트리거의 구체 규칙(전당포 매각, 대장간 구매, 전투 소모품 사용 등 각 행위의 인벤토리 반영 로직).
- 상단주 개인 물품 3종(전용 장비, 스토리 아이템, 개인용 버프) 사이에 세부 구분(같은 인벤토리 내 하위 분류 여부)이 필요한지.

## 5. 설계 단계로 넘길 기술 과제

- 4개 인벤토리를 어떤 인터페이스로 노출할지 — 카테고리마다 별도 인터페이스(`ITradeGoodsInventory`, `IEquipmentInventory`, `IConsumableInventory`, `IPersonalItemInventory`)로 쪼갤지, 공통 저장/조회 계약을 상위 인터페이스로 뽑고 카테고리별 특수 규칙(마차 연동 여부)만 구현체에서 분기할지 결정 필요(ISP 관점).
- 23번 문서에서 이미 제안된 재화 상한 재계산 구조(마차 획득/손실 이벤트 훅)를 교역품/전리품 용량 계산과 어떻게 공유할지 — 같은 `IPlayerResourceProvider`/`IPlayerResourceRepository` 계열에 통합할지, 마차 연동 전용 협력 객체로 분리할지.
- 아직 아이템 데이터 시스템이 없으므로 `CLAUDE.md` Placeholder 패턴에 따라 `PlaceholderXxxInventoryProvider` 계열이 카테고리마다 필요할 가능성.
- 아이템 데이터 정의 시 14번 문서(데이터 테이블 엑셀화)의 문자열 분리+도메인 폴더+Id 기반 패턴 재사용 여부.
