## 1. 기획 요약

- 상행을 **멈추고** 진행하는 이벤트. 랜덤(5초 판정 +2.5초 시점, 회당 3.3%, 난이도 무관)·확정(조건 성립, 중요도·FIFO 대기열). 같은 이벤트는 상행당 1회, 1회성은 게임 전체 1회.
- 흐름: 이벤트 대화 화면(전체화면, 상황 대사) → 선택 화면(전체화면) → 이벤트 대화 화면(결과 대사·효과) → [전투 → 승리 시 전투 후 대사] → 종료.
- 효과는 여러 개 묶음: 전투, 골드, 무역품, 이동 지연·단축, 도로 난이도(3방식), 합류, 이탈, 플래그, 마차·시설 내구도 증감(기획 90 — 상세는 [설계 91](91-2026-10-13-마차_시설_내구도_지속_아키텍처.md) §6).
- 효과를 그대로 적용할 수 없을 때(기획 §3.9): 골드·무역품은 있는 만큼만, 무역품 손실 대상 미지정은 무작위.

| 단위 | 위치 | 역할 |
|---|---|---|
| 이벤트 진행자 | FieldManager 하위 컴포넌트(설계 87 §6.1) | 판정, 화면 닫힘 대기, 정지 걸기·풀기, 대본 실행, 전투 연결, 종료 기록·신호 |
| 이벤트 고르기 | 순수 C# | 확정 대기열 차례 우선, 없으면 3.3% 랜덤 가중치 추첨(설계 87 §5) |
| 효과 실행기 | 효과별 작은 단위(순수 로직 + 기존 계약 연결) | Yarn 효과 명령 → 기존 기능(§5) |

| 선택 화면 | Field 씬, `IUIPanel`(모달 묶음) | 설명문·표시 인물·선택지(§6.2) |
| 정비창 열람 모드 | `IFieldFormationEditPolicy` 구현 하나 추가 | 이벤트 중 정비창: 보기만, 편집 요청 전부 거절 |

## 4. 이벤트 흐름

### 4.1 단계

| 단계 | 처리 |
|---|---|
| ① 판정 | 판정 시계의 이벤트 판정 신호(+2.5초). 확정 대기열 차례가 있으면(실행 직전 재검사 통과) 그것 — 그 시점 랜덤 판정 없음. 없으면 3.3% → 랜덤 후보 가중치 추첨 |
| ② 대기 | 정비창·방향성 지시가 열려 있으면 정지 조율자에 "이벤트 대기" → 상행 정지, 이동 대화 종료(88 §4.2). `IUIVisibilitySignal`의 모달 열림이 꺼지면 ③ |
| ③ 시작 | "이벤트" 정지 걸기(대기 정지는 풂). 방향성 지시·대화 버튼 비활성. 이벤트 대화 화면 열고 Yarn 노드 실행 |
| ④ 진행 | 클릭 넘김. `#choice` 줄 + 선택지 → 선택 화면, 선택 후 이벤트 대화 화면 복귀. 효과 명령은 순서대로 실행, 실행마다 결과 줄 |
| ⑤ 전투 | `<<battle>>` → 이벤트 화면 닫기 → 기존 전투 흐름(경고 → 전투 → 결과 정리 ①~③). 결과: 승리 = 이동 뷰 복귀 + "전투" 정지 해제(이벤트 정지 유지) → 이벤트 대화 화면 재오픈, 다음 줄(전투 후 대사)부터. 도주 = 대본 종료 → ⑥. 궤주·사망·포로 = 기존 패배 처리, 이벤트는 종료로 기록 |
| ⑥ 종료 | 발생 기록(전체·이번 상행). 이벤트 정지 해제 → 상행 재개. 신호: 이벤트 종료, (이벤트 안에서 전투가 있었으면) 전투 종료. 상단 버튼 복구 |

- 발생 기록은 끝까지 진행했을 때만(설계 87 §4.1). 이벤트의 "끝" = ⑥ 또는 패배로 흐름이 끝남.
- 이벤트는 대화와 달리 중단되지 않는다(이벤트 중엔 전투 판정·대화 검사가 상행 정지로 멈춘다).

### 4.2 기존 전투 흐름 연결

| 지점 | 변경 |
|---|---|
| 입구 | 전투 시작이 지금은 전투 판정(`EncounterManager.OnEncounterTriggered`)에서만 온다. 이벤트가 전투를 요청하는 입구(`IEventBattleRequester`)를 `EncounterManager`에 추가 — 확률 판정 없이 같은 인카운터 신호를 내므로, 흐름 조율자(`FieldEncounterFlowCoordinator`)의 기존 인카운터 처리(경고 → 전투 → 결과 정리)로 그대로 들어간다(2026-10-16 검진 — 표기 정정, 조율자 코드는 바뀌지 않음). 적 구성은 랜덤 전투와 같은 규칙(도로 난이도), 이벤트 지정 구성은 자리만 둔다(인자 없는 요청 + 향후 구성 Id 인자) |
| 결과 정리 ①~③ | 그대로(결과 팝업 → 회수 적재 → 대열 정리) |
| 마무리(`FinishStep`) | 이동 뷰 복귀·"전투" 정지 해제까지 같다. 정지 조율자에 "이벤트" 정지가 남아 있으면 **전투 종료 신호를 보내지 않고** 결과(승리·도주·패배)를 이벤트 진행자에 넘긴다 — 상행은 조율자가 정지 상태로 유지한다(설계 87 §6.2). 패배(궤주 등)는 기존 처리를 하되, 씬 전환 전에 이벤트 진행자에 패배를 알려 종료 기록을 남긴다 |

### 4.3 도로 난이도 변경 → 현재 구간 재계산

- 바뀐 도시 쌍이 현재 구간(출발·도착 도시, 방향 무관)이면 **인카운터 빈도와 남은 소요시간을 함께 재계산**.
- 새 총 소요시간 = 새 난이도 기본 시간(`TripTravelRules.ComputeDurationSeconds`) + 이미 더해진 추가 시간(파괴 마차 지연, 이벤트 지연·단축). **진행 비율 유지** — 경과 시간을 새 총 시간 × 진행 비율로 맞춘다(게이지가 튀지 않음).
- 필요한 변경: 상행 시계에 "추가 시간 누적"과 "총 시간 재설정(진행 비율 유지)", 여정 상태에 "현재 구간 난이도·빈도 갱신". 구간 계획(`TripLeg`)은 출발 시점 값이라(예상 일수 포함) 그대로 두고, 현재 구간의 실행 값만 따로 둔다.
- 현재 구간 실행 난이도 = 범위 자르기(도시 쌍 보이는 값(§5.2) + 이번 구간 증감). 이번 구간 증감은 요청 변경량을 그대로 누적한다(걸 때 자르지 않음 — 95에서 이번 구간 +10 → 100, 이어서 −10 → 95, 도시 쌍 방식과 같은 결과, 2026-10-16 보완 검진). 구간 기본 난이도는 지금과 같이 구성 도로 기본값의 길이 가중 평균(관문 짝 이동 제외).
- 세 방식 모두 바뀌는 순간 같은 계산. 날짜 기간 만료로 원래 값으로 돌아갈 때도 그 도시 쌍을 달리는 중이면 같은 계산.
- 재계산 시 진행 게이지의 구간 라벨(「구간 1/3 · 등급명」) 등급명도 새 난이도로 갱신한다.

## 5. 효과 명령

### 5.1 명령

| 명령 | 동작 | 결과 줄 |
|---|---|---|
| `<<battle>>` | §4.2. 끝날 때까지 대본 대기. 승리면 다음 줄 진행(= 전투 후 대사), 도주·패배면 대본 종료 | 없음(결과 팝업) |
| `<<gold N>>` | 양수: 개인 골드에 더함(기획 82 — 상한 없음, 출발 시 초과분 버림). 음수: **가진 만큼만**(0까지), 개인 골드 → 골드 상자 순(이벤트 골드 전용 계약의 "가진 만큼 잃기" — 실제 잃은 양 반환, §2) | 「골드 +100」「골드 −120」(실제 양). 잃는 효과인데 실제 0이면 「잃은 골드 없음」 |
| `<<goods_add 품목Id 수량>>` | 자동 배치(구매와 같은 빈자리 규칙). 남으면 임시 보관 → 결과 줄(클릭) → **회수 적재 화면 재사용**(정리 → 남으면 버림 확인, 기획 §3.6). 화면이 닫힐 때까지 대기. 결과 줄을 먼저 보이는 이유: 정리 화면에서 버린 뒤에 획득 문구가 뜨면 부자연스럽다(2026-10-16 보완 검진) | 「밀 ×2 획득」(요청 수량) |
| `<<goods_remove 품목Id 수량>>` | 가진 만큼만 제거(환급 없음 경로). 대상 순서: 임시 보관 → 적재(보유 마차 순서, 위 행·왼쪽부터) | 「밀 ×1 잃음」, 0개면 「밀 — 잃은 것 없음」 |
| `<<goods_remove random 수량>>` | 무역품 중 무작위, 가진 만큼만. 골드 상자 제외 | 「밀 ×1, 소금 ×1 잃음」, 0개면 「잃은 무역품 없음」 |
| `<<delay 초>>` | 양수 = 지연(기존 시간 늘리기), 음수 = 단축(새 기능). 단축은 지나온 시간 아래로 내려가지 않음 — 남은 시간이 0이면 상행 재개 직후 도착 | 「이동 지연 20초」「이동 단축 10초」 |
| `<<difficulty 증감 leg>>` | 현재 구간만 | 「도로 난이도 +10 (이번 구간)」 |
| `<<difficulty 증감 days N>>` | 현재 구간의 도시 쌍, 게임 날짜 N일 뒤 기본값 복귀 | 「도로 난이도 +10 (3일)」 |
| `<<difficulty 증감 permanent>>` | 현재 구간의 도시 쌍 현재값 영구 변경(다른 요인으로 재변경 가능) | 「도로 난이도 +10」 |
| `<<join 캐릭터Id>>` | 고용 명단 추가 → 정비창 팔레트에 표시(자동 배치 없음). 상한 없음(기획 80 §3-10) | 「○○ 합류」 |
| `<<leave 캐릭터Id>>` | 대열에서 제거(진행 중 배치·이동 취소) → 고용 명단 제거 → 고용 후보 복귀 | 「○○ 이탈」 |
| `<<durability 대상 퍼센트>>` | 대상 `wagon`/`facility`/`any`, 최대치 대비 %. 감소 = 무작위 1개, 회복 = 가장 손상된 1개. 0이면 파괴(마차: 화물 이동·마지막이면 궤주). 상세 [설계 91](91-2026-10-13-마차_시설_내구도_지속_아키텍처.md) §6 | 「마차이름1 내구도 −20」「시설이름1 파괴」 |
| 플래그 | Yarn `<<set $이름 to true>>` | 없음 |

- 난이도는 증감값, 기존 최소·최대로 자른다(도시 쌍 변경은 읽을 때 자른다, §5.2). 변경 후 §4.3 재계산.
- 결과 줄은 화자 없는 서술 줄(이벤트 대화 화면, 클릭 넘김). 문구 형식은 한 곳에 상수로.
- 실행 불가(없는 Id, 이미 고용된 캐릭터 합류, 미고용 캐릭터 이탈 등) → 효과 건너뜀 + 경고 로그, 대본 계속.

### 5.2 도로 난이도 3방식

| 방식 | 저장 | 복귀 |
|---|---|---|
| 이번 구간만 | 현재 구간 실행 값만 변경(도시 쌍 저장값은 그대로). 요청 변경량을 누적하고 읽을 때 자른다(§4.3) | 구간이 끝나면 자연 소멸 |
| 날짜 기간 | 도시 쌍 **기간 변경 항목**(사건 Id, 요청 변경량, 만료일) 추가(`RoadDifficultyState`) | 게임 날짜 변경 신호(`IDateReader.Changed`)에서 만료일이 지난 **그 항목만** 삭제 — 다른 기간 항목·영구 항목은 남음 |
| 영구 | 도시 쌍 **영구 변경 항목**(사건 Id, 요청 변경량) 추가 | 없음(향후 사건 Id로 항목 제거, §12) |

**도시 쌍 저장(§2 결정, 2026-10-16)**

- 키 = 두 도시 Id(방향 무관). 구간 = 출발 도시 → 다음 도시라, 관문을 지나는 구간도 키 하나다. 관문a–관문b 짝 이동은 난이도 계산에 쓰이지 않는다(지금과 같음).
- 값 = **변경 항목 목록 두 개**(2026-10-16 보완 검진 — 영구·기간 두 칸 누적 + 만료일 하나 구조를 대체). 영구 항목 = (사건 Id, 요청 변경량), 기간 항목 = (사건 Id, 요청 변경량, 만료일). 같은 사건 Id로 다시 걸어도 기존 항목을 고치지 않고 새 항목을 더한다. 두 목록이 모두 비면 그 도시 쌍 기록을 지운다.
  - 이유: 한 칸 누적 + 만료일 하나면, 상한에서 효과가 없던 기간 변경이 만료일만 덮어써 다른 기간 변경을 앞당겨 끝내거나 늘렸다(예: 기본 90, 10일 +10(20일 만료) → 100, 3일 +10은 효과 0인데 만료일이 14일로 바뀌어 14일에 90).
- **범위 자르기는 읽을 때 한다(B안)** — 걸 때는 요청 변경량을 그대로 저장한다.
  - 보이는 값 = 자르기( 자르기(구간 기본 난이도 + 영구 변경량 합) + 기간 변경량 합 ).
  - 영구를 먼저 자르는 이유: 기간 변경이 "유지되는 값" 위에서 보이고 만료되게 하기 위해서다(기본 90, 영구 +50, 기간 −10 → 90. 합을 한 번만 자르면 100이 되어 기간 −10이 안 보인다).
  - 요청량이 그대로 남으므로 항목 하나를 빼면 그 변경만 정확히 빠진다(향후 Id로 제거, 만료). 이전의 "실제 변한 양만 저장"·"초과분을 영구 칸에서 정리" 규칙은 없앤다.
  - 결과: 95에서 기간 +10 → 100, 이어서 기간 −10 → **95**(요청량 합 0). 상한에 막혀 보이지 않던 양도 저장값에는 남는다 — 2026-10-12 "95 +10 −10 = 90" 규칙을 대체(사용자 결정). 결과 줄은 지금처럼 요청 변경량(「도로 난이도 +10 (3일)」).
- 조회 계약: 증감 하나를 돌려주던 조회 대신 **구간 기본 난이도를 받아 보이는 값을 돌려주는 조회**와 **항목 목록 조회(읽기 전용)**를 둔다. 계산 규칙을 읽는 쪽마다 따로 두지 않기 위해서다. 변경 신호(`Changed`, 바뀐 도시 쌍)는 그대로.
- 상행 계획(`TripRoutePlanner`)의 구간 난이도 = 그 도시 쌍 보이는 값(기본 = 길이 가중 평균). 상행 정보 패널·예상 일수도 같은 값을 쓴다.

**사건 Id (2026-10-16 보완 검진)**

| 부분 | 규칙 | 예 |
|---|---|---|
| 이벤트 Id | 변경을 건 이벤트 Id(진행자가 자동으로 넘긴다 — 대본에 적지 않음). 이벤트 디버그 버튼은 `debug` | `E1` |
| 월일 | 변경을 건 날의 월·일, 두 자리씩 붙여 쓴다(월 01~06, 일 01~30). 날짜 계약이 없으면 1월 1일 | 3월 12일 → `0312` |
| 순번 | 같은 「이벤트Id-월일」 접두에 붙는 번호. 1부터, 플레이 세션 동안 증가하고 재사용하지 않는다. 도시 쌍과 무관 | `1`, `2` |

- 형식 `이벤트Id-월일-순번`(예 `E1-0312-1`, `debug-0312-1`). 구분자 `-`가 세 부분 사이에만 오도록 월일을 붙여 쓴다.
- 연도는 표시되지 않아 180일마다 같은 월일이 돌아오지만, 순번을 재사용하지 않으므로 Id는 저장소 전체에서 겹치지 않는다(항목 하나 특정 가능).
- Id 발급(순번 기록)은 난이도 저장소가 한다 — 항목과 같은 수명(플레이 세션). 저장·불러오기가 생기면 순번 기록도 함께 저장한다(§12).
- 용도: 출처 표시(이벤트 디버그 §7) + 향후 Id로 항목 제거(§12, 이번에 만들지 않음).
- 같은 관문을 쓰는 다른 도시 쌍(도시d–관문a–관문b–도시b)은 영향을 받지 않는다. 관문b–도시c 같은 다른 도로도 마찬가지.
- 기존 도로 조각별 변경 저장(`RoadKey` 기준 `SetDifficulty`/`ResetDifficulty`)은 호출처가 없어(기획 75 §6 향후용) 도시 쌍 저장으로 교체한다. 도로 조각의 기본값은 지금처럼 지도 데이터에서 읽는다.
- 같은 도시 쌍에 기간 변경이 겹치면 항목이 각각 남고 **각자 자기 만료일에** 끝난다. 영구·기간 항목은 서로를 건드리지 않는다(2026-10-16 보완 검진 — 이전 "누적 + 마지막 만료일로 덮기" 대체).

### 5.4 대본 작성 규칙 (이벤트 전용, 설계 87 §3.2 추가)

| 요소 | 규칙 |
|---|---|
| 선택 화면 설명문 | 선택지 바로 앞 줄에 `#choice` — 그 줄은 이벤트 대화 화면이 아니라 선택 화면 설명문으로 표시 |
| 표시 인물 | 같은 줄 `#people:인물Id,인물Id`(상단원·외부 인물, 0명 가능) |
| 선택 횟수 | 여러 번 가능 — 선택지 묶음마다 `#choice` 줄 하나 |
| 화자 자리 | `#left` / `#right`(88 §5.3과 같음) |

예시(E2):
```
title: E2_Toll
---
bandit_leader: #right 지나가려면 통행세를 내라.
merc_a: #left 단장, 어떻게 할까요?
무리가 길을 막고 통행세를 요구한다. #choice #people:bandit_leader,merc_a
-> 낸다 <<if gold() >= 300>> #lock:골드_300_필요
    <<gold -300>>
    bandit_leader: #right 현명한 선택이군.
-> 거절한다
    merc_a: #left 싸울 수밖에 없겠군요!
    <<battle>>
    merc_a: #left 정리됐습니다.
===
```

### 5.5 이벤트 전용 캐릭터 (기획 §3.7)

- `CharacterStats.xlsx`에 "고용 후보 제외" 열 추가 → 캐릭터 정보에 포함.
- 고용 후보 목록(`PlaceholderMercenaryCandidateProvider`)은 이 열이 켜진 캐릭터를 뺀다. `<<join>>`은 열과 무관.
- 합류한 전용 캐릭터의 이탈·사망 후 처리는 범위 밖(기획 §2 — 재고용·디폴트 용병 기획과 함께).

### 5.6 명령 명세 표 (2026-10-16 검진)

효과 명령·조건 함수의 이름과 인자 형식이 효과 등록, 대본 검증, Yarn 컴파일 선언 세 곳에 따로 적혀 있었다 — 명령 하나를 더하면 세 곳을 같이 고쳐야 하고, 하나가 빠지면 Yarn 컴파일 오류나 검증 오탐이 난다. 명세를 순수 정적 표 하나(Game.Core, 이벤트 폴더)에 두고 세 곳이 그것을 읽는다.

| 명세 | 내용 |
|---|---|
| 명령 | 이름 + 인자 종류 목록. 종류: 정수, 양의 정수, 실수(초), 품목Id, 품목Id 또는 `random`, 캐릭터Id, 난이도 방식 |
| 난이도 방식 | `leg`·`permanent`는 인자 2개, `days`는 3번째 인자로 양의 정수 — 방식별 인자 개수 규칙도 명세에 둔다 |
| 조건 함수 | 이름 + 반환 형식 + 인자 형식(`gold`→정수, `goods(문자열)`→정수, `hired(문자열)`→참거짓) |

| 소비자 | 쓰는 방식 |
|---|---|
| 효과 등록(`EventEffectCommands`) | 명령·함수 이름을 명세 상수로 쓴다 |
| 대본 검증(`EncounterContentValidator`) | 이름 존재·인자 개수·종류별 형식을 명세로 검사. 품목·캐릭터 존재 확인은 지금처럼 검사 규칙(`EventScriptRules`) 함수로 |
| Yarn 컴파일 선언(`EventYarnFunctionDeclarations`) | 함수 명세 목록을 돌며 선언 |

- 등록 결과와 명세가 어긋나지 않는지는 테스트로 묶는다: 등록된 명령·함수 이름 집합 = 명세 이름 집합, 등록 처리기의 인자 형식 = 명세 인자 종류의 형식(정수·실수·문자열).
- 효과 실행(인자 해석·효과 적용)은 지금처럼 명령별 메서드가 맡는다 — 명세는 "무엇을 받는가"만 갖는다.

## 6. 화면

### 6.1 이벤트 대화 화면 (전체화면)

```
┌──────────────────────────────────────────┐
│░░░░░░░░░ 반투명 어두운 배경 ░░░░░░░░░░░░░│
│░┌───────┐                  ┌───────┐░░░░░│
│░│       │ ┌──────────────┐ │       │░░░░░│
│░│ 일러1 │ │ 이름          │ │ 일러2 │░░░░░│ 말풍선 x .30~.70, y .36~.62
│░│(반전) │ │ 대사...    ▼  │ │(원본) │░░░░░│ 스탠딩 x .04~.28 / .72~.96, y .14~.86
│░│       │ └──────────────┘ │       │░░░░░│
│░└───────┘                  └───────┘░░░░░│
│[정비창 보기]                              │
└──────────────────────────────────────────┘
```

- 말풍선은 일러1·일러2 사이 중앙, 꼬리가 말하는 쪽을 가리킨다(서술·결과 줄은 꼬리 숨김, 이름 칸 비움, 양쪽 스탠딩 어둡게).
- 스탠딩: `#left`/`#right` 자리, 일러1 좌우반전·일러2 원본(그림만 반전, 이름은 별도 요소), 말하는 쪽 밝게·듣는 쪽 어둡게, 나오지 않는 자리 숨김. Placeholder(색 사각형 + 이름, 색은 Id로 결정).
- 클릭: 화면 아무 곳 — 출력 중 = 전체 표시, 출력 후 = 다음 줄. 자동 넘김 없음. 출력 완료 시 ▼.

### 6.2 선택 화면 (전체화면)

```
┌──────────────────────────────────────────┐
│░░░░░░░░░░░ 반투명 어두운 배경 ░░░░░░░░░░░│
│   ┌──────────────────────────────────┐   │
│   │ 설명문 (#choice 줄)               │   │ y .66~.90
│   └──────────────────────────────────┘   │
│      [인물A]     [인물B]                  │ y .40~.62 (0~여러 명, 가로 정렬)
│   ┌──────────────────────────────────┐   │
│   │ ① 낸다                            │   │
│   │ ② 거절한다                        │   │ y .08~.36
│   │ ③ (흐림) 뇌물 — 골드 300 필요     │   │
│   └──────────────────────────────────┘   │
│[정비창 보기]                              │
└──────────────────────────────────────────┘
```

- 설명문은 즉시 전체 표시(타자기 없음). 선택지 즉시 선택 가능, 제한시간 없음.
- 표시 인물: Placeholder, 반전 없음.
- 잠긴 선택지: 흐림 + 잠김 문구, 선택 불가. 선택지 행은 get-or-create 재사용.

### 6.3 형태·정비창 열람·전환

- 두 화면 모두 `IUIPanel`, 정비창과 같은 **모달 묶음**에 등록. 열기·닫기는 이벤트 진행자가 `UIManager`로(패널 규칙 — 패널은 스스로 닫지 않는다).
- "정비창 보기"(두 화면 좌하단): 정비창을 **열람 모드**로 연다 — 같은 모달 묶음 규칙으로 이벤트 화면은 숨겨졌다가, 정비창을 닫으면 복귀. 정비창이 열린 동안 대사 실행기 일시정지(모달 열림 신호).
- 이동 뷰 좌하단 버튼(정비창·방향성·대화)은 전체화면에 가려진다 — 이벤트 중 비활성(방향성·대화), 정비창은 위 버튼으로만. 이벤트 중에는 이동 뷰 UI 자체도 가린다(§13, 2026-10-16 검진).
- 전투 명령 → 이벤트 화면 닫기 → 전투. 승리 복귀 시 이벤트 대화 화면 재오픈.
- 요소 Id: `FieldEventUIElementIds`. Field 인스톨러(`Tools > Game > Build Field Scene`)에 get-or-create, `EditorUIBuilder` 사용 → Ctrl+S.
- 템플릿 참조(2026-10-16 검진): 선택 화면의 인물 줄·선택지 줄 템플릿에 작은 표시 컴포넌트를 붙여 하위 요소를 직렬화 참조로 든다(인물 줄 = 그림·이름, 선택지 줄 = 버튼·글자·투명도). 복제본도 같은 참조를 가지므로 화면 코드가 이름 문자열로 하위 요소를 찾지 않는다 — 인스톨러와 화면이 계층 이름을 이중으로 알던 결합이 없어지고, 투명도 컴포넌트 존재도 인스톨러가 보장한다. 인스톨러에서 이벤트 화면 위치를 정할 때 쓰는 회수 적재 패널은 그 조립 함수가 Transform을 돌려준다(결과 팝업 조립과 같은 방식).
- 좌표는 기준값 — 제작 시 Play 실측으로 겹침 점검.

### 6.4 예: E2에서 "거절한다"

1. 선택 화면 닫힘 → 이벤트 대화 화면 「싸울 수밖에 없겠군요!」
2. 이벤트 화면 닫힘 → 경고 → 전투 → 결과 정리
3. 승리 → 이동 뷰 복귀(상행은 여전히 정지) → 이벤트 대화 화면 「정리됐습니다.」
4. 종료 → 상행 재개 → 이후 20초 검사에서 '이벤트 직후'(우선)·'전투 직후' 대화 가능(88 §3)

| 대상 | 핵심 경우 |

| 합류·이탈 | 명단 추가, 이탈 시 대열·활동·명단 제거, 이미 고용/미고용 건너뜀 |

| 흐름(정지) | 대기 → 이벤트 정지 전환, 이벤트 전투 승리 후 정지 유지, 종료 시 재개 + 신호 2종, 패배 시 종료 기록 |

| 회귀 | 전체 EditMode, 랜덤 전투 흐름 불변 |

## 10. 제작 순서 (87·88 제작 완료 후)

1. 효과 실행기 + 테스트(골드·무역품·지연·합류·이탈), 고용 후보 제외 열
2. 도로 난이도 3방식·현재 구간 재계산·기간 복귀
3. 이벤트 진행자(판정·대기·정지·대본 실행·종료)
4. 전투 입구·마무리 분기
5. 이벤트 대화 화면·선택 화면·정비창 열람 모드·Field 인스톨러
6. E1~E4 콘텐츠
7. 디버그 도구
8. 사용자 Play 확인

### 10.1 Play 확인 항목 (사용자 실행)

- E1: 세 선택지 결과 줄, 무역품 공간 부족 시 정리 화면, 난이도 변경 후 남은 시간
- E2: 골드 300 미만 잠김, 거절 → 전투 → 승리 후 대사 → 상행 재개
- E3: 선택 없이 진행, 지연 반영(내구도 감소는 설계 91 묶음 D 제작 후 확인)
- E4: E1 돕기 후 확정 등장, 합류 후 정비창 팔레트 표시
- 이벤트 중 정비창 보기: 편집 불가, 닫으면 이벤트 복귀
- 정비창을 연 채 이벤트가 걸리면 닫은 직후 시작
- 디버그 도로 난이도 6개: 각 방식의 증가·감소 후 구간 라벨·남은 시간 변화, 3일 변경은 날짜 디버그로 날짜를 넘겨 기본값 복귀(그 구간을 달리는 중이면 재계산)
- 디버그 플래그: `helped_cart` 켜기 → 다음 판정에 E4 등장, 끄기 → 등장하지 않음
- (2026-10-16 검진) E1 "돕는다"를 골드 0으로 선택 → 「잃은 골드 없음」
- (2026-10-16 검진) 디버그 영구 +10 → 3일 +10 → 날짜 3일 넘김 → 영구분(+10)만 남음
- (2026-10-16 보완 검진) 디버그 상태에 항목별 사건 Id 표시(`debug-월일-순번`, 같은 날 두 번 누르면 순번 2). 기간 변경 두 개를 다른 날 걸면 각자 자기 날짜에 끝남
- (2026-10-16 보완 검진) 적재 공간이 찬 상태에서 E1 "짐 뒤지기" → 「획득」 결과 줄 클릭 후 회수 적재 화면
- (2026-10-16 검진) 이벤트 중 게이지·버튼·대화·Field 디버그 창 숨김, E2 거절 → 전투 중 보임 → 승리 후 다시 숨김, 정비창 보기 중에도 숨김 유지, 종료 후 복구(겹침 실측 1280×720·1920×1080)

## 13. 이벤트 중 Field UI 가림 (2026-10-16 검진 후 보완)

### 13.1 범위와 기준

- **숨김 대상(이동 뷰)**: 진행 게이지·구간 라벨, 구간 도착 알림, 「상단 배치」·「방향성 지시」 버튼, 전투 경고, 상행 대화(88) 말풍선·스탠딩·「대화」 버튼. 이동 뷰 배경은 남긴다.
- **숨김 대상(디버그)**: Field에서 그리는 상행·이력·대화·이벤트 디버그 창(접힌 버튼 포함). 전투 강제 승패 버튼은 전투 중에만 그려져 해당 없음.
- **숨기지 않음**: 이벤트 안에서 여는 정비창(열람 모드)·회수 적재 화면 — 이동 뷰 밖(ContentRoot 직속)이라 영향이 없다. Field에는 골드·날짜 표시가 없다(Hub 전용).
- **기준**: 이벤트 시작부터 종료까지 가린다. **이벤트 전투 동안만 보인다**(전투 요청 → 해제, 승리로 이벤트 화면 재오픈 → 다시 가림). "이벤트 화면이 열린 동안"을 기준으로 삼지 않는 이유: 정비창 보기를 열면 모달 묶음 규칙으로 이벤트 화면이 잠시 닫혀 게이지 등이 다시 나타나기 때문이다.

### 13.2 구성 (①안 — 원인별 가림 상태)

| 단위 | 위치 | 역할 |
|---|---|---|
| 화면 가림 상태 | FieldManager 하위 컴포넌트(정지 조율자와 같은 구조, 전역 DI 대상 아님 — FieldManager가 계약 단위로 대신 등록) | 원인(지금은 "이벤트" 하나) 집합. 원인이 하나라도 있으면 가림. 상행 시작·종료 신호로 원인을 비운다 |
| 쓰기 계약 | 원인 걸기·풀기 | 이벤트 진행자만 쓴다 |
| 읽기 계약 | 가림 여부 + 변경 신호 | 가림 적용 객체·Field 디버그 창이 쓴다. 쓰기·읽기를 나눈 이유: 읽기만 하는 소비자에게 걸기·풀기를 노출하지 않기 위해서다(ISP). 읽기 타입도 DI에 따로 등록한다(읽기 타입 미등록 시 조용히 null) |
| 가림 그룹 (2026-10-16 제작 계획 중 정정) | 이동 뷰 루트(`MovementView`)의 CanvasGroup **하나** + 배경 자기 CanvasGroup `ignoreParentGroups = true` | 인스톨러가 get-or-create로 붙이고 값을 기본값(투명도 1·입력 허용·클릭 차단 켬)으로 맞춘다(2026-10-16 보완 검진 — 에디터에서 바뀐 값이 남지 않게). 계층 구조는 바꾸지 않는다. 요소마다 붙이지 않는 이유: 구간 도착 알림·전투 경고는 자기 CanvasGroup 투명도로 페이드·점멸하므로 같은 그룹을 가림과 나눠 쓰면 서로 덮어쓴다. 새 이동 뷰 요소는 기본으로 가려지고, 남겨야 할 요소만 `ignoreParentGroups`로 뺀다 |
| 가림 적용 | plain C#(`FieldMovementViewHider`), `FieldUIWiring`이 Field 로드마다 만든다 | 로드 시점에 이동 뷰 루트의 CanvasGroup을 **한 번만** 찾는다. 만들 때 현재 상태를 바로 반영한다. 가림 = 투명도 0·입력 차단(CanvasGroup interactable·blocksRaycasts 끔), 해제 = 복구. 오브젝트를 끄지 않는다 — 게이지·알림의 구독·코루틴이 끊기지 않게(Hub 팝업 축의 CanvasGroup 규칙과 같다). Field 언로드 때 구독 해제 |
| Field 디버그 창 4개 | 각 OnGUI 뷰 | 시작 때 읽기 계약을 조회하고, 가려진 동안 그리지 않는다. 디버그 → 제품 코드 의존이라 결합 방향이 맞다 |

- 원인 기반으로 둔 이유: 나중에 다른 전체화면 연출(컷신 등)이 생기면 원인만 더하면 되고, 소비자(가림 적용·디버그)는 바뀌지 않는다. 한 원인을 풀어도 다른 원인이 남아 있으면 계속 가린다.
- 기존 상단 버튼 비활성(`SetTopLevelButtonsInteractable`)·정비창 열람 모드와는 따로 동작한다. CanvasGroup 해제는 버튼 자체의 활성 상태를 바꾸지 않는다.

### 13.3 흐름

| 시점 | 가림 |
|---|---|
| 이벤트 시작(③, 대기 정지 → 이벤트 정지 전환 직후) | 걸기 |
| `<<battle>>` 전투 요청(이벤트 화면 닫기와 함께) | 풀기 |
| 전투 승리 → 이벤트 화면 재오픈 | 걸기 |
| 이벤트 종료(대본 완료·도주·대본 실행 실패) | 풀기 |
| 이벤트 전투 패배 | 전투 요청 때 이미 풀림. 상행 종료 신호가 원인을 비운다 |
| 이벤트 진행 중 상행 종료(방어 경로 — 정상 흐름에선 오지 않음) | 진행자가 직접 풀기(2026-10-16 보완 검진 — 가림 상태의 상행 종료 비움에 기대지 않고, 이벤트가 끝나는 모든 경로가 진행자 안에서 가림을 푼다) |
| 상행 시작·종료 신호 | 원인 전부 비움(방어) |

- (2026-10-16 보완 검진 정정) 가림 상태는 FieldManager 하위 컴포넌트라 **실제 실행에서는 필수**다 — 없으면 FieldManager가 조기 실패한다(하위 컴포넌트 컨벤션). 진행자·소비자의 null 처리는 진행자 단위 테스트(가림 상태 없이 만든 경우)와 Bootstrap 미재빌드 때 디버그 창 등 소비자가 조회에 실패한 경우를 위한 것이며, 그때는 숨기지 않은 채 지금처럼 진행한다. 가림 적용 객체가 없어도(Field 인스톨러 미실행 — 표시 컴포넌트 0개) 아무것도 하지 않는다.
- 대화(88)는 이벤트 정지로 이미 끝나 있다 — 가림은 남은 스탠딩·「대화」 버튼까지 일관되게 숨기기 위한 것이다.

### 13.4 디버그 겹침

- 이벤트 중 Field 디버그 창이 그려지지 않으므로 이벤트 화면과의 겹침이 없어진다(§7 기존 미결 해소). 이벤트 전투 중에는 디버그 창과 전투 UI가 평소와 같다.
- 제작 시 1280×720·1920×1080에서 이벤트 진행 중(대화·선택·정비창 보기)과 이벤트 전투 중 겹침을 실측한다.
