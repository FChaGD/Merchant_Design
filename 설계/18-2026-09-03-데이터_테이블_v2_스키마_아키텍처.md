## 1. 배경

v1은 이미 코드로 구현되어 있다(미커밋). 기획 14번 §6이 v1에 구조 개선 3건(문자열/수치 분리, 도메인별 워크북 분리, Id 기반 참조)을 얹어 v2로 확정했다. 이 설계는 v1의 기존 구조(`EditorTableReader`, get-or-create 임포터, SO 에셋 + Provider 어댑터 패턴, `[SerializeField]` 배선)를 그대로 유지하면서, v2가 요구하는 변경만 최소로 얹는다 — v1 설계 17번의 결정(§1 배선 전례, §5 Provider 인터페이스 무변경 등)은 이 문서에서 재론하지 않는다.

## 2. 선결 버그 — `enumValueIndex`는 Id 기반 값 쓰기에 쓸 수 없다

**v2로 넘어가기 전에 반드시 고쳐야 하는 기존 코드 결함.** 현재 4개 임포터 전부 SerializedProperty에 enum 값을 쓸 때 이렇게 한다:

```csharp
element.FindPropertyRelative("MercenaryClass").enumValueIndex = (int)entry.MercenaryClass;
// TacticsTableImporter의 WriteOptionList/WritePartyOptionList도 동일 패턴(Convert.ToInt32 포함)
```

`SerializedProperty.enumValueIndex`는 enum의 **선언 순서상 위치(ordinal)**를 받는 필드지, enum 멤버의 **실제 정수값**을 받는 필드가 아니다. v1에서는 문제가 없었다 — 명시적 정수값이 없어 선언 순서와 실제 값이 우연히 같았기 때문(`Warrior`=순서 0=값 0). v2에서 9개 enum 전부에 **1부터 시작하는** 명시적 Id를 박으면(§3) 이 둘이 어긋난다 — 예를 들어 `MercenaryClass.Warrior = 1`일 때 `enumValueIndex = 1`을 쓰면 실제로는 `Archer`(선언 순서 1번째)가 저장된다. 조용히 다음 항목이 저장되는, 기획이 명시적으로 피하려는 "조용히 깨짐"의 정확한 사례다.

**해결**: `SerializedProperty.intValue`를 쓴다 — 이건 enum의 실제 정수값을 그대로 읽고 쓴다(선언 순서 무관). 4개 임포터의 enum 필드 쓰기 지점 전부(`.enumValueIndex = ...` 전부, `Convert.ToInt32(...)`를 `enumValueIndex`에 대입하던 지점 포함)를 `.intValue = ...`로 교체해야 한다. 반복될 실수를 막기 위해 `EditorTableReader`에 공용 헬퍼를 하나 추가한다:

```csharp
internal static class EditorTableReader
{
    // SerializedProperty에 enum 값을 쓰는 유일한 경로로 강제한다 - enumValueIndex(선언 순서)를
    // 실수로 쓰는 회귀를 원천 차단(§2 참고). 모든 임포터가 이 메서드를 통해서만 enum 필드를 쓴다.
    public static void SetEnumValue<TEnum>(SerializedProperty property, TEnum value) where TEnum : struct, Enum
        => property.intValue = Convert.ToInt32(value);
}
```

## 3. Enum 9종 — 명시적 Id 확정

기획 14번 §6.1 예시(`Warrior = 1, Archer = 2, ...`)를 따라 **1부터** 시작해 현재 선언 순서 그대로 배정한다. 0은 절대 유효 Id로 배정하지 않는다 — `default(TEnum)`(C#에서 필드 미초기화 시 자동으로 갖는 값)이 항상 0이므로, 0을 비워두면 "엑셀에서 안 읽어온 필드"와 "정상적으로 Id 0인 값"을 구분할 수 없다. 1부터 시작하면 `Enum.IsDefined` 검증이 초기화 누락까지 함께 잡아낸다(부수 이익).

| Enum | 멤버 = Id |
|---|---|
| `MercenaryClass` | Warrior=1, Archer=2, ShieldBearer=3 |
| `EnemyType` | Marauder=1, Monster=2, Adversary=3 |
| `RoleGroup` | Frontline=1, RangedDealer=2, Supporter=3, Assassin=4 |
| `TargetPriority` | Nearest=1, DeepestPenetration=2, HighestHpRatio=3, HighestAttack=4, LowestHp=5 |
| `LocalPositioning` | Charge=1, Blocking=2, Stationary=3, Surround=4, Disperse=5 |
| `SelfPreservation` | Resilient=1, FallBackOnHeavyDamage=2, Kiting=3, RetreatOnHit=4 |
| `EnemyRecognitionType` | OneSecondDelay=1, FiveSecondOrProximity=2, ProximityOrHit=3 |
| `ActivityRadiusPreset` | FormationHold=1, TripWide=2, FieldWide=3 |
| `PursuitPreset` | Autonomous=1, HuntToKill=2, OffensiveJudgment=3, NoPursuit=4, HoldPosition=5 |

기획 §6.2가 이미 확정한 대로 — 이 값은 enum 선언에 직접 박는다(`public enum MercenaryClass { Warrior = 1, Archer = 2, ShieldBearer = 3 }`). 별도 매핑 코드/서로게이트 Id 체계 없음. 멤버 **이름**을 바꿔도 이 정수값은 그대로 유지해야 엑셀 데이터가 안 깨진다(제작 단계 코드 리뷰 시 주의).

## 4. `EditorTableReader.ParseEnum<TEnum>` — Id 기반으로 전면 교체

v1의 문자열 이름 매칭(`Enum.TryParse<TEnum>(row[column], ...)`)을 정수 Id 매칭으로 완전히 대체한다(추가 오버로드가 아니라 기존 메서드의 구현/계약을 교체 — v2 워크북 어디에도 enum 이름 문자열 셀이 없으므로 문자열 매칭 경로는 죽은 코드가 된다).

```csharp
public static TEnum ParseEnum<TEnum>(IReadOnlyDictionary<string, string> row, string column) where TEnum : struct, Enum
{
    var id = ParseInt(row, column); // 셀 값 자체가 이제 "1", "2" 같은 정수 문자열
    if (!Enum.IsDefined(typeof(TEnum), id))
    {
        throw new FormatException($"컬럼 '{column}' 값 '{id}'은(는) {typeof(TEnum).Name}에 정의되지 않은 Id다.");
    }
    return (TEnum)Enum.ToObject(typeof(TEnum), id);
}
```

정의되지 않은 Id는 v1과 동일하게 즉시 예외로 드러난다(기획 §6.5-1의 "조용히 깨지지 않는다" 원칙 유지). `ParseBool`/`ParseFloat`/`ParseInt`/`GetOrCreateAsset<T>`는 v1과 동일 — 변경 없음.

## 5. String 조회 아키텍처

### 5.1 공용 엔트리 구조체

8개 enum(Id→한국어 라벨이 필요한 것 — `RoleGroup` 제외, 근거는 §6.2)이 전부 "Id, Ko" 2컬럼 동일 구조라, 공용 `[Serializable]` 구조체 하나를 재사용한다. 별도 클래스 8개를 만들지 않고 필드만 공유 — `TargetPriorityOption`/`LocalPositioningOption`/`SelfPreservationOption`처럼 축마다 별도 struct를 만드는 기존 관례(제네릭 SO는 인스펙터에 불안정 — `RoleGroupTacticsCatalogAsset.cs` 요약 주석)와는 다른 결이다: 그 관례는 "인스펙터에서 직접 편집하는 데이터"에 적용된 것이고, String 에셋은 **임포터만 쓰고 사람이 인스펙터에서 손대지 않는** 순수 임포트 산출물이라 제네릭 회피 이유가 적용되지 않는다. 값 구조 자체(Id+Ko)가 완전히 동일하므로 구조체 하나 공유가 SRP/재사용 원칙에 더 맞는다.

```csharp
[Serializable]
public struct LocalizedStringEntry
{
    public int Id; // enum의 실제 정수값(§3) - 타입은 소비하는 쪽 TryGetXxx 메서드가 강제
    public string Ko;
}
```

### 5.2 String 에셋 4종 — 워크북 1개당 1개

`PartyTacticsPolicyCatalogAsset`이 이미 "역할군 그룹핑 없는 3축을 리스트 3개로 한 에셋에 묶는" 전례를 세워뒀다(설계 17번 §10.1) — String 에셋도 같은 전례를 따라 **워크북 1개당 String 에셋 1개**로 묶는다(축/도메인마다 별도 에셋 8개를 만들지 않음). Data 에셋과 1:1 대응되는 워크북 구조(§7)를 String 에셋도 그대로 따른다.

```csharp
[CreateAssetMenu(fileName = "CharacterStringsTable", menuName = "Game/Table/Character Strings Table")]
public class CharacterStringsTableAsset : ScriptableObject
{
    [SerializeField] private List<LocalizedStringEntry> strings = new();
    public bool TryGetLabel(MercenaryClass id, out string ko) { /* 선형 탐색, TryGetEntry와 동일 스타일 */ }
}

[CreateAssetMenu(fileName = "EnemyStringsTable", menuName = "Game/Table/Enemy Strings Table")]
public class EnemyStringsTableAsset : ScriptableObject
{
    [SerializeField] private List<LocalizedStringEntry> strings = new();
    public bool TryGetLabel(EnemyType id, out string ko) { /* 동일 */ }
}

[CreateAssetMenu(fileName = "PartyTacticsPolicyStringsTable", menuName = "Game/Tactics/Party Tactics Policy Strings Table")]
public class PartyTacticsPolicyStringsTableAsset : ScriptableObject
{
    [SerializeField] private List<LocalizedStringEntry> recognitionStrings = new();
    [SerializeField] private List<LocalizedStringEntry> radiusStrings = new();
    [SerializeField] private List<LocalizedStringEntry> pursuitStrings = new();
    public bool TryGetRecognitionLabel(EnemyRecognitionType id, out string ko) { /* ... */ }
    public bool TryGetRadiusLabel(ActivityRadiusPreset id, out string ko) { /* ... */ }
    public bool TryGetPursuitLabel(PursuitPreset id, out string ko) { /* ... */ }
}

[CreateAssetMenu(fileName = "RoleGroupTacticsStringsTable", menuName = "Game/Tactics/Role Group Tactics Strings Table")]
public class RoleGroupTacticsStringsTableAsset : ScriptableObject
{
    [SerializeField] private List<LocalizedStringEntry> targetPriorityStrings = new();
    [SerializeField] private List<LocalizedStringEntry> positioningStrings = new();
    [SerializeField] private List<LocalizedStringEntry> selfPreservationStrings = new();
    public bool TryGetTargetPriorityLabel(TargetPriority id, out string ko) { /* ... */ }
    public bool TryGetPositioningLabel(LocalPositioning id, out string ko) { /* ... */ }
    public bool TryGetSelfPreservationLabel(SelfPreservation id, out string ko) { /* ... */ }

```

`TryGetXxxLabel`은 리스트를 선형 탐색해 `(int)id == entry.Id`인 항목을 찾는다 — 항목 수가 몇 개뿐인 소규모 카탈로그라 CLAUDE.md의 "Dictionary O(1)" 최적화 규칙(매 프레임 폴리 조회 대상) 범위 밖이다. 기존 `TryGetEntry` 메서드들과 동일한 선형 탐색 스타일을 유지한다.

### 5.3 조회 실패 시 폴백

`TableBattleUnitStatProvider`/`TableEnemyTypeCompositionProvider`(수치 Provider)는 항목 누락 시 `InvalidOperationException`으로 즉시 실패한다 — 전투 스탯은 게임플레이에 필수. String 조회는 순수 표시용이라 실패해도 게임을 막을 이유가 없다 — CLAUDE.md Placeholder 패턴의 "값 없음" 자리표시자 컨벤션을 그대로 적용한다: 소비자(§8의 `TacticsPanel`)가 `TryGetXxxLabel`이 `false`를 반환하면 라벨을 `"값 없음"`으로 채운다(창작 금지 원칙 - 있어 보이는 한국어 라벨을 임의로 만들어내지 않음).

## 6. Data 에셋 변경 — `DisplayName`/`DisplayLabel` 필드 제거 범위

전수 조사(코드 grep) 결과, 제거 대상 필드는 5개 파일의 구조체 8곳이다. `RoleGroup`은 화면에 노출되지 않는 내부 분류값이라(기획 §3.5 근거 유지) String 카운터파트가 없다 — 이미 v1도 `RoleGroup` 자체에 라벨 필드를 둔 적이 없어 변경 없음.

| 파일 | 구조체 | 제거 필드 | 대체 |
|---|---|---|---|
| `CharacterStatsTableAsset.cs` | `CharacterStatsEntry` | `DisplayName` | `CharacterStringsTableAsset` |
| `EnemyStatsTableAsset.cs` | `EnemyStatsEntry` | `DisplayName` | `EnemyStringsTableAsset` |
| `RoleGroupTacticsCatalogAsset.cs` | `TargetPriorityOption` | `DisplayLabel` | `RoleGroupTacticsStringsTableAsset.TargetPriorityStrings` |
| 〃 | `LocalPositioningOption` | `DisplayLabel` | 〃`.PositioningStrings` |
| 〃 | `SelfPreservationOption` | `DisplayLabel` | 〃`.SelfPreservationStrings` |
| `PartyTacticsPolicyCatalogAsset.cs` | `EnemyRecognitionOption` | `DisplayLabel` | `PartyTacticsPolicyStringsTableAsset.RecognitionStrings` |
| 〃 | `ActivityRadiusOption` | `DisplayLabel` | 〃`.RadiusStrings` |
| 〃 | `PursuitOption` | `DisplayLabel` | 〃`.PursuitStrings` |

**주의(조사로 확인된 사실)**: `CharacterStatsEntry.DisplayName`/`EnemyStatsEntry.DisplayName`은 현재 코드 어디서도 읽는 소비자가 없다(`TableBattleUnitStatProvider`/`TableEnemyTypeCompositionProvider` 둘 다 이 필드를 참조하지 않음 - grep으로 확인). 즉 이 두 필드는 지금도 "데이터는 있지만 아무도 안 읽는" 상태다. §5.2의 `CharacterStringsTableAsset`/`EnemyStringsTableAsset`도 마찬가지로 이번 제작에서는 **소비자 배선 없이 데이터만 준비**된다 - 향후 로스터/부대원 표시 기능이 생기면 그때 배선한다(기획 14번 §3.1이 원래 지목했던 `PlaceholderCaravanRosterProvider` 자리이나, 그 교체 자체는 이번 범위 밖).

반면 `RoleGroupTacticsCatalogAsset`/`PartyTacticsPolicyCatalogAsset`의 `DisplayLabel`은 `TacticsPanel.cs`가 실제로 6곳에서 읽고 있어(§8) 이번에 반드시 함께 배선해야 한다.

## 7. 워크북/임포터 재편 — 워크북 4개, 임포터 4개

기획 14번 §6.3의 폴더 구조를 그대로 따른다. v1은 임포터 2개(`CharacterStatsTableImporter`가 CharacterStats+EnemyStats+EnemyEncounterComposition 3시트, `TacticsTableImporter`가 나머지 7시트)였는데, 워크북이 도메인별로 4개로 쪼개지므로(기획 §6.3 근거: 편집 주기/담당자 분리) **임포터도 워크북 1개당 1개로 재편**한다 — "여러 워크북을 한 임포터가 열람"하던 v1 구조를 유지할 이유가 없어졌다(임포터-워크북 1:1이 더 단순하고, get-or-create 인스톨러 컨벤션의 "재실행해도 안전"과도 자연히 맞는다 - 워크북 하나 바뀌었는데 무관한 다른 도메인까지 다시 읽을 필요 없음).

| 임포터(신규 메뉴) | 대상 워크북 | 산출 에셋 |
|---|---|---|
| `CharacterStatsTableImporter`(기존 파일 재작성) | `Assets/Table/Character/CharacterStats.xlsx` | `CharacterStatsTableAsset`, `CharacterStringsTableAsset` |
| `EnemyStatsTableImporter`(신규 - v1의 `CharacterStatsTableImporter`에서 분리) | `Assets/Table/Enemy/EnemyStats.xlsx` | `EnemyStatsTableAsset`, `EnemyEncounterCompositionTableAsset`, `EnemyStringsTableAsset` |
| `PartyPolicyTableImporter`(신규 - v1의 `TacticsTableImporter`에서 분리) | `Assets/Table/Tactics/PartyPolicy.xlsx` | `PartyTacticsPolicyCatalogAsset`, `PartyTacticsPolicyStringsTableAsset` |
| `RoleGroupTacticsTableImporter`(기존 `TacticsTableImporter` 개명+축소) | `Assets/Table/Tactics/RoleGroupTactics.xlsx` | `MercenaryRoleGroupMapAsset`, `RoleGroupTacticsCatalogAsset`, `RoleGroupTacticsStringsTableAsset` |

각 메뉴는 `Tools/Game/Table/Import Character Stats` / `Import Enemy Stats` / `Import Party Policy` / `Import Role Group Tactics`. 4개 모두 §2의 `EditorTableReader.SetEnumValue`를 통해서만 enum 필드를 쓴다. `EnemyEncounterComposition` 시트의 `EnemyType` 컬럼도 이제 정수 Id 컬럼(`Id`, `EnemyStats.Id`를 가리키는 FK)이지 컬럼명이 `EnemyType`이 아니다 — 기획 §6.3 스키마의 실제 컬럼명(`Id`/`CharacterId`/`RoleGroupId`/`OptionId` 등, 시트마다 다름)을 임포터 작성 시 그대로 따른다.

편의를 위해 `[MenuItem("Tools/Game/Table/Import All")]`을 하나 추가해 4개를 순서대로(Character → Enemy → PartyPolicy → RoleGroupTactics) 호출한다 — 어차피 `TableAutoImportOnPlay`(§9)가 매 플레이 진입마다 같은 순서로 4개를 호출해야 해서, 그 호출 시퀀스를 재사용하는 것뿐이다.

**교차 파일 FK 처리**: `RoleGroupTactics.xlsx`의 `MercenaryRoleGroupMap.CharacterId`는 `Character/CharacterStats.xlsx`의 Id를 가리키지만(기획 §6.3), 임포트 시점에 그 워크북을 실제로 열어 존재를 검증하지는 않는다 — Id는 `MercenaryClass` enum 자체에 정의된 범위인지만 `Enum.IsDefined`로 검증하고(§4), "그 Id가 실제 CharacterStats 시트에도 존재하는가"는 검증 범위 밖(§11로 이월, v1 설계 17번 §7과 동일 판단).

## 8. 소비자 배선 변경

### 8.1 `TacticsPanel.cs`

`catalog`(`RoleGroupTacticsCatalogAsset`)/`partyPolicyCatalog`(`PartyTacticsPolicyCatalogAsset`) 옆에 필드 2개를 추가한다:

```csharp
[SerializeField] private RoleGroupTacticsStringsTableAsset roleGroupTacticsStrings;
[SerializeField] private PartyTacticsPolicyStringsTableAsset partyPolicyStrings;
```

기존 6곳의 `option => option.DisplayLabel`(제네릭 `SetOptions<T>(dropdown, IReadOnlyList<T>, Func<T,string>)` 오버로드에 넘기던 람다)을 각각 라벨 조회 람다로 교체한다:

```csharp
// 변경 전: SetOptions(recognitionDropdown, partyPolicyCatalog.RecognitionOptions, o => o.DisplayLabel);
SetOptions(recognitionDropdown, partyPolicyCatalog.RecognitionOptions, o => ResolveLabel(partyPolicyStrings.TryGetRecognitionLabel(o.Value, out var ko), ko));
// ResolveLabel(bool found, string ko) => found ? ko : "값 없음"; - 6곳이 공유하는 작은 헬퍼
```

`partyPolicyCatalog == null`/`catalog == null` 가드와 같은 자리에 `partyPolicyStrings == null`/`roleGroupTacticsStrings == null` 가드도 추가(§10.2의 `WarnMissing` 패턴 재사용).

### 8.2 인스톨러 배선

`PartyTacticsPolicyCatalogAsset`처럼 이번에 처음 생기는 에셋 4종(`CharacterStringsTableAsset`, `EnemyStringsTableAsset`, `PartyTacticsPolicyStringsTableAsset`, `RoleGroupTacticsStringsTableAsset`) 중 실제 소비자가 있는 2종(Party/RoleGroup Strings)만 자동 배선 대상이다(§6의 CharacterStrings/EnemyStrings는 소비자가 없어 배선 자체가 불필요 - 배선할 필드가 어디에도 없음).

| 파일 | 변경 |
|---|---|
| `ManagerHierarchyInstaller.cs` | `TacticsPanel` 배선부(기존 `partyPolicyCatalog` 배선 자리)에 `roleGroupTacticsStrings`/`partyPolicyStrings` 배선 추가 |
| `Editor/Debug/BattleTestSceneInstaller.cs` | `WirePartyPolicyCatalog` 계열 옆에 동일 배선 추가(BattleTest 씬도 `TacticsPanel`을 쓰는지 여부 확인 필요 - 안 쓰면 이 파일은 변경 대상에서 제외) |

`LiveBattleSimulationRule`/`BattleTestSimulationRule`/`InMemoryUnitConditionRepository`는 변경 없음(수치만 쓰고 라벨은 안 쓴다 - §6 확인 사항).

### 8.3 `InMemoryTacticsRepository.cs`

변경 없음 — 이 클래스는 enum 값(`RoleGroupTacticsOverride`, `PartyTacticsSettings`)만 저장/반환하고 라벨을 다루지 않는다. `ResolveDefaultPartySettings()` 등은 `partyPolicyCatalog.RecognitionOptions`의 `Value`/`IsDefault`만 읽으므로 `DisplayLabel` 제거의 영향을 받지 않는다.

## 9. `TableAutoImportOnPlay.cs` 갱신

`ExitingEditMode` 콜백이 호출하는 임포터를 2개(`CharacterStatsTableImporter`, `TacticsTableImporter`)에서 4개(§7 표)로 교체한다. 순서: Character → Enemy → PartyPolicy → RoleGroupTactics. 각 임포터가 실패해도(`Debug.LogError`만 남기고 조용히 중단) 다음 임포터는 계속 진행한다는 v1 원칙 유지 — 한 워크북 오류가 다른 도메인 임포트까지 막지 않는다.
