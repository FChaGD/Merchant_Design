## 1. 배경 / 범위

설계 37번에서 Hub UI를 **화면 depth 축**(depth에 따라 바뀌는 UI / depth와 무관한 상시 UI)으로 나눴다. 여기에 **팝업 축**(팝업이 떴을 때 숨는 UI / 팝업이 떠도 유지되는 UI)을 독립된 두 번째 관리 축으로 추가한다.

**사용자 확정 사항(2026-09-24)**
1. 팝업이 뜨면 비활성 대상 UI는 **숨김** 처리한다(클릭 차단만이 아님).
2. 숨김을 일으키는 팝업: 범용 팝업 개념 + **상행 준비 UI, 방향성 지시 UI, 상단 배치 UI**. 이하 "**모달 팝업**".
3. 팝업이 떠도 유지되는 UI: **재화 HUD만**. 인벤토리 호출 버튼 4종을 포함한 나머지는 모달 팝업 동안 숨는다(2026-09-24 제작 후 사용자 정정 — 한때 인벤토리 버튼을 유지 대상으로 정했다가, 모달 팝업을 켤 때는 인벤토리 버튼도 비활성화돼야 한다고 확정).
4. **인벤토리 팝업은 다른 UI를 숨기지 않는다** — 인벤토리 팝업이 떠도 다른 UI는 정상적으로 보이고 상호작용 가능하다. 이하 "**비모달 팝업**". 기획 31번 §3.5(카테고리별 별개 팝업, 동시 중첩 오픈)는 그대로 유효하다.
   - 경위: 처음엔 "재화 HUD만 유지 + 인벤토리 팝업도 숨김 유발"로 답했다가, 그 경우 인벤토리 팝업 하나를 열면 인벤토리 버튼이 숨어 31번 §3.5의 동시 중첩이 버튼으로 불가능해지는 충돌이 드러나 사용자가 전제를 정정했다.
5. 팝업 뒤 배경은 변화시키지 않는다(어둡게 처리 없음).
6. 두 관리 축과는 별개로, **씬 전환 시 모든 UI가 화면과 함께 자연스럽게 이동**해야 한다 — §10.

**범위 안**: depth 패널/모달 팝업 구분, 모달 팝업 열림 신호, Hub 레이어 재구성, Hub의 팝업 숨김 처리, 인터페이스 변경에 따른 Field/BattleTest 호출부 최소 수정, §10 전환 루트 정리.
**범위 밖**: 인벤토리 팝업 화면 자체(아직 없음), Field 씬에 depth/팝업 두 축 적용(37번 §3.5와 같은 후속 후보), 팝업 내부 탭 기능(사용자가 "구현 예정"으로 언급 — 별도 기획 대상).

## 2. 현재 구조의 문제

| 현재 방식 | 문제 |
|---|---|
| `UIManager`가 상행 준비/배치/방향성 지시 패널과 마을 카테고리 depth 패널을 **같은 목록·같은 네비게이션 스택**으로 관리한다. | 카테고리 depth에서 모달 팝업을 열면 단일 활성 정책 때문에 **카테고리 depth 패널이 닫혔다가** 팝업을 닫을 때 다시 열린다. depth 상태와 팝업 상태가 한 스택에 섞여 있다. |
| `OnAnyPanelOpenChanged` 하나로 "패널이 하나라도 열림"만 알린다. | depth 전환(루트 depth만 숨김)과 모달 팝업 열림(유지 대상 외 전부 숨김)을 구분할 수 없다. |
| Hub 레이어는 depth 축만 반영한다(모달 팝업 패널이 `DepthLayer` 안, 재화 HUD와 인벤토리 버튼이 `PersistentLayer`). | 모달 팝업 자신이 숨김 대상 레이어 안에 있다. 유지 대상 UI를 따로 모을 자리가 없다. |

## 3. 두 축의 정의

| | 모달 팝업 시 숨김 | 모달 팝업 시 유지 |
|---|---|---|
| **depth 의존** | 루트 depth 버튼(상행 준비/상단 배치/방향성 지시/카테고리 열), 카테고리 depth(시설 버튼/뒤로 가기) | (현재 없음 — §7) |
| **depth 무관** | 인벤토리 호출 버튼 4종 (+ 새 상시 UI의 기본 자리) | 재화 HUD |

- **depth 축**의 숨김은 `GameObject.SetActive`로 처리한다(기존 그대로 — 루트 depth 그룹, 카테고리 depth 루트).
- **팝업 축**의 숨김은 레이어 루트의 `CanvasGroup`(alpha 0, 클릭 차단, 상호작용 차단)으로 처리한다.
- 두 축이 **서로 다른 속성을 소유**하므로 한 오브젝트를 두 로직이 동시에 켜고 끄는 충돌이 없다. 최종 표시 = depth 축 활성 AND 팝업 축 표시. 예: 카테고리 depth에서 모달 팝업을 열었다 닫으면, 카테고리 depth의 활성 상태는 그대로 두고 팝업 축만 복구되어 원래 화면으로 돌아온다.
- **비모달 팝업(인벤토리)**은 팝업 축 신호에 참여하지 않는다 — 열려도 어떤 UI도 숨기지 않으므로, 인벤토리 팝업이 열린 상태에서도 인벤토리 버튼으로 다른 인벤토리 팝업을 열 수 있다(31번 §3.5 동시 중첩 유지). 모달 팝업이 떠 있는 동안에는 인벤토리 버튼이 숨으므로 버튼으로는 열 수 없다(시설 연계 등 다른 진입점은 별개).

## 4. 패널 종류 분리 — UIManager

### 4.1 등록

`IPanelRegistrar`의 등록 메서드를 종류별로 나눈다.

```csharp
public interface IPanelRegistrar
{
    void RegisterDepthPanel(IUIPanel panel);   // 화면 depth 전환 (마을 카테고리 depth, 후속 시설 화면)
    void RegisterPopupPanel(IUIPanel panel);   // 모달 팝업 (상행 준비/상단 배치/방향성 지시, 후속 범용 팝업)
}
```

- 종류를 인자(enum)로 받는 대신 메서드를 나눈 이유: 호출부에서 종류가 이름으로 드러나고, 잘못된 종류 지정을 코드 리뷰로 바로 볼 수 있다.
- 비모달 팝업(인벤토리 4종)은 기존대로 `InventoryPopupCoordinator`에 등록한다(설계 32번 §5 유지, 변경 없음).

### 4.2 네비게이션

`UIManager`가 `PanelNavigationStack` **인스턴스를 2개** 가진다(클래스 재사용).

| 스택 | 대상 | 동작 |
|---|---|---|
| depth 스택 | depth 패널 | 기존과 같은 단일 활성 + 복귀. 카테고리 depth → (후속) 시설 화면 → 닫으면 카테고리 depth. |
| 모달 팝업 스택 | 모달 팝업 | 기존과 같은 단일 활성 + 복귀. 상행 준비 → 상단 배치 → 닫으면 상행 준비. |

- `Open`/`Close`는 패널 Id로 어느 스택 소속인지 찾아 해당 스택에만 위임한다. **모달 팝업을 열어도 depth 스택은 건드리지 않는다** — §2 첫 행의 "카테고리 depth가 닫혔다 열리는" 문제가 사라진다.
- 씬 로드 시 `Reset`은 두 스택 모두 한다.
- `PanelNavigationStack`에 "현재 활성 패널이 있는가" 조회(`HasActive`)만 추가한다 — 두 신호(§4.3)를 스택 상태에서 바로 계산하기 위함이다.

### 4.3 상태 신호

`OnAnyPanelOpenChanged`를 제거하고 두 축의 신호로 나눈다. 소비자는 조회 전용이므로 `IUIManager`에서 분리한 읽기 전용 인터페이스로 제공한다(ISP).

```csharp
public interface IUIVisibilitySignal
{
    bool IsAtRootDepth { get; }
    event Action<bool> RootDepthChanged;       // true = depth 스택에 활성 패널 없음(루트 depth)
    bool IsModalPopupOpen { get; }
    event Action<bool> ModalPopupOpenChanged;  // true = 모달 팝업 스택에 활성 패널 있음
}

public interface IUIManager : IUIVisibilitySignal { ... }
```

- 각 신호는 해당 스택의 활성 여부가 **실제로 바뀔 때만** 발생한다. 모달 팝업끼리 전환(상행 준비→상단 배치→복귀)하는 동안에는 계속 true를 유지한다 — 기존 `OnAnyPanelOpenChanged`의 "중첩 전환 중엔 true 유지" 성질을 그대로 이어받는다.
- 인벤토리 코디네이터는 신호에 참여하지 않으므로 수정하지 않는다(비모달 — §3).

## 5. Hub 레이어 재구성

```
ContentRoot                     (씬 전환 루트 - 기존 그대로, §10)
 ├ Background
 ├ DepthLayer        [CanvasGroup: 모달 팝업 시 숨김]   depth 의존 · 숨김
 │   ├ RootDepth                                         (기존 - 루트 depth 버튼 + 카테고리 열)
 │   └ TownCategoryDepth                                 (기존)
 ├ PersistentLayer   [CanvasGroup: 모달 팝업 시 숨김]   depth 무관 · 숨김 (새 상시 UI의 기본 자리)
 │   └ InventoryShortcuts                                (위치 유지)
 ├ PopupLayer                                            ← 신규
 │   ├ ModalPopups       모달 팝업: FormationPanel / TripPanel / TacticsPanel (DepthLayer에서 이동)
 │   └ ModelessPopups    비모달 팝업: (후속) 인벤토리 팝업 4종 - 모달 팝업 위에 그려짐
 └ PopupExemptLayer                                      ← 신규: depth 무관 · 모달 팝업 시 유지
     └ PlayerCurrencyHud                                 (PersistentLayer에서 이동)
```

- **레이어 순서 = 렌더 순서**(37번 원칙 유지): 모달 팝업은 depth/상시 UI 위에, 인벤토리 팝업은 모달 팝업 위에, 재화 HUD는 가장 위에 그려진다. 재화 HUD가 팝업에 가려지지 않는다는 기존 요구(기획 27번 §3.5)가 구조적으로 유지된다.
- **새 UI의 기본값이 "모달 팝업 시 숨김"이 되도록**: 숨김은 요소별 표시가 아니라 레이어 단위(`DepthLayer`/`PersistentLayer`의 `CanvasGroup`)라서, 이 두 레이어 아래에 만든 새 UI는 자동으로 숨는다. 유지가 필요한 UI만 `PopupExemptLayer`에 의도적으로 둔다. 
- `RootDepth`의 기존 `CanvasGroup`(씬 전환 커튼 중 상호작용 차단)은 그대로 둔다. Unity의 중첩 `CanvasGroup`은 상호작용/클릭 차단이 AND로 합쳐지므로 두 용도가 서로 간섭하지 않는다.
- 인스톨러(`HubSceneInstaller`): `PopupLayer`(+`ModalPopups`/`ModelessPopups`)/`PopupExemptLayer` get-or-create, 레이어 순서 고정, 기존 요소를 마커로 찾아 이동(패널 3종 → `ModalPopups`, 재화 HUD → `PopupExemptLayer`, 인벤토리 버튼 → `PersistentLayer`), `DepthLayer`/`PersistentLayer`에 `CanvasGroup` 부착. 재실행 안전성은 37번 §3.4와 같은 방식이다.

## 6. 런타임 관리

| 대상 | 관리 주체 | 신호 | 처리 |
|---|---|---|---|
| `RootDepth` | `HubUIController`(기존) | `RootDepthChanged` | `SetActive(isAtRoot)` — 기존 `OnAnyPanelOpenChanged` 구독을 교체 |
| 카테고리 depth | `TownCategoryPanel`(기존) | depth 스택 Open/Close | 변경 없음 |
| `DepthLayer`/`PersistentLayer` | **신규 `HubPopupLayerGate`** | `ModalPopupOpenChanged` | `CanvasGroup` 숨김/표시 |
| 모달/비모달 팝업 | 각 패널 | 모달 스택/인벤토리 코디네이터 | 변경 없음 |
| `PopupExemptLayer` | 각 요소 컨트롤러 | — | 어떤 축의 로직도 참조하지 않는다 |

- `HubPopupLayerGate`는 `UIManager`와 같은 GameObject의 하위 컴포넌트다(전역 DI 대상 아님, `HubUIWiring`이 `GetComponent`로 조회 — 없으면 `InvalidOperationException`). 순수 C# 객체가 아니라 컴포넌트로 두는 이유: Hub 씬이 다시 로드될 때마다 같은 인스턴스가 이전 구독을 해제하고 새로 구독해야 영속 객체인 `UIManager`의 이벤트에 구독이 쌓이지 않는다(`HubUIController`의 `-=`/`+=` 패턴과 같음).
- 게이트는 숨길 `CanvasGroup` 목록만 받아 처리한다 — 어떤 레이어를 숨길지는 `HubUIWiring`이 요소 Id(`HubUIElementIds.DepthLayer`/`PersistentLayer`)로 조회해 넘긴다. Field에 재사용할 수 있게 Hub 요소 Id를 게이트 안에 넣지 않는다.

## 7. 지원하지 않는 조합

"depth 의존 + 모달 팝업 시 유지"(§3 표의 빈칸)는 현재 해당 UI가 없어 레이어를 만들지 않는다. 필요해지면 `PopupExemptLayer` 아래에 depth별 그룹을 두고 depth 신호(`RootDepthChanged`)로 켜고 끄는 방식으로 확장한다.

## 10. 씬 전환 이동 규칙 (두 관리 축과 독립)

### 10.1 현재 동작

Hub↔Field 전환 시 `SceneTransitionEffectController`는 **떠나는 씬이 등록한 콘텐츠 루트 1개**만 화면 밖으로 밀어내고(반대편에서 커튼이 함께 들어옴), 새 씬은 커튼이 걷히며 드러난다(설계 10번). 즉 "화면과 함께 이동하는 UI" = 그 콘텐츠 루트 하위의 UI뿐이다.

| 씬 | 등록된 콘텐츠 루트 | 루트 밖에 있는 UI | 판정 |
|---|---|---|---|
| Hub | `ContentRoot` | 없음(Canvas 직계 자식은 `ContentRoot` 하나 — 씬 파일 확인) | 충족. 전환 시점에 열려 있는 상행 준비 UI("상행 시작")도 `ContentRoot` 안이라 함께 이동한다. §5 재구성 후에도 모든 레이어가 `ContentRoot` 안이므로 유지된다. |
| Field | `MovementView` | `BattleView`, `FormationPanel`, `TacticsPanel`, `ResultPopup`, `TransitionCurtain`(이동↔전투 전환용) — 전부 Canvas 직계 | **미충족.** 아래 경우에 화면 일부가 제자리에 남는다. |

Field에서 Hub로 가는 전환 경로는 두 가지다(코드 확인).
1. 도착: 이동 뷰에서 결과 팝업("도착 성공") 확인 → 전환. 이동 뷰는 이동하지만 **결과 팝업은 루트 밖**이다(확인 버튼 후 팝업이 먼저 닫히는지는 미확인).
2. 패배-궤주: **전투 뷰**에서 결과 팝업("패배 - 궤주") 확인 → 전환. 화면에 보이는 것은 전투 뷰인데 **밀려나는 것은 화면 밖에 있는 이동 뷰**다 — 전투 뷰와 결과 팝업은 제자리에 남는다(실제 화면 동작은 미확인, 코드상 그렇게 된다).

### 10.2 규칙

**콘텐츠 씬의 모든 UI는 그 씬의 전환 루트 1개 아래에 둔다.** 전환 루트는 Canvas의 유일한 직계 자식이고, 이 씬이 `ISceneTransitionContentRootRegistry`에 등록하는 대상이다. depth 축·팝업 축의 레이어는 모두 전환 루트 **안에서** 나뉜다 — 세 번째 관심사(전환 이동)는 레이어 구조와 겹치지 않고 최상위 한 단계에서만 결정된다.

- 씬 전환 커튼 자체(Bootstrap 영속 스코프)는 규칙 대상이 아니다 — 콘텐츠와 반대편에서 동행하는 연출 요소다.
- BattleTest 씬은 씬 전환이 없어 대상이 아니다.

### 10.3 Field 정리

```
Canvas
 └ ContentRoot (신규, 전환 루트 — 전체 스트레치)
     ├ MovementView       (기존)
     ├ BattleView         (기존)
     ├ FormationPanel     (기존)
     ├ TacticsPanel       (기존)
     ├ ResultPopup        (기존)
     └ TransitionCurtain  (기존, 이동↔전투 전환용)
```

- 기존 요소의 형제 순서(렌더 순서)는 그대로 유지한 채 부모만 바꾼다. 이동↔전투 슬라이드(`FieldCameraController`)는 각 뷰의 부모 기준 `anchoredPosition`을 움직이므로 부모가 전체 스트레치인 `ContentRoot`로 바뀌어도 그대로 동작한다.
- `FieldUIWiring`은 등록 대상을 `MovementView` → `ContentRoot`로 바꾼다. 어느 뷰에 있든(이동/전투) 화면에 보이는 UI 전체가 함께 밀려난다.
- `FieldUIInstaller`는 Hub와 같은 방식으로 `ContentRoot`를 get-or-create한 뒤 기존 요소를 마커로 찾아 이동하고, 그 안에서 빌드한다(재실행 안전성). `FieldUIElementIds.ContentRoot` 추가.

### 10.4 남는 문제 — 전투 월드 오브젝트

전투 유닛은 UI가 아니라 Canvas 밖의 월드 오브젝트(`BattleWorldRoot`, 전투 카메라로 렌더링 — 설계 13번)다. 패배-궤주 경로에서 UI를 전부 밀어내도 **전투 유닛 스프라이트는 제자리에 남는다.** 선택지(§11-3에서 확인):
- A(추천): 궤주 확인 시 먼저 전투 뷰 → 이동 뷰 슬라이드(기존 승리 경로와 같은 연출)를 끝낸 뒤 씬 전환한다. 씬 전환은 항상 이동 뷰에서 시작한다는 기존 전제(설계 10번 §8)가 다시 성립하고, 전환 연출 코드는 바꾸지 않는다.
- B: 씬 전환 슬라이드 동안 전투 카메라도 같은 비율로 이동시킨다. 전환 연출이 Field 전투 카메라를 알아야 해서 결합이 생긴다.

### 10.5 인스톨러 검증

Hub/Field 인스톨러는 빌드 끝에 Canvas 직계 자식이 전환 루트 하나뿐인지 검사하고, 아니면 `Debug.LogWarning`으로 이름을 알린다 — 새 UI를 루트 밖에 만드는 실수를 조기에 드러낸다.
