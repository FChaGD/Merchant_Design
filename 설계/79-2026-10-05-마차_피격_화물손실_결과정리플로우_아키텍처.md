## 2. 전체 구조

```
[전투 중]                       [전투 종료 시점]                    [결과 정리 플로우]
BattleCargoLedger ──기록──▶ BattleAftermathReport ──▶ BattleAftermathApplier ──▶ BattleAftermathFlow
 (피격·파괴·잔해·도난)        (BattleResult에 실림)        (화물·마차·대열·시간 반영)    ① 결과 팝업
 BattleWagonWreck(표적)                                     → BattleAftermathSummary     ② 회수 적재
                                                                                         ③ 대열 정리
                                                                                         ④ 마무리
```

- **전투 중에는 저장소를 건드리지 않는다.** 화물 변화는 `BattleCargoLedger`(순수 C#)에 기록만 하고, 전투가 끝나 패배 결과(도주/궤주…)까지 정해진 뒤 `BattleAftermathApplier`가 한 번에 반영한다(§15-2).
- 반영은 ① 결과 팝업 **전에** 끝낸다(기획 78 §4-5) — 팝업이 반영 결과(재배치 수 등)를 보여 준다.
- 포로·사망(플레이 종료)은 반영하지 않는다(기획 77 §4-24).

## 3. 전투 중: 화물 기록

### 3.1 보호 대상에 로스터 Id·공격자 전달

- `BattleProtectedUnit`에 `string UnitId`(생성자 인자, 로스터 Id = 화물 섹션 Id) 추가. `LiveBattleSimulationRule.BuildProtectedPlacements`가 넘긴다.
- `event Action<BattleProtectedUnit, IBattleCombatant> OnHitBy` 추가. `TakeDamage`가 체력을 깎은 **직후, 파괴 판정 전**에 발생시킨다 — 파괴하는 마지막 일격도 피격 판정 1회를 먼저 받고(기획 77 §4-1), 그 뒤 파괴 판정(§4-6)이 남은 물품에 적용된다.
- 요약 주석의 "attacker는 쓰지 않는다"를 고친다.

### 3.2 `BattleCargoLedger` (순수 C#, 신규)

전투마다 새로 만든다. `LiveBattleSimulationRule.BuildSimulation`이 상단 물류품 조회 계약으로 마차별 적재 물품 스냅샷을 넘겨 생성한다.

| 상태(물품별) | 의미 | 생기는 경로 |
|---|---|---|
| 적재 | 그대로 마차에 있음 | 시작 상태 |
| 파손 | 사라짐 | 피격 10% / 파괴 30% |
| 도난(적 Id) | 그 적이 소유 | 피격 5% / 잔해 공격 25% |
| 무방비(마차 Id) | 잔해에 놓임 | 파괴 70% |
| 회수 대상 | 승리 시 회수 | 소유 적 사망 시 도난 → 회수 대상 |
| 도난 손실 | 사라짐 | 소유 적 도주 시 |

- 피격(`OnHitBy`): 그 마차의 적재 물품이 있으면 1회 굴림 — 파손/도난/없음, 대상은 무작위 1개(기획 77 §4.1).
- 파괴(`OnDied`): 남은 적재 물품마다 독립 굴림 — 파손 30% / 무방비 70%. 무방비 물품이 1개 이상이면 잔해 표적(§3.3)을 활성화.
- 도난 시 그 적의 `OnDied`/`OnFled`를 처음 한 번만 구독 — 사망 → 그 적의 도난품 전부 회수 대상, 도주 → 도난 손실.
- 난수는 `Func<float>`(0~1) 주입 — 테스트에서 고정값으로 결과를 검증한다. 실제는 `UnityEngine.Random.value`.
- 확률 값은 `CargoLossTuning`(정적, §12)에서 읽는다.
- 전투 종료 시 `BuildReport()` → `BattleCargoReport`(물품별 최종 상태 목록 + 파괴 마차 Id 목록).
- 배틀 테스트 씬·마차 0대 전투: 원장은 비어 있어 아무 일도 하지 않는다(기획 77 §4-23).

### 3.3 잔해 `BattleWagonWreck` (신규, `IDamageable`)

- 파괴된 마차 자리에 놓이는 **별도 표적 객체**다. 원래 마차 객체는 지금처럼 `IsAlive` false(파괴)로 남아 패배 판정·방진 보호 후보 계산이 그대로 동작한다(§15-1).
- `IsAlive` = "무방비 물품이 남아 있음"(기획 77 §4-10) → 기존 표적 선택 규칙(가장 가까운 것·각종 선택자)이 손대지 않고 잔해를 후보로 보거나 빼낸다(§4-12).
- `TakeDamage(amount, attacker)`: 체력 없음. 25%로 무방비 물품 1개를 공격자 소유로(원장에 위임). 마지막 물품이 빠지면 `OnDied`(표적 해제 신호).
- 잔해 목록은 원장이 들고, `BattleSimulationLoop`가 생성자 인자 `IReadOnlyList<IDamageable> extraEnemyTargets`(살아 있는 목록 참조)로 받아 매 틱 적 표적 후보에 더한다. 배틀 테스트는 빈 목록.
- 아군은 잔해를 표적으로 삼지 않는다(아군 표적은 적 목록뿐 — 변경 없음, §4-13).

### 3.4 장애물·뷰

- **장애물**: `BattleProtectedUnit.BlocksMovement` = `Kind == Wagon || IsAlive` 추가. `BattleObstacleField`의 생존 확인 4곳(설계 74 §2.6)을 이 값으로 바꾼다 — 마차는 파괴돼도 장애물로 남고(기획 77 §4-9), 시설은 지금처럼 빠진다. 통로도 양 끝이 모두 막는 동안만 감속.
- **뷰**: `BattleProtectedUnitView`의 파괴 처리 — 마차면 페이드아웃·제거 대신 **연두색으로 바꾸고 체력 게이지를 숨긴다**(기획 77 §4-8). 시설은 지금 그대로. 잔해 피격 플래시는 하지 않는다(체력이 없으므로).

## 4. 전투 종료: 결과 데이터

### 4.1 패배 원인

- `BattleDefeatCause { None, AllWagonsDestroyed, NoCombatants }` 신규.
- `BattleDefeatRule.ResolveCause(...)` 추가 — 조건 1이 성립하면 `AllWagonsDestroyed`(둘 다 성립해도 조건 1, 기획 78 §4-27), 아니면 조건 2면 `NoCombatants`. 기존 `IsDefeated`는 `ResolveCause != None`으로 위임.

### 4.2 `BattleResult` 확장

```csharp
public readonly struct BattleResult
{
    public BattleOutcome Outcome { get; }
    public BattleDefeatCause DefeatCause { get; }      // 승리면 None
    public BattleCargoReport CargoReport { get; }      // 화물·파괴 마차. 없으면 BattleCargoReport.Empty
}
```

- 기존 생성자 `BattleResult(outcome)`은 유지(배틀 테스트·Placeholder 규칙 무변경) — 원인 None, 보고서 Empty.
- `BattleManager`는 결과를 그대로 전달하므로 무변경.

## 5. 결과 반영 `BattleAftermathApplier`

Bootstrap 상주 `IManagedComponent`(신규). `FieldEncounterFlowCoordinator`가 패배 결과 판정 직후 호출한다.

```csharp
BattleAftermathSummary Apply(BattleResult result, DefeatConsequence? consequence); // 승리면 consequence = null
```

포로·사망이면 아무것도 하지 않고 빈 요약을 돌려준다. 그 외 순서:

| 순서 | 처리 | 근거 |
|---|---|---|
| 1 | **화물 제거** — 적재 외 상태(파손·도난·무방비·회수 대상·도난 손실)인 물품을 저장소에서 **환급 없이** 제거 | 기획 77 §4-19 |
| 2 | **유닛 전멸 패배 손실** — 원인이 `NoCombatants`이고 도주·궤주면, 파괴되지 않은 마차의 남은 물품마다 30%로 환급 없이 제거 | 기획 78 §4.7 |
| 3 | **파괴 마차 제거** — 보유 목록에서 제거 → 상단 물류품 섹션 제거(§5.2) | 기획 77 §3-8 |
| 4 | **대열 정리** — 파괴 마차 칸 비우기 + 영역 밖 유닛 재배치(§5.3) | 기획 77 §4-26·§4-28, 78 §4.6 |
| 5 | **회수 물품 임시보관** — 승리일 때만 회수 대상(무방비 + 죽은 적의 도난품)을 새 인스턴스로 임시보관에 넣음(차감 없음) | 기획 77 §4-16, 78 §4-15 |
| 6 | **상행 시간** — 승리·도주이고 파괴 마차가 있으면 현재 구간에 대당 20초 추가(§5.4) | 기획 77 §4-20 |

반환 `BattleAftermathSummary`: 파손 수·도난 손실 수·회수 대상 수·패배 손실 수·파괴 마차 수·재배치 수·팔레트 복귀 수·추가 초·대열 끊어짐 여부. 결과 팝업 요약 줄(기획 78 §4-7)과 단계 건너뜀 판정이 이 값만 읽는다.

### 5.1 상단 물류품 저장소 — 정산 전용 계약 `ITradeGoodsCargoSettlement` (신규, ISP)

정산만 쓰는 조작을 기존 `ITradeGoodsInventoryRepository`(구매·매각·정리 소비자)와 분리한다. `PlaceholderTradeGoodsInventoryRepository`가 구현하고 **이 타입으로 따로 등록**한다(읽기·보조 타입 미등록 함정 — 메모리 기록 사례).

| 조작 | 동작 |
|---|---|
| `RemoveWithoutRefund(instanceId)` | 골드 상자여도 지갑 환급 없음 |
| `StageWithoutCharge(definition)` | 새 인스턴스를 임시보관에 추가. 골드 상자여도 지갑 차감 없음 |
| `DiscardStaged()` | 임시보관 전부 버림(환급 없음) — 적재 단계 [넘어가기](§7) |

- 전투 시작 스냅샷은 기존 읽기 계약(`IInventoryReader.Items`, 섹션 Id = 마차 Id)으로 충분하다.
- `InventoryGrid`에 `StageNew(definition)`·`RemoveSection(sectionId)` 추가.

### 5.2 마차 제거

- 보유 목록: 제거 전용 계약 `IOwnedCaravanAssetRemover { bool TryRemoveOwned(string id); }` 신규 — 마구간 구매 소비자(`IOwnedCaravanAssetRoster`)에 제거 권한을 넓히지 않는다. `PlaceholderCaravanRosterProvider`가 구현·등록, 제거 후 `RebuildRoster` + `OnOwnedChanged`.
- 물류품 섹션: 저장소의 보유 동기화(`SyncSections`)가 "보유 목록에 없는 섹션 제거"도 하도록 확장. 제거 시점에 섹션은 이미 비어 있다(§5 순서 1 — 파괴 마차의 물품은 모두 적재 외 상태). 방어적으로 남은 물품이 있으면 임시보관으로 옮기고 경고 로그.

### 5.3 대열 정리 `FormationWreckRelocator` (순수 static, 신규)

입력: 현재 배치, 제거할 마차 Id 목록, 로스터 조회, 진행 중 활동 목록. 출력: 새 배치, 재배치 목록, 팔레트 복귀 목록, 취소할 활동 목록, 덩어리 수.

1. 파괴 마차 칸을 비운다.
2. 영역을 다시 계산하고, 있을 수 없는 칸의 유닛(시설은 자리 칸 밖, 캐릭터는 대열 밖)을 모은다.
3. **시설 먼저, 다음 캐릭터** 순으로(시설이 대열을 넓혀 캐릭터가 들어갈 칸이 생길 수 있음) 원래 칸에서 가장 가까운, 배치 가능하고 비어 있으며 다른 활동의 목표가 아닌 칸으로 옮긴다. 거리 = 칸 중심 직선거리, 동률이면 칸 번호가 작은 쪽. 한 유닛을 옮길 때마다 영역을 다시 계산한다. 마차가 0대면 기준 칸에 마차 외 유닛을 놓을 수 없어(기존 규칙) 전부 팔레트 복귀(기획 77 §4-29).
4. 진행 중 활동 처리(기획 78 §4.6, §15-5):

| 활동 | 처리 |
|---|---|
| 재배치·팔레트 복귀된 유닛의 활동 | 취소. 재배치 유닛은 새 칸에 배치 완료 상태 |
| 배치(Adding) 중, 목표 칸이 영역 밖 | 취소하고 목표 칸 기준으로 3과 같은 재배치(배치 완료 상태), 없으면 팔레트 |
| 이동(Moving) 중, 목표 칸이 영역 밖 | 취소. 출발 칸(배치상 위치)이 영역 안이면 거기 남고, 밖이면 3에서 이미 재배치됨 |
| 그 밖 | 그대로(④에서 재개 또는 궤주 시 강제 완료) |

5. 마차 연결은 검사하지 않는다(강제 경로) — 끊어짐은 ③ 대열 정리 단계(또는 궤주 시 마을 출발 조건)가 처리한다. 덩어리 수만 계산해 돌려준다.

`BattleAftermathApplier`가 결과를 `IFormationRepository.Apply` + 활동 저장소 `Cancel`로 반영한다. 활동 취소 이벤트가 정비창 화면 갱신을 이미 일으키므로 추가 통지는 없다.

### 5.4 상행 시간 추가

- `ISessionState`에 `void ExtendDuration(float seconds)` 추가. `SessionStateTracker`는 현재 구간 소요시간을 늘린다(경과는 유지 → 진행도 게이지가 그만큼 뒤로 물러남, §15-11).
- 이미 도착 처리된 구간이면 무시(전투 중 도착 불가라 실제로 발생하지 않음).

### 5.5 덩어리 계산 — `FormationArea` 확장

- 기존 연결 판정(4방향, 연결 칸)을 덩어리 라벨링으로 바꿔 `ComponentCount`(마차가 속한 덩어리 수, 마차 0~1대면 1)와 `GetComponentOf(slotIndex)`(-1 = 연결 칸 아님), `LargestComponentId`(마차 수 → 칸 수 → 덩어리 번호 순으로 큰 것)를 노출. `WagonsConnected` = `ComponentCount <= 1`.
- `FormationAreaRules`에 연결 기준 인자 `ConnectivityRule`(신규 enum) 추가:

| 값 | 허용 조건 | 사용처 |
|---|---|---|
| `RequireConnected`(기본) | 최종 상태에서 모두 연결 | 지금 그대로 |
| `NoNewSplit` | 최종 덩어리 수 ≤ 편집 전 덩어리 수 | 정리 모드(§8), 마을 정비창이 끊어져 있을 때(§9.3) |

편집 전이 이미 연결된 상태면 `NoNewSplit`도 "모두 연결"과 같아져, 마을 정비창은 상태와 관계없이 `NoNewSplit`을 넘겨도 된다(§9.3).

## 6. 결과 정리 플로우 `BattleAftermathFlow`

`FieldEncounterFlowCoordinator`의 결과 처리(`ShowResult`/`ShowDefeatConsequence`)를 단계 목록으로 바꾼다. 조율자는 "패배 결과 판정 → 반영(§5) → 플로우 시작"만 하고, 단계 진행은 `BattleAftermathFlow`(순수 C#, 신규)가 맡는다(SRP).

```csharp
internal interface IBattleAftermathStep
{
    bool AppliesTo(BattleAftermathContext context);   // 해당 없으면 건너뜀(기획 78 §4-2)
    void Run(BattleAftermathContext context, Action onDone);
}
```

| 단계 | 적용 | 화면 | 완료 |
|---|---|---|---|
| ① `ResultPopupStep` | 항상 | 전투 뷰 위 결과 팝업(§6.1) | 버튼 |
| ② `CargoRecoveryStep` | 승리 + 임시보관에 회수 물품 있음 | 전투 뷰 위 회수 적재 패널(§7) | [완료] (+ 경고) |
| ③ `FormationRepairStep` | 승리·도주 + 대열 끊어짐 | 전투 뷰 위 정비창 정리 모드(§8) | [완료] |
| ④ `FinishStep` | 항상 | 전투 뷰 → 이동 뷰 슬라이드(승리·도주·궤주) | 결과별 마무리 |

- ①~③은 모두 **전투 뷰 위**에서 진행하고, 이동 뷰 슬라이드는 ④에서 한다(§15-7 사용자 결정). 정비창 UI는 Field `ContentRoot` 하위(이동 뷰 하위 아님, `FieldUIInstaller`)라 전투 뷰 위에도 표시된다 — 다만 전투 월드 오브젝트(카메라 렌더링) 위에 정비창이 정상적으로 덮이는지는 미확인, 제작 시 확인.
- ③ 동안 정비창이 전투 화면을 가리므로, 정비창이 닫힌 뒤 ④ 슬라이드가 시작된다.
- ④ 마무리(기존 동작 이관): 승리·도주 → 상단 버튼 활성 + 활동 전부 재개 + 상행 재개 / 궤주 → 활동 강제 완료 + Hub 전환 / 포로·사망 → 활동 강제 완료 + 종료.
- 상단 버튼 활성은 지금처럼 ④의 슬라이드 시작 직전 — ①~③ 동안은 비활성이라 정리 중에 다른 화면(방향성 지시 등)을 열 수 없다.
- 시간: ①~③ 동안 상행·활동 모두 정지 상태 유지(이미 전투 시작 때 정지됨 — 추가 처리 없음, 기획 78 §4-4).

### 6.1 결과 팝업

- `FieldResultPopupView`에 상세 문구 라벨(`detailLabel`) 추가, `Show(message, detail, buttonText, onConfirm)`. 상세가 비면 숨김.
- 요약 줄 생성은 `BattleAftermathSummaryFormatter`(static, 신규)가 요약 값 → 문구(0인 줄 생략, 기획 78 §4-7).
- 버튼 문구: 다음 단계가 있으면 "다음", 없으면 지금 문구(기획 78 §4-8). 플로우가 ①을 실행할 때 뒤 단계의 `AppliesTo`로 판단한다.
- 인스톨러: `FieldUIInstaller.BuildResultPopup`에 상세 라벨 get-or-create 추가.

## 7. ② 회수 적재 패널 `FieldCargoRecoveryPanel`

- 무역품 구매 화면이 쓰는 방식 그대로 — 편집 본문을 `InventoryPopupUIBuilder.BuildArrangementBody`로 만들고 `InventoryArrangementController`로 편집한다(상단 물류품 사양: 회전·임시보관·마차 스테퍼). 기존 조작(끌어 놓기·회전·마차 간 이동·자동 정렬, 기존 적재물 이동 포함) 전부 그대로(기획 78 §4-10).
- 창 닫기 버튼·창 드래그 없음. **[완료]** 버튼만(§4-11). 파괴된 마차는 §5 순서 3에서 섹션이 이미 사라져 스테퍼에 나오지 않는다(기획 77 §4-17a).
- [완료]: 임시보관이 비었으면 바로 완료. 남았으면 확인 대화상자 "임시보관에 남은 물품 N개는 버려집니다. 그래도 넘어가시겠습니까?" [넘어가기]/[돌아가기] — 넘어가기 → `DiscardStaged()` 후 완료(§4-13). 자동 배치 없음(§4-14).
- 확인 대화상자는 공용 `ConfirmDialogView`(신규, 메시지 + 확인/취소 버튼 문구·콜백)를 쓴다 — 마을 출발 경고(§9.2)와 같은 뷰 클래스, 씬마다 인스턴스.
- 배치: 패널 로직은 Bootstrap의 Field UI 조율 쪽, 화면 요소는 Field 씬 `SceneUIRoot` 하위(`FieldUIInstaller`가 get-or-create). ID는 `FieldCargoRecoveryUIElementIds`.
- `IUIPanel` 구현(`PanelId` = `UIPanelIds.CargoRecovery`). 열기·닫기는 `UIManager`로만 한다. 패널은 완료 콜백만 받고, 닫기는 단계가 `UIManager.Close`로 위임한다.

## 9. 마을(Hub)

### 9.1 출발 조건 — 대열 연결 (기획 78 §4.8)

- `TripPanel` 출발 버튼 활성 = 기존 조건 + `FormationArea.WagonsConnected`(배치 없으면 충족).
- 끊어져 있으면 출발 버튼 비활성 + 상행 준비 UI 안내 문구 "대열이 끊어져 있습니다. 정비창에서 마차를 이어 붙이세요."(§4-33). 라벨은 Hub 인스톨러가 get-or-create, `TripUIElementIds`에 추가.
- 배치 변경 통지: `IFormationReader`에 `event Action Changed` 추가, `InMemoryFormationRepository.Apply`가 발생시킨다. `TripPanel`이 구독해 버튼·안내를 갱신(§15-13). `TripPanel`이 대열 영역을 계산하려면 로스터 조회가 필요 — `RegisterTripUI`에 `ICaravanRosterProvider` 인자 추가.

### 9.2 출발 경고 — 배치 유닛 0 (기획 77 §4-30)

- [상행 시작] 시 배치에 유닛(마차·시설·캐릭터)이 하나도 없으면 `ConfirmDialogView`로 "상단에 배치된 유닛이 없습니다. 이대로 습격받으면 위험합니다. 그래도 출발하시겠습니까?" [출발]/[취소]. 출발 → 기존 출발 처리.
- 연결 조건(비활성)과 별개(기획 78 §4-35).

### 9.3 마을 정비창 완화 (기획 78 §4-34)

- `HubFormationPanel`의 배치·이동·제거가 `ConnectivityRule.NoNewSplit`을 넘긴다. 연결된 상태에서는 지금과 결과가 같고(§5.5), 끊어진 상태에서만 완화된다. 마차 제거도 같은 기준.

## 10. 데이터 흐름 요약 (승리, 마차 1대 파괴)

1. 전투 중: 원장이 피격·파괴·잔해 도난을 기록. 파괴 마차는 연두색 잔해 + 장애물.
2. 적 전멸 → `LiveBattleSimulationRule.Report` → `BattleResult(Victory, None, 원장 보고서)`.
3. 조율자 → `BattleAftermathApplier.Apply` → 화물 제거, 마차 제거·섹션 제거, 대열 재배치, 회수 물품 임시보관, 구간 +20초 → 요약.
4. ① 팝업(요약, "다음") → ② 회수 적재 [완료] → ③(끊어졌으면) 정리 [완료] — 모두 전투 뷰 위 → ④ 상단 버튼 활성 → 이동 뷰 슬라이드 → 활동 재개·상행 재개.

## 14. 제작 순서

1. 전투 기록: 보호 대상 Id·피격 이벤트, 원장, 잔해, 장애물·뷰, 패배 원인, 결과 데이터 → 빌드·테스트.
2. 정산: 저장소 정산 계약·섹션 제거, 마차 제거 계약, 덩어리 계산·연결 기준, 재배치기, 시간 추가, 반영 컴포넌트 → 빌드·테스트.
3. 플로우: 단계 구조, 결과 팝업 상세, 회수 적재 패널, 확인 대화상자, 조율자 이관 → 빌드.
4. 정비창 정리 모드: 편집 정책 분리, 붉은 톤, 안내·완료 → 빌드.
5. 마을: 출발 조건·안내·경고, 마을 정비창 완화 → 빌드.
6. 인스톨러 → Unity 밖 테스트 실행 → 사용자 검증(§16).

## 16. 검증 (Field·Hub)

- 마차 피격 시 물류품이 줄어듦(전투 후 팝업 수치와 팝업 확인).
- 마차 파괴 → 연두색 잔해, 캐릭터가 계속 피함, 적이 잔해를 때리다 다 털리면 다른 표적으로 감.
- 승리: 결과 팝업 요약 → 회수 적재(파괴 마차 없음, 기존 적재물 이동 가능) → 남기고 [완료] 시 경고 → 버림.
- 파괴 마차가 대열을 끊으면 전투 뷰 위에서 정리 모드: 붉은 덩어리, 덩어리 증가 이동 거부, 이어지면 [완료] 활성, 즉시 반영.
- 구간 게이지가 파괴 마차당 20초만큼 늘어남.
- 패배-도주(유닛 전멸): 남은 마차 물품 일부 손실, 회수 없음. 마차 0대 도주 → 캐릭터·시설 전부 팔레트, 상행 속행.
- 패배-궤주 후 Hub: 대열이 끊겼으면 출발 버튼 비활성 + 안내, 마을 정비창에서 이으면 활성. 배치 유닛 0이면 출발 경고.
- 골드 상자: 파손돼도 재화 환급 없음, 회수해 실어도 재화 차감 없음.
