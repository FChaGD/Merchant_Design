## 1. 핵심 결정 — "현재 HP"를 별도 필드로 만들지 않는다

`BattleCharacterUnit`(`Core/Battle/Simulation/BattleCharacterUnit.cs:122`)은 생성 시 `currentHp = stats.MaxHp`로 시작한다. `BattleUnitStats.MaxHp`가 곧 "이번 전투 시작 시점 HP"다.

이번 기능 범위(기획 13번 §7-4)엔 전투 중 회복 수단이 없고, 상행 종료 전까지 상행 내 회복 수단도 없다(기획 13번 §4) — 즉 "진짜 최대 HP"와 "지금 시점에 낼 수 있는 HP"가 항상 같은 값이다. 그러므로 **저장된 HP를 그대로 이번 전투의 `BattleUnitStats.MaxHp`로 넣는다** — `BattleUnitStats`/`BattleCharacterUnit`(전투 핵심 런타임 타입)은 필드 하나도 건드리지 않는다.

> 후속에 전투 중 회복 수단이 생기면 이 단순화가 깨진다(회복이 "저장된 상한"까지만 가능해짐) — 그때는 `BattleUnitStats`에 별도 "진짜 MaxHp" 필드를 추가해야 한다. 기획 13번 §7-4가 이미 이 재검토 필요성을 남겨뒀다.

## 2. 새 인터페이스 — `IUnitConditionRepository`

위치: `Core/Battle/Condition/`(신규 폴더 — 전투 결과가 로스터 개체에 남기는 상태라는 의미로 Battle 도메인 소유. Formation 쪽은 참조만 한다).

```csharp
public interface IUnitConditionRepository
{
    // 저장된 값이 없으면(=아직 이 상행에서 초기화되지 않음) false.
    bool TryGetCurrentHp(string unitId, out float currentHp);
    bool IsDead(string unitId);

    // 전투 종료 시 LiveBattleSimulationRule이 호출한다. died=true면 currentHp는 무시하고 사망 처리한다.
    void ApplyBattleResult(string unitId, float currentHp, bool died);

    // 상행 시작/종료 시 FieldUIController가 호출한다 - 로스터 전원을 각자 직업 기준 만피로 리셋하고
    // 사망 상태도 전부 해제한다.
    void ResetAllToFull();
}
```

**`ICaravanRosterProvider`/`IFormationUnit`을 확장하지 않는 이유(ISP)**: `IFormationUnit`은 이미 "Formation UI는 MercenaryClass도 몰라도 된다"는 원칙으로 좁혀진 계약이다(`IMercenaryUnit`이 별도로 확장하는 이유와 동일, `IMercenaryUnit.cs` 요약 주석 참고). HP/사망이라는 전투 전용 가변 상태를 여기 얹으면 그 원칙이 깨진다. 대신 "unitId로 조회하는 별도 저장소"로 분리해, Formation 쪽은 필요할 때만(설계 16번, 팔레트 잔여수 계산) 이 인터페이스를 별도로 참조한다.

### 구현체 — `InMemoryUnitConditionRepository`

`InMemoryFormationRepository`와 같은 성격(MonoBehaviour, `IManagedComponent`, Bootstrap 상주, 앱 재시작 시 소멸 — 상행 스코프 데이터에 딱 맞는 생명주기).

```csharp
public class InMemoryUnitConditionRepository : MonoBehaviour, IUnitConditionRepository, IManagedComponent
{
    private readonly Dictionary<string, float> currentHpById = new();
    private readonly HashSet<string> deadUnitIds = new();
    private readonly IBattleUnitStatProvider statProvider = new PlaceholderBattleUnitStatProvider();
    private ICaravanRosterProvider rosterProvider;

    public void RegisterSelf(IDependencyRegistrar registrar) => registrar.Register<IUnitConditionRepository>(this);

    public void ResolveDependencies(IDependencyRegistrar registrar)
        => registrar.TryResolve(out rosterProvider); // 아직 등록 안 됐으면 ResetAllToFull이 조용히 아무 것도 안 함

    public bool TryGetCurrentHp(string unitId, out float currentHp) => currentHpById.TryGetValue(unitId, out currentHp);
    public bool IsDead(string unitId) => deadUnitIds.Contains(unitId);

    public void ApplyBattleResult(string unitId, float currentHp, bool died)
    {
        if (died) { deadUnitIds.Add(unitId); currentHpById.Remove(unitId); }
        else currentHpById[unitId] = currentHp;
    }

    public void ResetAllToFull()
    {
        currentHpById.Clear();
        deadUnitIds.Clear();
        if (rosterProvider == null) return;

        foreach (var unit in rosterProvider.GetRoster())
        {
            if (unit is IMercenaryUnit mercenary) // 캐릭터만 HP 추적 대상(기획 13번 §2) - 마차/시설 제외
            {
                currentHpById[unit.Id] = statProvider.GetStats(mercenary.Class).MaxHp;
            }
        }
    }
}
```

`PlaceholderBattleUnitStatProvider`를 필드에서 직접 `new`하는 방식은 `LiveBattleSimulationRule.cs:20`/`BattleTestSimulationRule.cs:39`와 동일한 기존 패턴 재사용(이 타입은 DI 등록 대상이 아니다).

## 3. `LiveBattleSimulationRule` 연동 — 순수 추가만

기존 `IRequiresFormationReader`/`IRequiresCaravanRoster`/`IRequiresTacticsReader`와 완전히 같은 패턴으로 새 마커 인터페이스를 추가한다.

```csharp
public interface IRequiresUnitConditionRepository
{
    void SetUnitConditionRepository(IUnitConditionRepository repository);
}
```

`BattleManager.ResolveDependencies`(현재 47-66줄)에 블록 하나 추가:

```csharp
if (resultRule is IRequiresUnitConditionRepository conditionConsumer
    && registrar.TryResolve<IUnitConditionRepository>(out var conditionRepository))
{
    conditionConsumer.SetUnitConditionRepository(conditionRepository);
}
```

`LiveBattleSimulationRule`은 이 인터페이스를 구현하고 필드로 보관한다. 두 지점에서 사용한다:

**(a) `BuildAllies()` — 배치 시점 동기화(현재 154줄 `var stats = statProvider.GetStats(mercenaryClass);` 직후)**

```csharp
var stats = statProvider.GetStats(mercenaryClass);
if (unitConditionRepository != null)
{
    if (unitConditionRepository.IsDead(unitId)) continue; // 방어적 - 정상 흐름이면 팔레트가 이미 배치를 막는다(설계 16번)
    if (unitConditionRepository.TryGetCurrentHp(unitId, out var currentHp))
    {
        stats = new BattleUnitStats(currentHp, stats.Attack, stats.Defense, stats.MoveSpeed, stats.AttackInterval, stats.Range, stats.MoraleSyncRate, stats.HpRegenPerSecond, stats.EnemyType);
    }
}
```

`unitId`는 이미 138-140줄에서 슬롯마다 확보돼 있는 값이라 새 조회가 필요 없다.

**(b) 전투 종료 시점 — 참여 아군의 최종 HP를 저장소에 되돌려 쓴다**

`BuildAllies()`가 유닛을 만들 때마다 `(unitId, unit)` 쌍을 필드(`private readonly List<(string, IBattleCombatant)> allyUnitIds = new();`, `BuildSimulation()` 시작 시 Clear)에 함께 적립해둔다. `IBattleCombatant`는 이미 `IDamageable.CurrentHp`를 노출하므로(`IDamageable.cs:19`) `BattleCharacterUnit`으로 캐스팅할 필요가 없다.

`Report(BattleOutcome outcome)`(현재 74-78줄) 안에서, `onResult` 호출과 함께 순회:

```csharp
if (unitConditionRepository != null)
{
    foreach (var (unitId, unit) in allyUnitIds)
    {
        unitConditionRepository.ApplyBattleResult(unitId, unit.CurrentHp, died: unit.CurrentHp <= 0f);
    }
}
```

`died` 판정에 `IsAlive`(도주/이탈 포함)가 아니라 `CurrentHp <= 0f`를 직접 쓰는 이유 — 기획 13번 §5/§6이 "사망만 배치 불가, 도주 등은 HP만 유지"로 구분했는데 `IsAlive`는 도주도 false로 만들어(§`hasLeftBattle`) 구분이 안 된다. `CurrentHp`는 오직 실제 사망(0 이하)일 때만 0이 된다.

## 4. 상행 생명주기 연결 — 새 이벤트 없이 기존 훅 재사용

`ISessionState`에 `OnBegin` 같은 새 이벤트를 추가하지 않는다. `Begin()`은 `FieldUIController.HandleSceneRevealed`(130줄)가 직접 호출하는 평범한 메서드 호출이라, **그 호출부에 나란히 리셋을 끼워 넣는 것으로 충분하다.**

`FieldUIController`가 `IUnitConditionRepository` 참조를 새로 받는다(`RegisterFieldUI(...)` 파라미터 추가, `FieldUIWiring.Wire`가 `registrar.TryResolve<IUnitConditionRepository>(...)`로 조회해 넘김 — `ICaravanRosterProvider`와 동일한 TryResolve 패턴).

```csharp
private void HandleSceneRevealed(ContentSceneId sceneId)
{
    if (sceneId != ContentSceneId.Field) return;
    formationButton.interactable = true;
    tacticsButton.interactable = true;
    unitConditionRepository?.ResetAllToFull(); // 상행 시작 = 전원 만피로 출발(기획 13번 §4-1)
    sessionState.Begin();
}

private void HandleArrived()
{
    unitConditionRepository?.ResetAllToFull(); // 상행 종료(허브 복귀) = 전원 회복(기획 13번 §4-3, 사용자 확정)
    uiManager.Close(UIPanelIds.Formation);
    uiManager.Close(UIPanelIds.Tactics);
    resultPopupView.Show("도착 성공", "도시 입장", onConfirm: () => gameManager.RequestSceneTransition(ContentSceneId.Hub));
}
```

## 5. DI 등록 순서에 대한 주의

`InMemoryUnitConditionRepository.ResolveDependencies`가 `ICaravanRosterProvider`를 TryResolve하므로, `DependencyManager`가 **모든 `RegisterSelf()`를 먼저 끝낸 뒤 모든 `ResolveDependencies()`를 호출하는 2단계 구조**라면 `managedComponents` 배열 순서와 무관하게 안전하다. 이미 프로젝트 전반에서 매니저들이 서로를 참조하는 패턴이 성립하고 있어(예: `BattleManager`가 `PlaceholderCaravanRosterProvider`를 참조) 이 가정이 맞을 가능성이 높지만, **제작 착수 시 `DependencyManager` 실제 구현을 먼저 확인**해 순서 의존성이 없는지 확정할 것.

## 6. 이 설계가 건드리지 않는 것

- `BattleCharacterUnit`, `BattleUnitStats`, `IDamageable`, `IBattleCombatant` — 필드/시그니처 무변경(§1 참고).
- `BattleTestSimulationRule`(배틀 테스트 씬) — 이 저장소를 전혀 참조하지 않는다. 그 씬은 독립 임시 로스터를 쓰는 별개 도구다(기획 13번 §2).
- `FormationLayout`/`FormationDragCoordinator`/`FormationGridView` — 배치 슬롯-Id 매핑 로직은 무변경. 이 설계는 "Id로 HP를 조회/기록"만 추가한다.
