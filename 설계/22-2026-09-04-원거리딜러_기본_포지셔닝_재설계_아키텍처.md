## 1. 개요

기획 17번의 결정을 코드/데이터에 반영한다 — 원거리딜러 국소적 포지셔닝 기본값을 자리 사수(Stationary)에서 **접근 공격**(ApproachAttack, 신규)으로 교체. 접근 공격의 이동 로직은 기존 전열 돌격형(`ChargePositioningStrategy`)과 완전히 동일하므로 새 전략 클래스를 만들지 않고 **인스턴스를 그대로 공유**한다(사용자 확정, 2026-09-04) — `PositioningStrategyFactory`의 기존 1:1 switch 구조에 새 `case`만 추가하면 된다.

## 2. `LocalPositioning` enum 변경

접근 공격이 정수값 1을 갖도록 기존 값을 전부 한 칸씩 민다(기획 17번 §3 확정).

```csharp
namespace Game.Core
{
    /// <summary>
    /// 역할군 축 - 활동 반경 안에서 전투 중 실제로 이동하는 세부 로직(Docs/기획/12번 §3.2).
    /// 명시적 정수값 = 데이터 테이블 Id(Docs/설계/18번 §3), 0은 비워둔다.
    /// </summary>
    public enum LocalPositioning
    {
        // 원거리딜러 - 사거리 밖이면 접근, 안이면 정지(Docs/기획/17번). 전열 Charge와 로직이
        // 완전히 같아 PositioningStrategyFactory가 같은 ChargePositioningStrategy 인스턴스를
        // 반환한다(클래스를 새로 만들지 않음, §3 참고).
        ApproachAttack = 1,
        // 전열 - 적에게 직진 접근(기존 기본 동작).
        Charge = 2,
        // 전열 - 아군과 적 사이에 위치해 전열 형성.
        Blocking = 3,
        // 원거리딜러 - 제자리에서 사격.
        Stationary = 4,
        // 원거리딜러 - 같은 타겟을 노리는 동료와 각도를 나눠 타겟을 감싸듯 자리잡음(Docs/설계/12번 §13.3).
        Surround = 5,
        // 원거리딜러 - 동료 원거리딜러와 일정 거리 이상 벌어져 사격(Docs/설계/12번 §13.2).
        Disperse = 6,
    }
}
```

기존 값을 참조하는 곳은 §6(제작 체크리스트)의 워크북 데이터뿐이다 — 코드 안에서 `(int)LocalPositioning.Xxx`를 하드코딩해 저장/비교하는 곳은 없음을 확인함(grep 결과, `LocalPositioning.Xxx` 리터럴 참조는 `PositioningStrategyFactory`/각 전략 클래스 자기 주석/`UnitTacticsBehaviors`/`FrontlineFormationCoordinator`/`RangedSurroundCoordinator`뿐이며 전부 enum 멤버 이름으로 비교하지 정수 리터럴로 비교하지 않는다) — enum 멤버 이름 기반 코드는 재배정의 영향을 받지 않는다.

## 3. `PositioningStrategyFactory` 변경

```csharp
public static IPositioningStrategy Create(
    LocalPositioning positioning, FrontlineFormationCoordinator frontlineCoordinator,
    RangedSurroundCoordinator rangedSurroundCoordinator, IUnitSpatialQuery spatialQuery)
{
    return positioning switch
    {
        LocalPositioning.ApproachAttack => new ChargePositioningStrategy(), // 신규 - 전열 Charge와 로직 공유
        LocalPositioning.Charge => new ChargePositioningStrategy(),
        LocalPositioning.Blocking => new BlockingPositioningStrategy(frontlineCoordinator),
        LocalPositioning.Stationary => new StationaryPositioningStrategy(),
        LocalPositioning.Surround => new SurroundPositioningStrategy(rangedSurroundCoordinator, spatialQuery),
        LocalPositioning.Disperse => new DispersePositioningStrategy(spatialQuery),
        _ => throw new ArgumentOutOfRangeException(nameof(positioning), positioning, null),
    };
}
```

`ChargePositioningStrategy`는 상태(필드)가 없는 순수 알고리즘이라 두 `case`가 각자 `new`로 별도 인스턴스를 만들어도 무해하다 — 굳이 인스턴스를 캐시해 공유할 이유가 없다(전투당 유닛마다 어차피 개별 `UnitTacticsBehaviors`를 조립하므로 인스턴스 공유는 최적화 실익이 없음).

**향후 갈라질 때**: 원거리딜러 접근 공격과 전열 돌격형의 동작을 다르게 만들고 싶어지면, 이 `case`를 `new ChargePositioningStrategy()`에서 새 클래스로 바꾸기만 하면 된다 — 다른 곳(팩토리 호출부, `UnitTacticsBehaviorsFactory`, 카탈로그)은 전혀 손댈 필요 없음.

## 4. `RoleGroupTacticsCatalog.asset` 데이터 변경 (내용)

`RoleGroupTacticsTableImporter`가 엑셀에서 덮어쓰므로 에셋을 직접 편집하지 않는다(§5 참고) — 재임포트 후 결과가 이렇게 되어야 한다는 것만 명시:

- **RoleGroup 1(전열)** `PositioningOptions`: `[2(Charge), 3(Blocking)]` — 기존 `[1, 2]`에서 값만 새 번호로, 순서(기본값=Charge)는 그대로.
- **RoleGroup 2(원거리딜러)** `PositioningOptions`: `[1(ApproachAttack), 4(Stationary), 5(Surround), 6(Disperse)]` — 접근 공격이 0번째(기본값)로 새로 추가되고, 나머지 3개는 값만 새 번호로 순서 유지.

## 5. `RoleGroupTactics.xlsx` 워크북 갱신 절차 (제작 단계에서 직접 편집)

`Assets/Table/Tactics/RoleGroupTactics.xlsx`(커밋 대상 실제 데이터 파일, 코드로 생성되지 않음)의 2개 시트를 수정한다.

**`PositioningStrings` 시트** (컬럼: `Id`, `Ko`):
| Id(기존→신규) | Ko |
|---|---|
| 1 → 2 | 돌격 |
| 2 → 3 | 방진 형성 |
| 3 → 4 | 자리 사수 |
| 4 → 5 | 포위 공격 |
| 5 → 6 | 산개 공격 |
| **(신규) 1** | **접근 공격** |

**`RoleGroupPositioningOptions` 시트** (컬럼: `RoleGroupId`, `OptionId`, `SortOrder`):
- RoleGroup 1의 기존 Charge 행: `OptionId` 1→2 (SortOrder 값은 그대로 유지 — 순서 불변).
- RoleGroup 1의 기존 Blocking 행: `OptionId` 2→3 (SortOrder 그대로).
- RoleGroup 2의 기존 Stationary 행: `OptionId` 3→4 (SortOrder 그대로).
- RoleGroup 2의 기존 Surround 행: `OptionId` 4→5 (SortOrder 그대로).
- RoleGroup 2의 기존 Disperse 행: `OptionId` 5→6 (SortOrder 그대로).
- **신규 행 추가**: `RoleGroupId=2, OptionId=1, SortOrder=<원거리딜러 기존 3행 중 최솟값보다 작은 값>` — 접근 공격이 0번째(기본값)가 되도록.

수정 후 `Tools > Game > Table > Import Role Group Tactics` 실행 → `RoleGroupTacticsCatalog.asset`/`RoleGroupTacticsStringsTable.asset`에 자동 반영 → 씬/프리팹 저장 불필요(런타임 로드 에셋이라 별도 인스톨러 재실행 대상 아님).

## 6. 제작 체크리스트

1. `LocalPositioning.cs` — §2 그대로 교체.
2. `PositioningStrategyFactory.cs` — §3의 `case` 한 줄 추가.
3. `Assets/Table/Tactics/RoleGroupTactics.xlsx` — §5의 두 시트 직접 편집.
4. `Tools > Game > Table > Import Role Group Tactics` 실행.
5. `Tools > Game > Table > Import All`(있다면) 또는 개별 임포터로 나머지 테이블에 회귀가 없는지 확인 — 이번 변경은 `RoleGroupTactics.xlsx` 한 워크북에만 국한되므로 다른 워크북은 영향 없음.
6. Unity 컴파일 확인.

## 7. 실전 검증 체크리스트

- 원거리딜러를 방향성 지시 기본값 그대로 배치했을 때, 국소적 포지셔닝 드롭다운에 "접근 공격"이 기본 선택돼 있는지(TacticsPanel UI).
- 전투 시작 후 원거리딜러가 사거리 밖이면 실제로 접근해 오는지, 사거리 안에서는 더 이상 접근하지 않고 멈추는지.
- 전열(§배경의 원인 조합)과 함께 배치했을 때 더 이상 "완전 정지" 현상이 재현되지 않는지 — 기획 17번 §1에서 진단한 조합(전열 부재 시에도 동일 재현 가능성 언급)을 이번 기회에 원거리딜러 단독 배치로도 확인.
- 자리 사수를 플레이어가 직접 선택했을 때는 기존 동작(및 §1에서 확인된 한계)이 그대로 유지되는지 — 회귀 없음 확인.
- 전열/원거리딜러 드롭다운에 남은 기존 옵션(방진 형성/포위 공격/산개 공격 등)의 한국어 라벨이 재배정 후에도 정상 표시되는지(Id 매핑 오타 확인).
