## 1. 조사 결과 — 전체 조회 API가 실제로 없다 (기획 §6-1 확인)

기획 점검 단계에서 이미 확인한 대로, 저장을 구현하려면 "현재 배치된 모든 도시/경로"를 순회할 수 있어야 하는데 지금 인터페이스로는 불가능하다:

- `ITripCityRepository`(`Core/Debug/Trip/`)는 쓰기 전용(`Add`/`UpdatePosition`/`Remove`/`Clear`) — 조회 메서드 없음.
- `ITripRouteReader`(`Core/UI/Trip/`, **정식** 인터페이스, `TripOriginDestinationAssigner`가 의존)는 `HasRoute`/`GetConnectedCityIds`(도시 1개 기준)만 있어 "전체 경로 쌍"을 바로 못 얻는다.
- 실제 데이터는 `TripMapInteractionCoordinator`의 `private` 필드(`markersByCityId`/`linesByRouteKey`)에만 있다.

부수 발견: `DEBUG_FEATURES.md` §2가 `ITripCityReader.cs`를 디버그 폴더 구성 파일로 이미 나열하고 있지만 실제로는 존재하지 않는다 — 설계 당시(03번 기획) 계획됐다가 만들어지지 않은 파일로 보인다. 이번 설계가 그 자리를 정확히 채운다(아래 §2).

## 2. 읽기 인터페이스 신설

### 2.1 도시 — `ITripCityReader`(신규, `Core/Debug/Trip/`)

`ITripRouteReader`(정식, `Core/UI/Trip/`)와 달리 도시 조회에는 아직 정식 소비자가 없다 — `DEBUG_FEATURES.md`가 원래 의도했던 위치 그대로, **디버그 폴더에 디버그 전용 인터페이스**로 만든다(`#if UNITY_EDITOR`). 나중에 정식 지역 시스템이 생겨 도시 조회가 정식 기능으로 필요해지면, 그때 `ITripRouteReader`처럼 `Core/UI/Trip/`으로 승격할지 판단한다 — 지금 미리 승격하지 않는다(YAGNI, 정식 소비자가 없는 인터페이스를 정식 위치에 두면 오해를 만든다).

```csharp
// Core/Debug/Trip/ITripCityReader.cs
public interface ITripCityReader
{
    IReadOnlyList<TripCity> GetAll();
}
```

`ITripCityRepository`가 이를 상속(기존 `ITripRouteRepository : ITripRouteReader`와 같은 패턴):

```csharp
public interface ITripCityRepository : ITripCityReader
{
    string Add(Vector2 mapPosition);
    void AddWithId(string cityId, Vector2 mapPosition); // 신규 - §3 참고, 불러오기 전용
    void UpdatePosition(string cityId, Vector2 mapPosition);
    void Remove(string cityId);
    void Clear();
    event Action<string> CityRemoved;
}
```

### 2.2 경로 — `ITripRouteRepository`에만 추가(정식 `ITripRouteReader`는 손대지 않음)

경로는 이미 정식 인터페이스(`ITripRouteReader`)가 있고 `TripOriginDestinationAssigner`가 그것에만 의존한다. "전체 경로 조회"는 저장 기능에만 필요한 능력이라, **정식 인터페이스를 건드리지 않고** 디버그 전용 쓰기 인터페이스(`ITripRouteRepository`, `Core/Debug/Trip/`)에만 추가한다 — ISP: `TripOriginDestinationAssigner`(정식 소비자)가 쓰지 않는 메서드를 그 계약에 얹지 않는다.

```csharp
public interface ITripRouteRepository : ITripRouteReader
{
    bool TryAddRoute(string cityIdA, string cityIdB);
    void RemoveRoute(string cityIdA, string cityIdB);
    void RemoveAllRoutesFor(string cityId);
    void Clear();
    IReadOnlyCollection<(string CityIdA, string CityIdB)> GetAllRoutes(); // 신규
    event Action<string, string> RouteAdded;
    event Action<string, string> RouteRemoved;
}
```

`InMemoryTripRouteRepository.GetAllRoutes()`는 이미 있는 `routeKeys`(정렬된 `"A|B"` 문자열 `HashSet`)를 그대로 순회해 `Split('|')`로 쌍을 복원하면 된다 — `Clear()`가 이미 같은 방식으로 키를 분해하고 있어 그대로 재사용 가능한 패턴.

## 3. 도시 Id 안정성 — `AddWithId` + 순번 재개 (기획 §6-4 확인)

`InMemoryTripCityRepository.Add(Vector2)`는 `debug-city-{nextSequence++}`로 Id를 자동 생성한다. 불러오기는 저장된 Id를 **그대로 보존**해야 한다(경로가 그 Id로 도시를 참조하므로 Id가 바뀌면 연결이 끊긴다) — 그래서 Id를 지정해서 추가하는 별도 메서드가 필요하다:

```csharp
public void AddWithId(string cityId, Vector2 mapPosition)
{
    citiesById[cityId] = new TripCity(cityId, mapPosition);

    // "debug-city-N" 형태면 N 이상으로 순번을 올려, 불러온 뒤 팔레트로 새 도시를 추가해도
    // 기존 Id와 충돌하지 않게 한다(기획 15번 §6-4).
    var dashIndex = cityId.LastIndexOf('-');
    if (dashIndex >= 0 && int.TryParse(cityId[(dashIndex + 1)..], out var sequence) && sequence >= nextSequence)
    {
        nextSequence = sequence + 1;
    }
}
```

저장된 Id가 `debug-city-N` 패턴이 아니어도(예: 향후 수기로 만든 기본 지도) 조용히 무시하고 그대로 저장만 한다 — Id 자체는 임의 문자열이어도 동작에 지장이 없다(딕셔너리 키일 뿐).

## 4. 저장 데이터 포맷 — `TripCityMapAsset` (기획 §6-2 확인)

기획 15번 §5의 결정("배치 도구는 디버그, 저장된 데이터는 정식")을 그대로 구조에 반영한다 — **에셋 타입 자체는 `#if UNITY_EDITOR`로 감싸지 않고**, 이 프로젝트의 기존 SO 에셋 패턴(`MercenaryRoleGroupMapAsset` 등)과 같은 자리(`Core/UI/Trip/`, 정식 코드 영역)에 둔다. `TripCity`(디버그 전용 struct)를 그대로 쓰지 않고 독립된 직렬화 구조체를 쓴다 — 에셋이 디버그 어셈블리 경계에 묶이지 않게 하기 위함.

## 5. 저장/불러오기 로직 — `TripCityMapPersistence`

`TripMapInteractionCoordinator`가 이미 여러 책임(드래그 배선, 마커/선 생성, 출발·도착 연동)을 지고 있어, "에셋 직렬화" 관심사를 더 얹지 않는다(SRP) — 데이터 테이블 임포터가 `EditorTableReader`를 별도로 뽑아둔 것과 같은 판단. 다만 `EditorTableReader.GetOrCreateAsset<T>`는 재사용할 수 없다 — 그 클래스는 `Assets/Scripts/Editor/`(에디터 전용 어셈블리)에 있고, `Core/Debug/Trip/`은 `#if UNITY_EDITOR`로 감싼 코드라도 일반 어셈블리(Assembly-CSharp)에 컴파일되어 에디터 전용 어셈블리를 참조할 수 없다(반대 방향은 가능하나 이 방향은 불가) — 그래서 새 클래스에 자체적으로 get-or-create 로직을 짧게 둔다(중복이지만 재사용이 애초에 불가능한 경우라 CLAUDE.md의 "재사용 우선" 원칙과 충돌하지 않는다).

```csharp
// Core/Debug/Trip/TripCityMapPersistence.cs
#if UNITY_EDITOR
using UnityEditor;

namespace Game.Core.DebugTools
{
    internal static class TripCityMapPersistence
    {
        private const string AssetPath = "Assets/Prefabs/ScriptableObejct/TripCityMap.asset";

        public static void Save(ITripCityReader cities, ITripRouteRepository routes)
        {
            var asset = AssetDatabase.LoadAssetAtPath<TripCityMapAsset>(AssetPath);
            if (asset == null)
            {
                asset = ScriptableObject.CreateInstance<TripCityMapAsset>();
                AssetDatabase.CreateAsset(asset, AssetPath);
            }

            var so = new SerializedObject(asset);
            WriteCities(so.FindProperty("cities"), cities.GetAll());
            WriteRoutes(so.FindProperty("routes"), routes.GetAllRoutes());
            so.ApplyModifiedProperties();

            EditorUtility.SetDirty(asset);
            AssetDatabase.SaveAssets();
            Debug.Log($"{nameof(TripCityMapPersistence)}: 도시 {cities.GetAll().Count}개, 경로 {routes.GetAllRoutes().Count}개 저장 완료.");
        }

        public static bool TryLoad(out TripCityMapAsset asset)
        {
            asset = AssetDatabase.LoadAssetAtPath<TripCityMapAsset>(AssetPath);
            return asset != null;
        }

        // WriteCities/WriteRoutes: SerializedProperty 배열에 엔트리를 채우는 짧은 헬퍼 - 임포터의
        // arraySize+GetArrayElementAtIndex 패턴 그대로.
    }
}
#endif
```

`Debug.Log`로 저장 결과를 알린다(기획 §6-5 - 최소 피드백, 데이터 테이블 임포터의 완료 로그와 동일 수준). UI 표시 등 더 풍부한 피드백은 제작 단계 재량.

## 6. `TripMapInteractionCoordinator` 배선 변경

`Bind(...)`에 `Button saveButton` 파라미터를 추가하고, 기존 `cityBulkDeleteButton`/`roadBulkDeleteButton`과 같은 자리에서 클릭을 배선한다:

```csharp
saveButton.onClick.RemoveAllListeners();
saveButton.onClick.AddListener(() => TripCityMapPersistence.Save(cityRepository, routeRepository));
```

**불러오기 시점 - 제작 중 발견한 버그로 최초 설계에서 수정됨(2026-09-03)**: 최초 설계는 `Bind(...)` 마지막에 곧바로 불러오는 것이었으나, 실제로 그렇게 구현했더니 **저장은 정상 동작했는데 다음 플레이에서 도시/경로가 화면에 나타나지 않는 버그**가 났다. 원인: `TripMapView.Content`/`Viewport`는 `Awake()` 이전엔 `null`인데(그 컴포넌트의 기존 주석에 이미 명시돼 있었음), 상행 준비 UI 패널은 씬에 비활성 상태로 배치돼 있어 `Awake`가 최초 활성화(`TripPanel.Open()`) 시점까지 지연된다. `Bind()`는 그보다 먼저(`RegisterTripUI`, 패널이 아직 비활성) 실행되므로, 그 시점에 `CreateMarker`를 호출하면 `mapView.Content`가 `null`이라 마커가 부모 없는 오브젝트로 생성돼 화면에 나타나지 않는다(내부 저장소 데이터는 정상 채워지므로 "저장은 됐는데 안 보인다"는 형태의 버그였다).

**수정된 설계**: `Bind(...)`는 불러오기를 하지 않는다. 대신 코디네이터에 세션당 1회만 실행되도록 가드한 공개 메서드를 둔다:

```csharp
private bool hasLoadedSavedMap;

public void EnsureSavedMapLoaded()
{
    if (hasLoadedSavedMap) return;
    hasLoadedSavedMap = true;

    if (!TripCityMapPersistence.TryLoad(out var asset)) return;

    foreach (var city in asset.Cities)
    {
        cityRepository.AddWithId(city.CityId, city.MapPosition);
        CreateMarker(city.CityId, city.MapPosition); // 기존 private 메서드 그대로 재사용
    }
    foreach (var route in asset.Routes)
    {
        routeRepository.TryAddRoute(route.CityIdA, route.CityIdB); // RouteAdded 이벤트로 선 뷰 자동 생성
    }
}
```

`hasLoadedSavedMap` 가드가 필요한 이유: `TripPanel.Open()`은 사용자가 패널을 여닫을 때마다(배치 UI 왕복 등) 반복 호출된다 — 가드가 없으면 열 때마다 저장된 도시를 중복 인스턴스화한다(딕셔너리는 덮어써지지만 이전 마커 GameObject가 파괴되지 않고 남는다).

출발/도착 배정(`assigner`)은 저장 대상이 아니므로(기획 §2) 불러온 직후에도 아무 도시에 역할이 없는 상태 그대로 시작한다 — 기존 팔레트 배치 직후와 동일한 초기 상태.

## 8. `HubSceneInstaller.BuildTripDebugMapControls` — 버튼 배치 (기획 §3.1 반영)

기존 4개 버튼이 상단 행(0.90~0.97)에서 0.06~0.62를 차지한다. 저장 버튼은 그 뒤 **0.64~0.78**에 이어 붙인다 — 기존 코드와 완전히 같은 패턴(`GetOrCreateUIObject` → `SetAnchors` → `EnsureImage` → `EnsureButton` → `EnsureLabel` → `EnsureMarker`):

```csharp
var saveGo = EditorUIBuilder.GetOrCreateUIObject(parent, "DebugMapSaveButton");
EditorUIBuilder.SetAnchors(saveGo.GetComponent<RectTransform>(), new Vector2(0.64f, top), new Vector2(0.78f, bottom));
EditorUIBuilder.EnsureImage(saveGo, new Color(0.6f, 0.85f, 0.6f, 1f)); // 저장=긍정 동작이라 기존 빨강(삭제)/황토(토글)와 구분되는 녹색 계열
EditorUIBuilder.EnsureButton(saveGo);
var saveLabel = EditorUIBuilder.EnsureLabel(saveGo.transform, "지도 저장");
saveLabel.fontSize = 10;
EditorUIBuilder.EnsureMarker(saveGo, TripUIElementIds.DebugMapSaveButton);
```

오브젝트 이름(`DebugMapSaveButton`)과 마커 상수(`TripUIElementIds.DebugMapSaveButton`) 모두 기존 3개 버튼처럼 `Debug` 접두사를 유지한다(기획 §3.2).

## 9. 정식 빌드에서도 로드돼야 하는가 — 아니오, 에디터 전용으로 확정 (기획 §6-3 확인)

사용자가 저장 버튼을 "임시 디버깅용 기능"으로 재차 명시했으므로(기획 §3.2), 저장/불러오기 로직 전체(§5~§6)를 기존 디버그 도구와 동일하게 **`#if UNITY_EDITOR`로 감싼다** — `LoadSavedMap()`은 에디터에서 Play할 때만 실행되고, 실제 플레이어 빌드에서는 컴파일조차 되지 않는다. `TripCityMapAsset`(데이터 타입 자체)만 `#if UNITY_EDITOR` 밖에 있어 향후 정식 지역 시스템이 이 `.asset` 파일을 읽는 새 코드를 작성할 때 재사용할 수 있다 — 지금 단계에서 그 정식 로더까지 만들지는 않는다(범위 밖).

## 11. 남은 미정 사항 (제작 단계)

1. `TripCityMapPersistence.Save`/`WriteCities`/`WriteRoutes`의 정확한 `SerializedProperty` 배열 쓰기 코드 — 임포터들과 동일 패턴이라 설계 문서에 전체를 옮기지 않음(§5 스케치 참고).
2. 저장 버튼 클릭 시 도시/경로가 0개인 상태(빈 지도)로 덮어써도 확인 없이 그냥 진행할지 — 기존 "도시 전체삭제"/"경로 전체삭제"도 확인 절차가 없어 동일하게 확인 없이 진행하는 쪽으로 기본값을 둔다(제작 단계에서 재확인).
3. `TripCityMapAsset`에 대응하는 `.meta` 생성은 Unity가 자동 처리(기존 관례와 동일) - 별도 조치 불필요.
