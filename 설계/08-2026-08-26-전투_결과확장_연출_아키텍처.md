## 1. 개요 및 범위

두 가지를 설계한다.

- **§10 결과 판정 확장**: `BattleResult.Defeat` 확정 뒤 궤주/포로/사망/도주 중 하나를 확률로 뽑아 `FieldEncounterFlowCoordinator`가 다른 팝업을 보여줄 수 있게 한다. `BattleResult` 자체는 확장하지 않는다(기획 §10 원칙 유지) — 별도 후처리 조회로 붙인다.
- **§11 전투 뷰 연출**: 06/07번 문서의 시뮬레이션 유닛(`BattleCharacterUnit`/`BattleProtectedUnit`, 순수 C# 객체)을 화면에 Placeholder 도형으로 보여주는 View 계층을 추가한다.

**범위 밖**: 기획 §14.4가 이미 "각 결과가 상행/로스터에 미치는 구체적 영향(용병 영구 손실 여부 등)은 미정"이라 못 박아 뒀다 — 이번 설계는 4종 판정이 **일어나는** 구조까지만 만들고, 궤주/포로/도주 각각의 실제 게임플레이 결과(로스터 반영, Hub 복귀 등)는 여전히 정의하지 않는다(§10).

## 3. 결과 판정 확장 — `DefeatConsequence`

```csharp
public enum DefeatConsequence
{
    Flee,       // 도주(속행)
    Rout,       // 궤주(실패·귀환)
    Captured,   // 포로
    Death,      // 사망(게임오버)
}

public interface IDefeatConsequenceRule
{
    DefeatConsequence Resolve();
}

/// <summary>
/// 기획 08번 문서 §10.1 테스트 확률(도주30/궤주35/포로25/사망10). 파티 전체에 대한 1회성 판정이라
/// PlaceholderBattleResultRule과 달리 지연 없이 즉시 값을 반환한다(코루틴 불필요).
/// </summary>
public class PlaceholderDefeatConsequenceRule : MonoBehaviour, IDefeatConsequenceRule
{
    private const float FleeProbability = 0.30f;
    private const float RoutProbability = 0.35f;
    private const float CapturedProbability = 0.25f;
    // 나머지(0.10)는 Death

    public DefeatConsequence Resolve()
    {
        var roll = UnityEngine.Random.value;
        if (roll < FleeProbability) return DefeatConsequence.Flee;
        if (roll < FleeProbability + RoutProbability) return DefeatConsequence.Rout;
        if (roll < FleeProbability + RoutProbability + CapturedProbability) return DefeatConsequence.Captured;
        return DefeatConsequence.Death;
    }
}
```

### 3.1 `BattleManager` 통합 (2026-09-01 갱신)

`IBattleResultRule`과 완전히 같은 패턴이다 — `BattleManager`는 `GetComponent`로 규칙을 찾아 델리게이트만 한다. 두 확장점이 서로 몰라도 된다(`IBattleResultRule`이 전투가 어떻게 끝나는지 모르는 채로 `IDefeatConsequenceRule`을 조회할 필요가 없다 — 후자는 오직 `Defeat`가 이미 확정된 뒤에만 호출된다).

**갱신**: 아래 `resultEvaluator`/`IBattleResultEvaluator`는 2026-08-26 리팩토링에서 삭제된 계층이다(설계01/설계04 §6 참고) — 지금은 `IBattleResultRule`을 직접 보유한다. 실제 코드는 `Core/Battle/BattleManager.cs`:

```csharp
public interface IDefeatConsequenceSource
{
    DefeatConsequence ResolveDefeatConsequence();
}

public class BattleManager : MonoBehaviour,
    IBattleController, IBattleResultSource, IDefeatConsequenceSource, IBattleSimulationEvents, IManagedComponent
{
    private IBattleResultRule resultRule;
    private IDefeatConsequenceRule consequenceRule;

    public void RegisterSelf(IDependencyRegistrar registrar)
    {
        registrar.Register<IBattleController>(this);
        registrar.Register<IBattleResultSource>(this);
        registrar.Register<IDefeatConsequenceSource>(this);
        registrar.Register<IBattleSimulationEvents>(this);
    }

    public void ResolveDependencies(IDependencyRegistrar registrar)
    {
        resultRule = GetComponent<IBattleResultRule>();
        if (resultRule == null)
            throw new InvalidOperationException($"{nameof(BattleManager)}와 같은 GameObject에 {nameof(IBattleResultRule)} 구현체가 없다.");

        consequenceRule = GetComponent<IDefeatConsequenceRule>();
        if (consequenceRule == null)
            throw new InvalidOperationException($"{nameof(BattleManager)}와 같은 GameObject에 {nameof(IDefeatConsequenceRule)} 구현체가 없다.");

        // 설계07에서 추가된 IRequiresFormationReader/IRequiresCaravanRoster(+ 설계12의
        // IRequiresTacticsReader) 선택 주입, IBattleSimulationEvents 중계는 설계04 §6 참고.
    }

    public DefeatConsequence ResolveDefeatConsequence() => consequenceRule.Resolve();

    // StartBattle/OnBattleEnded는 06번 문서 그대로 무변경
}
```

## 4. `FieldEncounterFlowCoordinator` 통합 (2026-09-01 갱신 — §14.4 확정 반영)

기획 §14.4가 이후 확정되며(2026-08-26), 아래 최초 설계가 "미정이라 4종 모두 동일 문구"로 남겨뒀던 `ShowDefeatConsequence`가 실제 4종 분기로 채워졌다. `Bind()`에 `IGameManager`(궤주 시 Hub 귀환 요청)까지 추가로 필요해졌다 — 실제 코드는 `Core/UI/Field/FieldEncounterFlowCoordinator.cs`(설계04 §5.2에 전체 구조 정리됨):

```csharp
private void ShowResult(BattleResult result)
{
    switch (result.Outcome)
    {
        case BattleOutcome.Victory:
            resultPopupView.Show("승리", "확인", onConfirm: () =>
                cameraController.TransitionToMovement(onComplete: sessionState.Resume));
            break;
        case BattleOutcome.Defeat:
            ShowDefeatConsequence(defeatConsequenceSource.ResolveDefeatConsequence());
            break;
    }
}

// 기획 §14.4 확정 반영(2026-08-26): 사망=플레이 종료, 도주=상행 속행(Victory와 동일 흐름),
// 궤주=Hub 귀환. 포로는 아직 콘텐츠가 없어(테스트 단계) 사망과 동일하게 임시 처리한다.
private void ShowDefeatConsequence(DefeatConsequence consequence)
{
    switch (consequence)
    {
        case DefeatConsequence.Death:
            resultPopupView.Show("패배 - 전멸", "플레이 종료", onConfirm: Application.Quit);
            break;
        case DefeatConsequence.Flee:
            resultPopupView.Show("패배 - 도주", "상행 속행", onConfirm: () =>
                cameraController.TransitionToMovement(onComplete: sessionState.Resume));
            break;
        case DefeatConsequence.Rout:
            resultPopupView.Show("패배 - 궤주", "귀환", onConfirm: () =>
                gameManager.RequestSceneTransition(ContentSceneId.Hub));
            break;
        case DefeatConsequence.Captured:
        default:
            resultPopupView.Show("패배 - 포로", "플레이 종료", onConfirm: Application.Quit);
            break;
    }
}
```

이 확정으로 `Bind()`에 `IGameManager gameManager`(궤주 분기용)까지 함께 추가됐다 — 최초 설계가 예견한 "판정 종류가 늘어나면 case를 추가하라"는 지점이 그대로 실현됐을 뿐 아니라, switch 하나로 4종을 흡수할 수 있었다(§9가 걱정했던 "재검토 필요"가 실제로는 별도 전략 패턴 분리 없이 해결됨).

## 5. 연출을 위한 시뮬레이션 이벤트 확장 (기획 §11)

뷰가 "피격/공격 순간"을 알려면 06/07번 인터페이스에 없던 이벤트가 필요하다. 죽음(`OnDied`)·도주(`OnFled`)만으로는 부족하다 — 살아있는 동안의 순간적인 반응(피격 플래시, 공격 모션)은 별도 이벤트가 있어야 폴링 없이 처리할 수 있다.

```csharp
public interface IDamageable
{
    Vector2 Position { get; }
    bool IsAlive { get; }
    float Defense { get; }
    float MaxHp { get; }                 // 신규 - 뷰가 직업별 크기 차이(§12)를 유추하는 데 사용(§6)
    event Action OnDied;
    event Action<float> OnDamaged;       // 신규 - 피격마다 발행(연출: 흰색 플래시)
    void TakeDamage(float amount);
}

public interface IBattleCombatant : IDamageable
{
    bool IsAlly { get; }
    bool IsFleeing { get; }
    event Action OnFled;
    event Action<IDamageable> OnAttacked;   // 신규 - 공격 실행 시 발행, 타겟 포함(연출: 근접 런지/원거리 투사체)
    void Tick(float deltaTime, IReadOnlyList<IDamageable> targets);
}
```

`BattleCharacterUnit`/`BattleProtectedUnit`의 변경은 기계적이다 — 기존 로직 순서는 그대로 두고 이벤트 발행만 끼워 넣는다.

```csharp
// BattleCharacterUnit
public float MaxHp => stats.MaxHp;
public event Action<float> OnDamaged;
public event Action<IDamageable> OnAttacked;

public void TakeDamage(float amount)
{
    if (!IsAlive) return;
    currentHp = Mathf.Max(0f, currentHp - amount);
    OnDamaged?.Invoke(amount);          // 신규 - 생사 여부와 무관하게 항상 발행
    if (currentHp <= 0f)
    {
        partyMorale.NotifyUnitLost();
        OnDied?.Invoke();
    }
}

// Tick()의 공격 실행부
attackCooldown -= deltaTime;
if (attackCooldown <= 0f)
{
    target.TakeDamage(damageFormula.ComputeDamage(stats.Attack, target.Defense));
    OnAttacked?.Invoke(target);          // 신규
    attackCooldown = stats.AttackInterval;
}
```

```csharp
// BattleProtectedUnit
public float MaxHp { get; }
public event Action<float> OnDamaged;

public BattleProtectedUnit(Vector2 position, float maxHp)
{
    Position = position;
    MaxHp = maxHp;
    currentHp = maxHp;
}

public void TakeDamage(float amount)
{
    if (!IsAlive) return;
    currentHp = Mathf.Max(0f, currentHp - amount);
    OnDamaged?.Invoke(amount);
    if (!IsAlive) OnDied?.Invoke();
}
```

## 6. 뷰 컴포넌트 (기획 §11 Placeholder 사양)

```csharp
/// <summary>
/// 기획 §11 - 단색 원형으로 BattleCharacterUnit 1기를 표현한다. 이동은 매 프레임 Position을 그대로
/// 따라가고, 공격/피격/사망/도주는 유닛이 발행하는 이벤트에 반응해서만 처리한다(폴링 없음).
/// </summary>
public class BattleCharacterUnitView : MonoBehaviour
{
    [SerializeField] private SpriteRenderer bodyRenderer;

    private const float HitFlashSeconds = 0.1f;
    private const float DeathFadeSeconds = 0.3f;
    private const float LungeDistance = 0.3f;
    private const float LungeSeconds = 0.1f;
    private const float RangedVisualThreshold = 2.5f;   // 이 거리 이상이면 원거리(투사체)로 간주 - 기획 §12 사거리 참고

    private IBattleCombatant unit;

    public void Bind(IBattleCombatant unit)
    {
        this.unit = unit;
        bodyRenderer.color = unit.IsAlly ? Color.blue : Color.red;
        // MaxHp를 크기 신호로 재사용 - 방패병(150) > 전사(100) > 궁수(70) 순서가 자연히 만들어진다(기획 §12).
        transform.localScale = Vector3.one * Mathf.Clamp(unit.MaxHp / 100f, 0.7f, 1.5f);

        unit.OnDamaged += HandleDamaged;
        unit.OnAttacked += HandleAttacked;
        unit.OnDied += HandleRemoved;
        unit.OnFled += HandleRemoved;
    }

    private void Update()
    {
        if (unit == null || !unit.IsAlive) return;
        transform.position = unit.Position;   // §5.2/§7.3 이동 결과를 그대로 반영 (도주 이동도 동일 경로)
    }

    private void HandleDamaged(float amount) => StartCoroutine(FlashWhite());

    private void HandleAttacked(IDamageable target)
    {
        var distance = Vector2.Distance(unit.Position, target.Position);
        if (distance < RangedVisualThreshold) StartCoroutine(Lunge(target.Position));
        else SpawnProjectile(target.Position);
    }

    private void HandleRemoved() => StartCoroutine(FadeAndDestroy());

    private IEnumerator FlashWhite() { /* HitFlashSeconds 동안 bodyRenderer.color를 흰색으로 바꿨다 복원 */ yield break; }
    private IEnumerator Lunge(Vector2 targetPosition) { /* LungeSeconds 동안 targetPosition 방향으로 LungeDistance만큼 갔다 복귀 */ yield break; }
    private void SpawnProjectile(Vector2 targetPosition) { /* 작은 점 스프라이트를 attacker→target 직선 이동시키고 도착 시 제거 */ }
    private IEnumerator FadeAndDestroy() { /* DeathFadeSeconds 동안 알파 0으로 페이드 후 Destroy(gameObject) */ yield break; }
}

/// <summary>기획 §11 - 단색 사각형으로 Wagon/Facility 1기를 표현한다. 이동 없음, 파괴 연출만 있다.</summary>
public class BattleProtectedUnitView : MonoBehaviour
{
    [SerializeField] private SpriteRenderer bodyRenderer;
    private IDamageable unit;

    public void Bind(IDamageable unit, Vector2 position)
    {
        this.unit = unit;
        transform.position = position;   // 고정 배치 - Update에서 갱신할 필요 없음(기획 §4 이동 없음)
        unit.OnDamaged += HandleDamaged;
        unit.OnDied += HandleDestroyed;
    }

    private void HandleDamaged(float amount) => StartCoroutine(FlashWhite());
    private void HandleDestroyed() => StartCoroutine(FadeAndDestroy());

    private IEnumerator FlashWhite() { yield break; }
    private IEnumerator FadeAndDestroy() { yield break; }
}
```

세부 연출(정확한 트윈 커브, 투사체 스프라이트 모양, 색상 값)은 코드 스니펫에 의사코드로만 남겨뒀다 — 실제 구현은 제작 단계에서 채운다. 이 문서가 확정하는 건 "무엇에 반응해서 무엇을 하는가"라는 이벤트-연출 매핑 구조다.

## 7. 뷰 스폰/바인딩 — `BattleViewPresenter`

`LiveBattleSimulationRule`(Bootstrap, `Core/Battle/`)은 렌더링을 몰라야 한다(SRP — 06/07번 내내 지켜온 원칙). 시뮬레이션이 새로 만들어졌다는 사실만 이벤트로 알리고, 실제 View 생성·배치는 콘텐츠 씬 쪽 협력 객체가 맡는다. `FieldEncounterFlowCoordinator`가 `RebindViews`로 씬별 참조를 다시 잡는 것과 같은 패턴이다.

```csharp
// LiveBattleSimulationRule에 추가
public event Action<BattleSimulationLoop> OnSimulationBuilt;

private BattleSimulationLoop BuildSimulation()
{
    // ... 06/07번 그대로 allies/enemies/protectedUnits 생성 ...
    var loop = new BattleSimulationLoop(allies, enemies, protectedUnits);
    OnSimulationBuilt?.Invoke(loop);   // 신규 - 뷰 스폰 트리거
    return loop;
}
```

`BattleSimulationLoop`는 `allies`/`enemies`/`protectedUnits`를 읽기 전용으로 노출해야 `BattleViewPresenter`가 순회할 수 있다 — `public IReadOnlyList<IBattleCombatant> Allies => allies;` 등 3개 프로퍼티를 추가한다(06번 문서의 `BattleSimulationLoop`에 대한 추가 변경).

```csharp
/// <summary>
/// 순수 C# 협력 객체. FieldUIController가 최초 1회 생성해 유지하고, LiveBattleSimulationRule의
/// OnSimulationBuilt를 구독해 매 전투 시작마다 View를 새로 스폰한다(FieldEncounterFlowCoordinator와
/// 같은 Bind/RebindViews 2단 구조 — 이벤트 구독은 최초 1회, 씬 참조 교체는 Field 씬 로드마다).
/// </summary>
internal class BattleViewPresenter
{
    private Transform allyContainer;
    private Transform enemyContainer;
    private BattleCharacterUnitView characterViewPrefab;
    private BattleProtectedUnitView protectedViewPrefab;

    private readonly List<BattleCharacterUnitView> activeCharacterViews = new();
    private readonly List<BattleProtectedUnitView> activeProtectedViews = new();

    public void Bind(ILiveBattleSimulationEvents simulationEvents) =>
        simulationEvents.OnSimulationBuilt += Present;

    public void RebindViews(
        Transform allyContainer, Transform enemyContainer,
        BattleCharacterUnitView characterViewPrefab, BattleProtectedUnitView protectedViewPrefab)
    {
        this.allyContainer = allyContainer;
        this.enemyContainer = enemyContainer;
        this.characterViewPrefab = characterViewPrefab;
        this.protectedViewPrefab = protectedViewPrefab;
    }

    private void Present(BattleSimulationLoop simulation)
    {
        Clear();
        foreach (var unit in simulation.Allies) SpawnCharacterView(unit, allyContainer);
        foreach (var unit in simulation.Enemies) SpawnCharacterView(unit, enemyContainer);
        foreach (var unit in simulation.ProtectedUnits) SpawnProtectedView(unit, allyContainer);
    }

    private void SpawnCharacterView(IBattleCombatant unit, Transform parent)
    {
        var view = UnityEngine.Object.Instantiate(characterViewPrefab, parent);
        view.Bind(unit);
        activeCharacterViews.Add(view);
    }

    private void SpawnProtectedView(IDamageable unit, Transform parent)
    {
        var view = UnityEngine.Object.Instantiate(protectedViewPrefab, parent);
        view.Bind(unit, unit.Position);
        activeProtectedViews.Add(view);
    }

    // 다음 전투 시작 시 이전 전투의 View가 남아있지 않도록 정리한다. 개별 View는 사망/도주 시
    // 스스로 Destroy되지만(§6 FadeAndDestroy), 전투가 도중에 중단되는 경우까지 대비한 안전장치다.
    private void Clear()
    {
        foreach (var view in activeCharacterViews) if (view != null) UnityEngine.Object.Destroy(view.gameObject);
        foreach (var view in activeProtectedViews) if (view != null) UnityEngine.Object.Destroy(view.gameObject);
        activeCharacterViews.Clear();
        activeProtectedViews.Clear();
    }
}
```

`LiveBattleSimulationRule`을 `BattleViewPresenter`가 직접 참조하지 않고 `ILiveBattleSimulationEvents`(`event Action<BattleSimulationLoop> OnSimulationBuilt`만 있는 좁은 인터페이스)로 받는 이유는 06/07번 내내 써온 ISP 원칙 그대로다 — 뷰 쪽은 "시뮬레이션이 만들어졌다"는 사실만 알면 되고, `Evaluate`/`SetFormationReader` 같은 `IBattleResultRule`/`IRequiresFormationReader`의 다른 멤버는 몰라도 된다.

`FieldUIController`는 `BattleViewPresenter`를 생성해 `Bind()`(최초 1회, DI로 얻은 `LiveBattleSimulationRule` 참조를 `ILiveBattleSimulationEvents`로 전달)하고, Field 씬이 로드될 때마다 `RebindViews()`로 씬 안의 컨테이너 Transform·프리팹 참조를 새로 넘긴다 — `FieldEncounterFlowCoordinator`가 이미 쓰는 패턴과 동일하다.

| 원칙 | 적용 |

| SRP | 결과 확률 판정(`IDefeatConsequenceRule`) / 판정 조회 창구(`IDefeatConsequenceSource`) / 팝업 표시(`FieldEncounterFlowCoordinator`) 분리. 뷰 계층도 유닛 표현(`BattleCharacterUnitView`) / 스폰·생명주기 관리(`BattleViewPresenter`)로 분리 — 시뮬레이션(`LiveBattleSimulationRule`)은 렌더링을 전혀 모른다 |

| DIP | `FieldEncounterFlowCoordinator`/`BattleViewPresenter` 모두 구체 타입(`BattleManager`, `LiveBattleSimulationRule`)을 몰이며 인터페이스로만 주입받는다 |

## 9. 최적화 요약

- `BattleCharacterUnitView.Update()`는 살아있는 유닛에 대해서만 `transform.position` 대입 1회 — 유닛 수가 적어(§9, 06번 문서) 부담 없다.
- 피격/공격/사망/도주 반응은 전부 이벤트 구독이라 폴링이 없다 — `CLAUDE.md`의 "입력 반응은 이벤트/콜백으로 처리" 원칙과 일치.
- `BattleViewPresenter`는 전투마다 View를 `Instantiate`/`Destroy`한다(풀링하지 않음) — 인카운터 빈도가 낮고(5초마다 30% 확률, [[07-2026-08-25-인카운터_판정_기획]]) 유닛 수도 적어(아군 최대 16, 적 3~5) 지금 단계에서는 오브젝트 풀링이 과할 수 있다. 실제 플레이에서 생성 비용이 체감되면 재검토(§10).

## 11. 실제 구현 반영 사항 (2026-08-26)

이 문서 작성 이후 실제 구현·플레이테스트 과정에서 아래처럼 바뀌었다 — §3.1/§4(결과 판정 통합)는 2026-09-01에 코드 기준으로 본문에 직접 반영했고, 아래는 그 외(뷰 계층, §5~§7) 델타만 남긴다.

- **렌더링이 SpriteRenderer가 아니라 UGUI다**: Field 씬이 전부 Canvas 기반이라(카메라 고정, 화면 전체를 채우는 Canvas UI) `SpriteRenderer`/`transform.position` 대신 `Image`/`RectTransform.anchoredPosition`을 쓴다. 시뮬레이션 좌표(대략 -8~8 범위) 1단위를 화면 픽셀로 바꾸는 `PositionScale = 40f` 상수가 추가됐다. §6의 `bodyRenderer`(SpriteRenderer)는 실제로는 `bodyImage`(Image)다.
- **유닛 형태는 원형이 아니라 사각형**: §6이 "단색 원형"을 가정했지만, 실제로는 스프라이트를 지정하지 않은 기본 `Image`(사각형)를 그대로 쓴다. 원형 전환은 이번 세션에서 스킵하기로 결정했다(우선순위 낮음).
- **보호 목표(Wagon/Facility) 아이콘**: §6의 "단색 사각형" 대신, 정비창(배치 UI) 팔레트 아이콘을 그대로 재사용한다(마차=삼각형/시설=원형) — `BattleProtectedUnit` 생성자에 `Sprite icon` 파라미터가 추가됐고, `IDamageable.Icon`이 뷰 전용 힌트로 신설됐다.
- **사망/도주 연출이 §6과 다르게 구체화됨**:
  - 사망: `OnDied` 시점에 즉시 빨간 틴트(`DeathTintColor`)로 덮고 1.1배 확대(`DeathGrowScale`) 후, 2초에 걸쳐 보간(Lerp) 페이드아웃하며 제거. `DeathFadeSeconds`(0.3초)는 폐지되고 `FadeOutSeconds`(2초)로 대체됐다.
  - 도주: `OnFled` 이후에도 이동을 멈추지 않는다 — `IBattleCombatant.FleeVelocity`(도주 방향×이동속도, 신규 힌트 프로퍼티)를 뷰가 이어받아 시뮬레이션 Tick 없이 계속 이동시키며 같은 2초 페이드아웃을 적용한다(사망과는 색/확대 여부로 구분).
  - 공통: `HandleRemoved`(단일 핸들러) 대신 `HandleDied`/`HandleFled`로 분리됐다.
- **결과 판정 확장(§10.1) 4종이 실제로 구현됨**: `ShowDefeatConsequence`가 더 이상 4종 모두 동일하지 않다 — 사망=Application.Quit, 도주=`cameraController.TransitionToMovement`+`sessionState.Resume()`(승리와 같은 흐름), 궤주=`IGameManager.RequestSceneTransition(SceneNames.Hub)`, 포로=콘텐츠 미구현이라 임시로 사망과 동일 처리. 이를 위해 `FieldEncounterFlowCoordinator.Bind()`에 `IGameManager` 파라미터가 추가됐고, `GameManager`에 있던 미사용 `HandleBattleEnded` TODO 스텁(같은 이벤트를 중복 구독하며 아무 일도 하지 않던 코드)은 제거됐다.
- **전투 뷰 전환 시 검은 커튼 추가**(이 문서에 없던 요소): 연속 전투 시 이전 전투의 잔여 유닛 뷰가 전환 슬라이드 도중 잠깐 보이는 문제가 있어, `FieldTransitionCurtainView`(화면 전체를 덮는 고정 오버레이)를 신설했다. `FieldCameraController`가 전투 진입 슬라이드와 함께 커튼을 동행시키고, 전투 상태가 실제로 재구성된 뒤(`StartBattle()` 완료 후) `FieldEncounterFlowCoordinator`가 걷는다.
- **이동뷰↔전투뷰 슬라이드에 가속 곡선 적용**(이 문서에 없던 요소): 일정한 속도(linear)로 움직이면 딱딱하다는 피드백에 따라, `FieldCameraController.SlideRoutine`이 3차 이징(ease-in cubic, `t³`)을 적용한다 — 초반은 느리고 후반으로 갈수록 빨라진다. 길이도 `SlideDurationSeconds` 0.6초→0.9초로 늘렸다(2차 곡선 0.6초일 때보다 초반이 더 완만해지면서도, 종료 시점 속도는 비슷하게 맞춘 결과).
- **씬 전환 시 EventSystem/AudioListener 중복 경고 수정**(이 문서 범위 밖, `SceneLoader.cs`): 콘텐츠 씬 전환(Hub↔Field) 때마다 "There can be only one active Event System"/"2 audio listeners" 경고가 떴다 — 새 씬을 먼저 로드한 뒤 이전 씬의 EventSystem/AudioListener를 파괴하던 순서 때문에 한 프레임 동안 두 개가 동시에 활성화됐다. 이전 것들을 먼저 파괴하고 한 프레임 기다린 뒤에 새 씬을 로드하도록 순서를 바꿔 해소했다. 전투 시스템 자체와는 무관한 Field 씬 인프라 수정이라 별도 설계 문서([[04-2026-08-25-Field씬_아키텍처]]) 대상이지만, 이번 세션에서 궤주(Hub 귀환) 기능을 테스트하며 발견·수정된 것이라 여기에 함께 기록한다.
