# 게임 시간 시스템 아키텍처

작성일: 2026-10-11
상태: 섹션 ①~⑤ 사용자 승인(2026-10-11), 문서 검토 대기. 작업 브랜치 `system`.
기획: [84 게임 시간 시스템](../기획/시스템/84-2026-10-11-게임_시간_시스템_기획.md)
관련 설계: 76(상행 소요시간·난이도 — 구간 진행·이동 수치), 79 §5.4(파괴 마차 지연), 81 §6.4(상행 종료 처리), 83 §6.1(재화 HUD·디버그 줄 배치)

---

## 1. 기획 요약

- 일 단위, 1개월 30일, 1년 6개월. 시작 1월 1일, 6월 30일 다음 1월 1일(순환). Hub HUD에만 "n월 n일".
- 시간은 상행 이동에서만 흐른다. 30초 = 1일, 가산 시점마다 30초 미만 버림.
- 가산 시점: 구간 도착(중간 도시·최종 도착). 도주는 가산 없음(누적 유지). 궤주는 직전 도시부터 궤주까지 이동 초 × 1.5.
- 상행정보 패널 예상 소요 → 구간별 "약 n일"(버림) + 합계(구간 일수 합).
- 디버그: Hub 날짜 진행 버튼, Field 누적 초·예정 가산 표시.

## 2. 접근안 (사용자 선택: A)

| 안 | 내용 | 판단 |
|---|---|---|
| **A** | 전역 날짜 매니저(`DateManager`) + 순수 계산 클래스. 가산은 구간 진행·전투 마무리가 기존 경과 시간을 읽어 호출 | 채택. 경과 시간은 이미 `SessionStateTracker`가 센다(전투 중 정지·도주 후 이어짐 포함) — 중복 계측 없음 |
| B | 별도 상행 시간 누적 객체가 초를 직접 누적 후 정산 | 기각. 경과 시간 이중 계측, 정지·재개 규칙을 두 곳에서 맞춰야 함 |
| C | 날짜 매니저가 상행 진행 도착 이벤트를 직접 구독 | 기각. 궤주는 도착 이벤트가 없어 경로가 둘로 갈림, 전역 → 상행 방향 결합 |

## 3. 구성 요소

### 3.1 날짜 (Bootstrap 전역)

| 구성 요소 | 종류 | 역할 |
|---|---|---|
| `GameDate` | 순수 값 형식(struct) | 누적 일수 → 경과 해(0부터)·월(1~6)·일(1~30), 표시 문구 "n월 n일". 1개월 30일·1년 6개월은 기획 고정 규칙이라 상수로 둔다 |
| `GameCalendar` | 순수 클래스 | 누적 일수 보관·진행. 0 이하 진행은 무시, 실제로 바뀌었을 때만 `Changed` 1회. `DateManager`가 감싸며 EditMode 테스트 대상 |
| `IDateReader` | 계약 | 오늘 날짜(`GameDate Today`), `event Action Changed`. Hub 날짜 HUD·디버그가 사용 |
| `IDateAdvancer` | 계약 | `AdvanceDays(int days)`. 상행 날짜 정산·디버그만 사용 |
| `DateManager` | `MonoBehaviour`, `IManagedComponent` | `Managers` 루트 아래 `GameManager`와 나란히 둔다. `IDateReader`·`IDateAdvancer`를 각각 등록(상위·하위 타입 등록으로는 조회되지 않음 — 골드 보유 서비스와 같은 규칙). `ResolveDependencies`에서 누적 0일(1월 1일)로 초기화. 상행 규칙은 모른다 |

- 읽기·진행 계약을 나누는 이유(ISP): 날짜 HUD처럼 읽기만 하는 소비자에게 진행 메서드를 노출하지 않는다.
- 저장/불러오기가 없어 Play마다 1월 1일로 시작한다(기획 84 §2).
- `GameCalendar`가 `Changed`를 갖고 `DateManager`는 그 이벤트를 자기 `Changed`로 중계한다 — `ResolveDependencies`가 다시 불려 달력을 새로 만들어도 소비자 구독이 끊기지 않게 한다(`GoldHoldingsService`와 같은 이유).

### 3.2 환산 규칙 (상행 이동 수치)

| 대상 | 변경 |
|---|---|
| `TripTravelSettings` | `SecondsPerDay`(기본 30), `RoutDayMultiplier`(기본 1.5) 추가. `Default()`에도 포함 |
| `TravelDayRules` (신설, 순수 정적) | `ToDays(settings, seconds)` = floor(seconds ÷ SecondsPerDay), `ToRoutDays(settings, seconds)` = floor(seconds × RoutDayMultiplier ÷ SecondsPerDay). 설정값이 0 이하면 기본값 사용(기존 씬에 저장된 설정에는 새 필드가 없음). 음수 초는 0일 |

- 환산 값을 `DateManager`가 아니라 `TripTravelSettings`에 두는 이유: 상행 계획(정보 패널 예상)과 실제 가산이 같은 수치를 읽어야 예상과 실제가 일치한다. 이동 수치는 이미 `TripItineraryState` 인스펙터 한곳에 모여 있다.
- 버림의 부동소수 오차: 구간 소요시간은 공식 계산값(float)이라 89.99999초처럼 경계 바로 아래로 나올 수 있다. 나눗셈 결과에 아주 작은 보정(1e-4일)을 더한 뒤 버린다.

### 3.3 상행 연결

| 대상 | 변경 |
|---|---|
| `ISessionState` | `ElapsedSeconds`(현재 구간 경과 초), `DurationSeconds`(현재 구간 소요시간 — 파괴 지연 반영) 조회 추가. `SessionStateTracker` 구현 |
| `ITripTravelSettingsReader` (신설) | `TripTravelSettings Settings`. `TripItineraryState`가 추가 등록. 기존 여정 계약(`ITripItinerary`)에 넣지 않는다 — 구간 진행만 필요한 소비자에게 이동 수치를 노출하지 않기 위함 |
| `TripDateAccrual` (신설, Field 전용 plain C#) | 의존: `ISessionState`, `IDateAdvancer`(선택), `ITripTravelSettingsReader`(선택). `AccrueLegArrival()` = `ToDays(DurationSeconds)`, `AccrueRout()` = `ToRoutDays(ElapsedSeconds)`. 계산 결과 0일이면 진행 호출 없음. 날짜 진행 계약이 없으면 아무것도 하지 않음, 이동 수치 계약이 없으면 기본값 |
| `FieldTripLegCoordinator` | `HandleLegArrived` 첫머리(두 분기 공통 — 중간 도시·최종 도착, 다음 구간 `Begin` 전)에서 `AccrueLegArrival()` |
| `FinishStep` | 궤주 분기 진입 직후(`FinishTrip`·씬 전환 전)에 `AccrueRout()` |
| `FieldUIWiring` | `IDateAdvancer`·`ITripTravelSettingsReader`를 `TryResolve`, `TripDateAccrual` 생성 후 `FieldUIController.RegisterFieldUI` 인자로 전달 → 구간 진행 생성자와 `FieldEncounterFlowCoordinator.Bind` → `FinishStep` 생성자로 전달 |

동작 근거:
- 구간 도착은 경과 초가 아니라 최종 소요시간을 쓴다 — 도착 프레임의 경과 초는 소요시간을 약간 넘을 수 있고, 소요시간 기준이어야 전투·파괴 지연이 없을 때 패널 예상과 정확히 같다.
- 궤주는 경과 초를 쓴다. 전투 중엔 진행이 멈춰 있으므로 결과 처리 시점에 읽어도 전투 시작 시점 값과 같다.
- 도주는 호출하지 않는다. `FinishStep`의 상행 속행 분기가 `sessionState.Resume()`으로 같은 구간 경과를 이어 가므로 다음 도착 때 합산된다.
- 정산은 반드시 다음 구간 `Begin` 전에 한다 — `Begin`이 경과를 0으로 되돌린다. 구간 도착 알림(2초) 동안 진행은 멈춰 있고 `Begin`은 알림 콜백에서 호출되므로 첫머리 호출이면 충분하다.
- 여정 없이 Field에서 바로 Play: 기존 30초 구간 하나 → 도착 시 1일.
- 디버그 "상행 완료"(즉시 완료)도 **정상 완료와 같은 일수가 흐른다**(사용자 결정 2026-10-11, §5). 디버그 뷰가 건너뛰기 전에 남은 일수를 직접 더하고, 마지막 구간은 0.01초로 끝나 도착 정산이 0일이 되므로 이중 가산이 없다. 게임 코드는 바뀌지 않는다.
- 포로·사망은 `Application.Quit()` — 정산 없음.

```
Hub 출발 ─▶ Field
  구간 진행(SessionStateTracker: 경과/소요)
    ├─ 도착 이벤트 ─▶ FieldTripLegCoordinator.HandleLegArrived
    │                   └─ TripDateAccrual.AccrueLegArrival ─▶ IDateAdvancer
    └─ 인카운터 ─▶ 전투 ─▶ 결과 정리 흐름 ─▶ FinishStep
                          ├─ 승리·도주: Resume (정산 없음)
                          ├─ 궤주: TripDateAccrual.AccrueRout ─▶ IDateAdvancer ─▶ Hub
                          └─ 포로·사망: 종료
```

### 4.2 상행정보 패널

| 대상 | 변경 |
|---|---|

## 5. 디버그

기존 규칙: 게임 코드에 흔적을 남기지 않는다, 전용 인스톨러(Install/Remove 서브메뉴), `DebugToolsBulkInstaller` 등록, `#if UNITY_EDITOR`.

| 대상 | 내용 |
|---|---|
| `GameDateDebugView` (신설, OnGUI) | `DateManager`와 같은 GameObject(Bootstrap 상주)에 부착, Hub 로드 중에만 그린다. [+1일] [+10일] [+30일] — 고정 버튼(직접 입력보다 단순, 30일 = 월 넘김, 반복으로 해 넘김 검증). Awake에서 같은 오브젝트의 `IDateAdvancer` 조회 |
| 버튼 위치 | 날짜 패널 바로 아래 줄이 후보. 제작 단계 겹침 실측 후 확정 |
| `GameDateDebugInstaller` (신설) | `Tools/Game/Debug/...` Install/Remove. 걷어낼 때 절차를 클래스 주석에 남긴다 |
| `TripDebugView` (기존에 한 줄 추가) | 기존 버튼 2줄 아래 표시 전용 줄: "구간 경과 n초 / 소요 n초 · 도착 시 +n일 · 궤주 시 +n일". 이미 보유한 `ISessionState`의 새 조회 값 + `TravelDayRules`(이동 수치는 이 뷰가 Awake에서 이미 찾아 두는 `TripItineraryState`의 `Settings`). 설치는 기존 `TripDebugInstaller` 그대로 |
| `TripDebugView` 상행 완료 버튼 | 건너뛰기 전에 남은 일수를 `IDateAdvancer`로 더한다 — 현재 구간은 `ToDays(sessionState.DurationSeconds)`(파괴 지연 반영, 지난 경과 포함 구간 전체), 이후 구간은 각각 `ToDays(leg.DurationSeconds)`의 합. 구간별 버림이라 정상 완료(구간마다 도착 정산)와 같은 값. 그 뒤 기존대로 마지막 구간을 0.01초로 시작 → 도착 정산 0일. 여정이 없으면 현재 구간(30초) = 1일. `IDateAdvancer`는 Awake에서 `FindFirstObjectByType<DateManager>`로 조회, 없으면 날짜 가산 없이 기존 동작 |

## 6. 테스트·검증

### 6.1 EditMode (`Scripts/Tests/EditMode/`)

| 대상 | 경우 |
|---|---|
| `GameDate` | 0일 = 1월 1일, 29 = 1월 30일, 30 = 2월 1일, 179 = 6월 30일, 180 = 1월 1일(경과 해 1), 문구 "n월 n일" |
| `TravelDayRules` | 29.9초 → 0, 30 → 1, 100 → 3, 89.99999 → 3(보정), 궤주 100초 → 5, 기획 84 예시(90 도착 + 100 궤주 = 8), 설정 0 이하 → 기본값, 음수 → 0 |
| `GameCalendar` | 0 이하 무시, 변경 시에만 `Changed` 1회 |
| `TripDateAccrual` | 대역 사용. 도착 = 소요시간 기준(연장 반영), 궤주 = 경과 × 1.5, 진행 계약 없음 → 무동작, 0일 → 진행 호출 없음 |
| `TripTravelTests`(추가) | 구간 `EstimatedDays` = 소요 ÷ 30 버림, `TotalEstimatedDays` = 구간 합 |
| 회귀 | EditMode 전체(현재 347) |

### 6.2 CLI 런타임 (Play + eval, 작업 전 playMode 확인)

- 시작 시 Hub "1월 1일", 디버그 +30일 월 넘김·+180일 해 넘김.
- 다구간 상행: 중간 도시마다 가산, Hub 복귀 후 합계 = 패널 예상(전투 없는 구간).
- 디버그 상행 완료: 출발 직후·중간 구간 도중에 눌러도 합계 = 패널 예상(남은 구간 전체).
- 날짜 패널·날짜 디버그 버튼 겹침 실측(§4.1 상태 목록).

### 6.3 사용자 실행 확인

- 도주 후 도착: 도주 시점 무가산, 도착 시 구간 전체로 가산.
- 궤주: 직전 도시부터 이동 초 × 1.5.
- 마을 행동(구매·고용·정리) 후 날짜 불변.
- 전투 결과는 상행 디버그(인카운터 즉시 발생)·전투 강제 승패 도구로 만든다.

### 6.4 제작 후 사용자 안내

Bootstrap 씬: Tools > Game > Build Bootstrap Scene → Ctrl+S. Hub 씬: Hub 인스톨러 실행 → Ctrl+S. 날짜 디버그: Install 메뉴(또는 Install All).

## 8. 향후 확장 (기획 84 §5)

- 마을 행동의 시간 소모: `IDateAdvancer` 소비자를 추가하면 된다(날짜 매니저 변경 없음).
- 시간 경과의 결과(재입고·급여·이벤트): `IDateReader.Changed` 구독자로 붙인다. 하루 단위 처리가 필요하면 변경 전후 일수를 알리도록 이벤트 확장 검토.
- 저장/불러오기: `GameCalendar` 누적 일수 하나만 저장하면 된다.
