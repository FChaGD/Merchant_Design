## 1. 개요

게임의 초기 기반 시스템으로, 전역 상태·흐름을 조율하는 매니징 오브젝트 7종과 그 하위 컴포넌트 구조를 정의한다.

**핵심 원칙**: 매니저는 매니저 간 통신과 하위 컴포넌트 관리(조율)만 담당한다. 실질적 기능은 모두 매니저 산하 컴포넌트 또는 개별 개체(유닛 등)의 컴포넌트에서 구현한다.

---

## 2. 매니징 오브젝트 목록 및 역할

| 매니저 | 역할 |
|---|---|
| **DependencyManager** | 매니저 간 의존성 등록/조회 중개. 게임 로직 없음. 나머지 6개 매니저보다 먼저 초기화. |
| **GameManager** | 최상위 흐름 총괄. 메타(본부) ↔ 세션(상행) 씬 전환 트리거, 상행 시작/종료 판정 시점 관리. |
| **InputManager** | 원시 입력 수집, 현재 입력 컨텍스트(필드 이동/정비창/전투 등) 판별 후 해당 대상에 라우팅. |
| **UIManager** | UI 화면/오버레이(정비창, 방향성 지시, HUD, 결과창 등)의 오픈·클로즈·전환 상태 관리. |
| **BattleManager** | 전투 세션(시작~종료) 총괄. 승패 판정 기준 적용, 진형·전술 설정값을 하위 컴포넌트에 전달. |
| **AIManager** | 필드/전투 상 AI 제어 대상의 활성 목록 관리, 전역 AI 파라미터 관리. |
| **EncounterManager** | 상행 중 인카운터 발생 조건 판정(랜덤/확정)과 인카운터 생성, 전투 시작 요청. |

### 씬 전환 해석
- **메타↔세션 전환** = 본부(마을) 씬 ↔ 상행(필드) 씬 간 전환. GameManager 관할.
- **정비창/방향성 지시 호출**은 씬 전환이 아니라 현재 씬 내 UI 오버레이. UIManager 관할이며, 실제 배치·진형 데이터는 BattleManager 하위 컴포넌트가 소유한다.

## 3. SOLID 원칙 적용 규칙

| 원칙 | 적용 방식 |
|---|---|
| **SRP** | 매니저 = 조율만. 실제 규칙 연산은 하위 컴포넌트/개체 컴포넌트가 전담. |
| **OCP** | 확장 지점(인카운터 종류, AI 행동, 전투 판정 규칙 등)은 전략 패턴/인터페이스로 개방. 신규 종류 추가 시 매니저 코드 수정 불필요. |
| **LSP** | 하위 컴포넌트 인터페이스의 모든 구현체는 계약을 어기지 않고 상호 치환 가능해야 함. |
| **ISP** | 매니저 간 노출 인터페이스는 필요한 기능만 좁게 분리 (예: 명령 수신용과 결과 조회용 인터페이스를 별도로 분리). |
| **DIP** | 매니저는 다른 매니저의 구현체가 아닌 인터페이스에 의존. 정적 싱글톤(`XManager.Instance`) 직접 참조 금지. |

## 4. 의존성 주입(DI) 구조

수동 DI 방식을 채택한다. 외부 DI 프레임워크(VContainer, Zenject 등) 없이 전용 매니저(DependencyManager)가 결선을 담당한다.

### 4.1 공통 인터페이스

```
IDependencyRegistrar   (DependencyManager가 구현 — 등록 전용)
    - void Register<T>(T instance) where T : class

IDependencyResolver    (DependencyManager가 구현 — 조회 전용)
    - T Resolve<T>() where T : class                        // 필수 조회, 미등록 시 예외(fail-fast)
    - bool TryResolve<T>(out T instance) where T : class    // 선택 조회, 미등록이어도 예외 없이 false

IManagedComponent   (모든 매니저가 구현 — DependencyManager 자신 포함)
    - void RegisterSelf(IDependencyRegistrar registrar)        // 1단계: 자신이 제공하는 인터페이스 등록
    - void ResolveDependencies(IDependencyResolver resolver)   // 2단계: 자신이 필요로 하는 인터페이스 조회
```

**갱신(2026-09-20, 리팩토링 A.1)**: 초기 설계에서는 `IDependencyRegistrar` 하나에 등록/조회가 함께 있었다. 등록 단계 콜백에서 조회하거나 조회 단계 콜백에서 등록하는 규약 위반을 타입이 막지 못하고, 조회만 하는 소비자(콘텐츠 씬 UI 배선, 배틀 테스트 컨트롤러)가 쓰기 권한까지 갖는 ISP 위반이었다. 두 인터페이스로 분리해 각 단계 콜백이 자기 단계에 맞는 쪽만 받게 했다(상속 없이 완전 분리). 이 문서 이후의 다른 설계 문서에 남아 있는 `ResolveDependencies(IDependencyRegistrar registrar)` 예시 코드는 작성 당시 스냅샷이며 현재 시그니처는 위와 같다. 상세: `Docs/Refactor/2026-09-08_공통.md` §8.

### 4.2 초기화 2단계 플로우

Unity의 `Awake`/`Start` 실행 순서는 보장되지 않으므로, 등록과 조회를 분리한 2단계 초기화로 순서 문제를 회피한다.

1. **등록 단계**: DependencyManager가 관리 대상 매니저 목록(인스펙터에서 명시적으로 할당, 암묵적 탐색 금지)을 순회하며 각 매니저의 `RegisterSelf(this)` 호출. 각 매니저는 이 시점에 자신이 제공하는 인터페이스만 등록.
2. **조회 단계**: 전체 등록 완료 후, DependencyManager가 각 매니저의 `ResolveDependencies(this)` 호출. 각 매니저는 이 시점에 필요한 인터페이스만 `registrar.Resolve<T>()`로 조회해 내부 필드에 보관.

### 4.3 매니저별 인터페이스 예시 (시그니처는 후속 조정 가능)

```
IGameManager          : 씬 전환 요청, 세션 시작/종료 판정
IInputManager          : 입력 컨텍스트 전환, 입력 이벤트 구독
IUIManager             : UI Open/Close 요청, UI 상태 이벤트
IBattleController      : StartBattle(context), 진형/전술 데이터 전달
IBattleResultSource     : OnBattleEnded 이벤트 (승패 결과)
IAIManager             : Register/Unregister(IAIControllable)
IEncounterManager       : 인카운터 체크 트리거, OnEncounterTriggered 이벤트
```

### 4.4 통신 방식 구분

- **명령(요청-응답)**: 인터페이스 직접 호출. 예(수정, 2026-08-25): `IBattleController.StartBattle()`은
  `EncounterManager`가 아니라 `FieldEncounterFlowCoordinator`가 인카운터 경고·전투 뷰 전환이 끝난
  시점에 호출한다 - `EncounterManager`가 인카운터 발생과 동시에 호출하면 전투 뷰에 들어가기도 전에
  결과가 나와버리는 문제가 있었다([[04-2026-08-25-Field씬_아키텍처]] §4, Docs/제작/02-2026-08-25-인카운터_전투전환_구현.md 참고).
- **상태 통지(브로드캐스트)**: 이벤트 기반(C# event 또는 이벤트 채널). 예: 전투 종료 → `IBattleResultSource.OnBattleEnded` 구독자(GameManager, UIManager)에게 통지.

명령 방향과 통지 방향을 분리해 순환 의존(A→B, B→A 동시 직접 참조)을 방지한다.

## 5. 하위 컴포넌트 구조

하위 컴포넌트는 두 종류로 구분한다.

- **(A) 매니저 산하 컴포넌트**: 매니저가 소유·조합하는 정적 구성요소.
- **(B) 개체(엔티티) 컴포넌트**: 유닛 등 개별 게임 오브젝트가 소유, 매니저에 동적으로 등록.

### 5.1 공통 결합 규칙

- **형제 컴포넌트 간 직접 참조 금지**: 같은 매니저 산하 컴포넌트끼리(예: FormationComponent ↔ MoraleComponent)는 서로를 직접 참조하지 않는다. 상태 전달이 필요하면 부모 매니저가 값을 읽어 다른 컴포넌트에 파라미터로 전달한다.
- **매니저 산하 컴포넌트는 전역 DependencyManager에 등록하지 않는다**: 전역 등록 대상은 매니저(7개)뿐이다. 하위 컴포넌트를 외부에 공개해야 할 경우, 매니저가 자신의 등록 인터페이스를 통해 필요한 최소 데이터만 노출한다(캡슐화).
- **개체 컴포넌트는 매니저별 로컬 registry에 자진 등록**: 전역 DI와는 별개로, 각 매니저가 `Register(T entity)/Unregister(T entity)`를 노출하고 개체가 스폰/디스폰 시점에 스스로 호출한다. 매니저는 씬을 탐색하지 않는다.

### 5.2 매니저별 하위 컴포넌트

**BattleManager**

| 컴포넌트 | 인터페이스 | 비고 |
|---|---|---|
| FormationComponent | `IFormationProvider` | 정비창 배치 데이터·진형 상태 |
| TacticsComponent | `ITacticsProvider` | 방향성 지시 데이터·적응 상태 |
| MoraleComponent | `IMoraleSystem` | 사기 수치, 도주 판정 트리거 |
| BattleResultEvaluator | `IBattleResultRule` | 승패 판정 규칙 (OCP 확장점) |

**EncounterManager**

| 컴포넌트 | 인터페이스 | 비고 |
|---|---|---|
| RandomEncounterRule, FixedEncounterRule | `IEncounterRule` | 전략 패턴 — 신규 인카운터 유형은 구현체 추가만으로 확장 |
| EncounterDataProvider | `IEncounterDataSource` | 인카운터별 스폰 데이터 조회 |

**AIManager**

| 컴포넌트 | 인터페이스 | 비고 |
|---|---|---|
| (개체 컴포넌트) UnitAIBehavior | `IAIControllable` | 유닛 개체 소유, AIManager에 Register/Unregister |
| AIProfileComponent | `IAIProfile` | 난이도/파라미터 등 전역 AI 설정값 관리 |

### 5.2.1 실제 구현 반영 사항 (2026-09-01, 코드 기준 재확인)

위 표는 초기 설계 시점의 예정 구조다. 실제 전투 AI/사기/판정 시스템이 구현되며 상당 부분이 이 틀을 벗어났다 — 표는 역사적 기록으로 남기고, 실제 상태를 여기 정리한다.

- **TacticsComponent(`ITacticsProvider`, BattleManager 산하)는 실현되지 않았다.** 방향성 지시는 대신 `Core/Battle/Tactics/`의 독립 서브시스템(타겟 선택/추적 정책/포지셔닝/자기보호 등 전략 인터페이스 다수 + `TacticsPanel`/`ITacticsRepository`)으로 구현됐고, `BattleManager`를 거치지 않고 `BattleCharacterUnit` 생성 시점에 직접 주입된다. "매니저 산하 컴포넌트"라는 원래 틀 자체가 이 서브시스템에는 적용되지 않았다.
- **MoraleComponent(`IMoraleSystem`)도 마찬가지다.** `Core/Battle/Morale/`(`PartyMorale`, `MoraleWaveCoordinator` 등)로 구현됐지만 BattleManager 산하 컴포넌트가 아니라 `BattleCharacterUnit`에 직접 주입되고, 파동 전파는 시뮬레이션 레벨 코디네이터가 담당한다.
- **BattleResultEvaluator(`IBattleResultRule`)는 2026-08-26 리팩토링에서 삭제됐다**(`Docs/Refactor/2026-08-26-Field.md` 참고) — 불필요한 중간 계층으로 판단됨. 지금은 `BattleManager`(`Core/Battle/BattleManager.cs`)가 `IBattleResultRule` 구현체를 `GetComponent`로 직접 보유하고 `StartBattle()`에서 바로 위임한다. "컴포넌트"라는 별도 존재가 아니라 매니저 자신의 필드다.
- **AIManager 산하(UnitAIBehavior/AIProfileComponent)는 미착수 스켈레톤이다.** `AIManager.cs`는 `Register`/`Unregister` 리스트만 가진 빈 뼈대이고 `ResolveDependencies`에 "TODO: AIProfileComponent 연결 - 하위 컴포넌트 설계 후 구현" 주석이 그대로 남아있다. 실제 전투 AI는 이 매니저를 전혀 거치지 않고 위 Tactics 서브시스템이 직접 처리한다 — 죽은 코드는 아니고, 정식 설계의 일부로 의도적으로 남겨진 미완성 골격이다.
- **EncounterManager 산하**: `RandomEncounterRule`만 구현됐다. `FixedEncounterRule`은 여전히 미착수(기획 단계부터 알려진 미정 사항과 일치).

**UIManager**

| 컴포넌트 | 인터페이스 | 비고 |
|---|---|---|
| FormationPanel, TacticsPanel, HUDPanel, ResultPanel 등 | `IUIPanel` (Open/Close/Bind) | 패널 단위 분리, 신규 패널은 인터페이스 구현만으로 추가 |

**InputManager**

| 컴포넌트 | 인터페이스 | 비고 |
|---|---|---|
| FieldInputHandler, FormationInputHandler, BattleInputHandler 등 | `IInputContextHandler` | 컨텍스트별 전략, InputManager는 라우팅만 |

**GameManager**

| 컴포넌트 | 인터페이스 | 비고 |
|---|---|---|
| SceneLoader | `ISceneLoader` | 실제 씬 로드/언로드 실행 |
| SessionStateTracker | `ISessionState` | 현재 상행 진행 상태(위치/진행도) 보관 |

**DependencyManager**: 하위 컴포넌트 없음(등록/조회 중개 로직만 자체 보유).

### 5.3 개체 컴포넌트 예시 (용병 유닛)

용병 유닛은 여러 컴포넌트의 조합으로 구성되며, 각각 필요한 매니저에만 등록한다.

- `UnitAIBehavior` (`IAIControllable`) → AIManager에 등록
- `UnitBattleParticipant` (`IBattleParticipant`) → 전투 시작 시 BattleManager에 등록, 종료 시 해제

유닛 자체의 스탯/체력 등 개체 도메인 상세는 이번 설계 범위(매니징 오브젝트) 밖이며 별도 세션에서 다룬다.

## 6. 남은 이슈 / 후속 결정 사항

- 각 인터페이스의 정확한 메서드 시그니처는 구현(제작) 단계에서 확정.
- DependencyManager의 씬 전환 간 생존 범위(영속 여부)는 구현 세부사항으로 후속 결정.
- 정비창/방향성 지시 데이터를 BattleManager 산하에 둔 것에 대한 재검토 여지는 있으나 현재는 확정 상태로 유지.
