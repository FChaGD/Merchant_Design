## 1. 개요

[[02-2026-08-23-상행준비UI]] 기획을 구현하기 위해 추가/변경한 구조. 기존 배치(Formation) UI 아키텍처(Bootstrap 씬의 로직 컴포넌트 + Hub 씬 `SceneUIRoot`/`UIElementMarker` 기반 뷰 바인딩)를 그대로 따르고, 두 화면(상행 준비 UI ↔ 배치 UI) 간 왕복 전환을 위해 `UIManager`에 네비게이션 정책을 추가했다.

## 3. 화면 전환 — `PanelNavigationStack`

기존 `UIManager.Open`/`Close`는 단순히 패널을 찾아 `Open()`/`Close()`를 호출하는 것이 전부였다. 상행 준비 UI에서 배치 UI를 열었다가 되돌아오는 흐름을 지원하기 위해, "이전에 활성화돼 있던 패널을 기억했다가 닫힐 때 복귀시키는" 정책을 `PanelNavigationStack`이라는 별도 객체로 분리했다(SRP — `UIManager`는 패널 조회/등록만, 네비게이션 정책은 이 클래스만 담당).

```csharp
internal class PanelNavigationStack
{
    public string BeginOpen(string panelId);           // 숨겨야 할 이전 패널 id 반환 (없으면 null)
    public string ResolveReturnTarget(string closedId); // 복귀할 패널 id 반환 (없으면 null)
}
```

`Dictionary<string,string>` 한 칸짜리 매핑이지만, 매 `Open` 호출 시점의 "현재 활성 패널"만 기록하는 구조라 임의 깊이의 왕복(A→B→C→…)에도 그대로 대응한다.

**중요한 규칙**: 각 `IUIPanel.Close()`는 "숨기기"만 한다. 복귀 여부 판단은 반드시 `UIManager.Close(PanelId)`를 거쳐야 한다 — 패널이 자기 `Close()`를 직접 호출하면(예: 버튼 핸들러에서) 복귀 로직이 누락된다. `FormationPanel.cs`/`TripPanel.cs`의 `Close()` 위 주석 참고.

## 4. 인터페이스 분리 — `IFormationReader`

상행 준비 UI의 "현재 편성 요약"은 `FormationLayout`을 읽기만 하면 되는데, 기존 `IFormationRepository`에는 `Apply`(쓰기)까지 포함돼 있었다. `TripPanel`이 쓰기 권한까지 갖는 것은 ISP 위반이라 판단해 읽기 전용 `IFormationReader`를 추출했다.

```csharp
public interface IFormationReader { bool TryLoadCurrent(out FormationLayout layout); }
public interface IFormationRepository : IFormationReader { void Apply(FormationLayout layout); }
```

`TripPanel`은 `IFormationReader`만 의존한다.

---

## 5. Editor 인스톨러 공용화 — `EditorUIBuilder`

`TripUIInstaller`를 만들 때 처음에는 `FormationUIInstaller`의 private 헬퍼(`GetOrCreateUIObject`, `EnsureImage` 등)를 `internal`로 열어 재사용했으나, 이는 두 기능이 서로의 구현 세부사항에 결합되는 잘못된 방향이었다(리뷰 후 수정). 저수준 씬 조립 헬퍼를 `EditorUIBuilder`(공용 `internal static` 유틸리티)로 추출해, `FormationUIInstaller`/`TripUIInstaller` 둘 다 이 공용 협력자에만 의존하도록 정리했다.

---

## 6. SOLID 적용 요약

| 원칙 | 적용 사례 |
|---|---|
| SRP | `UIManager`(등록/조회) ↔ `PanelNavigationStack`(네비게이션 정책) 분리 |
| ISP | `IFormationRepository` → `IFormationReader`(읽기 전용) 추출 |
| DIP | `TripPanel`은 `IUIManager`/`IGameManager`/`IFormationReader`/`ITripInfoProvider` 등 추상화에만 의존 |
| 결합 방향 | `FormationUIInstaller`/`TripUIInstaller`가 서로가 아니라 `EditorUIBuilder`(공용 협력자)에 의존 |

---

## 7. 씬 배치

- `TripPanel`(로직): Bootstrap 씬, `UIManager`와 같은 GameObject (`FormationPanel`과 동일 패턴).
- 상행 준비 UI 시각 요소: Hub 씬의 `SceneUIRoot` 하위, `TripUIElementIds` 상수로 마킹.
- `PlaceholderTripInfoProvider`: 전역 매니저 루트(`Managers`) 하위, `IManagedComponent`로 DI 등록.

---

## 8. 남은 이슈 / 후속 결정 사항

- `ITripInfoProvider`/`ITripLocationInfo`의 실제 구현은 지역 시스템 설계 이후 연결 — 현재는 `Placeholder` 접두사 클래스로만 대체돼 있음 (`[[02-2026-08-23-상행준비UI]]` 7절 참고).
- 상행 준비 UI로 복귀할 때 `TripPanel.Open()`이 매번 전체 재초기화된다 — 출발지/도착지 클릭 상태가 유지되지 않는다. 문제로 드러나면 Open(전체 초기화)과 Show(단순 재활성화)를 분리하는 리팩터 검토.
- 배치 UI 결과가 상행정보 패널의 "위험도/보상" 등에 실제로 영향을 주는 로직은 범위 밖.
