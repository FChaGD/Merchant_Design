## 2. Hub/Field 배치 UI 분리 — 공용 기반 + 정책 분리

### 2.1 현재 구조의 문제

`FormationPanel`(단일 클래스)이 "그리드/팔레트 렌더링+드래그 중계"(공용으로 남을 부분)와 "드롭 시 무엇을 할지"(Hub: 로컬 `currentLayout`에만 기록 후 Apply 버튼으로 일괄 반영, Field: 즉시 반영+타이머 시작)를 한 몸에 갖고 있다. 이 두 정책이 근본적으로 다르므로(사용자 확정) 분리한다.

### 2.2 분리 방식 — 합성으로 공용 로직 추출, 정책은 인터페이스로 주입

**공용 부분을 새 내부 클래스 `FormationGridEditor`로 추출**한다(기존 `FormationDragCoordinator`처럼 `internal`, MonoBehaviour 아닌 순수 C# 협력 객체). 현재 `FormationPanel`의 다음 부분을 그대로 옮긴다 — 로직 자체는 무변경, 소속만 이동:
- `TryBind`(PanelRoot/PaletteRoot/GridRoot/InfoPanelRoot/CloseButton 조회, `#if UNITY_EDITOR` 디버그 패널 포함)
- `BuildCategorySummaries`/`CollectPlacedIds`/`FindAvailableUnit`(팔레트 잔여수 계산)
- `RefreshSlot`/`RefreshAllSlots`/`RefreshPalette`
- `FormationDragCoordinator` 소유 및 `HandleGridIconBeginDrag`/`HandleIconDrag`/`HandlePaletteRowBeginDrag`/`HandlePaletteRowClicked` 중계

**드롭/이동/제거 시 실제로 어떤 데이터를 바꿀지는 새 인터페이스로 뽑는다**(Hub/Field가 갈리는 지점, ISP):

```csharp
namespace Game.Core
{
    /// <summary>
    /// FormationGridEditor가 드롭/드래그/제거 이벤트를 감지한 뒤 "실제로 무엇을 반영할지"를
    /// 위임하는 정책 인터페이스 - Hub(로컬 편집+Apply 버튼)와 Field(즉시 반영+배치 시간)가 이
    /// 인터페이스의 구현체만 다르다(Docs/기획/시스템/20번 §3.1).
    /// </summary>
    internal interface IFormationEditingHandler
    {
        // 팔레트에서 빈/점유 슬롯으로 드롭(신규 배치 시도).
        void HandlePaletteDrop(IFormationUnit unit, int targetSlotIndex);
        // 그리드 내 슬롯→슬롯 이동(드래그).
        void HandleGridMove(string unitId, int originSlotIndex, int targetSlotIndex);
        // 그리드 밖으로 드래그해 배치 취소, 혹은 명시적 제거 버튼(§3.4).
        void HandleRemove(string unitId, int slotIndex);
        // FormationGridEditor가 렌더링에 쓸 "현재 실제 반영 상태" 스냅샷을 요청한다 - Hub는
        // 로컬 편집 중인 사본을, Field는 IFormationRepository의 현재 값을 그대로 돌려준다.
        FormationLayout GetDisplayLayout();
    }
}
```

`FormationGridEditor`는 매 프레임/이벤트마다 `handler.GetDisplayLayout()`을 읽어 그리는 것이 아니라, `Open()`/명시적 `RequestRefresh()` 호출 시점에만 다시 읽는다(기존 `RefreshAllSlots` 호출 시점과 동일한 빈도 — Field는 §3의 저장소가 상태를 바꿀 때마다 `RequestRefresh()`를 불러주면 된다).

### 2.3 두 구체 패널

- **`HubFormationPanel`**(기존 `FormationPanel`을 이 이름으로 좁힘): `IFormationEditingHandler`를 자기 자신이 구현 — `HandlePaletteDrop`/`HandleGridMove`/`HandleRemove`가 전부 로컬 `FormationLayout` 사본만 수정(기존 `HandleSlotDropped`/`HandleIconEndDrag` 로직 그대로), `Apply` 버튼 클릭 시에만 `IFormationRepository.Apply(...)` 호출. 기존 동작과 **완전히 동일**(회귀 없음).
- **`FieldFormationPanel`**(신규): `IFormationEditingHandler`를 구현하되, `HandlePaletteDrop`/`HandleGridMove`/`HandleRemove`가 §3의 `IFieldFormationActivityRepository`에 액션을 등록하고, `GetDisplayLayout()`은 `IFormationRepository.TryLoadCurrent(...)`(현재 실제 반영된 값)를 그대로 돌려준다. Apply 버튼 자체가 없다(화면 요소 인스톨러에서 제외).

두 패널 다 `PanelId => UIPanelIds.Formation`을 그대로 쓴다(`UIPanelIds` 변경 없음) — Hub/Field는 서로 다른 콘텐츠 씬이라 동시에 로드되지 않으므로, `HubUIWiring`이 `HubFormationPanel`을, `FieldUIWiring`이 `FieldFormationPanel`을 각자 `panelRegistrar.RegisterPanel(...)`하면 `UIManager`의 `panelsById["Formation"]`에는 현재 로드된 씬의 패널만 들어있다(기존 "재바인딩" 패턴과 동일한 원리, `UIManager`/`PanelRegistrar` 자체는 무변경).

### 2.4 이 설계가 건드리지 않는 것

`FormationGridView`, `FormationSlotView`(§5의 오버레이 추가 제외), `FormationUnitIconView`, `FormationPaletteView`, `FormationInfoPanelView`, `FormationDragCoordinator`, `FormationLayout`, `IFormationRepository`/`InMemoryFormationRepository`(Hub의 Apply 대상, 무변경), `FormationCategoryKey`/`FormationCategorySummary` — 전부 기존 그대로 재사용.

## 3. Field 배치 활동 저장소 — 백그라운드 틱

### 3.1 데이터 모델

```csharp
namespace Game.Core
{
    public enum FormationActivityKind { Adding, Moving }

    /// <summary>
    /// Field에서 진행 중인 배치/이동 행동 하나. Adding은 OriginSlotIndex/PathSlotIndices가
    /// 의미 없다(-1/빈 리스트). RequiredSeconds는 Adding=소요시간 그대로, Moving=경로 길이/이동
    /// 속도로 환산한 값 - 두 종류를 같은 ElapsedSeconds/RequiredSeconds 진행률로 다뤄 §3.3의
    /// 일시정지/재개/강제완료 로직을 하나로 공유한다(Docs/기획/시스템/20번 §3.2/§3.3 대칭 구조).
    /// </summary>
    public sealed class FormationActivity
    {
        public string UnitId { get; }
        public FormationActivityKind Kind { get; }
        public int TargetSlotIndex { get; }
        public int OriginSlotIndex { get; } // Adding = -1
        public IReadOnlyList<int> PathSlotIndices { get; } // Adding = 빈 리스트, §4 참고
        public float RequiredSeconds { get; }
        public float ElapsedSeconds { get; internal set; }
        public bool IsPaused { get; internal set; }

        public float Progress01 => RequiredSeconds <= 0f ? 1f : Mathf.Clamp01(ElapsedSeconds / RequiredSeconds);

        internal FormationActivity(string unitId, FormationActivityKind kind, int targetSlotIndex, int originSlotIndex, IReadOnlyList<int> pathSlotIndices, float requiredSeconds)
        {
            UnitId = unitId; Kind = kind; TargetSlotIndex = targetSlotIndex; OriginSlotIndex = originSlotIndex;
            PathSlotIndices = pathSlotIndices; RequiredSeconds = requiredSeconds;
        }
    }
}
```

`InMemoryFieldFormationActivityRepository : MonoBehaviour, IFieldFormationActivityRepository, IManagedComponent` — `InMemoryFormationRepository`와 같은 성격의 Bootstrap 상주 저장소. `ManagerHierarchyInstaller.managedComponents`에 등록해 항상 살아있게 한다(Field UI 패널이 닫혀 있어도 `Update()`가 계속 돈다 — 기획 20번 §1 전제 2).

```csharp
private readonly List<FormationActivity> activities = new();
private IFormationRepository formationRepository; // ResolveDependencies에서 TryResolve

public void ResolveDependencies(IDependencyRegistrar registrar)
{
    registrar.TryResolve<IFormationRepository>(out formationRepository);
}

private void Update()
{
    // 역순 순회 - 완료된 항목을 즉시 리스트에서 제거해도 다음 인덱스가 안 밀린다.
    for (var i = activities.Count - 1; i >= 0; i--)
    {
        var activity = activities[i];
        if (activity.IsPaused) continue;

        activity.ElapsedSeconds += Time.deltaTime;
        if (activity.ElapsedSeconds >= activity.RequiredSeconds)
        {
            Complete(activity);
        }
    }
}

private void Complete(FormationActivity activity)
{
    activities.Remove(activity);
    ApplyToLayout(activity);
    OnActivityCompleted?.Invoke(activity);
}

// Adding: 대상 슬롯에 기록. Moving: 출발 슬롯을 비우고 대상 슬롯에 기록 - 실제 FormationLayout은
// 이동 도중 내내 "출발 슬롯에 그대로 있음"으로 취급된다(§2.2 GetDisplayLayout이 돌려주는 값과
// 일치, §5의 유령 표시는 별도 오버레이일 뿐 진짜 배치 데이터가 아니다).
private void ApplyToLayout(FormationActivity activity)
{
    if (formationRepository == null || !formationRepository.TryLoadCurrent(out var layout)) return;

    if (activity.Kind == FormationActivityKind.Moving)
    {
        layout.Clear(activity.OriginSlotIndex);
    }
    layout.SetUnitId(activity.TargetSlotIndex, activity.UnitId);
    formationRepository.Apply(layout); // 이미 참조로 들고 있던 인스턴스를 그대로 재적용 - 값 갱신 알림 목적
}
```

`ForceCompleteAll()`은 `activities`를 스냅샷 복사해 순회하며 각각 `Complete(activity)`(진행률 무시, 즉시 완료 처리) — 기획 20번 §3.2/§3.3의 "패배(도주 제외) 시 그 즉시 완료 처리"와 정확히 대응한다.

## 4. 그리드 회피 경로 탐색

정비창 그리드가 이미 `columnCount × rowCount`의 정수 좌표계이므로, 그 위에서 표준 **너비 우선 탐색(BFS)**로 충분하다(그리드가 최대 8×2 수준이라 A*의 이점이 없다 — 단순한 쪽을 선택, CLAUDE.md "새 추상화 전 기존 확장 우선").

```csharp
internal static class FormationPathFinder
{
    // blocked: 점유된 슬롯 판정 - FormationLayout에 실제 기록된 슬롯 + IFieldFormationActivityRepository의
    // 모든 TargetSlotIndex(§3.3) 합집합. origin/target 자신은 blocked여도 항상 통과 가능한 것으로 본다
    // (출발점=자기 자신이 비우는 중인 슬롯, 도착점=이 이동이 예약한 슬롯이므로).
    public static IReadOnlyList<int> FindPath(int origin, int target, int columnCount, int rowCount, IReadOnlySet<int> blocked)
    {
        if (origin == target) return new[] { origin };

        var queue = new Queue<int>();
        var cameFrom = new Dictionary<int, int>();
        queue.Enqueue(origin);
        cameFrom[origin] = origin;

        while (queue.Count > 0)
        {
            var current = queue.Dequeue();
            if (current == target) return ReconstructPath(cameFrom, origin, target);

            foreach (var next in GetNeighbors(current, columnCount, rowCount))
            {
                if (cameFrom.ContainsKey(next)) continue;
                if (next != target && blocked.Contains(next)) continue; // target은 항상 통과 허용
                cameFrom[next] = current;
                queue.Enqueue(next);
            }
        }

        // 경로가 없으면(사방이 막힘) 직선(2점) 폴백 - 시각적으로 다른 유닛과 겹쳐 보일 수 있으나
        // 배치 자체를 막지는 않는다(사용자 확정 전까지 잠정 처리, §9 제작 체크리스트 참고).
        return new[] { origin, target };
    }

    private static IEnumerable<int> GetNeighbors(int index, int columnCount, int rowCount)
    {
        var col = index % columnCount;
        var row = index / columnCount;
        if (col > 0) yield return index - 1;
        if (col < columnCount - 1) yield return index + 1;
        if (row > 0) yield return index - columnCount;
        if (row < rowCount - 1) yield return index + columnCount;
    }

    private static IReadOnlyList<int> ReconstructPath(Dictionary<int, int> cameFrom, int origin, int target)
    {
        var path = new List<int> { target };
        var current = target;
        while (current != origin)
        {
            current = cameFrom[current];
            path.Add(current);
        }
        path.Reverse();
        return path;
    }
}
```

`FieldFormationPanel.HandleGridMove`가 도착지 드래그가 바뀔 때마다(기획 20번 §3.3 "도착지가 결정될 때마다 경로를 다시 긋는다") 이 탐색을 다시 호출한다 — 그리드가 작아 매 프레임 재계산해도 비용이 미미하다.

## 5. 시각 표현 — 반투명 오버레이 + 타이머 텍스트 + 경로선

### 5.1 슬롯 오버레이 — `FormationSlotView` 확장

```csharp
// FormationSlotView에 추가
[SerializeField] private FormationActivityOverlayView activityOverlay; // 반투명 아이콘 + 잔여시간 텍스트, 기본 비활성

public void SetActivity(FormationActivity activity, IFormationUnit unit)
{
    if (activityOverlay == null) return;
    if (activity == null) { activityOverlay.gameObject.SetActive(false); return; }

    activityOverlay.gameObject.SetActive(true);
    activityOverlay.Bind(unit?.Icon, remainingSeconds: activity.RequiredSeconds - activity.ElapsedSeconds);
}
```

`FormationActivityOverlayView`(신규, `Core/UI/Formation/`) - `Image`(반투명, alpha 낮춘 유닛 아이콘) + `TMP_Text`(잔여 초) 2개 자식만 갖는 단순 뷰. `FieldFormationPanel`이 매 프레임(Field 패널이 열려 있을 때만 - §2.2의 `RequestRefresh` 빈도 그대로) `IFieldFormationActivityRepository.ActiveActivities`를 순회해 해당 슬롯(Adding: `TargetSlotIndex` 1곳, Moving: `OriginSlotIndex`+`TargetSlotIndex` 2곳 모두)에 `SetActivity(...)`를 호출한다.

### 5.2 경로선 — 신규 `FormationPathLineView`

`Core/UI/Formation/FormationPathLineView.cs`(신규) - `RectTransform` 여러 개를 웨이포인트 슬롯 중심 좌표 사이에 얇은 `Image`로 이어 붙이는 단순 폴리라인(그리드가 Screen Space Canvas라 `LineRenderer`가 아니라 UI `Image` 스트레치 방식을 쓴다 - `FormationGridView`가 이미 UGUI 기반이므로 좌표계를 맞추기 쉽다). get-or-create로 세그먼트 개수만큼 재사용(CLAUDE.md 최적화 규칙). `FieldFormationPanel`이 이동 활동 하나당 이 뷰 하나를 붙였다 뗀다.

### 5.3 이 설계가 건드리지 않는 것

Field 필드 월드 공간(이동/전투 뷰) 자체는 무변경 — §5의 모든 시각 요소는 정비창 UI(Screen Space Canvas) 안에서만 존재한다(기획 20번 §1 전제 2).

### 6.3 전투 중 신규 소환 유령의 전장 표시 (기획 20번 §9, 사용자 확정 2026-09-05 - 실전 검증 중 범위 추가)

전투가 이미 시작된 상태에서는 정비창 UI를 열 수 없어(전투 뷰로 전환됨) §5의 오버레이를 볼 수 없다 — 그 공백을 메우기 위해 진행 중인 Adding 활동을 전장(`BattleWorldRoot`)에도 반투명 유령으로 표시한다. 정비창 UI 오버레이(§5)와 별개의 표시 채널이다.

**데이터**: `PendingReinforcementInfo`(신규, `Core/Battle/Simulation/`) - `{ UnitId, Position, RemainingSeconds }`. `IBattleSimulationEvents`에 `event Action<IReadOnlyList<PendingReinforcementInfo>> OnPendingReinforcementsChanged` 추가, `BattleManager`가 그대로 흘려보낸다.

**발행**: `LiveBattleSimulationRule.Update()`가 `simulation.Tick(...)` 직후 매 틱 `NotifyPendingReinforcements()`를 호출 - `fieldActivityRepository.ActiveActivities` 중 `FormationActivityKind.Adding`이면서 로스터 상 `FormationUnitKind.Character`인 것만(마차/시설은 전투 중 합류 자체를 지원하지 않음, §6.1) 목표 슬롯의 전장 좌표로 환산해 통째로 넘긴다. `Report()`(전투 종료) 시점에 빈 목록을 한 번 더 발행해 유령이 화면에 남지 않게 한다.

**표시**: `BattlePendingReinforcementView`(신규, `Core/UI/Field/Battle/`) - `SpriteRenderer`(반투명 아군색 사각형, `BattlePlaceholderSprite.WhiteSquare` 재사용) + 자식 `TextMeshPro`(월드 스페이스, 잔여 초). `BattleViewPresenter`가 `OnPendingReinforcementsChanged`를 구독해 get-or-create 풀로 관리(`activeReinforcementViews`) - 개수가 줄면 숨기기만 하고 파괴하지 않는다. `Present()`(다음 전투 시작)와 `Report()`(이번 전투 종료) 양쪽에서 `Clear()`/빈 목록 발행으로 정리된다.

**한 프레임 겹침 허용**: 활동이 완료되는 프레임에 `InMemoryFieldFormationActivityRepository.Update()`와 `LiveBattleSimulationRule.Update()`의 실행 순서가 보장되지 않아, 유령과 실제 캐릭터 뷰가 한 프레임 겹쳐 보일 수 있다 - Script Execution Order를 강제하지 않고 허용한다(사용자 확인 필요 시 재검토, 체감상 무시할 수준으로 판단).

## 7. 임의 연속 좌표 스폰 (이동 중단)

새 인터페이스나 좌표계 확장이 필요 없다 — `BattleFieldLayout.ComputeAllyPosition(column, row, columnCount)`는 이미 순수 함수라, 출발 슬롯과 도착 슬롯 각각의 결과를 `Vector2.Lerp`로 보간하면 충분하다.

```csharp
// BuildSingleAlly 내부, position 계산 부분만 교체
Vector2 position;
if (fieldActivityRepository != null && fieldActivityRepository.TryGetActivity(unitId, out var activity)
    && activity.Kind == FormationActivityKind.Moving)
{
    var originPos = ComputeSlotPosition(activity.OriginSlotIndex, layout.ColumnCount);
    var targetPos = ComputeSlotPosition(activity.TargetSlotIndex, layout.ColumnCount);
    position = Vector2.Lerp(originPos, targetPos, activity.Progress01);
}
else
{
    position = ComputeSlotPosition(slotIndex, layout.ColumnCount); // 기존 로직
}
```

정비창 UI에서 그리는 경로(§4의 그리드 회피 경로)는 화면 표시 전용이고, 실제 전장 스폰 좌표는 이 직선 보간만으로 충분하다 — 회피 경로의 굴곡을 전장 좌표에도 그대로 재현할 필요는 없다(사용자에게 노출되지 않는 순수 계산값이라 시각적 일치가 요구되지 않음, `MoraleWaveCoordinator`가 화면에 안 보이는 순수 판정용 개념인 것과 같은 종류의 단순화).

{

    {
        case BattleOutcome.Victory:
            fieldActivityRepository?.ResumeAll(); // 신규 - Moving까지 포함해 전부 재개

            break;
        case BattleOutcome.Defeat:

            break;
    }
}

private void ShowDefeatConsequence(DefeatConsequence consequence)
{
    switch (consequence)
    {
        case DefeatConsequence.Death:
            fieldActivityRepository?.ForceCompleteAll(); // 무의미하지만(곧 Application.Quit) 일관성 위해 호출
            resultPopupView.Show("패배 - 전멸", "플레이 종료", onConfirm: Application.Quit);
            break;
        case DefeatConsequence.Flee:
            fieldActivityRepository?.ResumeAll(); // 신규 - 승리와 동일(기획 20번 §3.2/§3.3 확정)
            resultPopupView.Show("패배 - 도주", "상행 속행", onConfirm: () =>
                cameraController.TransitionToMovement(onComplete: sessionState.Resume));
            break;
        case DefeatConsequence.Rout:
            fieldActivityRepository?.ForceCompleteAll(); // 신규 - Hub 귀환 전에 진행 중이던 것 전부 완료 처리
            resultPopupView.Show("패배 - 궤주", "귀환", onConfirm: () =>
                gameManager.RequestSceneTransition(ContentSceneId.Hub));
            break;
        case DefeatConsequence.Captured:
        default:
            fieldActivityRepository?.ForceCompleteAll();
            resultPopupView.Show("패배 - 포로", "플레이 종료", onConfirm: Application.Quit);
            break;
    }
}

## 10. 실전 검증 체크리스트

- Field 정비창에서 캐릭터/마차/시설을 팔레트에서 빈 슬롯으로 드래그 → 반투명 표시+타이머가 뜨고, 시간이 지나면 실제로 배치되는지.
- 배치 진행 중 정비창을 닫았다 다시 열어도 타이머가 계속 흐르고 있었는지(백그라운드 진행 확인).
- 배치 진행 중 인카운터 발생 → 타이머 정지, 전투 시작 시 재개, 타이머가 전투 중 0에 도달하면 그 즉시 전장에 유닛이 나타나는지.
- 이미 배치된 유닛을 다른 슬롯으로 드래그 → 실시간 이동 애니메이션, 도착지 드래그로 재조정, 경로가 다른 유닛 슬롯을 피해 그려지는지.
- 이동 도중 인카운터 발생 → 이동이 멈추고 그 중간 위치에서 전투가 시작되는지.
- 승리 또는 패배+도주로 전투 종료 → 배치는 타이머 재개, 이동은 중단 지점부터 애니메이션이 이어지는지.
- 패배(궤주/포로/사망)로 전투 종료 → 진행 중이던 배치/이동이 그 즉시 완료 처리되는지(배치=즉시 배치 확정, 이동=도착지로 즉시 스냅).
- 진행 중인 유닛을 제거 시도 → 즉시 취소되고 팔레트에 가용 개체로 다시 나타나는지.
- 마차/시설이 1개만 남았을 때 제거 시도가 막히는지.
- Hub 정비창(기존 Apply 버튼 모델)에 회귀가 없는지.
- (§6.3) 배치 진행 중 인카운터 발생 → 전투가 시작된 뒤, 목표 슬롯의 전장 좌표에 반투명 유령+잔여초가 표시되는지, 타이머가 0에 도달하면 유령이 사라지고 실제 유닛으로 교체되는지, 전투가 끝나면 유령이 화면에 남지 않는지.

이 문서는 제작 착수 전 최종 설계다. 규모가 커서 §9 체크리스트를 여러 세션에 나눠 진행할 가능성이 높다 — 순서는 §3(저장소)→§6/§7(전투 연동)→§2(UI 분리)→§4/§5(시각 요소) 순으로 안쪽(데이터/로직)부터 바깥쪽(UI)으로 가는 것을 권장한다(각 단계마다 컴파일이 되는 상태를 유지하기 쉽다).
