## 1. 목적

기획 106의 공통 체계를 데이터·상태·판정 구조로 만들고, 상인조합 의뢰 수락형을 실제로 동작시킨다. `PlaceholderGuildQuestBoard`를 제거한다.

## 4. 데이터 (`Quest.xlsx`)

열거형 열은 이름 문자열(기존 TownStock·Encounter와 같은 방식). 문자열(제목·의뢰자·설명·목표 표시문)은 기존 문자열 분리 방식대로 `QuestStrings` 시트에 둔다. 임포트 시 참조(도시 Id·아이템 Id·퀘스트 Id·목표 Id·이벤트 Id) 검증, 오류는 예외로 임포트 중단.

| 시트 | 열 |
|---|---|
| `Quest` | `Id`, `Kind`(Main/General), `Repeat`(Once/Repeatable), `Acceptance`(Request/Trigger/Event), `Completion`(Instant/Report), `ReportCityId`(Report일 때 필수), `BoardCityIds`(게시 대도시, 쉼표 구분 — Request일 때 필수), `RequiredQuestId`(선택), `MinReputation`(선택), `RepostDays`(선택 — 반복성: 완료·실패 후 재게시 일수 필수 / 단발성: 실패·포기 후 재게시 일수, 빈칸 = 영구 소멸), `FailReputation`, `FailGold`(0 이상, 빈칸 0), `ReturnCargoOnFail`(true/false), `BonusTiming`(OnSuccess/Immediate) |
| `Objective` | `QuestId`, `ObjectiveId`(퀘스트 안에서 유일), `Role`(Core/Bonus), `Type`(Arrive/Deliver/Deadline/BattleWin/Preserve), `CityId`, `ItemId`, `Count`, `EnemyType`(선택, 적 스탯 테이블 Id), `QuestBattleOnly`(true/false), `DeadlineDays` 또는 `DeadlineDate`(`경과연차-월-일`, 0년 1월 1일 = 0일) |
| `Reward` | `QuestId`, `ObjectiveId`(빈칸 = 성공 보상, 값 = 그 보조 목표 추가 보상), `Type`(Gold/Reputation/Item/Unit), `ItemId`(Item·Unit), `Amount` |
| `Cargo` | `QuestId`, `ItemId`(의뢰 화물 전용 행), `Count` — 수락 시 지급. 행이 없으면 조달형 |
| `Effect` | `QuestId`, `Scope`(Destination/AllTrips), `DifficultyBonus`, `EventId`(선택, Encounter.xlsx Event 행), `EventRepeat`(PerQuest/PerTrip), `EventTiming`(Progress/Random), `ProgressMin`, `ProgressMax`(Progress면 Min만 사용) |
| `FollowUp` | `QuestId`, `NextQuestId`, `Mode`(Board/AutoAccept), `RequiredBonusId`(선택 — 이 보조 목표 달성 시에만) |
| `QuestStrings` | `Id`(퀘스트 Id 또는 `퀘스트Id.목표Id`), `Title`, `Requester`, `Description` |

임포트 검증 규칙:
- 핵심 목표 1개 이상.
- `Deliver`: `CityId`·`ItemId`·`Count` 필수. `Completion=Report`면 `CityId == ReportCityId` **[판단]**(납품 차감이 보고 시점이므로 보고처가 곧 납품처).
- `Arrive`: `CityId` 필수. `Deadline`: 둘 중 하나만. `BattleWin`: `Count` ≥ 1. `Preserve`: 그 퀘스트에 `Cargo` 행 필수.
- `Cargo.ItemId`는 무역품 테이블의 의뢰 화물 행(무역품 테이블에 `QuestCargo` true/false 열 추가 **[판단]**). 의뢰 화물 행은 마을 재고·구매 목록에 넣지 않는다.
- `Kind=Main`은 이번 구현에서 게시 대상 아님(구조만, 임포트는 허용).
- `Effect.Scope=Destination`이면 대상 도시 = 그 퀘스트의 첫 `Arrive`/`Deliver` 목표 도시(없으면 오류) **[판단]**.

의뢰 화물 행은 일반 무역품과 같게 동작한다(적재·피격 손실·버리기). 표시 이름으로 구분된다(데이터 작성 몫).

## 5. 상태 (`QuestManager`)

### 5.1 인스턴스

| 필드 | 내용 |
|---|---|
| `QuestId` | 정의 참조 |
| `State` | Active → Reportable(보고형, 핵심 충족) → 종료(Completed/Failed/Abandoned) |
| `AcceptedDay`, `SourceCityId` | 수락일·수락 조합 |
| `DeadlineDay`(목표별) | 수락 시 확정(`DeadlineDays` → 수락일 + N, `DeadlineDate` → 그 날짜) |
| `ObjectiveProgress` | 목표별 진행 값(전투 횟수 등)·충족 여부·불가 여부 |
| `GivenCargoCount` | 지급한 의뢰 화물 수(보존·납품 불가 판정 기준) |
| `BonusPaid` | 즉시 지급형 보조 보상 지급 여부(중복 방지) |
| `EventFiredThisQuest`, `EventFiredThisTrip`, `EventTriggerProgress` | §9 |

동시 수락 무제한. 같은 퀘스트 Id는 한 번에 하나만 진행.

### 5.2 게시 상태

| 필드 | 내용 |
|---|---|
| `CompletedOnce` | 단발성 성공 이력(이후 게시 안 함), 선행 조건 판정 |
| `RepostDay`(퀘스트별) | 이 날짜 이후 다시 게시. 없으면 게시 가능, `Never`면 영구 소멸 |
| `UnlockedByFollowUp` | 후속 Board 방식으로 열린 퀘스트(선행 조건과 별개로 게시 허용) **[판단]** |

게시 판정(마을 M, 오늘 D): `Acceptance=Request` ∧ `Kind=General` ∧ M ∈ `BoardCityIds` ∧ 진행 중 아님 ∧ (단발성이면 미성공) ∧ `RepostDay` 없음 또는 ≤ D ∧ 선행 조건(`RequiredQuestId` 성공 이력 또는 후속 해금) ∧ 평판 ≥ `MinReputation`. 미충족은 목록에 나타나지 않는다(기획 106 §4.1).

### 5.3 저장 대비

저장 시스템이 없어 런타임에만 유지한다. 저장 대상: §5.1 인스턴스 전체, §5.2 게시 상태, 평판 값. 정의는 데이터에서 다시 읽으므로 저장하지 않는다. 저장 시 직렬화 가능한 순수 데이터로만 상태를 두는 것을 이번 구현 규칙으로 한다(Unity 참조·델리게이트를 상태에 두지 않음).

## 6. 판정

### 6.1 신호 → 판정기

`QuestManager`가 아래 신호를 구독해 진행 중 인스턴스마다 해당 유형의 판정기를 부른다. 신호 원천은 모두 Bootstrap 상주이며 등록 타입으로 `TryResolve`한다(없으면 그 유형 판정만 멈추고 경고 1회).

| 유형 | 신호 | 판정 |
|---|---|---|
| Arrive | **최종 도착 신호**(신규, §6.2) | 도착 도시 == `CityId` → 충족 |
| Deliver | 최종 도착(즉시형) / 보고 요청(보고형) | 그 시점 무역품 인벤토리(적재+임시 보관)의 `ItemId` 개수 ≥ `Count` → 충족(차감은 완료 처리 §6.3). 지급형은 인벤토리 변경마다 개수 < `Count`면 **불가** |
| Deadline | 날짜 변경(`IDateReader.Changed`) | 오늘 > `DeadlineDay` → 만료. 핵심이면 실패, 보조면 미달 확정. 성공 시점에 만료 전이면 보조 충족 |
| BattleWin | 전투 종료(`IBattleResultSource.OnBattleEnded`) | 승리 ∧ (`EnemyType` 비었거나 결과 적 종류 일치) ∧ (`QuestBattleOnly`면 진행 중 이벤트가 이 퀘스트의 확정 이벤트) → 횟수 +1, `Count` 도달 시 충족 |
| Preserve | 무역품 인벤토리 변경 | 의뢰 화물 개수 < `GivenCargoCount` → 불가(보조면 미달 확정, 핵심이면 실패) |

- 전투 결과에 적 종류가 없다 → `BattleResult`에 `EnemyType`(문자열, 없으면 null) 추가. 실전 전투 규칙이 편성 시 고른 적 종류를 넣는다. 배틀 테스트 씬·Placeholder는 null.
- 진행 중 이벤트 판별은 기존 `IEventEncounterStatus.CurrentEventId`(전투 중에도 이벤트가 진행 상태로 유지됨).
- 인벤토리 변경은 이동·회전에도 오므로 개수만 다시 센다(개수 변화 없으면 무시).
- 퀘스트 자신의 차감·회수 중에는 Deliver/Preserve 판정을 건너뛴다(처리 중 플래그).

### 6.2 최종 도착 신호

`FieldTripLifecycle.CompleteArrival`(최종 도착만 부름)에 새 계약 `ITripArrivalSink.NotifyFinalArrival(cityId)`를 추가 호출한다. 현재 위치 저장소의 변경 신호는 구간 도착마다 와서 쓰지 않는다. 구현은 Bootstrap 상주 `TripArrivalSignal`(`ITripArrivalSink` + `ITripArrivalSource { event Action<int> FinalArrived }`) **[판단]** — 상행 계기(`TripMilestone`)에 넣지 않는 이유: 기존 계기 수신자들이 도착 도시를 쓰지 않고, 패배 종료와 구분이 필요하다.

호출 순서: 위치 갱신 뒤 도착 신호(퀘스트가 현재 위치를 읽어도 일관).

### 6.3 상태 전이

| 계기 | 처리 |
|---|---|
| 수락 | 수락 조건 재확인 → 지급 화물 공간 판정(부족 시 거부) → 지급 → 인스턴스 생성, 기한 확정 |
| 핵심 전부 충족 | 즉시형: 완료 처리. 보고형: Reportable(기한은 계속 흐름 — 마감일 다음 날까지 보고하지 않으면 실패, §16) |
| 핵심 하나라도 불가·만료 | 실패 처리 |
| 보고(보고형, 보고 도시 게시판) | Deliver 재판정(개수 부족이면 Reportable 유지·버튼 비활성 사유) → 보상 공간 판정(부족 시 차단) → 완료 처리 |
| 포기 | 일반 퀘스트만. 실패 처리와 같되 상태 Abandoned |
| 보조 충족(`BonusTiming=Immediate`) | 그 보조 보상 즉시 지급 |

완료 처리: Deliver 차감 → 성공 보상 + 충족 보조 보상(OnSuccess) 지급 → 이력 기록 → 재게시 일정(반복성) → 후속 처리(§6.4).
실패 처리: 불이익(평판·위약금) → `ReturnCargoOnFail`이면 남은 의뢰 화물 회수 → 재게시 일정 → 메인이면 `MainQuestFailed` 이벤트(구독자 없음 = 경고, 흐름은 후속 기획).

판정 결과가 바뀔 때마다 `QuestManager.Changed` 1회.

### 6.4 후속

`FollowUp` 행 중 조건(`RequiredBonusId` 없음 또는 그 보조 충족)을 만족하는 것마다: Board → 해금 표시(게시 판정 §5.2), AutoAccept → 즉시 수락 흐름(공간 부족 등으로 실패하면 Board 해금으로 대체하고 경고) **[판단]**.

### 6.5 트리거형·이벤트형·메인 (구조만)

수락 진입점은 `IQuestStarter.TryStart(questId, QuestStartSource)` 하나로 둔다(게시판은 Request로 호출). 이벤트 대본 명령 연결은 하지 않는다. 메인은 포기 불가·실패 이벤트까지만.

## 7. 보상·불이익 (`QuestRewardDispatcher`)

| 종류 | 처리 | 계약 |
|---|---|---|
| Gold | 개인 골드 지급 | `IGoldIncome`(설계 104) |
| Reputation | 증감(범위 자르기) | `IReputationAdjuster` |
| Item | 무역품 인벤토리에 배치. 보고형: 사전 판정으로 전부 들어갈 때만 진행. 즉시형: 못 놓은 것은 임시 보관(§8.3) | `QuestCargoService` |
| Unit | `IQuestUnitRewardGranter.Grant(characterId)` 호출 — 구현체 없음(등록 안 함). 없으면 경고 후 건너뜀 | 신규 계약만 |
| 위약금 | 개인 골드에서 가진 만큼 차감 **[판단]**(부족해도 실패 처리는 진행) | 기존 지갑 계약 |

## 8. 의뢰 화물·적재 (`QuestCargoService`)

### 8.1 배치·차감·회수

- 배치: 이벤트 무역품 효과(`EventCargoGoods`)와 같은 빈자리 규칙(`CargoPurchasePlanner`)을 재사용한다.
- 차감·회수: 환급 없는 제거 경로(`ITradeGoodsCargoSettlement.RemoveWithoutRefund`), 순서는 임시 보관 → 적재.

### 8.2 공간 사전 판정

여러 아이템이 **모두** 들어가는지 실제 배치 없이 판정하는 순수 함수 `CargoFitSimulator.CanFitAll(sections, items, definitions)` — 가상 배치 목록에 하나씩 계획을 쌓는다(계획기의 기존 아이템 인자에 가상 배치를 더해 넘김). 수락(지급 화물)·보고(보상 아이템)에 사용. 이동이 필요한 계획(기존 물품 재배치)은 허용한다(실제 배치도 같은 계획기를 쓰므로 결과 일치).

### 8.3 즉시 완료형·즉시 보조 보상 → 임시 보관 → 즉시 정리 팝업

못 놓은 보상 아이템은 임시 보관으로 보내고, **보상을 얻은 그 자리에서** 정리 화면을 연다(사용자 결정 2026-10-27). `QuestManager`는 `RewardStaged` 이벤트만 내고, 화면을 여는 쪽은 씬별 배선이 맡는다(상태 저장소가 화면을 모르게).

| 상황 | 처리 |
|---|---|
| 최종 도착(즉시 완료) | 도착 처리(`CompleteArrival`) 뒤 도착 팝업을 띄우기 **전에** 정리 대기가 있으면 Field 회수 적재 화면(`FieldCargoRecoveryPanel`, 이벤트가 쓰는 정리 화면)을 연다 → 닫히면 기존 "도착 성공" 팝업 → Hub 전환 |
| 상행 중 즉시 보조 보상(전투 승리 등) | Field 배선의 `FieldQuestRewardCleanup`이 `RewardStaged`를 받아 회수 적재 화면을 연다. 이벤트 진행·전투·전투 뒤 정산·다른 모달이 열려 있으면 그 흐름이 끝난 뒤 연다(대기 1건으로 합침). 화면이 열린 동안은 이벤트 화면과 같은 상행 정지 원인을 건다 |
| Hub에서 발생 | 무역품 인벤토리 팝업을 연다(임시 보관 영역 포함). 시설 화면·모달이 열려 있으면 닫힌 뒤. 경로: 보고형 퀘스트의 즉시 보조 납품 목표를 Hub 구매로 충족(검진 2에서 확인, `HubQuestRewardCleanup`) |

출발 시 임시 보관 버림 경고는 기존 흐름 그대로.

### 8.4 버리기 경고

- 대상: 진행 중 퀘스트의 지급 의뢰 화물 Id를 포함한 버리기 — 인벤토리 정리 화면의 버리기 확인, 상행 출발 시 임시 보관 일괄 버림 확인.
- 조회 계약 `IQuestCargoWarnings.Describe(itemIds) → 퀘스트 이름 목록`(없으면 빈 목록). 기존 확인 창에 경고 문구 줄을 추가한다(새 팝업을 만들지 않고 기존 확인/취소를 사용 **[판단]**). 문구: "의뢰 화물입니다(퀘스트명). 퀘스트 수행이 불가능해질 수 있습니다."
- 확인 후 실제 판정은 인벤토리 변경 신호로 §6.1이 한다(경고 경로가 판정을 하지 않음).
- 판매: 무역품 판매 기능이 없어 해당 없음. 생기면 같은 조회 계약을 쓴다.

## 9. 상행 영향 (`QuestTripEffects`)

### 9.1 적용 대상

인스턴스가 Active이고 `Scope=AllTrips`, 또는 `Scope=Destination`이며 이번 상행 최종 목적지 == 대상 도시. Reportable·종료 인스턴스는 적용 안 함 **[판단]**.

### 9.2 난이도 가산

- 계약 `IQuestDifficultyModifier.GetBonus(int destinationCityId) → int`(적용 인스턴스 `DifficultyBonus` 합).
- 상행 계획기(`TripRoutePlanner`)와 구간 실행(`CurrentLegRuntime`)이 구간 난이도 = 자르기(도시 쌍 값 + 퀘스트 가산) + 이번 구간 변경으로 계산. 상행 내 모든 구간에 적용 **[판단]**.
- 수락·종료로 가산이 바뀌면 `Changed` → 계획 재계산(준비 화면 갱신), 진행 중 구간은 실행 난이도 재계산(기존 변경 경로).

### 9.3 확정 이벤트·전투

- Encounter.xlsx Event 행: `Occurrence=Fixed`, `Repeat=PerTrip`, 조건 `Quest:퀘스트Id`. 확정 전투는 그 대본의 기존 전투 명령.
- 조건 키 `Quest`를 기본 등록부에 추가(인자 = 비어 있지 않은 Id). 판정은 `EncounterConditionContext`에 추가하는 `IQuestEncounterGate`로: 적용 대상(§9.1) ∧ 현재 구간 == 발생 구간 ∧ 구간 진행률 ≥ 발생 구간 진행률 ∧ 미발생(`PerQuest`면 퀘스트 인스턴스당, `PerTrip`이면 이번 상행).
- 발생 위치는 상행 시작(계기 TripStarted) 때 인스턴스마다 (발생 구간, 구간 진행률)로 확정해 저장한다. 두 방식을 모두 구현한다(사용자 결정 2026-10-27).

| `EventTiming` | 발생 위치 |
|---|---|
| Progress | **상행 전체 진행률** `ProgressMin`(0~1). 상행 계획의 구간별 기본 소요시간 누적 비율로 해당 구간과 구간 내 진행률을 환산한다 |
| Random | **무작위 구간** 하나(상행 구간 중 균등) + 그 구간 안 [`ProgressMin`, `ProgressMax`] 무작위 진행률 |

- 발생 위치 계산은 순수 함수 `QuestEventPlacement.Resolve(timing, legDurations, min, max, random01)`로 둔다(새 방식은 열거값 + 분기 하나 추가). 현재 구간 번호는 여정 상태(`ITripItinerary`)에서 읽는다.
- 구간 실행 시간이 계획과 달라져도(난이도 변경·궤주) 발생 구간·구간 진행률은 고정한다 — 다시 계산하면 이미 지난 위치로 옮겨 발생이 누락될 수 있다.
- 발생 기록: 이벤트 진행자에 `event Action<string> EventStarted`(`IEventEncounterStatus`에 추가)를 두고 퀘스트가 구독해 기록한다. 이벤트는 중단되지 않으므로 시작 = 발생으로 본다(설계 89 §4).
- 반복 퀘스트가 같은 이벤트를 쓰는 경우를 위해 이벤트 쪽 `Once` 대신 `PerTrip`을 쓰고, 퀘스트당 1회는 퀘스트 인스턴스가 판정한다.

## 10. 평판 (`ReputationManager`)

- `IReputationReader { int Value; int Min; int Max; event Action Changed }`, `IReputationAdjuster : IReputationReader { int Adjust(int delta) }`(실제 변화량 반환). 0 시작, 범위 인스펙터 기본 −100~100.

## 11. 게시판 (`GuildQuestBoard`)과 화면

### 11.1 계약 확장

`IGuildQuestBoard`(설계 103)를 다음으로 확장한다.

| 멤버 | 내용 |
|---|---|
| `Quests` | 현재 마을 기준 행 목록(`GuildQuestInfo` + `Status`: Available/Active/Reportable) — Available(이 조합 게시) ∪ Active(이 조합 수락) ∪ Reportable(이 조합이 보고처, 수락 조합 무관) |
| `GetDetail(questId)` | 제목·의뢰자·설명·보상 문구, 목표 줄 목록(핵심/보조 구분, 진행 `n/m`·충족·불가 표시), 기한 문구(`M월 D일까지`, 남은 일수) |
| `CanAccept/CanAbandon/CanReport(questId, out reason)` | 버튼 활성·사유(공간 부족·보고 불가 사유 등) |
| `TryAccept/TryAbandon/TryReport` | `QuestManager`에 위임 |
| `Changed` | `QuestManager.Changed`·평판·날짜·현재 위치·인벤토리 변경을 묶어 전달 |

현재 마을은 `ITripCurrentLocationRepository`(등록 타입)로 읽는다. 보상 문구는 보상 행에서 생성(예: "골드 300, 평판 +5, 약초 ×2" / 보조: "(보조) …").

### 11.2 화면 변경 (`MerchantGuildPanel`, `MerchantGuildUIBuilder`)

- 행 상태 문구: Active "진행 중", Reportable "보고 가능"(기존 "수락함" 대체).
- 상세: 목표 목록 텍스트, 기한 텍스트 요소 추가. 버튼: 수락(Available), 포기·보고(Active/Reportable — 보고는 Reportable이고 보고처일 때). 비활성 사유는 기존 사유 툴팁 공용 장치를 쓴다.
- 포기는 확인 창(실패 불이익 안내)을 거친다 **[판단]** — 기존 모달 확인 패턴 재사용.
- 요소 ID는 `MerchantGuildUIElementIds`에 추가. Hub 인스톨러 재실행.

### 11.3 Placeholder 제거

`PlaceholderGuildQuestBoard` 삭제, `ManagerHierarchyInstaller`에서 `GuildQuestBoard`·`QuestManager`·`ReputationManager`·`TripArrivalSignal`로 교체·추가, 삭제 오브젝트는 `RemovedPlaceholderGuildQuestBoardName` 정리. `PlaceholderGuildQuestBoardTests`는 실제 게시판 테스트로 대체.

## 14. 사용자 확인(Play) — 제작 후

상인조합: 게시 목록·수락(지급 화물 적재, 공간 부족 시 사유)·상세 진행 표시 → 상행 준비 예상 난이도 가산 → 상행 중 확정 이벤트 발생(진행률 기반·무작위 구간 각각) → 상행 중 즉시 보조 보상 정리 화면 → 최종 도착 즉시 완료(보상 → 임시 보관 → 도착 팝업 전 정리 화면) / 보고형 보고 → 기한 초과 실패·불이익 → 포기 확인 → 의뢰 화물 버리기 경고 → 반복 퀘스트 재게시(숙소 휴식으로 날짜 진행) → 평판 HUD 증감.

## 15. 범위 밖

퀘스트 목록 UI(이력 포함), 메인 퀘스트 실패 흐름, 트리거형·이벤트형 대본 연결, 유닛 보상 구현, 평판 효과, 시청 퀘스트, 저장/불러오기, 무역품 판매.
