### 3.1 계산기 규칙 (`TripDayCounter`)

- 이동 초 추가: 나머지 += 초 → 일수 = 구간 일수 환산(나머지)(기존 부동소수 경계 보정 그대로) → 나머지 = max(0, 나머지 − 일수 × 하루 초). 경계 보정으로 나머지가 미세하게 음수가 되는 것을 0으로 막는다.
- 구간 이동 초: 이동 초 추가 때 함께 늘고 중간 도시 도착에서 0. 구간 시계의 경과는 난이도 재계산(Rebase) 때 진행 비율로 다시 맞춰져 실제 이동과 어긋나므로 궤주에 쓰지 않는다(검진 후 개정 2026-10-18).
- 궤주 환산(구간 이동 초 m): 일수 = 구간 일수 환산(나머지 + m × 궤주 추가 비율) → 나머지·구간 이동 초 0(기획 92 §3-4 버림).
- 초기화: 나머지 0, 누적 이동 초 0.
- 이동 수치는 호출마다 인자로 받는다 — 인스펙터 튜닝값을 Play 중에 바꿔도 다음 호출부터 반영되고, 계산기는 설정 소스를 모른다.
- 기획 92 예시 검증: 구간 1:30 / 2:00, 두 번째 구간 1:40에 궤주 → 이동 190초 = 6일, 나머지 10초 → 10 + 100 × 0.5 = 60초 → 2일 → 합계 8일.

### 3.2 궤주 추가 비율

인스펙터의 "궤주 배율 1.5"(`RoutDayMultiplier`)는 그대로 두고 **배율 − 1**을 추가 비율로 해석한다. 총량 1.5배라는 의미가 유지되고 Bootstrap 씬 값을 바꿀 필요가 없다. 툴팁을 "궤주 시 직전 도시부터 이동 시간 × (배율 − 1)을 추가로 더한다(기획 92 §3-4)"로 고친다.

## 4. 흐름

### 4.1 이동 중 (매 프레임, `SessionStateTracker.Update`)

```
정지·도착이면 return
moved = 구간 시계 경과 증가(Time.deltaTime)     // 실제 늘어난 초
moved > 0 이면 OnMoved(moved)                    // 날짜 시계 → 계산기 → 넘긴 일수만큼 날짜 진행
진행 알림(OnProgressChanged)
진행 ≥ 1 이면 도착
```

- 날짜가 바뀌면 기존 구독자가 그대로 반응한다: Hub HUD(Field에선 표시 없음), 도로 난이도 기간 만료 → 현재 구간 재계산(설계 89 §4.3).
- 재계산은 이번 프레임 경과 증가가 끝난 뒤라 이동 초가 이중으로 세어지지 않는다. 재계산 후 진행 비율은 유지되므로 같은 프레임의 도착 판정도 그대로다.
- 전투·이벤트·정지 중에는 `Update`가 일찍 끝나 신호가 없다(기획 92 §3-2).

### 4.2 상행 단위

| 시점 | 날짜 시계 |
|---|---|
| 상행 시작 신호(`TripStarted`) | 초기화 |
| 중간 도시 도착(`MidCityArrived`) | 구간 이동 초만 0 — 나머지는 다음 구간으로 이어진다. 구간 사이 도착 알림(2초) 동안은 정지라 세지 않는다 |
| 도주 | 아무것도 하지 않는다(같은 구간 재개, 기획 92 §3-6) |
| 궤주 | 전투 마무리 단계가 상행 종료 처리 **전에** `ITripDayRout`를 호출 → 직전 도시부터 실제 이동 초(날짜 시계가 센 값)로 궤주 환산 → 날짜 진행 |
| 상행 종료 신호(`TripEnded`, 최종 도착·궤주) | 초기화(나머지 버림, 기획 92 §3-3) |

- 사망·포로 종료는 플레이 종료라 별도 처리하지 않는다. 다음 상행 시작 신호가 어차피 초기화한다.

### 4.3 DI·설치

- `TripDayClock.Bind(ISessionState, ITripMilestoneSource, IDateAdvancer, ITripTravelSettingsReader)` — 판정 시계와 같은 묶기 방식. 날짜 진행자·이동 수치는 선택적(없으면 날짜 진행 없음 / 기본 이동 수치).
- `FieldManager.RegisterSelf`: `Require<TripDayClock>()`, `ITripDayRout`·`ITripDayClockDebug` 등록. `ResolveDependencies`에서 Bind. `ITripTravelSettingsReader`는 여정 상태가 등록하는 타입 그대로 조회한다.
- `ManagerHierarchyInstaller`: FieldManager 오브젝트에 `GetOrAddComponent<TripDayClock>` (판정 시계 옆 줄). 제작 때 CLI로 Bootstrap 열기 → Build Bootstrap → 저장.
- 구독 해제: `OnDestroy`에서 이동 신호·상행 신호 해제(판정 시계와 같은 수명).

## 6. 디버그 (`TripDebugView`)

| 항목 | 변경 |
|---|---|
| 3번째 줄 | "구간 경과 n초 / 소요 n초 · 상행 이동 n초 · 다음 날까지 n초 · 궤주 시 +n일". 값은 `ITripDayClockDebug`에서 읽는다 |
| "상행 완료" 버튼 | 남은 이동 초 = (현재 구간 소요 − 경과) + 이후 구간 소요 초 합을 `ITripDayClockDebug`의 이동 초 추가로 넣고, 구간을 넘긴 뒤 바로 도착(0.01초) 처리. 정상 완료와 같은 누적 규칙으로 날짜가 진행된다 |

- 바로 도착 처리의 0.01초도 이동 신호로 세지만 직후 상행 종료 초기화로 버려진다.
- 날짜 시계 디버그 계약이 없으면(Bootstrap 미재빌드) 3번째 줄은 구간 경과/소요만, 상행 완료는 날짜 없이 진행.
- 같은 줄·같은 박스를 쓰며 위치는 바꾸지 않는다. 글이 박스 폭을 넘으면 폭만 조정하고 Play 실측으로 겹침을 점검한다.
- 3번째 줄은 표시 단위(초 정수·0.1초·일)로 값이 바뀔 때만 문자열을 만들고 폭을 잰다(검진 후 개정 2026-10-18) — OnGUI는 한 프레임에 여러 번 불린다.
- `TripDebugView`의 날짜 매니저 직접 참조(`FindFirstObjectByType<DateManager>`)는 상행 완료에서만 쓰이므로 제거하고 `ITripDayClockDebug`로 대체한다.

## 7. 짧은 상행 수치 (기획 75 개정)

| 항목 | 현재 | 변경 |
|---|---|---|
| 짧음 최소 / 폭 | 60 / 120 (1:00~3:00) | **20 / 160 (0:20~3:00)** |
| 식(거리 d, 난이도 k) | 60 + 0.14×d + 0.364×(k−1) | 20 + 0.2067×d + 0.364×(k−1) |

- 코드 기본값: `TripTravelSettings.Default()`의 짧음 항목.
- 씬 값: Bootstrap 여정 상태(`TripItineraryState`)에 직렬화된 거리 구분 첫 항목을 CLI(SerializedObject 편집)로 바꾸고 씬 저장. 인스톨러로 덮어쓰지 않는다 — 다른 튜닝값까지 기본값으로 돌아갈 수 있다.
- 최소·폭 값은 소요 시간 계산식에서만 쓴다(검색 확인). 30초 미만 구간에서 판정(이벤트·대화·인카운터)이 한 번도 오지 않을 수 있으나 기존 1분 구간과 같은 성격이라 범위 밖.
- 기획 75 §4.1 짧음 행과 예시에 개정 주석을 남긴다(제작 때).

## 9. 결정 사항(작성 중 발견)

1. **판정 시계 한 프레임 이중 계산(작성 중 발견)**: 판정 시계(`TripCheckClock`)는 진행 알림마다 `Time.deltaTime`을 더한다. 진행 알림은 이동 프레임 외에 재계산·지연·단축에서도 나온다. 이번 개정으로 이동 중 날짜가 바뀌어 기간 변경이 만료되면, 같은 프레임에 재계산 알림이 한 번 더 와서 그 프레임 시간이 판정 시계에 두 번 더해진다(만료 1회당 1프레임, 약 0.016초). 기존에도 정지 중 지연·단축·재계산 알림에서 같은 일이 있다.
   - **결정(2026-10-18, 추천안)**: 판정 시계를 진행 알림 대신 **이동 신호(실제 이동 초)**에 얹고, 신호가 주는 초를 그대로 더한다(`Time.deltaTime` 직접 읽기 제거). 날짜와 판정이 같은 시간 기준을 쓰게 되고 이중 계산이 사라진다. 변경은 판정 시계 구독·처리기와 요약 주석.
   - 판정 시계 테스트가 진행 알림을 흉내 내고 있으면 이동 신호로 바꾼다.
