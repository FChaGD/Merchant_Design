# 숙소 휴식 하루 흐름·휴식 중 이벤트 제작 계획

> 실행: 이 세션에서 직접 제작(이전 시스템과 같은 방식), 끝난 뒤 검진 여부 확인. 단계는 `- [x]` 체크박스로 추적.

**목표:** 설계 109대로 숙소 휴식을 "대기 → 확정 → 랜덤 → 하루 처리" 흐름으로 바꾸고, 휴식 전용 이벤트를 Hub에서 기존 이벤트 시스템으로 실행한다.

**구조:** 데이터(장소·제목) → 조건·검증 → 효과 명령 라우터·진행자 확장(상행 회귀) → 하루 흐름(순수) → 휴식 이벤트 진행자(Bootstrap) → Hub 화면·인스톨러 → 디버그·테스트 데이터.

**기술:** Unity 6000.3.7f1, C#, NUnit EditMode, ClosedXML(에디터 임포트), Yarn Spinner.

**설계:** `Docs/설계/109-2026-10-29-숙소_휴식_이벤트_아키텍처.md`(기획 108). 실행자는 두 문서를 함께 읽는다.

## 공통 제약

- 네임스페이스 `Game.Core`(에디터 `Game.Core.Editor`). 휴식 순수·상태는 `Core/Town/Inn/`, 이벤트 공용은 `Core/Narrative/Event/`, 테스트 `Tests/EditMode/`.
- DI는 **등록 타입**으로 조회. 현재 위치는 `ITripCurrentLocationRepository`로만 등록되어 있다(읽기 타입 미등록).
- 선택 의존성이 없으면 경고 1회 후 그 기능만 건너뛴다.
- 값 없는 텍스트는 `PlaceholderText.Missing`.
- `.unity`/`.prefab` 직접 편집 금지 — 인스톨러 get-or-create. 인스톨러 실행·씬 저장은 CLI로 직접(`editor_status` playMode가 stopped일 때만).
- 주석은 한국어, "왜"를 우선. 기존 주석 밀도에 맞춘다.
- 테스트: `~/.claude/projects/C--Users-addmin-Desktop-Merchant/tools/ut.sh ALL`. 기대: 기존 968 + 신규 전부 통과.
- 커밋은 사용자 지시 후. `Docs/`는 커밋 대상 아님.
- 인스펙터 값: 랜덤 1일 확률 0.35, 1일 비용 10(기존).

### 설계 대비 제작 시 확정 사항

- 라우터는 `EventEffectCommands`의 기존 생성자(서비스·호스트 고정)를 유지하고, 서비스 공급 함수를 받는 생성자를 추가한다 — 기존 효과 명령 테스트를 그대로 둔다. 라우터 자신이 `IEventEffectHost`를 구현해 현재 맥락 호스트로 위임한다.
- 장소별 이벤트 목록은 순수 클래스 `EncounterEventLists`가 만든다(조회자 MonoBehaviour는 보관만).
- (2026-10-29 제작) 공용 서비스 조립은 `IEventEffectRouter.CreateBaseServices()`가 아니라 정적 `EventEffectCommandHub.CreateBaseServices(resolver)` — 상행 껍데기(FieldManager 하위)가 허브보다 먼저 ResolveDependencies를 받아 허브가 resolver를 아직 갖지 못한다. 각 껍데기가 자기 resolver로 부르면 초기화 순서에 묶이지 않는다. 라우터 계약은 Enter/Exit만.
- (2026-10-29) 진행자 `Finished`는 대본 실행 실패·`Abort`에서는 내지 않는다(부른 쪽이 안다). `Abort`는 대기 중이면 대기만 푼다. 라우터 Exit는 `Reset`에서 — 패배 경로도 맥락을 뺀다.
- (2026-10-29) 휴식 문맥에서 `progress` 조건은 거짓(`!HasTown`) — 상행의 구간 없는 문맥은 기존대로 진행률 판정.
- (2026-10-29) 휴식 규칙은 `RestEventSession`(순수, `IRestEventRunner`·`IRestEndRequest`·`IRestEventViewBinder`·`IRestEventDebug`), MonoBehaviour `InnRestEventCoordinator`(UIManager 하위)는 DI·Update만. 디버그 강제 지정은 휴식 시작에 지우지 않는다(휴식 전에 골라 두는 순서 허용, 한 번 쓰면 지워짐). `IRestEventDebug`에 `ForcedNextId`·`RestEvents` 추가, `ForceNext`는 휴식 이벤트가 아니면 false.
- (2026-10-29) `InnRestDayFlow`는 실행기 끝 알림을 이벤트마다 토큰으로 묶어 중단 뒤 늦은 알림을 무시한다. 진행 화면 이벤트 기록은 최근 5줄. 결과 시 게이지는 성립 일수로 맞춘다.
- (2026-10-29) 진행 화면에 `ProgressBoxGold`("예상 남은 적재 골드") 줄 추가, 표시 행 간격 재배치(이벤트·회복 영역 높이 0.21~0.43). 날짜 줄은 "날짜 {오늘}".
- (2026-10-29) 상행 이벤트 디버그 목록도 `EventsAt(Trip)`만. Hub 휴식 디버그는 `EncounterDebugView`에 오른쪽 아래 한 줄(토글 "휴식 이벤트" → ◀ Id ▶ [지정] [해제]).
- (2026-10-29 사용자 확인 후 수정, §10.1 7번) 이벤트 동안 진행 화면을 숨기고 끝나면 다시 보인다 — 흐름 `IsEventRunning`(확정·랜덤 이벤트 단계) 동안 진행 화면 시각 루트만 끈다. 패널 Close가 아니라서 휴식·재화 HUD 입력 차단은 유지된다. 확정→랜덤이 이어지면 계속 숨김, 이벤트 강제 종료 시 결과 상태로 다시 보인다(CLI Play 확인, EditMode 1041/1041).
- (2026-10-29 검진 후 수정, 사용자 결정)
  - 이벤트 화면 묶음·회수 적재 패널 조립을 `FieldEventScreens.TryCreate`·`FieldCargoRecoveryPanel.TryCreate`로 옮겨 Field·Hub 배선이 같이 쓴다(정비창 보기 버튼 표시는 인자). 경고 문구는 씬별로 호출자가 낸다.
  - 휴식 이벤트 결과에 `Completed`(대본이 끝까지 감 = 진행자 기록 여부)를 싣는다. 끊긴 이벤트는 기록 없이 다음 단계로 가지 않고 그날 미성립·`Stopped`로 끝낸다.
  - 하루 처리는 `IInnRestService.CanSettleDay`(휴식 중·예정 일수 안)일 때만 부른다. 흐름이 확인 후 부르고, 거짓이면 그날 미성립·`Stopped`. 서비스는 조건 밖 호출을 `InvalidOperationException`으로 거부한다("골드 부족" 결과와 섞지 않음).
  - 오류 검사 배치: 조건 장소·휴식 제목은 임포터(행을 읽을 때 바로), 명령 장소는 검증기. 검증기의 표 장소 검사와 노드 목록만 받는 대본 검증 오버로드는 지우고, 테스트는 장소 지정 버전으로 바꿨다. 장소 이름은 `EventPlaceNames`.
  - 진행 화면의 지출 계약은 필수로 주석·코드를 맞췄다.
  - `Event.yarn`의 `$rest_met_archer`는 11-2 "합류/플래그" 테스트 데이터(플래그 쓰기만, 읽는 조건 없음) — 향후 사용 근거가 없어 제거(사용자 결정 2026-10-29).
- (2026-10-29) CLI Play 검증 시 에디터가 포커스를 잃으면 Play 프레임이 멈춘다(`Application.runInBackground` false) — 검증 스크립트에서 런타임에만 true로 켰다(프로젝트 설정은 바꾸지 않음).

## 검토 초점

1. 하루 경계에서 큰 프레임 지연(창 비활성 후 복귀) — 하루를 건너뛰지 않고 한 날만 진행(Task 6 `LargeDelta_StopsAtDayBoundary`).
2. 이벤트 진행 중 Hub 언로드·진행 화면 닫힘 — 실행기 중단 요청 후 이력 기록 없이 종료, 다음 휴식에서 정상 시작(Task 8 `Abort_DuringEvent_RequestsRunnerAbort`, Task 5 `Abort_NoRecordNoSignal`).
3. 강제 종료 요청 상태가 다음 이벤트로 새어 나감 — 끝 알림에서 읽은 뒤 지움(Task 9 `ForcedEnd_ClearedAfterOutcome`).
4. 라우터 맥락이 끝난 뒤에도 남은 대본(Drain)의 효과 명령이 적용됨 — Exit 후 `IsRunning` false(Task 4 `AfterExit_CommandsNoEffect`).
5. 결제 실패일에 이미 날짜·회복이 반영됨 — 실패 시 상태 무변경(Task 7 `SettleDay_Insufficient_NoDateNoRecovery`).
