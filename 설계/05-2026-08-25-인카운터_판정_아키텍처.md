## 1. 개요

[[07-2026-08-25-인카운터_판정_기획]]에서 확정한 "5초마다 30% 확률로 랜덤 인카운터 판정"을 `EncounterManager`에 배선한다. 새 매니저는 추가하지 않는다 — `EncounterManager` 내부에 타이머 역할과 판정 전략 객체를 채우는 것으로 해결된다.

**핵심 배치 원칙**: `EncounterManager`는 "판정을 언제 실행할지(주기)"만 알고, "그 판정에서 실제로 터질지(확률)"는 모른다. 확률 판단은 `RandomEncounterRule`(`IEncounterRule`)에 위임해, 확률 모델이 바뀌거나(예: 구간별 가중치) `FixedEncounterRule`이 추가되어도 `EncounterManager`의 타이밍 로직은 그대로 둘 수 있게 한다(OCP).

## 3. 판정 타이밍 — `ISessionState.OnProgressChanged` 재사용

`EncounterManager`가 별도 `Update()`로 시간을 누적하는 대신, `SessionStateTracker`가 이미 구현해 둔 pause-aware per-frame 이벤트(`OnProgressChanged`)를 틱 소스로 재사용한다.

`SessionStateTracker.Update()`는 `paused`(전투 중) 또는 `arrived`(도착) 상태면 `OnProgressChanged`를 아예 발행하지 않는다(`SessionStateTracker.cs` 49~66행, 이미 구현됨). `EncounterManager`가 이 이벤트에 얹혀 경과 시간을 누적하면 "전투 중에는 판정 타이머도 멈추고, `sessionState.Resume()`이 호출되는 시점(결과 팝업 확인 후)에 정확히 다시 흐르기 시작한다"는 동작이 **별도 코드 없이** 자동으로 보장된다. 도착 이후(`arrived`)에도 이벤트가 영구히 멈추므로 도착 후 인카운터가 발생하는 일도 없다.

```csharp
public class EncounterManager : MonoBehaviour, IEncounterManager, IManagedComponent
{
    [SerializeField] private float checkIntervalSeconds = 5f;

    private ISessionState sessionState;
    private IBattleController battleController;
    private readonly IEncounterRule randomRule = new RandomEncounterRule();
    private float elapsed;

    public void ResolveDependencies(IDependencyRegistrar registrar)
    {
        // Pause() 하나만 쓰던 기존 의존성(ISessionPauseControl)을, 주기 판정에 OnProgressChanged
        // 구독이 필요해진 지금 ISessionState로 확장한다 - 04 문서 §4 "남은 이슈"에서 이미 예견된 확장.
        sessionState = registrar.Resolve<ISessionState>();
        sessionState.OnProgressChanged += HandleProgressChanged;
        battleController = registrar.Resolve<IBattleController>();
    }

    private void HandleProgressChanged(float _)
    {
        elapsed += Time.deltaTime;
        if (elapsed < checkIntervalSeconds)
        {
            return;
        }

        elapsed = 0f;   // 판정 성공 여부와 무관하게 리셋 - 매 주기 독립 판정(07 문서 §3)
        if (randomRule.ShouldTrigger())
        {
            TriggerEncounter();
        }
    }

    private void TriggerEncounter()
    {
        sessionState.Pause();
        OnEncounterTriggered?.Invoke();
        battleController.StartBattle();
    }
}
```

- `elapsed`는 판정 성공 여부와 무관하게 매 주기 종료 시 리셋한다 — "5초마다 독립적으로 30% 확률 판정"이라는 [[07-2026-08-25-인카운터_판정_기획]] §3 정의를 그대로 반영한다(실패한 시도가 다음 판정에 유리하게 누적되는 방식은 채택하지 않음).
- `TriggerEncounter()` 안에서는 `elapsed`를 따로 리셋하지 않는다 — `Pause()` 직후 `OnProgressChanged` 발행 자체가 멈추므로 리셋할 필요가 없다. `sessionState.Resume()`으로 이벤트가 재개되면 `elapsed`는 판정 직전 값(0에 가까움)에서 이어서 누적되므로, 전투가 끝나고 이동을 재개하자마자 곧바로 다음 판정이 뜨는 일은 없고 다음 판정까지 최소 거의 5초의 여유가 생긴다.

## 4. `RandomEncounterRule`을 GetComponent가 아닌 직접 소유로 결정한 이유

[[01-2026-08-25-매니징오브젝트_컴포넌트구조]] §5.2는 `RandomEncounterRule`/`FixedEncounterRule`을 `EncounterManager` 산하 컴포넌트로만 나열했고, 조회 방식은 명시하지 않았다. 이 프로젝트는 매니저 산하 컴포넌트를 보통 같은 GameObject에 붙이고 `GetComponent<IXxx>()`로 조회하는 패턴(`BattleResultEvaluator` 등)을 쓰지만, `IEncounterRule`은 **같은 GameObject에 두 구현체(`RandomEncounterRule`, `FixedEncounterRule`)가 동시에 존재할 예정**이라 `GetComponent<IEncounterRule>()`로는 어느 쪽이 반환될지 구분할 수 없다(인터페이스가 같으므로 먼저 붙은 컴포넌트만 반환됨).

`RandomEncounterRule`은 Unity 생명주기(Update/Awake 등)가 필요 없는 순수 판정 로직(`UnityEngine.Random.value < 0.3f`)이므로, `FieldCameraController`/`PanelNavigationStack`과 동일하게 **MonoBehaviour가 아닌 순수 C# 합성 객체**로 만들어 `EncounterManager`가 필드로 직접 생성·소유한다. `FixedEncounterRule`이 실제로 설계될 때도 같은 방식(EncounterManager가 직접 소유하는 별도 필드)을 따르면 이름 충돌 문제 자체가 애초에 발생하지 않는다.

```csharp
public interface IEncounterRule
{
    bool ShouldTrigger();
}

// 순수 C# 객체 - Unity 생명주기 불필요, EncounterManager가 필드로 직접 소유(§4 참고)
internal class RandomEncounterRule : IEncounterRule
{
    // 테스트 단계 추정치 - Docs/기획/07-2026-08-25-인카운터_판정_기획.md §3, 실제 밸런싱 전까지 유지
    private const float TriggerProbability = 0.3f;

    public bool ShouldTrigger() => UnityEngine.Random.value < TriggerProbability;
}
```

## 5. `FixedEncounterRule` — 이번 설계 범위 밖

[[07-2026-08-25-인카운터_판정_기획]] §4/§5에 명시된 대로, 확정 인카운터의 트리거 조건(특정 시점/조건)이 아직 설계되지 않았다. `EncounterManager`의 주기 판정 루프(§3)는 `RandomEncounterRule` 전용이며, `FixedEncounterRule`이 추가되어도 이 루프에 얹히지 않는다 — 확정 인카운터는 별도의 외부 조건(스토리 플래그 등)이 `TriggerEncounter()`를 직접 호출하는 경로가 될 가능성이 높다(예: `EncounterManager`에 `public void TriggerFixedEncounter()` 같은 별도 진입점 추가). 이 경로 자체는 확정 인카운터 트리거 조건이 설계될 때 함께 정의한다.

## 6. SOLID 적용 요약

| 원칙 | 적용 |
|---|---|
| SRP | "언제 판정할지"(`EncounterManager`, 타이머) ↔ "판정에서 터질지"(`RandomEncounterRule`, 확률) 분리 |
| OCP | `IEncounterRule` 전략 분리 — 확률 모델이 바뀌거나 `FixedEncounterRule`이 추가되어도 `EncounterManager.HandleProgressChanged` 수정 불필요 |
| ISP 재검토 | `EncounterManager`가 `ISessionPauseControl`(Pause 전용)만으로는 더 이상 충분하지 않아 `ISessionState` 전체로 의존성을 확장했다 — [[04-2026-08-25-Field씬_아키텍처]] §4가 이미 예견했던 지점. 쓰지 않는 `Resume()`/`Begin()`까지 노출되는 트레이드오프는 감수한다 |
| DIP | `EncounterManager`는 `IEncounterRule`/`ISessionState`/`IBattleController` 인터페이스에만 의존 |

---

## 7. 최적화 요약

- 별도 `Update()`를 추가하지 않고 `SessionStateTracker`가 이미 매 프레임 발행하는 `OnProgressChanged`에 편승 — 시간 누적 로직이 두 곳에서 중복 폴링되지 않는다.
- `checkIntervalSeconds`/`TriggerProbability`는 상수/직렬화 필드 조회이므로 매 프레임 추가 연산은 `float` 덧셈+비교 1회 수준.

---

## 8. 남은 이슈

- `FixedEncounterRule`과 그 트리거 진입점은 미설계(§5) — 확정 인카운터 조건 기획 시 함께 설계.
- `IEncounterManager.OnEncounterTriggered`가 랜덤/확정 구분 정보를 실어나르지 못하는 문제는 [[04-2026-08-25-Field씬_아키텍처]] §11에서 이미 지적된 채로 미해결 — 이번 설계도 그대로 둔다.
- `checkIntervalSeconds`/`TriggerProbability` 수치는 [[07-2026-08-25-인카운터_판정_기획]] §3 값을 그대로 가져온 테스트값이며, 플레이테스트 후 조정 대상.
- 정식 소요시간(거리+변수) 도입으로 `SessionStateTracker` 내부 계산 방식이 바뀌어도 `OnProgressChanged` 이벤트 계약 자체는 유지되므로 `EncounterManager`는 무변경으로 버틸 가능성이 높다 — 단, 이벤트 발행 빈도(프레임당 1회 가정)가 달라지면 재검토 필요.
