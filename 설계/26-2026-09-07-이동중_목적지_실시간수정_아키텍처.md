# 이동 재배치 중 목적지 실시간 수정 아키텍처

기획: [21-2026-09-07-이동중_목적지_실시간수정_기획.md](../기획/21-2026-09-07-이동중_목적지_실시간수정_기획.md)

> 이 문서는 실전 검증 중 세 차례 정정을 거쳤다. 과거 검토했던 대안과 그 이유는 남겨두되, **각 절의 "채택" 표시가 현재 유효한 최종 구현**이다.

## 1. 개요

Field 정비창에서 이동(Moving) 활동이 진행 중인 유닛의 도착 슬롯 반투명 마크(고스트)를 드래그해 목적지를 바꿀 수 있게 한다. 이미 지나온 구간(출발지→현재 위치)은 그대로 두고, 현재 위치→새 목적지 구간만 새로 경로/소요시간을 계산해 이어서 진행한다(기획 21번 §3.1). 목적지가 점유돼 있으면 기존 맞바꾸기 규칙(버그#8 정정, `FieldFormationPanel.HandleGridMove`)을 재사용해 "상대는 이 유닛의 원래 출발지로 향한다"로 처리한다(§3.2).

기존 설계(설계 25번)의 데이터 모델·경로 탐색·보간 유틸리티를 최대한 재사용하고, 새 상호작용(고스트 드래그)만 기존 드래그 파이프라인(`FormationDragCoordinator`/`FormationGridEditor`)에 세 번째 드래그 종류로 추가한다. 다만 §2에서 정리하듯 "정확한 연속 좌표에서 이어지기" 요구 때문에 보간 유틸리티(`FormationPathInterpolation`)는 구조 확장이 필요했다.

## 2. "현재 위치" 정의 — 연속 좌표 정확 접합 (최종 채택)

기획 21번 §5는 "이미 지나온 연속 좌표를 새 경로의 시작점으로 정확히 잇는 방법"을 설계 단계 과제로 남겼다. 두 방식을 검토했다:

- **(A) 연속 좌표 정확히 접합(최종 채택)**: 드래그 시작 순간의 정확한 보간 좌표(그리드에 맞지 않는 임의 지점)에서 그대로 이어서 움직인다.
- **(B) 다음 노드로 스냅(1차 채택 → 기각)**: 진행 중인 구간은 "다음 노드까지는 이미 도착한 것"으로 취급해 스냅한다. 처음에는 구조 변경이 없다는 이유로 채택했으나, 실전 검증에서 리다이렉트할 때마다 캐릭터가 다음 그리드 노드로 순간이동하듯 뚝뚝 끊겨 보인다는 문제가 확인돼(2026-09-07) 기각했다.

**(A)로 정정**. "구간 소요시간 균등"이라는 기존 전제를 깨야 하지만, 아래처럼 "구간 하나만 다른 가중치를 갖는" 형태로 일반화하면 기존 로직 대부분(경로 탐색, 렌더링 파이프라인)은 그대로 두고 보간 수학(`FormationPathInterpolation`)만 확장하면 된다.

### 2.1 부분 구간(Partial Segment) 모델

한 활동의 경로(`PathSlotIndices`)는 여러 구간(슬롯 사이)으로 이뤄지고, 기본적으로 전 구간이 동일한 소요시간(`FormationTiming.MoveSecondsPerSlot`)을 갖는다. 리다이렉트로 만들어진 활동만 예외적으로 **정확히 하나의 구간**이 다른 가중치를 갖는다 - 그 구간은 리다이렉트 시점에 이미 일부 지나온 구간이라, 남은 비율만큼만 시간이 배정된다.

`FormationActivity`에 추가:

```csharp
// 기본값(-1 / 1)은 "부분 구간 없음"(일반 이동)과 동일하게 동작한다.
public int PartialSegmentIndex { get; internal set; } = -1;
public float PartialSegmentWeight { get; internal set; } = 1f;   // 0..1, 그 구간에 남은 비율
```

`PartialSegmentIndex`가 가리키는 구간(`PathSlotIndices[i]`→`[i+1]`)의 **시작 좌표 자체**(그리드 노드가 아닌 연속 좌표)는 좌표계를 모르는 `FormationActivity`가 갖지 않는다 - 소비자(UI 앵커 좌표를 아는 `FormationGridView`, 전장 월드 좌표를 아는 `LiveBattleSimulationRule`)가 각자 `FormationPathInterpolation.ApplyPartialSegment`로 그 지점 하나만 정확한 위치로 치환한다(§5).

### 2.2 `FormationPathInterpolation` 확장

```csharp
// waypoints[i]→[i+1] 구간만 partialSegmentWeight 가중치를 갖고, 나머지는 전부 가중치 1이다.
// partialSegmentIndex<0이면 전 구간 균등(기존 2-인자 호출과 완전히 동일하게 동작 - 하위 호환).
public static Vector2 Evaluate(IReadOnlyList<Vector2> waypoints, float progress01, int partialSegmentIndex = -1, float partialSegmentWeight = 1f);

// 좌표 없이 "지금 몇 번째 구간의 몇 %(localT) 지점인지"만 알고 싶을 때 쓴다 - HandleRedirectMove가
// "지금 정확히 어디 있는지" 알아내는 데 쓴다(§3).
public static (int segmentIndex, float localT) Locate(int waypointCount, float progress01, int partialSegmentIndex, float partialSegmentWeight);

// waypoints[partialSegmentIndex] 좌표 하나만 "그 구간을 partialSegmentWeight만큼 남긴 지점"의
// 정확한 연속 좌표로 치환한다. partialSegmentIndex<0이면 아무 것도 하지 않는다.
public static void ApplyPartialSegment(IList<Vector2> waypoints, int partialSegmentIndex, float partialSegmentWeight);
```

`Evaluate`/`Locate` 둘 다 내부적으로 "구간을 순서대로 누적 가중치와 비교"하는 O(구간 수) 루프다 - 그리드가 작아(최대 8×2류) 성능 문제가 없고, `partialSegmentIndex=-1`일 때 기존 O(1) 공식과 정확히 같은 결과를 낸다(대수적으로 증명 - `firstSegmentWeight`류 특수 케이스 없이 일반식 하나로 통일).

## 3. "지금 정확히 어디 있는지" 계산 — `FieldFormationPanel.HandleRedirectMove`

```csharp
var (segmentIndex, localT) = FormationPathInterpolation.Locate(activity.PathSlotIndices.Count, activity.Progress01, activity.PartialSegmentIndex, activity.PartialSegmentWeight);
var fromNode = activity.PathSlotIndices[segmentIndex];
var toNode = activity.PathSlotIndices[segmentIndex + 1];
```

이 활동 자신이 이전 리다이렉트로 이미 부분 구간을 갖고 있어도(`PartialSegmentIndex`/`Weight`) 같은 `Locate` 호출로 정확히 반영된다 - 연속 리다이렉트를 몇 번 반복해도 항상 "지금" 기준으로만 계산한다.

`toNode == newTargetSlotIndex`면 이미 그 지점으로 향하는 중이므로 아무 것도 하지 않는다.

**출발지→현재 위치(fromNode까지) 구간은 저장된 옛 경로 배열을 잘라 쓰지 않고 매번 새로 BFS 계산한다** - 이 부분이 실전 검증 중 가장 크게 헤맨 지점이다. 최초 구현은 저장된 `PathSlotIndices`의 앞부분을 그대로 재사용했는데, 그 배열 자체가 이전 리다이렉트들의 우회 경로를 계속 이어붙인 상태라 리다이렉트를 반복할수록 이미 무의미해진 과거 목적지들의 우회 구간까지 화면에 계속 누적되어 남았다(스크린샷으로 확인 - 최신 목적지와 무관한 옛 경로가 화면 반대편까지 뻗어 있었음). 저장된 배열을 아예 참고하지 않고 **"현재 위치→새 목적지" 구간과 완전히 같은 방식으로 매번 새로 계산**하면 이 문제가 원천적으로 사라진다.

**전진 vs 반전 - 더 짧은 쪽 선택(2026-09-07 추가 정정)**: fromNode→toNode 구간을 "무조건 toNode까지 마저 가고" 시작하면, 반대 방향으로 목적지를 바꿨을 때 원래 가던 방향으로 한 칸 더 갔다가 되돌아오는 부자연스러운 움직임이 생겼다(실전 확인). 그렇다고 "지금 위치에서 바로 반대 방향으로 매끄럽게 꺾기"는 그 중간 지점이 fromNode/toNode 축 위에만 있고 다른 어떤 실제 그리드 노드와도 이어지지 않아, 완전히 매끄럽게 표현하려면 부분 구간 모델을 양방향으로 또 한 번 확장해야 한다(과설계 판단, 기각). 대신 **두 후보 모두 계산해 총 남은 거리가 더 짧은 쪽을 쓴다**:

- **전진**: `(1-localT)`(남은 구간 가중치) + `suffixForward.Count-1`(toNode→새 목적지) - §2.1의 부분 구간 모델 그대로, 끊김 없이 이어진다.
- **반전**: `localT`(지금까지 지나온 만큼 되짚는 거리) + `suffixBackward.Count-1`(fromNode→새 목적지) - 이 경우만 fromNode로 스냅하는 근사를 쓴다(`partialSegmentIndex=-1`). 그래도 "무조건 toNode까지 전진 후 반전"보다는 훨씬 짧아 체감상 자연스럽다.

```csharp
public void HandleRedirectMove(string unitId, int newTargetSlotIndex)
{
    if (activityRepository == null || formationRepository == null) return;
    if (!activityRepository.TryGetActivity(unitId, out var activity) || activity.Kind != FormationActivityKind.Moving) return;
    if (!formationRepository.TryLoadCurrent(out var layout)) return;

    var (segmentIndex, localT) = FormationPathInterpolation.Locate(activity.PathSlotIndices.Count, activity.Progress01, activity.PartialSegmentIndex, activity.PartialSegmentWeight);
    var fromNode = activity.PathSlotIndices[segmentIndex];
    var toNode = activity.PathSlotIndices[segmentIndex + 1];

    if (toNode == newTargetSlotIndex) return;

    // 목적지 점유 시 맞바꾸기(기획 21번 §3.2, 버그#8과 동일 규칙) - 상대는 이 유닛의 원래 출발지로 향한다.
    var targetUnitId = layout.GetUnitId(newTargetSlotIndex);
    if (!string.IsNullOrEmpty(targetUnitId) && targetUnitId != unitId)
    {
        if (activityRepository.IsUnitBusy(targetUnitId)) activityRepository.Cancel(targetUnitId);
        StartMove(layout, targetUnitId, newTargetSlotIndex, activity.OriginSlotIndex);
    }

    var blocked = CollectBlockedSlots(layout, excludeUnitId: unitId);
    var prefix = FormationPathFinder.FindPath(activity.OriginSlotIndex, fromNode, layout.ColumnCount, layout.RowCount, blocked);

    var suffixForward = FormationPathFinder.FindPath(toNode, newTargetSlotIndex, layout.ColumnCount, layout.RowCount, blocked);
    var suffixBackward = FormationPathFinder.FindPath(fromNode, newTargetSlotIndex, layout.ColumnCount, layout.RowCount, blocked);
    var forwardRemaining = (1f - localT) + Mathf.Max(0, suffixForward.Count - 1);
    var backwardRemaining = localT + Mathf.Max(0, suffixBackward.Count - 1);

    List<int> combinedPath;
    int partialSegmentIndex;
    float partialSegmentWeight;
    if (forwardRemaining <= backwardRemaining)
    {
        combinedPath = prefix.Concat(new[] { toNode }).Concat(suffixForward.Skip(1)).ToList();
        partialSegmentIndex = prefix.Count - 1;   // fromNode→toNode 구간의 combinedPath 상 인덱스
        partialSegmentWeight = 1f - localT;       // 이미 localT만큼 지나왔으니 남은 가중치
    }
    else
    {
        combinedPath = prefix.Concat(suffixBackward.Skip(1)).ToList();
        partialSegmentIndex = -1;                 // 반전은 fromNode로 스냅(근사)
        partialSegmentWeight = 1f;
    }

    var requiredSeconds = partialSegmentIndex >= 0
        ? (Mathf.Max(0, prefix.Count - 1) + partialSegmentWeight + Mathf.Max(0, suffixForward.Count - 1)) * FormationTiming.MoveSecondsPerSlot
        : Mathf.Max(1, combinedPath.Count - 1) * FormationTiming.MoveSecondsPerSlot;
    var elapsedSeconds = Mathf.Max(0, prefix.Count - 1) * FormationTiming.MoveSecondsPerSlot;

    activityRepository.RedirectMove(unitId, newTargetSlotIndex, combinedPath, requiredSeconds, elapsedSeconds, partialSegmentIndex, partialSegmentWeight);
}
```

`elapsedSeconds`를 정확히 "prefix 완료 시점"으로 세팅해두면, `Progress01 = elapsedSeconds/requiredSeconds`가 딱 부분 구간의 시작(`localT_result=0`)에 해당한다 - 그 지점의 좌표를 §5의 `ApplyPartialSegment`로 정확한 연속 좌표로 치환해두면, "전진"을 선택했을 때는 리다이렉트 직후 첫 보간 결과가 순간이동 없이 정확히 "드래그하던 그 순간의 위치"와 일치한다(수식으로 검증됨). "반전"을 선택했을 때는 fromNode로의 작은 스냅이 발생한다(최대 한 구간 이하 거리 - §2의 트레이드오프).

`HubFormationPanel.HandleRedirectMove`는 빈 구현(Hub는 진행 활동이 없어 이 경로가 호출될 일이 없다 - `GetActiveActivities()`가 항상 빈 목록을 반환하는 것과 같은 이유, 기존 `IsUnitReserved` Hub 스텁과 동일 패턴).

## 4. 새 활동 반영 — `IFieldFormationActivityRepository.RedirectMove`

기존 `Cancel`+`BeginMove` 조합을 쓰지 않는다 - `BeginMove`는 항상 `ElapsedSeconds=0`으로 시작하므로 이미 진행된 시간을 이어받을 수 없다. 대신 전용 메서드를 추가한다.

```csharp
// IFieldFormationActivityRepository
void RedirectMove(string unitId, int newTargetSlotIndex, IReadOnlyList<int> pathSlotIndices, float requiredSeconds, float elapsedSeconds, int partialSegmentIndex, float partialSegmentWeight);
```

`InMemoryFieldFormationActivityRepository` 구현 - 기존 활동을 제거하고 새 `FormationActivity`(Moving, `OriginSlotIndex`는 원래 값 유지 - 정비창 UI의 "출발지" 마크는 최초 출발점을 계속 가리켜야 하므로)를 만들어 `ElapsedSeconds`/`PartialSegmentIndex`/`PartialSegmentWeight`를 즉시 세팅한다(전부 `internal set`이라 같은 어셈블리인 이 클래스에서 생성자 호출 직후 대입 가능 - 새 생성자 오버로드 불필요):

```csharp
public void RedirectMove(string unitId, int newTargetSlotIndex, IReadOnlyList<int> pathSlotIndices, float requiredSeconds, float elapsedSeconds, int partialSegmentIndex, float partialSegmentWeight)
{
    var index = activities.FindIndex(a => a.UnitId == unitId && a.Kind == FormationActivityKind.Moving);
    if (index < 0) return;

    var originSlotIndex = activities[index].OriginSlotIndex;
    activities.RemoveAt(index);
    var activity = new FormationActivity(unitId, FormationActivityKind.Moving, newTargetSlotIndex, originSlotIndex, pathSlotIndices, requiredSeconds)
    {
        ElapsedSeconds = elapsedSeconds,
        PartialSegmentIndex = partialSegmentIndex,
        PartialSegmentWeight = partialSegmentWeight
    };
    activities.Add(activity);
}
```

`ApplyToLayout`(완료 처리, 버그#8/#9 정정으로 이미 "출발 슬롯은 지금도 자기 자신일 때만 비움" 가드가 있음)은 무변경 - 새 `TargetSlotIndex`를 그대로 써서 정상 동작한다.

## 5. 렌더링/시뮬레이션 소비자 — 부분 구간 반영

`PathSlotIndices`를 좌표로 변환하는 모든 소비자가 같은 패턴을 따른다: ① 평소처럼 슬롯 좌표 목록을 만든다 → ② `FormationPathInterpolation.ApplyPartialSegment(waypoints, activity.PartialSegmentIndex, activity.PartialSegmentWeight)`로 부분 구간 지점 하나만 정확한 좌표로 치환한다 → ③ `Evaluate`를 부를 때도 같은 `PartialSegmentIndex`/`Weight`를 넘긴다.

- **`FormationGridView`(UI 앵커 좌표)** - `SetPathLines`/`SetTravelerIcons`가 공유하는 `BuildWaypoints(FormationMovePathVisual)` 헬퍼에서 처리. `FormationMovePathVisual`도 `PartialSegmentIndex`/`Weight` 두 필드를 추가로 실어 나른다(`FormationGridEditor.TickActivityOverlays`가 `activity`에서 그대로 전달).
- **`LiveBattleSimulationRule.ComputeAllyPositionForSlot`(전장 월드 좌표)** - 인카운터 중단 지점 계산(설계 25번 §7)도 동일하게 적용해야, 화면에 보이던 위치와 실제 스폰 위치가 어긋나지 않는다.

경로선(`FormationPathLineView`) 자체와 `SetTravelerIcons`의 나머지 로직은 무변경 - 입력 waypoints가 이미 올바르게 치환되어 들어오므로 그대로 그리면 된다.

## 6. 드래그 상호작용 — 고스트를 세 번째 드래그 종류로 추가

### 6.1 `FormationActivityOverlayVisual` — 리다이렉트 가능 여부 노출

```csharp
public bool IsRedirectableTarget => Activity.Kind == FormationActivityKind.Moving && SlotIndex == Activity.TargetSlotIndex;
```

새 생성자 인자 불필요 - 이미 갖고 있는 `Activity`/`SlotIndex`로 계산되는 파생값이라 `TickActivityOverlays()`의 기존 호출부는 무변경.

### 6.2 `FormationActivityOverlayView` — `FormationUnitIconView`와 동일한 드래그 인터페이스 패턴

```csharp
public class FormationActivityOverlayView : MonoBehaviour, IBeginDragHandler, IDragHandler, IEndDragHandler
```

`Bind`에 드래그 델리게이트 3개 + 대상 unitId를 추가로 받는다(리다이렉트 불가능한 오버레이는 델리게이트를 null로 받아 자연히 무해). `OnBeginDrag`/`OnDrag`/`OnEndDrag`는 `FormationUnitIconView`와 동일하게 그대로 전달만 한다.

### 6.3 `FormationGridView.SetActivityOverlays` — 델리게이트 전달

`FormationGridEditor`로부터 받은 세 콜백(`onGhostBeginDrag`/`onGhostDrag`/`onGhostEndDrag`)을 매 오버레이 바인딩 시 `overlay.IsRedirectableTarget`인 경우에만 넘긴다.

### 6.4 `FormationDragCoordinator` — 세 번째 드래그 종류

```csharp
public bool IsRedirect { get; private set; }
public void BeginRedirect(IFormationUnit unit, PointerEventData eventData) => BeginDrag(unit, originSlotIndex: null, eventData, isRedirect: true);
```

`BeginDrag`/`EndDrag`/`CancelActiveDrag`에 `isRedirect` 플래그를 더해 세팅·리셋한다. 팔레트 드래그(`DraggedFromSlot == null && !IsRedirect`)와 명확히 구분된다.

### 6.5 `FormationGridEditor` — 배선

- `HandleActivityGhostBeginDrag(string unitId, PointerEventData)`: `unitsById`에서 유닛을 찾아 `dragCoordinator.BeginRedirect(unit, eventData)`.
- `HandleSlotDropped(int targetSlotIndex)`: 맨 앞에 분기 추가 -
  ```csharp
  if (dragCoordinator.IsRedirect)
  {
      dragCoordinator.MarkDropHandled();
      handler.HandleRedirectMove(dragCoordinator.DraggedUnit.Id, targetSlotIndex);
      return;
  }
  ```
- `HandleActivityGhostEndDrag(PointerEventData)`: `dragCoordinator.EndDrag()`만 호출하고 끝 - 슬롯 리프레시가 필요 없다(다음 프레임 `TickActivityOverlays()`가 새 목적지 위치로 자연히 다시 그린다). 빈 곳에 드롭해도(취소) 활동은 그대로 유지된다 - 기존 유닛 아이콘 드래그의 "빈 곳 = 제거" 규칙과 다르다(고스트를 드래그하다 놓쳤다고 진행 중인 이동 자체가 취소되면 안 된다).
- `TickActivityOverlays()`에서 `gridView.SetActivityOverlays(overlays, HandleActivityGhostBeginDrag, HandleIconDrag, HandleActivityGhostEndDrag)`로 콜백 3개를 넘기도록 호출부 확장(`HandleIconDrag`는 드래그 고스트 아이콘 위치 갱신뿐이라 유닛 아이콘 드래그와 동일 델리게이트를 그대로 재사용).

## 7. 이 설계가 건드리지 않는 것

- 유닛 아이콘 자체를 다시 드래그해 재조정하는 기존 기능(설계 25번 §3.2 안전장치) - 고스트 드래그와 별개 경로로 공존한다. 두 드래그가 동시에 발생할 수는 없다(하나의 `FormationDragCoordinator`가 한 번에 하나의 드래그만 추적).
- 경로선(`FormationPathLineView`) 자체의 세그먼트 렌더링 로직 - §5에서 정리했듯 입력 waypoints가 이미 올바르게 치환되어 들어오므로 무변경.
- 마차/시설 최소 개수 제한(기획 20번 §3.4, 2026-09-07 수정 - 마차만 적용) - 이번 기능과 무관, 그대로 유지.

1. `FormationPathInterpolation`에 `Locate`/`ApplyPartialSegment` 추가, `Evaluate`를 `partialSegmentIndex`/`Weight` 지원하도록 일반화(기존 2-인자 호출 하위 호환).
2. `FormationActivity.PartialSegmentIndex`/`PartialSegmentWeight` 추가.
3. `IFieldFormationActivityRepository.RedirectMove` 시그니처 확장 + `InMemoryFieldFormationActivityRepository` 구현.
4. `IFormationEditingHandler.HandleRedirectMove(...)` 추가 + `FieldFormationPanel`(실제 로직)/`HubFormationPanel`(빈 구현) 구현.
5. `FormationMovePathVisual`에 `PartialSegmentIndex`/`Weight` 추가, `FormationGridEditor.TickActivityOverlays`가 전달.
6. `FormationGridView`에 `BuildWaypoints` 헬퍼 추가(`SetPathLines`/`SetTravelerIcons` 공유), `ApplyPartialSegment` 적용.

8. `FormationActivityOverlayVisual.IsRedirectableTarget`, `FormationActivityOverlayView` 드래그 인터페이스, `FormationDragCoordinator.IsRedirect`/`BeginRedirect`, `FormationGridEditor` 배선(§6).

## 9. 실전 검증 체크리스트

1. ✅ 이동 중인 유닛의 도착 고스트를 드래그해 빈 슬롯으로 놓으면, 리다이렉트 순간 캐릭터가 스냅/순간이동 없이 정확히 그 자리에서부터 자연스럽게 새 방향으로 이어서 움직이는지(같은 방향 미세 조정 - "전진" 케이스) - 실전 확인 완료.
1-1. ✅ 진행 방향과 반대쪽으로 목적지를 바꾸면(반전 케이스), 원래 가던 방향으로 한 칸 더 갔다가 되돌아오지 않고 짧게 되돌아가는지 - 실전 확인 완료("자연스럽게 동작한다").
2. ✅ 소요시간이 진행된 만큼 반영돼 있는지(다시 처음부터 시작하지 않는지) - 실전 확인 완료.
3. ✅ 새 목적지가 이미 점유돼 있으면 그 유닛도 자신의 원래 출발지 쪽으로 이동을 시작하는지(맞바꾸기) - 실전 확인 완료.
4. ✅ 고스트를 빈 곳에 드롭(취소)해도 기존 이동이 그대로 계속되는지(취소되지 않는지) - 실전 확인 완료(출발 슬롯 아이콘 재조정 드래그의 빈 공간 드롭 케이스로 검증, 2026-09-07).
5. ✅ 같은 유닛을 여러 번 연속으로 리다이렉트해도 옛 목적지들의 우회 경로가 화면에 누적되어 남지 않는지 - 실전 확인 완료(스크린샷 기반 버그 수정 후 재검증).
6. ✅ 리다이렉트 직후 인카운터가 발생해도 중단 지점 계산이 정상 동작하는지(전장 스폰 위치가 화면에 보이던 위치와 일치하는지) - 실전 확인 완료.
7. ✅ 유닛 아이콘 자체를 다시 드래그하는 기존 재조정 기능이 여전히 정상 동작하는지(회귀 없음) - 실전 확인 완료.
8. ⬜ Hub 정비창에서는 이 상호작용 자체가 나타나지 않는지(활동이 없으므로 고스트 자체가 없음) - 아직 명시적으로 확인되지 않음(Hub는 진행 활동이 없어 논리적으로는 안전하나 미검증).

## 10. 대각선 이동 확장 (2026-09-07 추가, 사용자 확정)

드래그 재배치(일반 재조정 + 고스트 리다이렉트 둘 다) 시 대각선 경로도 허용한다 - 배치된 타일을 침범하지 않는 선에서.

**확정 사항(사용자, 2026-09-07)**:
- 대각선 1칸 소요시간은 직선의 √2배(실제 거리 비례) - 같은 취급(1배)이 아니다.
- 모서리 컷팅 차단 - 대각선 이동의 양옆 두 직선 이웃이 모두 점유돼 있으면 그 사이를 대각으로 지나갈 수 없다.

**구현**:
- `FormationPathFinder`: BFS(무가중치) → 다익스트라(가중치, 그리드가 작아 우선순위 큐 없이 선형 탐색으로 충분)로 교체. 이웃을 4방향→8방향으로 확장, 대각선 비용은 `DiagonalCost`(√2) 상수. 모서리 컷팅은 대각 이동 시 양옆 두 직선 이웃이 모두 점유(`blocked`)면 그 대각 후보 자체를 건너뛴다.
- `SegmentCost(a, b, columnCount)`: 이미 확정된 경로 위 인접 두 슬롯 사이의 비용(직선 1 / 대각선 √2)을 재계산 - 소요시간 계산과 보간 가중치가 같은 값을 공유하도록 공용 헬퍼로 뽑았다.
- `TotalCost(path, columnCount)`: 경로 전체 비용 합계 - 소요시간 계산에 쓴다(`FormationTiming.MoveSecondsPerSlot` 곱함).
- `ComputeSegmentWeights(pathSlotIndices, columnCount, partialSegmentIndex, partialSegmentWeight)`: 경로의 구간별 비용 배열을 만든다(부분 구간만 남은 비율 곱함) - `FormationPathInterpolation.Locate`/`Evaluate`에 그대로 넘긴다.
- `FormationPathInterpolation.Locate`/`Evaluate`: `(partialSegmentIndex, partialSegmentWeight)` 스칼라 2개 대신 `IReadOnlyList<float> segmentWeights`(구간별 가중치 배열, null이면 전 구간 1 - 하위 호환) 하나를 받도록 일반화했다. `ApplyPartialSegment`는 무변경(순수 기하 보간이라 비용 단위와 무관).
- `FieldFormationPanel.StartMove`/`HandleRedirectMove`: 소요시간 계산을 `path.Count-1`(칸 수) 기반에서 `FormationPathFinder.TotalCost(...)`(실제 비용 합) 기반으로 교체. §3의 "전진 vs 반전" 비교도 칸 수가 아니라 비용으로 비교(대각선 구간이 섞이면 칸 수만으로는 어느 쪽이 더 빠른지 정확히 알 수 없다).
- `FormationGridView.SetTravelerIcons`/`LiveBattleSimulationRule.ComputeAllyPositionForSlot`: `Evaluate` 호출 전에 `ComputeSegmentWeights`로 배열을 만들어 넘기도록 갱신.
- `FormationPathLineView`(경로선 렌더링)는 무변경 - `PlaceSegment`가 이미 `Atan2`로 임의 각도를 계산해 대각선도 그대로 그린다.
- `FormationActivity`는 무변경 - `PartialSegmentIndex`/`PartialSegmentWeight` 두 필드만으로 충분하다(구간별 기본 비용은 저장하지 않고 `PathSlotIndices`+그리드 열 수로 그때그때 다시 계산 - 상태 중복 없음).

### 10.1 이 확장이 건드리지 않는 것

- `FormationActivity`/`IFieldFormationActivityRepository`/`IFormationEditingHandler`의 필드·시그니처 - 전부 §2~§6에서 이미 확정된 그대로다. 대각선은 순수하게 "경로 계산 결과"와 "그 결과를 소요시간/보간으로 환산하는 공식"만 바뀐다.
- 드래그 상호작용(§6) - 유닛 아이콘 드래그, 고스트 드래그 둘 다 무변경. `FormationPathFinder.FindPath`가 이제 대각선을 포함한 경로를 돌려줄 뿐, 호출 방식은 그대로다.

### 10.2 실전 검증 체크리스트(추가)

1. ✅ 대각선 방향으로 드래그 재배치하면 대각선 경로로 이동하는지(직선 두 번이 아니라) - 실전 확인 완료(2026-09-07).
2. ✅ 대각선 이동의 소요시간이 직선보다 더 걸리는지(√2배) - 잔여초 표시가 정수 반올림이라 배율까지 눈으로는 확인 어려우나, 계산 로직상 정확히 반영됨(대각선 경로 자체가 정상 작동하는 것으로 간접 확인, 2026-09-07).
3. ✅ 점유된 두 타일이 모서리로 맞닿아 있으면 그 사이를 대각으로 통과하지 않고 우회하는지(모서리 컷팅 차단) - 실전 확인 완료(2026-09-07).
4. ✅ 대각선 구간이 섞인 경로에서 고스트 리다이렉트(전진/반전 포함)를 해도 순간이동/스냅 이상 없이 정상 동작하는지 - 실전 확인 완료(2026-09-07).
5. ✅ 인카운터로 대각선 이동 중 중단돼도 중단 지점이 화면에 보이던 위치와 정확히 일치하는지 - 실전 확인 완료(2026-09-07).

## 11. 실전 버그 수정 기록 (2026-09-07, 대각선 확장 이후)

세 건 모두 실전 검증 완료.

1. **드래그 고스트 미제거**: 도착 고스트를 드래그해 놓지 않은 채 유닛이 목적지에 도착(활동 완료)하면, 오버레이는 사라져도 별도 오브젝트인 드래그 고스트만 화면에 남아 마우스 커서를 계속 따라다녔다. `FormationGridEditor.CancelDragIfRedirectingUnit(unitId)`를 추가해 `FieldFormationPanel`의 활동 완료/취소 이벤트 핸들러에서 호출 - 드래그 중인 유닛의 활동이 끝나면 드래그 상태를 즉시 정리한다.
2. **출발지 오점유 판정**: `FormationLayout`은 이동 완료(Complete) 전까지 출발 슬롯을 계속 점유 중으로 기록한다(설계 의도, §3 주석 참고 - 완료 처리 로직이 그 값에 의존). 이 값을 "목적지 점유 여부" 판정에 그대로 쓰면, 이동 중인 유닛의 출발지로 다른 유닛을 드래그했을 때 점유로 오인해 원래 이동이 취소되고 엉뚱한 맞바꾸기가 일어났다. `FieldFormationPanel.GetOccupantTreatingMovedOriginAsEmpty(layout, slotIndex)`를 추가해 `HandleGridMove`/`HandleRedirectMove`의 점유 판정에서만 사용 - 그 슬롯이 어떤 유닛의 "지금 멀어지고 있는 출발지"와 정확히 일치할 때만 빈 것으로 취급한다(데이터 자체는 무변경).
3. **출발 슬롯 아이콘 드래그 예외처리**: 이동 중인 유닛의 출발 슬롯 아이콘(레이아웃 상 여전히 점유 중으로 기록돼 평범한 배치 아이콘처럼 집힌다)을 일반 그리드 이동으로 드래그하면, 활동이 취소+재시작되며 출발지로 순간이동한 뒤 처음부터 다시 이동하는 것처럼 보였다. `FormationDragCoordinator.BeginRedirectFromGrid`(출발 슬롯을 픽업하되 `IsRedirect=true`)를 추가하고, `FormationGridEditor.HandleGridIconBeginDrag`에서 집으려는 슬롯이 그 유닛 자신의 현재 이동 출발지와 일치하면 이 경로로 전환 - 도착 고스트 드래그와 동일하게 `HandleRedirectMove`로 처리된다. 빈 곳 드롭 시 취소되지 않고 기존 이동이 유지되도록 `HandleIconEndDrag`도 `IsRedirect`일 때 `HandleRemove` 호출을 건너뛰게 정정했다.
