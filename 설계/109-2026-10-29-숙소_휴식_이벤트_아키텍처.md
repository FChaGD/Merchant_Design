## 3. 데이터·조건·이력 (섹션 1, 승인)

### 3.1 이벤트 테이블 (Encounter.xlsx)

| 변경 | 내용 |
|---|---|
| Event 시트 `Place` 열 | `Trip`/`Rest`. 빈칸 = `Trip`(기존 행 수정 불필요) |
| `EventEntry.Place` | `EventPlace { Trip, Rest }`, 기본 `Trip` |
| **EventStrings 시트(신규)** | `Id`, `Title` — 진행 화면 기록 목록의 이벤트 제목(기획 108 §3.4). `PersonStrings`와 같은 문자열 분리 방식. `Rest` 이벤트는 필수(없으면 임포트 오류), `Trip`은 선택 |
| `EventEntry.Title` | 임포트 시 EventStrings에서 채움. 없으면 빈 문자열(표시는 "값 없음") |
| 중요도·반복·가중치 | 기존 칸 그대로 |

- 별도 시트 대신 열을 둔 이유: Yarn 노드·검증기·임포터가 이벤트 목록 하나만 다룬다.
- 조회자(`IEncounterContentReader`)에 장소별 목록 `EventsAt(EventPlace)`를 추가한다. 등록 시 한 번 나눠 두고 판정마다 거르지 않는다.
- 상행 이벤트 고르기(`EventEncounterSelector`)와 디버그 강제 시작은 `Trip` 목록만, 휴식은 `Rest` 목록만 받는다.

### 3.2 조건

| 조건 | 상행 | 휴식 |
|---|---|---|
| `town:도시Id`(신규) | 항상 거짓 | 현재 체류 도시와 같으면 참 |
| `region:지역Id` | 출발·도착 도시 지역(현행) | 현재 체류 도시의 지역 |
| `from`·`to`·`road`·`progress`·`quest` | 현행 | 거짓(구간 없음) |
| `month`·`date`·`flag`·`seen` | 현행 | 동일 |

- `EncounterConditionContext`에 `HasTown`, `TownCityId`, `TownRegionId`를 더한다. 상행 문맥은 `HasTown = false`.
- `region` 판정: `HasLeg`면 출발·도착 지역, 아니면 `HasTown`이면 체류 도시 지역, 둘 다 아니면 거짓.
- 휴식 문맥 생성은 휴식용 문맥 공급자(§5.3)가 현재 위치(`ITripCurrentLocationReader`)·지도(`IWorldMapReader`)·날짜·이력으로 채운다. 팩토리에 휴식용 생성 메서드를 추가한다.

### 3.3 이력

- 플래그·발생 기록은 상행과 공유(현행 저장소).
- "반복 = 휴식 1회당 1번": 기존 "이번 상행" 기록을 **"이번 회차(상행 1회 또는 휴식 1회)"**로 넓힌다. 휴식 시작 시 휴식 이벤트 진행자가 `ResetTrip()`을 부른다. 상행 시작 때도 이미 비우므로 상행 판정에는 영향 없음.
- 계약 이름(`OccurredThisTrip`·`ResetTrip`)은 유지하고 요약 주석에 회차 의미를 적는다(호출부 전부 수정을 피함). 디버그 버튼 문구 "이번 상행 초기화" → "이번 회차 초기화".

### 3.4 검증

| 경우 | 처리 |
|---|---|
| `Rest` 이벤트 대본에 상행 전용 명령(`battle`·`delay`·`difficulty`) | 검증기 오류(자산 테스트) |
| `Trip` 이벤트 대본에 휴식 전용 명령(`rest_end`, §5.4) | 검증기 오류(자산 테스트) |
| `Rest` 행에 상행 전용 조건(`from`·`to`·`road`·`progress`·`quest`) | 임포트 오류 |
| `Trip` 행에 `town` 조건 | 임포트 오류 |
| `Rest` 행 EventStrings 제목 없음 | 임포트 오류 |

- (2026-10-29 검진 후 개정, 사용자 결정) 오류 검사는 두 곳으로 나눈다 — 표 한 행으로 아는 검사는 임포터가 임포트를 막고, 대본·다른 테이블과 맞춰 봐야 아는 검사는 검증기(`EncounterContentValidator`)가 자산 테스트에서 알린다. 같은 검사를 두 곳에 두지 않는다. 장소 이름 문구는 `EventPlaceNames`를 함께 쓴다.

- 명령별 허용 장소는 명세 표(`EventCommandSpecs`)의 `EventCommandSpec`에 `Places` 값(Trip/Rest/Both)으로 둔다 — 등록·검증·선언이 같은 표를 읽는 현행 구조 유지. 조건 키별 허용 장소도 `EncounterConditionKeys`에 같은 방식으로 둔다.

## 4. 하루 진행 흐름 (섹션 2, 승인)

### 4.1 구성

| 단위 | 계층 | 담당 |
|---|---|---|
| `RestProgressRun`(개정) | 순수 C# | 하루치 대기 시간만 잰다. 하루 대기가 끝나면 경계에서 멈추고 `BeginNextDay()` 전까지 진행하지 않는다. 한 프레임 여러 날 넘김 제거 |
| `InnRestDayFlow`(신규) | 순수 C# | 하루 순서 상태 기계, 종료 사유, 성립 일수·실제 지출 합계, 이벤트 기록 목록 |
| `InnRestProgressPanel`(개정) | UI | 코루틴·실제 시간(unscaled) 진행·표시. 흐름 객체의 `Changed` 알림으로 다시 그림 |
| `InnRestService`(개정) | Bootstrap 상주 | 하루 결제·날짜·회복 연결 지점 |

### 4.2 `InnRestDayFlow` 상태

```
Waiting ──대기 완료──▶ FixedCheck ──후보 있음──▶ FixedEvent ──끝(강제 종료 아님)──▶ RandomCheck
                           │ 없음                     │ 강제 종료                         │
                           └──────────────▶ RandomCheck  └──▶ Ended(ForcedByEvent)         │
RandomCheck ──발생──▶ RandomEvent ──끝──▶ Settle  /  미발생 ──▶ Settle
Settle ──결제 성공──▶ (성립 일수 +1) ──남은 날 있음──▶ Waiting / 마지막 날 ──▶ Ended(Completed)
       ──결제 실패──▶ Ended(InsufficientGold)
Waiting ──중단 버튼──▶ Ended(Stopped)
```

- 이벤트 단계 진입 시 이벤트 실행기(§5.2)에 시작을 요청하고, 끝 콜백(`RestEventOutcome { EventId, Title, ResultSummary, ForcedEnd }`)을 받으면 다음 단계로 간다. 실행기가 없거나 시작 실패(화면 없음·대본 없음)면 "발생 없음"으로 보고 넘어간다.
- 이벤트가 끝날 때마다 기록 목록에 `(일차, 제목, 결과 요약)`을 추가한다. 일차 = 성립 일수 + 1(그날).
- `CanStop` = `Waiting`일 때만 참. 패널은 이 값으로 중단 버튼 표시를 정한다.
- `Abort()`: 비정상 종료(패널 Close·Dispose). 실행 중 이벤트가 있으면 실행기에 중단을 요청하고 `Ended(Stopped)`로 끝낸다.
- 흐름 객체는 Unity를 모르고 실행기·서비스를 인터페이스로 받는다 — 순서·사유를 EditMode로 검증.

### 4.3 휴식 서비스 계약

```csharp
public enum RestDaySettlement { Paid, InsufficientGold }

public interface IInnRestService
{
    int CostPerDay { get; }
    void BeginRest(int plannedDays);
    RestDaySettlement SettleDay();   // AdvanceDay 대체
    void EndRest(int restedDays);
}

/// 휴식 1일 성립 시 회복(기획 108 §3.1). 지략·행정력 구현 때 구현체 등록 - 지금은 없음.
public interface IRestDayRecovery { void RecoverOneDay(); }
```

- `SettleDay`: `IGoldSpender.TrySpend(CostPerDay)`(개인 → 상자 자동 인출). 성공 → `IDateAdvancer.AdvanceDays(1)` → `IRestDayRecovery?.RecoverOneDay()` → `Paid`. 실패 → 상태 변경 없이 `InsufficientGold`.
- 지갑 직접 차감(`IPlayerCurrencyWallet`) 의존은 제거하고 `IGoldSpender`·`IRestDayRecovery`를 선택적으로 조회한다. `IGoldSpender`가 없으면 경고 후 결제 없이 `Paid`(현행 "지갑 없음" 동작과 같은 성격).
- `InnRestSession`의 "하루 더 보낼 수 있는가" 판정은 유지하고 `SettleDay` 앞에서 쓴다.

### 4.4 종료 사유와 결과 문구

| 사유 | 형식(문구는 제작 때 확정) |
|---|---|
| Completed | "n일 휴식 완료, 비용 x" |
| Stopped | "n일 휴식 중단, 비용 x" |
| ForcedByEvent | "n일 휴식 후 이벤트로 종료, 비용 x" |
| InsufficientGold | "골드 부족으로 n일에서 종료, 비용 x" |

- n = 성립 일수, x = 실제 지출 합계(n × 1일 비용).

### 4.5 휴식 시작 차단 (기획 94 4-11 개정)

- `InnRestPlan.BlockReason`이 개인 골드 대신 "지불 가능 여부"(`IGoldSpender.CanAfford(총 비용)`)를 받는다. 문구 "골드가 부족합니다."
- 숙소 화면은 표시용 `IGoldHoldingsReader`에 더해 `IGoldSpender`를 받아 판정한다(변경 이벤트도 같은 계약에 있음).

## 5. 이벤트 실행

### 5.1 효과 명령 라우터 (공용)

현재 Yarn 명령은 실행기에 한 번만 등록할 수 있고, Field 이벤트 진행자(`EventEncounterCoordinator`)가 자기 진행자로만 중계한다. 휴식 진행자가 생기면 같은 명령이 지금 실행 중인 진행자를 찾아가야 한다.

| 단위 | 계층 | 담당 |
|---|---|---|
| `EventEffectCommandRouter`(신규) | Bootstrap 상주 `IManagedComponent` | 명령 등록을 한 번만 한다. `IEventEffectRouter`로 DI 등록 |
| `IEventEffectRouter` | 계약 | `Enter(IEventEffectHost host, EventEffectServices services)` / `Exit(IEventEffectHost host)` |

- 명령 객체(`EventEffectCommands`)는 고정된 서비스·호스트 대신 라우터의 "현재 맥락"을 읽는다. 맥락이 없으면 `IsRunning = false`로 보여 모든 명령이 효과 없이 지나간다(현재 Drain 동작과 같음).
- 진행자가 이벤트를 시작할 때 Enter, 끝(정상·중단 모두)에 Exit. 이미 다른 맥락이 들어와 있으면 경고 후 덮어쓴다(상행과 휴식은 동시에 일어나지 않음 — 방어).
- 서비스 묶음은 맥락마다 다르다: 상행 = 현행 전부, 휴식 = 골드·무역품·합류/이탈 + 휴식 종료 요청(§5.4). 휴식 묶음에 없는 서비스(상행 시계·도로 난이도·전투)는 null → 명령은 경고 후 건너뜀(검증기가 사전에 막으므로 정상 경로엔 없음).
- `EventEncounterCoordinator`의 명령 등록·`HostRelay`·서비스 조립은 라우터로 옮긴다. 서비스 조립 공용 부분(골드·무역품·명단)은 라우터가 한 번 만들어 두고, 각 진행자 껍데기는 자기 맥락 전용 서비스만 더해 묶음을 만든다.
- 등록 위치: `ManagerHierarchyInstaller`의 managedComponents(대사 실행기 뒤).

### 5.2 진행자 변경 (`EventEncounterDirector`)

| 변경 | 이유 |
|---|---|
| `bool TryBegin(EventEntry entry)` 공개 | 휴식 흐름이 직접 고른 이벤트를 시작한다(디버그 시작과 같은 경로, 조건 무시는 호출자 책임) |
| `event Action<EventFinish> Finished` | 끝날 때(기록 여부·이벤트 Id 포함) 알림 — 휴식 흐름 재개용. 상행은 기존 신호(EventEnded) 유지 |
| `void Abort()` 공개 | 현행 `TripEnded` 방어 분기(기록·신호 없이 종료 + Drain)를 메서드로 추출해 휴식 비정상 종료에도 쓴다 |
| 결과 줄 수집 | 이벤트마다 `PresentResult` 텍스트를 모아 `EventFinish.ResultLines`로 넘긴다 — 기록 목록의 결과 요약 |
| 라우터 Enter/Exit | `EventEncounterSources`에 맥락 서비스 묶음·라우터를 받아 시작·끝에서 호출 |

- 상행 정지(`Halt`)·마일스톤·전투·Field 가림은 이미 선택적 — 휴식 인스턴스는 null로 만든다.
- `OnEventCheck`(상행 판정)는 `EventsAt(Trip)`만 쓴다.

### 5.3 휴식 이벤트 진행자 (`InnRestEventCoordinator`)

- Bootstrap 상주 `IManagedComponent`(별도 매니저 오브젝트, `InnRestService` 옆). 등록 계약:

```csharp
public readonly struct RestEventOutcome { string EventId; string Title; string ResultSummary; bool ForcedEnd; }

public interface IRestEventRunner
{
    bool IsRunning { get; }
    void BeginRestSpan();                                 // 회차 이력 초기화(§3.3)
    bool TryStartFixed(Action<RestEventOutcome> onDone);  // 후보 없음·시작 실패 = false
    bool TryStartRandom(Action<RestEventOutcome> onDone);
    void Abort();
}

public interface IRestEventViewBinder { void BindScreens(IEventEncounterScreens screens); }
```

- 내부: `EventEncounterDirector` 인스턴스 1개(Halt·Milestones·Battle·UIHide = null), 휴식 문맥 공급자, 휴식 강제 종료 요청 상태, `Update`에서 진행자 `Tick`(대사 재생). 화면이 언로드되면(IsAvailable false) 다음 프레임에 연결을 끊는다(Field 껍데기와 같은 방식).
- 인스펙터 값: 랜덤 1일 확률 `randomChancePerDay = 0.35`.
- 콘텐츠·이력·대사 실행기 중 하나라도 없으면 `TryStart*`가 항상 false — 휴식은 이벤트 없이 진행.
- 휴식 진행자도 퀘스트 확정 사건용 `EventStarted`를 중계할지: 휴식 이벤트는 `quest` 조건을 쓸 수 없으므로(§3.4) 중계하지 않는다.

### 5.4 휴식 강제 종료 명령

| 명령 | 장소 | 동작 | 결과 줄 |
|---|---|---|---|
| `<<rest_end>>` | Rest | 휴식 진행자의 종료 요청 상태를 켠다. 대본은 끝까지 계속 | 「휴식이 중단되었다」(문구 제작 때 확정) |

- 효과 서비스에 `IRestEndRequest { void RequestEnd(); }`를 추가. 휴식 맥락에서만 채운다.
- 진행자 끝 알림에서 종료 요청 상태를 읽어 `RestEventOutcome.ForcedEnd`에 싣고 상태를 지운다.

### 5.5 후보 고르기 (`RestEventSelector`, 순수 함수)

| 함수 | 규칙 |
|---|---|

## 6. Hub 화면

### 6.1 배치

- Hub 씬 `SceneUIRoot` 하위에 이벤트 대화 화면·선택 화면·회수 적재 패널을 배치한다. 조립은 기존 `FieldEventUIBuilder`와 회수 적재 조립 로직을 `HubSceneInstaller`가 호출한다. 회수 적재 조립은 지금 `FieldUIInstaller` 내부 private 메서드(`BuildCargoRecoveryPanel`)이므로 공용 빌더(`CargoRecoveryUIBuilder`, internal static)로 먼저 추출해 두 인스톨러가 함께 쓴다(인스톨러 간 내부 메서드 공유 금지 규칙). 마커 Id가 `Field.CargoRecovery.Root`처럼 Field 접두 문자열이지만 씬이 달라 충돌하지 않으므로 그대로 둔다.
- 시설 화면(휴식 진행 화면) 위에 그려지는 팝업 레이어에 둔다. 정확한 레이어·정렬 순서는 제작 때 기존 Hub 모달 레이어 규칙에 맞추고 겹침 실측 점검(CLAUDE.md "UI 배치 겹침 점검")을 한다.
- 요소 Id는 기존 `FieldEventUIElementIds`·회수 적재 Id를 그대로 쓴다(씬이 달라 충돌 없음).

### 6.2 화면 묶음

- `FieldEventScreens`를 그대로 재사용한다. Hub에서는 상단 버튼(`IFieldTopButtons`)·정비창 열람 모드를 null로 넘긴다 — 휴식 중엔 재화·날짜 HUD 입력이 이미 막혀 있고(설계 103 §3), 숙소 화면이 마을 버튼을 가린다.
- **정비창 보기 버튼은 Hub에서 숨긴다**(내 판단): Hub 정비창은 편집 화면이고 열람 전용 모드가 없어, 이벤트 중에 대열을 바꿀 수 있게 된다. 대화·선택 뷰에 "정비창 보기 표시 여부" 설정을 추가하고 Hub 배선이 끈다.
- 회수 적재: Hub용 `FieldCargoRecoveryPanel` 인스턴스를 만들어 넘긴다 — 상행과 같은 정리 → 포기 확인 흐름(기획 108 §3.5).
- 배선: `HubUIWiring`이 Hub 로드마다 `IRestEventViewBinder.BindScreens(...)`. 패널은 팝업 패널로 등록(시설 화면을 닫지 않음).

### 6.3 휴식 진행 화면 표시 (기획 108 §3.4)

| 요소 | 변경 |
|---|---|
| 게이지 | 대기 단계에서만 차오름. 이벤트·하루 처리 중 정지 |
| 일수 | "n / 총 m일" — n = 성립 일수 |
| 날짜 | 실제 오늘 날짜(`IDateReader.Today`). 날짜는 성립 시에만 넘어가므로 시작 + n과 같다 |
| 누적 비용 | 실제 지출 합계 |
| 예상 남은 개인 골드 / 골드 상자 | 남은 비용 = (m − n) × 1일 비용. `IGoldSpender.PreviewWithdrawal(남은 비용)`으로 인출될 상자 수를 구해 개인 = 현재 개인 + 인출 상자 × 가치 − 남은 비용, 상자 = 현재 적재 골드 − 인출 상자 × 가치. 합계로도 모자라면 "부족" 표시 |
| 이벤트 영역 | 기록 목록 — 한 줄 `n일차 제목 — 결과 요약`, 누적. 결과 상태에서도 유지. 결과 요약이 없으면 제목만 |
| 중단 버튼 | `CanStop`일 때만 표시 |
| 결과 | §4.4 문구 |

- 재렌더 시점: 흐름 객체 `Changed`, 골드 `Changed`(이벤트 골드 효과). 매 프레임은 게이지만.
- 이벤트 영역 요소는 현재 빈 자리(기획 94 4-7)에 텍스트 레이블을 추가한다(인스톨러 get-or-create). 줄이 넘치면 위에서부터 잘리게 둔다 — 휴식 최대 30일·하루 최대 2건이라 스크롤은 넣지 않는다(내 판단, 실측에서 넘치면 제작 중 보고).
- "회복 표시 자리"는 그대로 비워 둔다(지략·행정력 구현 때).

## 7. 디버그

- 기존 인카운터 디버그 화면(`EncounterDebugView`)에 휴식 항목을 추가한다: "다음 휴식일 강제 이벤트" 선택(Rest 이벤트 Id) — 다음 확정 점검에서 조건·횟수를 무시하고 그 이벤트를 시작한다. 계약 `IRestEventDebug { void ForceNext(string eventId); }`를 휴식 진행자가 구현.
- 이력 초기화 버튼 문구 변경(§3.3).
- 별도 인스톨러 없음 — 기존 디버그 도구 인스톨러에 포함되어 있다(제작 때 확인).

## 8. 내구도 효과 연결 지점 (설계 91 D와의 접점)

- 설계 91 §6.2 "마지막 마차 0 → 화물 포기 → 궤주"는 상행 맥락 규칙이다. 휴식 맥락은 기획 108 §3.6에 따라 **화물을 임시 보관으로 옮기고 휴식을 계속**한다.
- 이 분기를 맥락 서비스로 둔다: 효과 서비스 묶음에 `IEventLastWagonPolicy`(상행 = 궤주 진입점, 휴식 = 임시 보관 이동만)를 D 제작 때 추가하고, 이 문서의 휴식 서비스 묶음 조립 지점(§5.1)에서 휴식 구현을 넣는다.
- D 제작 때 함께 풀 과제(기획 108 §6): 마차 0대 + 임시 보관 남음 상태에서 상단 물류품 팝업 닫기 차단 규칙(기획 39 §3.5)과의 충돌.
- 이번 제작에서는 `durability` 명령이 없으므로 휴식 이벤트 대본에 쓰면 검증기가 "모르는 명령"으로 막는다(현행).

### 10.1 Play 확인 항목 (사용자 실행)

1. 이벤트 없는 휴식(완주·중단) — 기존과 같게 진행, 중단 버튼은 대기 중에만.
2. 확정 휴식 이벤트 — 게이지 정지 → 전체화면 이벤트 → 복귀 후 재개, 기록 목록 한 줄.
3. 강제 종료 이벤트 — 그날 미성립(날짜·비용 그대로), 결과 문구.
4. 골드 손실 이벤트로 결제 부족 → 골드 부족 종료, 상자 인출 확인.
5. 무역품 획득 공간 부족 → Hub 회수 적재 정리 → 포기 확인.
6. 상행 이벤트 회귀(라우터 이관 후 상행 이벤트·효과 정상).
7. 겹침 실측: 이벤트 화면·회수 적재 패널이 휴식 진행 화면·HUD 위에 정상 표시.

## 12. 미정·후속

- 이벤트 화면 클래스의 `Field` 접두사(`FieldEventScreens`·뷰·회수 적재 패널)를 Hub에서도 쓰게 된다 — 이름 정리는 MonoBehaviour 참조 보존 문제가 있어 이번 범위에서 제외, 후속 리팩토링 후보.
