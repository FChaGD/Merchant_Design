## 1. 범위 재확인

34번 문서가 지목한 enum 9종(`MercenaryClass`/`EnemyType`/`RoleGroup`/`TargetPriority`/`LocalPositioning`/`SelfPreservation`/`EnemyRecognitionType`/`ActivityRadiusPreset`/`PursuitPreset`)을 제거하고 문자열 식별자로 전체 교체한다. 아래 §2는 34번 §4가 "설계 단계 대상"으로 미뤄둔 실제 영향 범위 조사 결과다.

## 2. 실제 조사 결과 — 92개 파일의 실체

파일을 열어 직접 확인한 결과, "이 enum들이 게임 로직을 분기한다"는 34번 문서의 우려는 **일부만 해당**한다. 92개 파일 대부분은 분기 로직이 아니라 필드/매개변수 타입 선언이다.

### 2.1 실제 분기(switch) 지점 — 8곳뿐

| 파일 | 대상 enum | 형태 |
|---|---|---|
| `Core/Battle/Tactics/TargetSelectorFactory.cs` | TargetPriority | `switch` 식 → 전략 객체 |
| `Core/Battle/Tactics/PositioningStrategyFactory.cs` | LocalPositioning | 〃 |
| `Core/Battle/Tactics/ActivityRadiusZoneFactory.cs` | ActivityRadiusPreset | 〃 |
| `Core/Battle/Tactics/EnemyRecognitionTrackerFactory.cs` | EnemyRecognitionType | 〃 |
| `Core/Battle/Tactics/PursuitPolicyFactory.cs` | PursuitPreset | 〃 |
| `Core/Battle/Tactics/SelfPreservationModifierFactory.cs` | SelfPreservation | 〃 |
| `Core/UI/Field/Battle/BattlePlaceholderSprite.cs`(`ForEnemyType`) | EnemyType | `switch` 식 → Sprite |
| `Core/Battle/BattleTest/BattleTestSpawnPointReservations.cs`(`GetCount`) | EnemyType | `switch` 식 → int(배틀테스트 전용) |

**형태가 전부 동일하다**: `enum switch { EnumValue => 결과, ... }`. `RoleGroup`/`MercenaryClass`는 분기 대상이 아니라, `if (unit.RoleGroup == RoleGroup.Frontline)` 같은 **동등 비교**로만 쓰인다(`FrontlineFormationCoordinator.cs` 등) — 문자열로 바꿔도 `==` 비교는 그대로 성립해 사실상 무변경.

### 2.2 진짜 규모 — 대부분은 "타입 선언"

나머지 84개 안팎 파일은 이 enum들을 필드 타입(`MercenaryClass Class`), 매개변수 타입(`GetStats(MercenaryClass mercenaryClass)`), 또는 테이블 엔트리 구조체의 컬럼 타입으로만 갖고 있다 — 분기 로직이 없다. 교체는 "타입을 `string`으로 바꾼다"는 기계적 작업이고, 동작이 바뀌는 지점이 아니다.

**결론**: 34번 문서가 우려한 "전투 AI 분기 로직 전체 재설계"는 실제로는 **8개 파일의 8개 switch 식**으로 한정된다. 나머지는 위험도가 낮은 타입 치환이다. (여전히 인스펙터 드롭다운 UX 손실 등 다른 트레이드오프는 있다 — §5 참고.)

## 3. 문자열 식별자 표기 규칙

**enum 멤버 이름을 그대로 문자열로 쓴다**(예: `MercenaryClass.Warrior` → `"Warrior"`, `LocalPositioning.Blocking` → `"Blocking"`). 14번 문서 §3.1(v1)이 원래 쓰던 방식으로 되돌아가는 것과 같다.

33번 문서(아이템)의 kebab-case 슬러그(`"iron-sword"`)와 다른 표기를 쓰는 이유: 아이템 슬러그는 순수 콘텐츠 식별자라 사람이 새로 짓는 이름이지만, 이 9종은 **여전히 C# `switch` 케이스 라벨과 1:1 대응**해야 한다(§2.1). 기존 enum 멤버 이름을 그대로 쓰면 `case "Warrior":`처럼 코드 가독성이 유지되고, 시트 값과 코드 케이스 라벨을 대조하기 쉽다. 새 표기를 발명할 이유가 없다.

## 4. 변경 대상별 처리 방식

### 4.1 Factory 8곳 (§2.1)

매개변수 타입만 바뀐다. 예:

```csharp
// 변경 전
public static ITargetSelector Create(TargetPriority priority, IUnitSpatialQuery spatialQuery)
{
    return priority switch
    {
        TargetPriority.Nearest => new NearestTargetSelector(spatialQuery),
        ...
        _ => throw new ArgumentOutOfRangeException(nameof(priority), priority, null),
    };
}

// 변경 후
public static ITargetSelector Create(string priority, IUnitSpatialQuery spatialQuery)
{
    return priority switch
    {
        "Nearest" => new NearestTargetSelector(spatialQuery),
        ...
        _ => throw new ArgumentOutOfRangeException(nameof(priority), priority, null),
    };
}
```

나머지 7곳(§2.1 표)도 동일 패턴으로 처리한다.

### 4.2 테이블 엔트리 구조체

`CharacterStatsEntry.MercenaryClass`, `EnemyStatsEntry.EnemyType`, `MercenaryRoleGroupEntry.{MercenaryClass,RoleGroup}`, `RoleGroupCatalogEntry.RoleGroup`, `TargetPriorityOption.Value` 등 — 필드 타입을 전부 `string`으로 바꾼다. `TableEntryLookup.TryFind`는 이미 제네릭(`TKey`)이라 무변경.

### 4.3 임포터 — `ParseEnum`/`SetEnumValue` → `ParseSlug`

35번 설계에서 만든 `EditorTableReader.ParseSlug(row, column, seenIds)`를 그대로 재사용한다. `CharacterStatsTableImporter` 등 4개 도메인 임포터에서:

```csharp
// 변경 전
MercenaryClass = EditorTableReader.ParseEnum<MercenaryClass>(row, "Id"),
...
EditorTableReader.SetEnumValue(element.FindPropertyRelative("MercenaryClass"), entry.MercenaryClass);

// 변경 후
MercenaryClass = EditorTableReader.ParseSlug(row, "Id", seenIds),
...
element.FindPropertyRelative("MercenaryClass").stringValue = entry.MercenaryClass;
```

`ParseSlug`는 33번 아이템 테이블처럼 "빈 값/시트 내 중복 즉시 예외"만 검증한다 — `Enum.IsDefined`가 주던 "정의되지 않은 값 즉시 차단"은 **임포트 시점이 아니라 Factory 사용 시점**(§4.1의 `_ => throw ArgumentOutOfRangeException`)으로 늦춰진다. 실행 흐름상 태틀 설정 직후(유닛 스폰/전술 갱신)에 바로 걸리므로 사실상 체감 지연은 거의 없지만, "임포트 버튼을 눌렀을 때 바로 알 수 있었던 오탈자"가 "그 값이 실제로 쓰일 때"로 늦춰진다는 점은 감수해야 하는 트레이드오프다.

### 4.4 Catalog `ScriptableObject` 자산 (Inspector 편집성 손실)

`MercenaryRoleGroupMapAsset`/`RoleGroupTacticsCatalogAsset`은 `RoleGroupTacticsCatalogAsset.cs` 자체 주석에 "기획자가 인스펙터에서 바로 편집 가능해야 한다는 요구(11번 §8-1)"가 설계 근거로 적혀 있다. enum 필드는 Unity Inspector에서 자동으로 드롭다운이 되지만, `string` 필드는 자유 텍스트 입력으로 바뀐다 — 사용자 확인 결과(2026-09-23) 항상 Excel 임포트로만 값을 채우고 인스펙터 직접 편집은 안 한다 — 드롭다운 UX 손실이 실사용 워크플로에 영향 없음. 문자열 전환 그대로 진행.

### 4.5 나머지 필드/매개변수 타입 선언 (~84개 파일)

기계적 치환(IDE 타입 변경 + 리팩토링)으로 처리한다. 대표 사례: `LiveBattleSimulationRule.cs`(`IMercenaryUnit.Class`), `PlaceholderCaravanRosterProvider.cs`(`MercenaryClass.Warrior` 리터럴), `UnitTacticsProfileResolver.cs`(`RoleGroup.Frontline` 리터럴+동등비교), `TacticsPanel.cs`(드롭다운 바인딩 — enum 값 대신 문자열 리스트로 옵션 채움, UI 표시 로직 자체는 이미 `RoleGroupTacticsStringsTableAsset`로 라벨 분리돼 있어 영향 적음).

## 5. 트레이드오프 요약 (재확인)

- **얻는 것**: 33번 문서 아이템 시스템과 Id 체계 일관성. 향후 새 옵션(예: 새 `TargetPriority` 값) 추가 시 enum 재컴파일 불필요 — 다만 이 9종은 애초에 "계속 늘어나는 콘텐츠"가 아니라 3~10개 안팎 고정 집합에 가까워, 이 이점이 아이템만큼 크지 않다(34번 문서에서 이미 지적한 지점, 여전히 유효).
- **잃는 것**: `Enum.IsDefined` 즉시 검증(§4.3), Inspector 드롭다운 UX(§4.4, 미확인 영향).
- **생각보다 작았던 것**: 실제 분기 로직 재작성은 8개 switch 식뿐(§2.1) — 34번 문서가 우려한 "대규모 리팩토링"은 파일 개수(92) 기준으로는 맞지만, 로직 위험도 기준으로는 대부분 기계적 타입 치환이다.

## 6. 마이그레이션 순서 (권장)

의존 방향을 따라 아래 순서로 진행 — 각 단계는 컴파일 가능한 상태를 유지한다.

1. 9개 enum 파일 삭제(§ "실제 조사" 표에 나열된 선언 파일).
2. `Core/Table/SlugLocalizedStringEntry`(35번에서 이미 존재) 재사용 확인.
3. 테이블 엔트리 구조체 8종(§4.2) 필드 타입 변경.
4. 4개 도메인 임포터(§4.3) `ParseEnum`→`ParseSlug` 전환.
5. Factory 8곳(§4.1) 매개변수 타입 변경 + 케이스 라벨 문자열화.
6. Catalog 자산 2종(§4.4) 필드 타입 변경.
7. 나머지 ~84개 파일(§4.5) 타입 선언 일괄 치환 — 컴파일 오류를 따라가며 전수 확인(92개 전수 조사를 컴파일러가 대신해준다).
8. `EditorTableReader.ParseEnum<TEnum>`/`SetEnumValue<TEnum>`/`RoleGroupTacticsCatalogAsset`의 열린 제네릭 관련 주석 등, enum 전제로 쓰인 문서 주석 정리.

## 7. 회귀 검증 계획

34번 §4가 나열한 기존 검증 완료 기능을 배틀 테스트 씬([[project_battle_test_scene]])에서 재검증한다: 방향성 지시(타겟 우선순위/포지셔닝/자기보존 3축), 파티 방침(인식방식/활동반경/추격방침 3축), 적 진영 스프라이트 구분(약탈자/괴수/적대자 도형), 원거리딜러 포지셔닝, 자리 사수 복귀. `TacticsCatalogValidator`가 있다면 문자열 버전으로도 동작하는지 함께 확인.
