## 1. 현재 구조

- 인벤토리 팝업 4종의 루트는 전부 `ModelessPopups`의 직계 자식이고, 형제 순서가 곧 표시 순서다(뒤 형제가 위).
- 순서를 바꾸는 곳은 `InventoryPopupPanel.Open`의 `SetAsLastSibling` 한 곳뿐이다.

## 2. 감지 방식 — "팝업 안 어디든 누르는 순간"

### 2.1 UI 이벤트(IPointerDownHandler)로는 부족한 이유

| 방식 | 문제 |
|---|---|
| 팝업 루트에 `IPointerDownHandler` | Unity UI의 누르기 이벤트는 레이캐스트에 맞은 요소부터 부모 방향으로 **처음 처리하는 하나**에만 전달된다. 버튼(자동 정렬·닫기)은 누르기 이벤트를 스스로 처리하므로 루트까지 올라오지 않는다 → 버튼을 눌렀을 때 누락(기획 45번 §3 "버튼 포함" 위반) |
| 하위 요소마다 중계 컴포넌트 부착 | 요소가 추가될 때마다 빠뜨릴 위험. 런타임 복제 요소(아이템 뷰)에도 필요 |

### 2.2 채택: 입력 시스템의 포인터 누르기 액션 + 위치 판정

- Input System 액션 하나(바인딩 `<Pointer>/press` — 마우스 왼쪽 버튼·터치 공통)의 `performed` 콜백에서 포인터 위치를 읽는다.
- 열려 있는 인벤토리 팝업 루트를 **현재 표시 순서의 위쪽부터** 확인해, 포인터가 들어 있는 첫 팝업을 맨 위로 올린다. 겹친 영역을 누르면 화면에 보이는 팝업(가장 위)이 선택되고, 그 팝업이 이미 맨 위면 순서가 바뀌지 않는다.
- UI 이벤트 경로와 무관하게 동작하므로 버튼·아이템·스크롤 영역 등 하위 요소 종류에 관계없이 누락이 없다. `Update` 폴링이 아니라 이벤트 콜백이다(Q 회전과 같은 방식, 설계 40번 §5.3).
- Hub 캔버스는 Screen Space - Overlay(`m_RenderMode: 0`)라 화면 좌표를 그대로 판정에 쓴다. 다른 렌더 모드에 대비해 캔버스 카메라를 넘기는 형태로 둔다.

## 3. 책임 위치 — 별도 협력 객체 `PopupFocusOnPress` (`Core/UI/Common/`)

| 후보 | 판단 |
|---|---|
| 각 `InventoryPopupPanel`이 스스로 판정 | 팝업마다 독립적으로 "포인터가 내 안에 있으면 올린다"를 하면 겹친 영역에서 여러 팝업이 동시에 반응해 처리 순서에 따라 결과가 달라진다. **여러 팝업을 한꺼번에 아는 쪽**이 판정해야 한다 |
| `InventoryPopupCoordinator` | 열림 상태(`IUIPanel`)만 다루고 화면 요소(RectTransform)를 모른다. 표시 순서까지 넣으면 "열림 제어"와 "표시 순서" 두 책임이 섞인다(SRP) |
| **새 협력 객체(채택)** | 창 루트 목록을 받아 "누르면 해당 창을 맨 위로"만 한다. 인벤토리를 모르는 범용 동작이라 `DraggableWindow`와 같이 Common에 둔다 |

```csharp
/// 같은 부모 아래의 창들 중 포인터로 누른 창을 맨 위(마지막 형제)로 올린다.
public sealed class PopupFocusOnPress : IDisposable
{
    public void Rebind(IEnumerable<RectTransform> windowRoots, Camera eventCamera); // 씬 로드마다 새 루트로 교체
    public void Dispose();                                                         // 입력 액션 해제
}
```

- 소유: `HubUIWiring`(영속 컴포넌트)이 하나 소유하고, Hub 배선 때 인벤토리 팝업 루트들로 `Rebind`한다(창 위치 저장소와 같은 방식). 입력 액션은 한 번 만들어 계속 쓴다.
- 비활성(닫힌) 창과 파괴된 창(Hub를 떠난 뒤)은 판정에서 건너뛴다 — Field 씬에서는 대상이 없어 아무 일도 하지 않는다.
- 패널은 루트를 외부에 노출해야 한다: `InventoryPopupPanel.WindowRoot`(읽기 전용 속성) 추가.
- 열 때 맨 위로 올리는 기존 동작(`Open`)은 그대로 둔다.

## 5. 검증

- EditMode: 판정 로직을 입력과 분리한 순수 함수(창 목록 + 좌표 → 올릴 창)로 두고 테스트 — 겹친 영역에서 위쪽 창 선택, 닫힌 창 제외, 이미 맨 위면 변화 없음, 어느 창에도 없으면 변화 없음.
- Unity 실전(Play만): 팝업 여러 개를 연 뒤 뒤쪽 팝업의 제목 줄·그리드·아이템·자동 정렬 버튼·빈 영역을 각각 눌러 맨 위로 오는지, 뒤쪽 팝업에서 아이템을 끌 때 끄는 동안 가려지지 않는지, 겹친 영역을 누르면 보이는 쪽이 유지되는지.

## 6. 확인 항목 → 확정 (사용자, 2026-09-26)

1. **감지 방식(§2.2)** — 입력 시스템의 포인터 누르기 + 위치 판정. 대안(루트의 UI 누르기 이벤트)은 버튼을 눌렀을 때 누락되어 기획과 맞지 않는다.
2. **책임 위치(§3)** — 새 범용 협력 객체 `PopupFocusOnPress`를 Common에 두고 `HubUIWiring`이 소유.
