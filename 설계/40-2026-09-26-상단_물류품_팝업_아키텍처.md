## 1. 범위

- 데이터 계층: 회전 상태, 임시 보관(스테이징) 상태, 여러 아이템의 원자적 재배치.
- 정책 계층: 드롭 결과 판정(이동/교환/불가), 자동 정렬, 닫기 시 임시 보관 아이템 자동 배치.
- UI 계층: 팝업 패널, 그리드/임시 보관/아이템 뷰, 아이템 드래그 + Q 회전, 창 드래그, 닫기 차단.
- 인스톨러: Hub `ModelessPopups` 아래 팝업 시각 요소 생성.
- 범위 밖: 나머지 인벤토리 팝업 3종(구조는 재사용 가능하게 두되 생성·배선은 하지 않음), Field 씬 인벤토리, 상시 호출 키, 창 간 앞으로 가져오기.

## 3. 데이터 계층 — `Core/Inventory/`

### 3.1 배치 인스턴스 확장

```csharp
public readonly struct InventoryItemInstance
{
    public string InstanceId { get; }
    public IInventoryItemDefinition Definition { get; }
    public GridPosition Position { get; }   // IsStaged면 의미 없음
    public int QuarterTurns { get; }        // 신규 - 시계방향 90° 회전 횟수(0~3)
    public bool IsStaged { get; }           // 신규 - 임시 보관 영역에 있음(그리드 칸 점유 안 함)
    public int Width  => QuarterTurns % 2 == 1 ? Definition.FootprintHeight : Definition.FootprintWidth;
    public int Height => QuarterTurns % 2 == 1 ? Definition.FootprintWidth : Definition.FootprintHeight;
}
```

- 그리드 계산은 전부 `Definition.Footprint*` 대신 인스턴스의 `Width/Height`를 쓴다.
- 회전을 "가로·세로 뒤바뀜" 불리언이 아니라 **시계방향 90° 회전 횟수**로 저장한다(사용자 확정, 2026-09-26). 점유 칸 모양은 짝/홀만으로 결정되지만, 드래그 중 잡은 칸 추적(§5.2)과 이후 아이콘 방향 표시에는 네 방향 구분이 필요하다.
- 임시 보관을 별도 컬렉션이 아니라 **같은 `InventoryGrid` 안의 "칸을 점유하지 않는 상태"**로 둔다. `InventoryGrid.Resize`가 이미 "목록엔 있지만 점유 칸에선 빠진 아이템"을 다루고 있어 같은 개념의 확장이고, 그리드↔임시 보관 이동이 한 자료구조 안의 원자적 조작이 된다.

### 3.2 원자적 재배치

```csharp
// 한 아이템의 목표 상태. Position == null이면 임시 보관 영역.
public readonly struct ItemPlacement
{
    public string InstanceId { get; }
    public GridPosition? Position { get; }
    public int QuarterTurns { get; }
}

public class InventoryGrid
{
    public IReadOnlyCollection<InventoryItemInstance> Items { get; }        // 그리드에 놓인 것만(기존 의미 유지)
    public IReadOnlyList<InventoryItemInstance> StagedItems { get; }        // 신규 - 임시 보관 순서 유지
    public bool TryApplyPlacements(IReadOnlyList<ItemPlacement> placements); // 신규
}
```

- `TryApplyPlacements`: 대상 아이템의 점유를 모두 해제 → 새 위치 전부 검사(범위·겹침) → 하나라도 실패하면 원상 복구 후 `false`. 이동/교환/임시 보관/정렬/닫기 시 자동 배치가 전부 이 하나로 표현된다.
- 재배치는 아이템이 인벤토리를 떠나거나 새로 들어오는 게 아니므로 **재화 지갑을 건드리지 않는다**. 골드 상자 지갑 연동은 기존대로 `TryPlaceItem`(유입)/`RemoveItem`(유출)에만 남는다.

### 3.3 저장소 계약 (ISP)

```csharp
// 팝업의 정리 조작 전용. 읽기(IInventoryReader)와 유입·유출(IInventoryRepository)과는 소비자가 다르다 -
// 시설(구매/매각)은 이 조작을 볼 필요가 없다.
// StagedItems/OnChanged는 읽기 전용 상위 계약 IInventoryStagingReader(§5.5)에서 상속.
```

- 나머지 3종 저장소는 이번에 구현하지 않는다(해당 팝업 제작 시 마커 인터페이스에 추가).

## 4. 정책 계층 — `Core/Inventory/` (순수 C#, EditMode 테스트 대상)

### 4.1 드롭 판정 — `InventoryDropResolver`

미리보기(3색)와 실제 드롭이 **같은 판정**을 쓰도록 하나로 둔다.

```csharp
public enum InventoryDropKind { Move, Swap, Invalid }

public readonly struct InventoryDropResult
{
    public InventoryDropKind Kind { get; }
    public IReadOnlyList<ItemPlacement> Placements { get; } // Invalid면 비어 있음
}

public static class InventoryDropResolver
{
    // dragged: 드래그 시작 시점의 인스턴스(원래 위치·회전·임시 보관 여부 포함)
    public static InventoryDropResult ResolveGridDrop(InventoryGrid grid, InventoryItemInstance dragged, GridPosition target, int quarterTurns);
}
```

| 조건 | 결과 |
|---|---|
| 목표 점유 범위가 그리드를 벗어남 | Invalid |
| 겹치는 아이템 없음(자기 자신의 원래 칸은 제외) | Move: 드래그 아이템 → 목표 |
| 겹치는 아이템 1개(B) | B → 드래그 아이템의 원래 자리(원래 자리가 임시 보관이면 임시 보관, 그리드면 원래 좌상단 좌표 + B의 회전 유지). 두 아이템 모두 범위·겹침 검사 통과 시 Swap, 아니면 Invalid |
| 겹치는 아이템 2개 이상 | Invalid |

- 실제 검사는 `grid`를 복제하지 않고 "대상 아이템을 뺀 점유"를 기준으로 계산하는 조회 메서드를 `InventoryGrid`에 둔다(`CanPlace(placements)` — `TryApplyPlacements`와 같은 검사 로직 공유).
- 임시 보관 영역으로의 드롭은 판정이 필요 없다(항상 성공: `Position = null`).

### 4.2 자동 정렬 — `InventoryAutoSorter`

```csharp
public static class InventoryAutoSorter
{
    // 그리드 + 임시 보관 전부를 대상으로 새 배치를 계산. 전부 못 넣으면 false(배치 변경 없음).
    public static bool TryBuildSortedLayout(InventoryGrid grid, out List<ItemPlacement> placements);
    // 임시 보관 아이템만 기존 그리드 빈칸에 넣는다(기존 아이템은 움직이지 않음). 전부 못 넣으면 false.
    public static bool TryBuildStagedFlush(InventoryGrid grid, out List<ItemPlacement> placements);
}
```

- 순서: 점유 칸 수 내림차순 → 동률은 정의 Id → InstanceId(결과가 매번 같도록).
- 배치: 각 아이템마다 위쪽 행부터, 행 안에서 왼쪽부터 첫 빈자리 탐색. 원래 방향으로 못 넣으면 시계방향 90° 회전해서 재시도(정사각형은 생략).
- 결과는 `TryApplyPlacements`로 한 번에 적용 → 실패 시 원래 상태 유지(기획 39번 §3.6)가 자료구조 수준에서 보장된다.
- 탐욕 배치라 "원래는 다 들어가 있던 구성"이 정렬로는 안 들어갈 수 있다. 이 경우 정렬 취소로 처리된다(기획 확정과 일치).

### 5.2 아이템 드래그 흐름 — 잡은 칸 기준 (사용자 확정, 2026-09-26)

**기준점**: 드래그를 시작할 때 포인터가 눌린 아이템 내부 칸("잡은 칸", 아이템 기준 로컬 좌표 `grab`)을 기억한다. 드래그 동안 **잡은 칸의 중심이 포인터 위치에 오도록** 고스트를 배치하고, 목표 좌상단 칸 = 포인터가 있는 그리드 칸 − `grab`.

**회전**: Q 1회 = 시계방향 90°. 회전 후에도 **잡은 칸이 포인터 아래에 그대로 남도록** `grab`을 같은 회전으로 변환한다(회전 축 = 잡은 칸).

```
로컬 좌표: x = 오른쪽, y = 아래. 회전 전 크기 W×H → 회전 후 H×W
시계방향 90°: (x, y) → (H − 1 − y, x)

예) 2×1 아이템의 오른쪽 칸(grab = (1,0))을 잡고 Q
    회전 전 [A][B*]        회전 후 [A]      grab (1,0) → (1−1−0, 1) = (0,1)
                                    [B*]     ← 잡은 칸 B가 아래 칸이 되고, 포인터 아래 유지
```

1. `InventoryItemView.OnBeginDrag` → 원래 인스턴스와 `grab`(포인터 위치 → 아이템 내부 칸) 기억, 원래 뷰를 반투명 처리, 고스트(아이템 뷰 1개 재사용) 표시, **그 아이템을 선택 상태로**(기획 39번 §4.4). 임시 보관 목록에서 끌어온 경우 `grab`은 아이템 뷰 내부 칸 좌표로 같은 방식으로 계산한다(목록 뷰의 아이템도 점유 칸 모양 그대로 그린다).
2. `OnDrag` → 목표 좌상단 칸 계산 → `InventoryDropResolver`로 판정 → 미리보기 칸을 이동 가능/교환 가능/불가 색으로 칠함.
3. Q 키 → `QuarterTurns = (QuarterTurns + 1) % 4`, `grab` 변환, 고스트 크기·위치 갱신, 2단계 재계산.
4. `OnEndDrag` → 포인터가 그리드 위: 판정 결과가 Move/Swap이면 `TryApplyPlacements`, Invalid면 아무것도 안 함(원위치·원래 회전 유지). 임시 보관 영역 위: `Position = null`(회전 상태는 드래그 중 값 유지)로 적용. 그 밖: 아무것도 안 함.
- 드롭 대상 판정은 칸마다 `IDropHandler`를 두지 않고 `RectTransformUtility`로 그리드/임시 보관 영역 사각형을 한 번 검사한다(칸 수만큼 레이캐스트 대상이 생기지 않음).
- 클릭과 드래그 구분은 EventSystem 기본 동작에 맡긴다(드래그가 일어나면 `OnPointerClick`이 발생하지 않음).
- 드래그 중에만 필요한 갱신은 `OnDrag` 콜백에서 처리한다 — `Update` 폴링 없음.

### 5.3 Q 키 입력

- `InventoryItemDragController`가 `InputAction`(바인딩 `<Keyboard>/q`)을 하나 소유하고 **드래그 시작 시 Enable, 종료 시 Disable**, `performed` 콜백으로 회전한다. 이벤트 기반이며 드래그 중이 아닐 때 Q가 다른 기능과 충돌하지 않는다.
- `Game.Core.asmdef` references에 `Unity.InputSystem` 추가(패키지 1.18.0은 이미 설치됨).
- `IInputManager` 경유는 하지 않는다. 현재 뼈대만 있어 거칠 이점이 없다 — 입력 매니저가 실제로 설계될 때 이 바인딩을 옮길 대상으로 기록해 둔다(§10).

### 5.4 닫기와 코디네이터 변경

```csharp
// 닫기 전에 정리 작업을 하고, 닫을 수 없으면 false. 닫기 버튼과 상시 호출 버튼 토글이 같은 경로를 탄다.
public interface IPanelCloseGuard { bool TryPrepareClose(); }

public interface IInventoryPopupCoordinator
{
    void RegisterPopup(IUIPanel popup);
    void Toggle(string popupId);
    bool IsOpen(string popupId);
    void Reset(); // 신규 - 씬 로드 시 등록·열림 기록 초기화
}
```

- 코디네이터 `Toggle`: 열려 있으면 `popup is IPanelCloseGuard g && !g.TryPrepareClose()`일 때 닫지 않는다.
- 패널의 `TryPrepareClose`: 임시 보관이 비었으면 true. 아니면 `TryBuildStagedFlush` → 성공 시 적용 후 true, 실패 시 정보 줄에 안내 문구 표시 후 false.
- 팝업의 닫기 버튼은 `uiManager.ToggleInventoryPopup(popupId)`를 호출한다 — 패널이 자기 `Close()`를 직접 부르지 않는 규칙 유지.
- `UIManager.HandleSceneLoaded`가 기존 채널 `Reset()`과 함께 `inventoryPopupCoordinator.Reset()`을 호출한다(§2 잠재 버그 해소).

### 5.5 씬 전환과 임시 보관 — "상행 시작" 조건 추가 (사용자 확정, 2026-09-26)

- 인벤토리 팝업은 비모달이라 상행 준비(모달)와 동시에 열려 있을 수 있고, 그 상태로 "상행 시작" 시 Hub가 언로드되면 닫기 차단이 개입할 수 없다.
- Hub를 떠나는 경로는 "상행 시작" 하나뿐이다(`RequestSceneTransition` 호출부 조사: Hub 쪽은 `TripPanel` 1곳, 나머지 2곳은 Field→Hub). 따라서 **임시 보관 영역에 아이템이 있으면 "상행 시작" 버튼을 비활성화**하는 것으로 누수 경로가 막힌다.
- `TripPanel`의 기존 활성 조건(`sceneRevealed && 도착지 배정`)에 `!임시 보관 아이템 있음`을 AND로 추가한다. 임시 보관 상태가 바뀔 때 저장소 `OnChanged`로 버튼을 갱신한다(상행 준비 창이 열린 채 인벤토리 팝업에서 정리해도 즉시 반영).
- 비활성 사유 문구는 이번 범위에서 두지 않는다 — 향후 UI/UX 개선 과제(§10).
- `TripPanel`이 필요한 것은 "임시 보관 아이템이 있는가 + 변경 알림"뿐이므로 읽기 전용 계약을 분리한다(ISP):

```csharp
public interface IInventoryStagingReader
{
    IReadOnlyList<InventoryItemInstance> StagedItems { get; }
    event Action OnChanged; // IInventoryReader.OnChanged와 같은 이벤트 멤버 하나로 구현된다
}

public interface IInventoryArrangement : IInventoryStagingReader
{
    bool TryApplyPlacements(IReadOnlyList<ItemPlacement> placements);
}
```

- 조건은 인벤토리 카테고리 공통으로 둔다: `RegisterTripUI`는 `IReadOnlyList<IInventoryStagingReader>`를 받아 하나라도 비어 있지 않으면 비활성. 지금은 교역품/전리품 1개만 전달하고, 나머지 팝업이 생기면 목록에 추가만 한다.
- 저장소가 없으면(선택적 의존성) 빈 목록 → 조건 없음과 같다.

### 5.6 화면 요소와 ID

`InventoryPopupUIElementIds`(popupId별 접두사, 4종 공용):

| 요소 | 내용 |
|---|---|
| Root | 창 전체(SetActive로 열기/닫기) |
| TitleBar | 제목 텍스트 + `DraggableWindow` |
| CloseButton | 우상단 |
| GridArea | `InventoryGridView` — 칸 크기는 영역 크기 ÷ 그리드 칸 수(가로·세로 중 작은 값)로 계산해 마차 수가 바뀌어도 영역에 맞춤 |
| StagingArea | `InventoryStagingView` — 그리드 오른쪽 |
| SortButton | 자동 정렬 |
| InfoLabel | 하단 정보 줄(선택 아이템 이름 / 닫기 차단 안내) |
| ItemTemplate / CellTemplate | 런타임 풀링 복제 원본(비활성) |

- 아이템 색(사용자 확정, 2026-09-26): **품목(Id)별로 다른 색**. 정해진 팔레트(구분이 쉬운 색 8종)에서 Id 문자열의 고정 해시(FNV-1a — `string.GetHashCode`는 실행마다 값이 달라질 수 있어 쓰지 않음)로 하나를 고른다. 같은 품목은 항상 같은 색, 테이블 변경 불필요. 품목이 8종을 넘으면 색이 겹칠 수 있다 — 아이콘이 생기면 아이콘으로 대체되는 임시 식별 수단이라 허용. 선택 시 테두리 강조. 이름이 없으면 "값 없음"(카탈로그가 이미 처리).
- 기본 위치: 화면 좌측.

## 6. 배선 — `HubUIWiring`

```csharp
registrar.TryResolve<ITradeGoodsInventoryRepository>(out var tradeGoodsRepository);
if (tradeGoodsRepository != null && InventoryPopupElements.TryBind(sceneUIRoot, InventoryPopupIds.TradeGoods, out var elements))
{
    var popup = new InventoryPopupPanel(InventoryPopupIds.TradeGoods, elements, tradeGoodsRepository, tradeGoodsRepository, uiManager, windowPositionStore);
    inventoryPopupRegistrar.RegisterPopup(popup);
}
```

- 코디네이터 등록 경로: `IPanelRegistrar`에 `RegisterInventoryPopup(IUIPanel)`을 추가해 `UIManager`가 코디네이터로 위임한다(기존 `RegisterDepthPanel`/`RegisterPopupPanel`과 같은 경로 — 배선이 코디네이터를 직접 알지 않음).
- 저장소 부재·요소 부재 시 경고 후 건너뜀(기존 선택적 의존성 규칙).

## 9. 검증

EditMode 테스트:
- `InventoryGrid`: 회전(0~3) 배치 점유 칸, `TryApplyPlacements` 성공/실패 시 원상 복구, 임시 보관 전환 시 점유 해제.
- 잡은 칸 회전 변환: 네 방향 순환 후 원래 좌표 복귀, 2×1/1×2/2×2 예시값.
- `InventoryDropResolver`: 빈칸 이동, 자기 칸과 겹친 이동, 같은 크기 교환, 다른 크기 교환 성공/실패, 2개 겹침 불가, 범위 초과 불가, 임시 보관에서 끌어온 아이템의 교환(밀린 아이템 → 임시 보관).
- `InventoryAutoSorter`: 정렬 결과 결정성, 회전으로만 들어가는 경우, 실패 시 false, 임시 보관 자동 배치 성공/실패.
- 저장소: 골드 상자 재배치·임시 보관 시 지갑 불변.
- 코디네이터: 가드 false면 열린 상태 유지, `Reset` 후 첫 토글이 열기.
- 품목 색: 같은 Id는 항상 같은 색(해시 결정성).

Unity 실전(사용자): 버튼으로 열기/닫기, 드래그 이동·교환·Q 회전·미리보기 색, 임시 보관 왕복, 자동 정렬, 닫기 차단 문구, 창 드래그·화면 클램프·재오픈 위치, Hub↔Field 왕복 후 재오픈, 임시 보관에 아이템이 있을 때 "상행 시작" 비활성·비우면 재활성.

## 10. 후속 과제

- 나머지 인벤토리 팝업 3종: 해당 저장소에 `IInventoryArrangement` 구현 + 배선 + 인스톨러 호출만 추가하면 된다.
- 입력 매니저 설계 시 Q 회전 바인딩 이관.
- 비모달 팝업 여러 개가 겹칠 때 클릭한 창 앞으로 가져오기.
- **(UI/UX 개선) "상행 시작" 비활성 사유 표시** — 현재 비활성 조건(화면 표시 완료 전 / 도착지 미배정 / 임시 보관 아이템 있음) 중 어느 것 때문인지 플레이어에게 알려주는 수단이 없다. 조건별 사유 문구 또는 툴팁 표시를 향후 확장·개선 방안으로 검토(2026-09-26 사용자 지시로 기록).
