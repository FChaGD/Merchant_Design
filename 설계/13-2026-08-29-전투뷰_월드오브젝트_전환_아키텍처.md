## 1. 목표/비목표

**목표**: 전투 뷰(캐릭터/보호목표 표시, 카메라 드래그팬+휠줌)를 UGUI(RectTransform/Image/ScrollRect)에서 월드 오브젝트(Transform/SpriteRenderer/Camera)로 전환한다. 시뮬레이션 좌표(미터)와 렌더링 좌표(월드 유닛)가 1:1이 되어 `CoordinateToPixelScale` 변환 자체가 사라지고, `BattleDebugGizmoView` 같은 Scene 뷰 디버그 도구가 화면과 자연스럽게 겹친다. Physics2D/정렬 레이어 같은 표준 2D 툴링도 이후 자유롭게 쓸 수 있게 된다.

**비목표(동작 동일성 유지)**: 카메라 규칙(기획 09번 — 정사각형 바운딩 박스 클램프, 최소 줌=전장 전체 보임, 최대 줌=최소 줌×2.5, 커서 고정 줌, 관성 없음, 전투 시작마다 리셋)은 그대로 유지한다. 캐릭터 뷰의 시각 동작(사망/도주 페이드, 피격 플래시, 근접 러지, 원거리 투사체)도 동일하게 유지한다. 새 게임플레이 기능을 추가하지 않는다 — 순수 기술 전환.

**시뮬레이션 레이어는 무변경**: `Core/Battle/Simulation/*`, `Core/Battle/Tactics/*`(포위/방진 등)는 이미 순수 Vector2(미터) 좌표로 동작하므로 전혀 손대지 않는다. 이번 전환은 `Core/UI/Field/Battle/*`(뷰)와 그 배선(`FieldUIInstaller`/`FieldUIController`)에 한정된다.

## 2. 좌표계 변경

`BattleFieldGeometry.CoordinateToPixelScale`(=40, 시뮬레이션 좌표→픽셀 배율)를 폐기한다 — 월드 오브젝트는 `transform.position = new Vector3(unit.Position.x, unit.Position.y, 0)`로 직접 배치되므로 배율 변환이 필요 없다("1유닛=1m"이 곧 "1시뮬레이션 좌표=1월드 유닛"이 된다). `BattleFieldGeometry`에는 `SpawnPointCount`만 남는다.

## 3. 렌더링 - `BattleCharacterUnitView`/`BattleProtectedUnitView`

`RectTransform`+`Image` → `Transform`+`SpriteRenderer`로 교체한다. 로직(피격 플래시/사망 페이드/도주 이동/근접 러지/원거리 투사체)은 좌표 프로퍼티만 `anchoredPosition`→`position`(Vector3, z=0 고정), `Image.color`→`SpriteRenderer.color`로 바꾸면 그대로 이식된다 — 코루틴 기반 보간 로직 자체는 변경 없음.

**Placeholder 스프라이트**: 기존엔 UGUI 기본 흰 이미지에 `Image.color`로 색을 입혔다(아군=파랑, 적=빨강 등, `baseColor`가 매 유닛 다름). `SpriteRenderer.color`도 같은 곱연산 틴트 방식이라 **흰색 정사각형 스프라이트 하나**만 있으면 된다. `FormationPlaceholderIcons`(Editor 전용, 파란색으로 고정 구워진 PNG)는 이 용도로 못 쓴다 — 색이 고정이라 틴트가 어긋난다. 대신 런타임에 `Sprite.Create(Texture2D.whiteTexture, ...)`로 1x1 흰 스프라이트를 코드에서 직접 만든다(에셋 파일 불필요, Editor 의존성 없음) — 이후 실제 아트가 준비되면 이 생성부만 걷어내면 되는 Placeholder 성격은 동일하게 유지.

`BattleProtectedUnitView`가 `unit.Icon`(마차=삼각형/시설=원형, `FormationPlaceholderIcons` 산출물)을 그대로 쓰는 부분은 문제없다 — `Sprite`는 `Image`든 `SpriteRenderer`든 공유 가능한 자산이라 그대로 재사용된다.

**정렬**: 현재도 겹침 정렬 요구사항이 없다(Canvas 형제 순서로 우연히 정해지던 것뿐). 월드 전환 후에도 단일 `sortingLayer`/`sortingOrder=0`으로 충분하다고 보되, 겹쳐 보이는 게 실플레이에서 문제가 되면 Y좌표 기반 정렬(`sortingOrder = -Mathf.RoundToInt(position.y * 100)` 같은 통상적인 탑다운 기법)을 후속으로 추가한다.

## 4. 카메라 - `BattleFieldWorldCameraView`(신규, `BattleFieldCameraView` 대체)

**수학은 100% 재사용**: `ScrollRectZoomController`의 커서 고정 줌/경계 클램핑 계산(최소 줌=contain-fit, 최대 줌=최소 줌×2.5, 커서 아래 지점 고정)은 좌표계만 바꾸면 그대로 옮길 수 있다 — `RectTransform.localScale`→`Camera.orthographicSize`(작을수록 확대이므로 반비례 관계로 뒤집어야 함), `RectTransform.anchoredPosition`→`transform.position`(Vector2). 새 클래스(`OrthographicCameraZoomController` 등)로 옮기되 로직 구조는 그대로 본뜬다 — `TripMapView`가 쓰는 기존 `ScrollRectZoomController`는 손대지 않는다(상행 지도는 계속 UGUI).

**입력 캡처는 UGUI를 유지하는 하이브리드로 제안**: 드래그팬/휠줌 입력 자체는 기존처럼 전체화면 투명 `Image`+`IDragHandler`/`IScrollHandler`(EventSystem 경유)로 받고, 그 델타를 `BattleFieldWorldCameraView`에 그대로 전달해 실제 Camera를 움직인다. Raw `Input.GetMouseButton` 폴링으로 바꾸지 않는 이유는 CLAUDE.md 최적화 규칙("입력 반응은 Update() 폴링이 아니라 이벤트/콜백으로 처리") 및 기존 EventSystem 인프라(Overlay Canvas, 레이캐스팅)를 그대로 재사용하기 위함 — 렌더링만 월드로 옮기고 입력 경로는 검증된 기존 방식을 유지하는 절충.

**합성(컴포지팅)**: `ProjectSettings/GraphicsSettings.asset` 확인 결과 이 프로젝트는 URP가 아니라 **Built-in Render Pipeline**이다. Field/Hub UI Canvas는 둘 다 `renderMode: ScreenSpaceOverlay`(카메라 미지정)라, 씬에 어떤 Camera가 있든 항상 화면 맨 위에 그려진다 — 즉 전투용 월드 Camera를 새로 추가하거나 기존 `Main Camera`를 재활용해도 URP 카메라 스택 같은 별도 합성 설정 없이 기존 UI 위에 자연스럽게 깔린다. 배경/"전투 중..." 라벨은 지금처럼 Overlay Canvas에 남겨 카메라 밖(항상 풀스크린)에 고정한다.

**레이어**: 현재 프로젝트에 전투 전용 레이어가 없다(`TagManager.asset` 확인 — 빈 슬롯 다수). 월드 Camera의 `cullingMask`를 격리하려면 새 레이어(예: "Battle")가 필요한데, 이는 Unity 에디터의 Project Settings > Tags and Layers에서 사람이 직접 추가해야 하는 항목이다(스크립트/인스톨러로 자동화 불가한 프로젝트 설정) — 제작 착수 시 사용자 작업으로 안내 필요. 다만 지금 씬엔 다른 월드 오브젝트가 없어 레이어 격리 없이도 당장은 동작한다 - 필수는 아니고 위생적 차원의 권장 사항.

## 6. 확인 사항 (확정됨, 2026-08-29)

1. **카메라 = 기존 `Main Camera` 재사용(확정)**. 현재 Field 씬의 Main Camera는 이미 Orthographic이고, `AudioListener`도 붙어 있으며, UI가 Screen Space Overlay라 실질적으로 아무 데도 쓰이지 않는 상태(위치/orthographic size 모두 임의값)였다 — 새로 만들지 않고 이 오브젝트의 설정(위치/orthographic size/cullingMask)만 다시 잡는다. 씬당 AudioListener 중복 문제도 자연히 피한다.
2. **"Battle" 레이어 신설(확정, 사용자가 직접 추가 완료)**. `ProjectSettings/TagManager.asset` 확인 결과 **User Layer 6 = "Battle"** — `LayerMask.NameToLayer("Battle")`은 6을 반환한다. 캐릭터/보호목표 스프라이트 오브젝트의 `gameObject.layer`를 이 레이어로 설정하고, Main Camera의 `cullingMask`에 최소한 이 레이어(+기존 UI가 필요로 하던 레이어)가 포함되도록 조정한다.
3. **정렬 = Y좌표 기반(B안, 확정)**. 모든 캐릭터/보호목표 SpriteRenderer에 `sortingOrder = -Mathf.RoundToInt(position.y * 100)`(또는 동등한 스케일) 방식을 적용해, 화면상 아래쪽(Y가 작은) 유닛이 항상 위쪽 유닛보다 위에 그려지게 한다. 유닛은 매 프레임 이동하므로(뷰의 `Update()`에서 위치 갱신 시 sortingOrder도 함께 갱신 필요 — `BattleCharacterUnitView.Update()`가 이미 위치를 매 프레임 따라가므로 같은 자리에서 처리), 캐릭터 뷰뿐 아니라 이동하지 않는 `BattleProtectedUnitView`(고정 배치)도 최초 배치 시 한 번은 계산해야 한다.

이 문서는 설계 단계 산출물이다. 위 3가지가 모두 확정됐으므로 제작 착수 준비가 됐다 — 실제 제작은 사용자의 별도 "제작 시작" 지시를 받고 진행한다(작업 규칙).

## 7. 최종 재점검 결과 (2026-08-29) — "카메라 수학 100% 재사용" 정정

§4에서 "수학은 100% 재사용"이라고 쓴 것은 부정확했다. 재점검 결과 실제 재작업이 필요한 지점을 다시 정리한다.

1. **줌 공식은 이름만 바꿔 옮길 수 없다** — UGUI는 "고정 콘텐츠를 확대"(scale↑=확대), Orthographic 카메라는 "가변 시야를 좁힘"(orthographicSize↓=확대)라 관계가 반대다. 직접 재유도한 결과:
   - `minOrthographicSize = fieldRadius / max(1, aspect)` (aspect = 화면 가로/세로 비율) — 기존 cover-fit(여백 없음)과 동일한 결과를 내려면 이 공식이 맞다.
   - `maxOrthographicSize = minOrthographicSize / maxZoomRatio` — 기존처럼 **곱하기**가 아니라 **나누기**(작을수록 확대이므로).
2. **드래그팬은 신규 구현** — 기존엔 Unity 표준 `ScrollRect`가 전담해 자체 코드가 없었다. "화면 픽셀 드래그량 → 월드 이동량"(현재 줌 배율 반영) 변환을 새로 짜야 한다.
3. **커서 고정 줌의 카메라 참조** — `eventData.pressEventCamera`는 Screen Space Overlay라 항상 null(09번 문서 §10에 기록됨). 월드 좌표 변환(`ScreenToWorldPoint`)은 반드시 전투 카메라 인스턴스를 직접 참조해야 한다.
4. **프리팹 재생성 필요** — `Assets/Prefabs/UI/Battle/BattleCharacterUnitView.prefab`/`BattleProtectedUnitView.prefab`이 이미 RectTransform+Image로 저장된 실제 에셋이다. Editor 코드(`FieldUIInstaller.GetOrCreateCharacterViewPrefab`류)에서 SpriteRenderer 버전으로 재생성해야 한다.
5. **크기 재조정 기준값** — 현재 캐릭터 24px, 보호목표 28px(=`CoordinateToPixelScale`(40) 기준 0.6~0.7 월드 유닛). SpriteRenderer는 텍스처 Pixels-Per-Unit에 따라 크기가 달라지므로, 이 0.6~0.7 유닛을 목표값으로 PPU/localScale을 맞춘다.
6. **프로젝트 첫 월드 렌더링 사례** — Hub.unity/Field.unity 전체에 `SpriteRenderer` 사용례가 0건(전부 UGUI, grep으로 확인). 참고할 기존 컨벤션이 없어 이번에 만드는 패턴이 향후 기준이 된다.

## 8. 그리드 타일 배경 (사용자 확정, 2026-08-29)

실전투 확인 중 카메라 `backgroundColor`(§7 버그 수정) 방식이 그저 단색 채우기라는 한계가 드러나, 실제 오브젝트(SpriteRenderer 그리드) 기반으로 교체했다.

- **배치 영역**: 적 스폰 링을 전부 감싸는 정사각형. 스폰 링 반지름은 `FieldRadius`(카메라가 쓰는 값)와 다르다 - `ComputeSpawnRadius = ComputeFieldRadius + FieldBoundaryGap(2m)`, 기존엔 `BattleFieldLayout`의 `private` 헬퍼였다. `IBattleFieldGeometry.ComputeSpawnRadius`로 공개 승격하고 `BattleSimulationLoop.SpawnRadius`(신규 프로퍼티, `FieldRadius`와 같은 자리)까지 꿰었다.
- **타일 크기**: 2m×2m(사용자 확정 - 반지름 15m 기준 약 225개, 1m 대비 오브젝트 수 1/4, 유닛 몸크기(0.6~0.7유닛)보다 충분히 커서 타일 경계가 거슬리지 않음).
- **확장성(사용자 요구사항)**: 타일은 평범한 `SpriteRenderer`라 나중에 개별 타일의 `sprite`/`color`를 직접 바꿔도 이 시스템(`BattleBackgroundGridView`) 자체는 무수정. 지금은 전부 같은 Placeholder 색(`DefaultTileColor`)으로 초기화.
