## 3. 캐릭터 카탈로그

| 요소 | 역할 |
|---|---|
| `CharacterProfile`(값 타입) | 캐릭터 Id, 이름, 직업 Id, 직업명, 스탯(`BattleUnitStats`), 고용비 |
| `ICharacterCatalogReader` | 전체 목록(테이블 행 순서) + Id로 조회. 읽기 전용 |
| `TableCharacterCatalog` | 위 세 자산을 조인해 구현(plain C#, `TableItemCatalog`와 같은 성격). 조회는 `Dictionary` |
| `CharacterCatalogProvider` | MonoBehaviour + `IManagedComponent`. 세 자산을 `[SerializeField]`로 받고 **`RegisterSelf` 단계에서** 카탈로그를 만들어 `ICharacterCatalogReader`로 등록 — 로스터가 자기 `ResolveDependencies`에서 카탈로그를 읽으므로 호출 순서에 의존하지 않게 한다 |

- 전투는 카탈로그를 쓰지 않는다. 전투는 기존대로 스탯 자산에서 직접 스탯 제공자를 만들고 키만 바꾼다(§5) — 전투 쪽 DI 구조 변경을 피한다.

## 4. 로스터 (Placeholder)

### 4.1 유닛 계약

- `IMercenaryUnit`에 `CharacterId` 추가(데이터 키). 직업(`Class`)은 유지 — 역할군·방향성 지시·정비창 팔레트 분류용.
- 로스터 인스턴스 Id는 캐릭터 Id와 같게 둔다(`Warrior01`). 캐릭터는 테이블에서 유일하고 한 번만 고용되므로 충돌이 없다. 실제 로스터 시스템에서 인스턴스 Id를 분리할 경우를 위해 `CharacterId`를 별도 속성으로 둔다.
- `DisplayName`은 직업명 유지(카탈로그의 직업명) — 정비창 팔레트·정보 패널은 이름을 표시하지 않는다(기획 53번 §3.2).

### 4.2 `PlaceholderCaravanRosterProvider` 변경

| 항목 | 변경 |
|---|---|
| 초기 용병 | 카탈로그에서 직업별 테이블 순서 앞 2명(상수 `StartingCharactersPerClass = 2`) |
| 마차·시설 | 기존 5개 고정 유지 |
| 카탈로그 조회 | `registrar?.TryResolve(out catalog)` — 없으면 용병 없이 시작 + 경고. 기존 EditMode 테스트(`ResolveDependencies(null)`로 마차만 사용)가 그대로 통과하도록 null 허용 |
| 신규 계약 구현 | `IHiredCharacterRoster`(§7.2) — 고용 여부 조회, 직업별 보유 수, 고용 추가, 변경 이벤트 |
| 직업 아이콘 | `IMercenaryClassIconReader`(직업 Id → 아이콘) 구현 — 아이콘 필드가 이 클래스에만 있음. Placeholder와 함께 제거 대상 |

### 4.3 로스터 변경을 소비자가 아는 방법

| 소비자 | 처리 | 변경 필요 |
|---|---|---|
| 정비창 팔레트 | 열릴 때마다 로스터를 다시 읽는다(`RefreshRosterCache`) | 없음 |
| 개체별 HP 저장소 | 상행 시작 시 로스터 전체를 만피로 초기화. 그 전에는 저장값이 없어 전투가 만피로 시작 | 최대 HP 조회 키만 변경(§5) |
| 전투 편성 | 전투 시작 시 로스터를 순회 | 키만 변경(§5) |
| 교역품 그리드 크기 | 마차 수만 사용 | 없음 |
| 고용 화면 | `IHiredCharacterRoster` 변경 이벤트로 좌측 목록·후보 목록 갱신 | 신규 |

- 고용은 Hub의 모달 화면에서만 일어나고 그동안 정비창은 닫혀 있다 — 목록 변경과 순회가 겹치지 않는다.

## 6. 배틀 테스트 씬

### 6.1 현재
- 배틀 테스트는 자체 로스터가 직업 종류(`BattleTestUnitKind`)로 유닛을 만들고, 스탯을 직업으로 조회한다(13번 §2 — 영구 로스터와 무관).

### 6.2 문제
- 스탯 테이블 키가 캐릭터 Id가 되면 직업으로는 스탯을 찾을 수 없다.

### 6.3 변경
- 직업 → 대표 캐릭터 Id 변환을 스탯 자산에 둔다: "해당 직업의 테이블 첫 행"(`TryGetFirstOfClass`). 배틀 테스트 아군은 이 대표 캐릭터 스탯을 쓴다. 방향성 지시는 직업 그대로.
- 대표 캐릭터를 코드 상수(`Warrior01` 등)로 박지 않는 이유: 테이블 행이 바뀌어도 배틀 테스트가 깨지지 않게 한다.

### 8.3 갱신

- 열 때: 후보 조회(현재 마을 Id), 선택 해제, 좌측·후보·정보 전부 그림.
- 재화 변경 이벤트 → 정보 패널(판정)만. 로스터 변경 이벤트 → 좌측 목록 + 후보 재조회 + 선택 해제(고용한 후보는 목록에서 사라짐).
- 비활성 사유 문구: 재화 부족 "재화가 부족합니다.", 보유 상한 "해당 직업은 더 고용할 수 없습니다.(최대 5명)".

### 8.4 배선

- `HubUIWiring.RegisterMercenaryContact(...)` — 무역품 구매 등록과 같은 형태. 의존성(지갑·후보 조회·로스터 쓰기·카탈로그·아이콘) 또는 화면 요소가 없으면 경고 후 등록 생략.
- 시설 진입 시 인벤토리 팝업 일괄 닫기는 기존 시설 공통 처리를 그대로 탄다.

| 시작 보유 캐릭터 지정 | 로스터 상수(직업별 테이블 앞 2명) | 테이블에 "시작 보유" 열 추가 | 로스터 자체가 Placeholder라 교체 시 함께 사라짐. 테이블 열은 실제 로스터 설계 때 판단 |

## 12. 검증 절차 (제작 후)

1. Play 1회(자동 임포트로 새 직업명 자산 생성) → 종료 → Bootstrap.unity에서 `Tools > Game > Build Bootstrap Scene` → Hub.unity에서 `Build Hub Scene` → 각 씬 Ctrl+S.
2. EditMode 테스트 전체 통과.
3. Play → 주점 지구 → 용병단 접촉: 재화 패널 외 숨김, 좌측 "전사 2/5" 등 + 이름 6명, 후보 9명.
4. 후보 선택 → 정보 패널 스탯·고용비 → 고용: 재화 1,000 감소, 좌측 추가, 후보에서 제거.
5. 재화 디버그 버튼으로 1,000 미만 → 고용 버튼 비활성 + 사유.
6. 한 직업 3명 추가 고용 → 5/5, 해당 직업 후보 소진.
7. 나가기 → 주점 지구 복귀. 정비창 팔레트 보유 수 증가 확인(예: 궁수 5/5).
8. 상행 → 전투: 고용한 캐릭터 배치·전투 정상(스탯 조회 오류 없음).
9. 배틀 테스트 씬: 아군 생성·전투 정상.
