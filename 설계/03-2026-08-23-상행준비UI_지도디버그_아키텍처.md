## 1. 개요

기획 문서 02/03/04/05가 정의한 "지도 위 도시 배치·경로 연결(디버그) + 출발/도착 지정(정식)" 기능을 구현하기 위한 구조다. 설계 목표는 사용자 지시대로 세 가지다.

- **SOLID**: 특히 디버그 기능(교체·제거 대상)과 정식 로직(유지 대상)이 서로 물리적으로는 데이터를 주고받지만, 코드 의존 방향은 정식 로직 → 인터페이스 → 디버그 구현체가 되도록(DIP) 강제한다. 실제 지역/경로 시스템이 들어올 때 구현체만 교체하고 정식 로직 코드는 건드리지 않는 것이 목표다.
- **확장성**: 드래그 상호작용(이동/선 긋기)이 늘어나도, 역할 지정 규칙이 늘어나도 기존 클래스를 고치지 않고 추가할 수 있게 한다(OCP).
- **최적화**: ID 조회·경로 존재 확인을 O(1)에 가깝게, 시각 요소는 get-or-create로 재사용한다(CLAUDE.md 최적화 컨벤션).

## 2. 전체 구조

```
TripPanel (기존, 조율자)
 └─ TripMapInteractionCoordinator (신규)         ← 지도/디버그 관련 배선을 전담, TripPanel의 책임 분리(SRP)
     ├─ ITripCityRepository (배치된 도시 저장소, 디버그)
     ├─ ITripRouteRepository (경로 연결 저장소, 디버그)
     ├─ ITripDebugRoadModeController (on/off 토글 상태, 디버그)
     ├─ ITripOriginDestinationAssigner (출발/도착 상태 머신, 정식)
     │    └─ ITripRouteReader 에만 의존 (DIP — 위 ITripRouteRepository를 이 인터페이스로만 바라봄)
     └─ 뷰들: TripDebugCityPaletteView, TripDebugCityMarkerView(N개), TripDebugRoadToggleView,
             TripDebugRoadLineView(N개), TripLocationInfoView(출발/도착 각 1개, 기존)
```

`TripPanel`은 기존처럼 정보 패널/버튼/편성 요약을 조율하되, 지도·디버그 배선은 `TripMapInteractionCoordinator`에 위임한다. 배치 UI가 `UIManager`↔`PanelNavigationStack`으로 SRP를 분리했던 것과 동일한 판단이다 — `RegisterTripUI`가 이번 기능까지 다 떠안으면 비대해진다.

## 3. 도메인/저장소 계층

### 3.1 도시 (디버그)

```csharp
public readonly struct TripCity
{
    public string Id { get; }
    public Vector2 MapPosition { get; }   // 지도 content 로컬 좌표
}

public interface ITripCityReader
{
    IReadOnlyList<TripCity> GetAll();
    bool TryGet(string cityId, out TripCity city);
}

public interface ITripCityRepository : ITripCityReader
{
    string Add(Vector2 mapPosition);      // 새 디버그 도시 생성, id 반환
    void Remove(string cityId);
    void Clear();
    event Action<string> CityRemoved;     // 역할 해제/경로 연쇄삭제 연동용
}
```

- **ISP**: 기존 `IFormationReader`/`IFormationRepository` 분리와 동일한 패턴. `ITripOriginDestinationAssigner`나 `ITripRouteRepository`는 읽기만 필요하므로 `ITripCityReader`만 받는다.
- **최적화**: 구현체 `InMemoryTripCityRepository`는 내부를 `Dictionary<string, TripCity>`로 유지해 `TryGet`/`Remove`를 O(1)에 처리한다(CLAUDE.md: ID 조회는 Dictionary로).
- **지속성**: `InMemoryFormationRepository`와 동일하게 세션(앱 실행) 동안만 유지 — `IManagedComponent`로 DI 등록.

### 3.2 경로 연결 (디버그, 정식 로직의 데이터 소스 겸용)

```csharp
public interface ITripRouteReader
{
    bool HasRoute(string cityIdA, string cityIdB);   // 무방향 — (A,B)와 (B,A) 동일하게 취급
}

public interface ITripRouteRepository : ITripRouteReader
{
    bool TryAddRoute(string cityIdA, string cityIdB);  // 중복이면 false (04번 문서 4.3 — 단일 경로만)
    void RemoveRoute(string cityIdA, string cityIdB);
    void RemoveAllRoutesFor(string cityId);             // 도시 삭제 시 연쇄 삭제(04번 4.4)
    void Clear();
    IReadOnlyList<(string A, string B)> GetAll();        // 연결선 렌더링용
}
```

- **경로는 무방향**이라는 기획 05번 문서의 "설계 참고 사항"을 여기서 확정한다: 저장 키를 `string.CompareOrdinal(a,b) < 0 ? $"{a}|{b}" : $"{b}|{a}"`처럼 정렬해 정규화하고 `HashSet<string>`에 보관 — `HasRoute`/`TryAddRoute`/`RemoveRoute`가 O(1).
- **최적화**: 도시별 인접 목록도 `Dictionary<string, HashSet<string>>`으로 함께 유지해 `RemoveAllRoutesFor(cityId)`가 그 도시의 연결 개수만큼만 순회하도록 한다(전체 스캔 금지).
- **DIP의 핵심 지점**: `ITripOriginDestinationAssigner`(정식)는 `ITripRouteReader`(읽기 전용 인터페이스)에만 의존한다. 지금은 이 인터페이스를 디버그 저장소(`TripDebugRoadRepository`)가 구현하지만, 실제 경로 시스템이 생기면 그 시스템이 `ITripRouteReader`를 구현하도록 갈아끼우기만 하면 된다 — `TripOriginDestinationAssigner`는 한 줄도 안 바뀐다. DI 등록 지점(`ManagerHierarchyInstaller` 혹은 `TripMapInteractionCoordinator` 생성부) 한 곳만 바뀐다.

## 4. 정식 로직 — `TripOriginDestinationAssigner`

```csharp
public enum TripRole { Origin, Destination }

public interface ITripOriginDestinationReader
{
    string OriginCityId { get; }        // null = 미배정
    string DestinationCityId { get; }
    bool IsBothAssigned { get; }        // "상행 시작" 게이팅에 사용 (02번 5절)
}

public interface ITripOriginDestinationAssigner : ITripOriginDestinationReader
{
    void HandleCityClicked(string cityId);       // 기본 지도 클릭 흐름 (02번 3.1절)
    void HandlePanelClicked(TripRole role);       // 변경 모드 on/off (02번 3.1.1절)
    void HandleCityDeleted(string cityId);        // 03번 4.3 — 역할 해제(반대편 유지)
}
```

`TripOriginDestinationAssigner`는 `ITripRouteReader` 하나만 생성자 주입받는다(DIP). 도시 존재 여부 자체는 검증하지 않는다 — 클릭 이벤트는 이미 존재하는 도시 아이콘에서만 발생하므로 신뢰한다(내부 컴포넌트 간 신뢰, CLAUDE.md 원칙).

### 4.1 상태

```csharp
private string originCityId;
private string destinationCityId;
private TripRole? activePanelRole;   // 3.1.1절 "변경 모드"
private TripRole? awaitingRole;      // 3.1.1절 케이스4 "R' 지정 대기" — 상대편이 없어 즉시 확정한 뒤 다음 클릭을 기다리는 상태
```

`awaitingRole`이 왜 필요한지가 이 설계의 핵심이다: 기획 문서의 "케이스 4"(반대편이 미배정이면 클릭한 도시가 먼저 확정되고, *다음* 클릭이 반대편을 채운다)는 `activePanelRole`만으로는 표현할 수 없다 — 첫 클릭 직후에도 여전히 "같은 역할 모드"인 것처럼 보이면 두 번째 클릭이 다시 같은 역할을 덮어쓰게 된다. 그래서 "지금 이 클릭이 채워야 할 역할"을 별도로 추적해야 한다.

### 4.2 `HandleCityClicked` (기본 흐름, 02번 3.1절)

```csharp
public void HandleCityClicked(string cityId)
{
    if (awaitingRole.HasValue)
    {
        HandleAwaitingPick(cityId);
        return;
    }

    if (activePanelRole.HasValue)
    {
        HandlePanelModePick(cityId);
        return;
    }

    // 기본 상태 머신 (패널 모드가 꺼져 있을 때만)
    if (originCityId == null)
    {
        originCityId = cityId;
    }
    else if (destinationCityId == null)
    {
        if (cityId == originCityId) { originCityId = null; }
        else if (routeReader.HasRoute(originCityId, cityId)) { destinationCityId = cityId; }
        // 경로 없으면 무시
    }
    else
    {
        // 둘 다 배정된 상태 → 무조건 리셋 후 새 출발지
        originCityId = cityId;
        destinationCityId = null;
    }
}
```

### 4.3 `HandlePanelClicked` / 패널 모드 픽 (02번 3.1.1절)

```csharp
public void HandlePanelClicked(TripRole role)
{
    if (awaitingRole.HasValue) { awaitingRole = null; activePanelRole = null; return; }   // C-6: 대기 취소, 이미 확정된 값은 유지
    activePanelRole = (activePanelRole == role) ? (TripRole?)null : role;                  // 재클릭 = 취소
}

private void HandlePanelModePick(string clickedCityId)
{
    var role = activePanelRole.Value;
    var oppositeRole = Opposite(role);
    var current = Get(role);
    var opposite = Get(oppositeRole);

    if (clickedCityId == current) { Set(role, null); activePanelRole = null; return; }              // 케이스1
    if (opposite != null && clickedCityId == opposite) { Swap(); activePanelRole = null; return; }   // 케이스2

    if (opposite != null)                                                                             // 케이스3
    {
        if (routeReader.HasRoute(clickedCityId, opposite)) { Set(role, clickedCityId); activePanelRole = null; }
        return; // 실패 시 모드 유지
    }

    Set(role, clickedCityId);       // 케이스4 — 게이팅 없이 즉시 확정
    awaitingRole = oppositeRole;    // 다음 클릭은 반대편을 채운다
}

private void HandleAwaitingPick(string clickedCityId)
{
    var role = awaitingRole.Value;
    var opposite = Get(Opposite(role));
    if (routeReader.HasRoute(clickedCityId, opposite))
    {
        Set(role, clickedCityId);
        awaitingRole = null;
        activePanelRole = null;
    }
    // 실패 시 awaitingRole 유지 — 방금 확정된 반대편 값은 그대로(부분 성공)
}
```

같은 도시를 두 역할에 동시에 배정하려는 시도(자기 자신을 반대편으로도 클릭)는 `routeReader.HasRoute(city, city)`가 항상 `false`(자기 자신에 대한 연결선은 저장되지 않음)라 별도 분기 없이 자연스럽게 거부된다.

### 4.4 `HandleCityDeleted` (03번 4.3 연동)

```csharp
public void HandleCityDeleted(string cityId)
{
    if (originCityId == cityId) { originCityId = null; }
    if (destinationCityId == cityId) { destinationCityId = null; }
    // 반대편은 건드리지 않음. 경로 삭제와 달리 도시 삭제는 소급 해제 대상(02번 3.1절 "반대편 유지"와는 별개 규칙 — 이건 자기 역할만 해제)
}
```

`TripMapInteractionCoordinator`가 `cityRepository.CityRemoved += assigner.HandleCityDeleted`로 배선한다 — 저장소(디버그)가 정식 로직을 직접 참조하지 않고, 이벤트를 통해 조율자가 연결한다(결합 방향 준수).

## 5. 디버그 배치/연결 — 드래그 전략 패턴 (OCP)

지도 위 도시 아이콘 드래그의 의미가 "이동"과 "선 긋기" 두 가지이고, road-mode 토글로 전환된다(04번 4.2). 이 분기를 `TripDebugCityMarkerView`에 `if (roadMode.IsActive) ... else ...`로 박아넣지 않고 전략 패턴으로 뽑는다 — 나중에 드래그 의미가 하나 더 늘어나도(예: 삭제 모드) 기존 코드를 안 건드리고 구현체만 추가하면 된다.

```csharp
public interface ICityDragBehavior
{
    void OnDragBegin(string cityId, Vector2 startPosition);
    void OnDragUpdate(Vector2 currentPosition);
    void OnDragEnd(string cityId, string droppedOnCityId /* null 가능 */, bool droppedInsideMap);
}

public class MoveCityDragBehavior : ICityDragBehavior      // road-mode off
public class DrawRoadDragBehavior : ICityDragBehavior       // road-mode on
```

`TripDebugCityMarkerView`는 드래그 이벤트를 자신이 해석하지 않고, 매 드래그 시작 시점에 `roadModeReader.IsRoadModeActive`를 보고 두 전략 중 하나에 위임한다. **클릭**(드래그가 아닌 `OnPointerClick`)은 이 전략들과 무관하게 항상 `assigner.HandleCityClicked(cityId)`를 직접 호출한다 — 04번 문서 C-2("road-mode 중 클릭은 영향 없음")가 이 분리 덕분에 자연스럽게 성립한다.

- `MoveCityDragBehavior`: 드래그 중 아이콘을 커서에 따라 이동, `OnDragEnd`에서 지도 밖이면 `cityRepository.Remove(cityId)`(단, `roadMode.IsRoadModeActive`가 이미 false일 때만 이 컴포넌트 자체가 활성화되므로 별도 체크 불필요), 지도 안이면 `TryUpdatePosition`.
- `DrawRoadDragBehavior`: 드래그 중 임시 라인 렌더링, `OnDragEnd`에서 `droppedOnCityId`가 있으면 `routeRepository.TryAddRoute(cityId, droppedOnCityId)`, 없으면 무효(취소).

road-mode 중 삭제 차단(04번 C-3)은 `MoveCityDragBehavior` 자체가 road-mode일 때 선택되지 않으므로 개별 드래그 삭제는 자동으로 막힌다. "전체 삭제" 버튼은 `TripDebugCityBulkDeleteButton`이 `roadModeReader.IsRoadModeActive`를 구독해 `interactable`을 직접 갱신한다.

## 7. Editor 인스톨러

기존 컨벤션(씬 직접 편집 금지, `EditorUIBuilder` 공용 유틸리티 재사용) 그대로 따른다.

- `TripUIInstaller`(기존)에 추가:
  - 도시 팔레트 영역, road-mode 토글 버튼, 도시/경로 "전체 삭제" 버튼 2종을 `EditorUIBuilder`의 기존 헬퍼(`GetOrCreateUIObject`, `EnsureImage`, 버튼 부착 등)로 생성.
  - `TripLocationInfoView`에 "변경 모드" 버튼(패널 클릭 자체가 트리거이므로 `Button` 컴포넌트를 `TripLocationInfoView`가 있는 루트에 부착).
- 새로 필요해지는 저수준 헬퍼(예: 드래그 가능한 아이콘 프리팹 배치)가 생기면 `FormationUIInstaller`에서 이미 쓰는 패턴(팔레트 아이콘 인스톨)과 통일해 `EditorUIBuilder`에 추가한다 — 두 인스톨러가 서로를 참조하지 않는다.

## 8. DI/등록 (구현 단계에서 확정)

- `ITripCityRepository`, `ITripRouteRepository`, `ITripDebugRoadModeController`의 구현체는 애초 계획(씬에 배치해 `GetComponent`로 조회)보다 더 단순화했다 — 이 데이터를 필요로 하는 소비자가 오직 `TripMapInteractionCoordinator` 자신뿐이라, 씬 배치나 `MonoBehaviour`가 전혀 필요 없다. `InMemoryTripCityRepository`/`InMemoryTripRouteRepository`/`TripDebugRoadModeController` 모두 순수 C# 클래스로 만들어 `TripMapInteractionCoordinator`가 필드로 직접 `new` 생성·소유한다. `TripMapInteractionCoordinator` 자신도 `TripPanel`(Bootstrap 씬, 영속)의 필드로 `RegisterTripUI` 시점에 한 번만 생성되므로, 별도 DI 없이도 세션 내내 유지된다.
- `ITripOriginDestinationAssigner`(후속 구현)도 동일하게 `TripMapInteractionCoordinator`가 `new`로 생성해 소유할 예정이다 — 간단한 상태 머신이라 `MonoBehaviour`나 전역 DI가 필요 없다.

## 11. 최적화 요약

## 14. 구현 노트 (2026-08-23, 제작 완료 — `system`/`develop` 브랜치 push 완료, 커밋 `12e423a`)

설계 대비 단순화한 지점, 구현 중 실제로 발견해 고친 버그 3건을 남긴다. 특히 버그 1~3은 이 패널류(비활성 상태로 시작하는 UI, 드래그 인터랙션이 있는 UI)를 다시 건드릴 때 똑같이 재발할 수 있는 비직관적 함정이라 반드시 먼저 읽을 것.

### 14.1 설계 대비 단순화
- 8절에서 이미 기록했듯, 저장소들(`ITripCityRepository` 등)은 씬 배치형 컴포넌트가 아니라 `TripMapInteractionCoordinator`가 직접 `new`로 소유하는 순수 C# 필드로 구현했다.
- "도시 전체삭제"/"경로 전체삭제" 버튼은 별도 View 클래스 없이 평범한 `UnityEngine.UI.Button`을 코디네이터가 직접 `onClick`으로 배선했다(굳이 감쌀 이유가 없었음).

### 14.2 구현 중 발견해 고친 버그 (교훈)

1. **비활성 패널의 `Awake` 지연 함정**: `TripPanel`의 패널 루트는 씬에 `SetActive(false)` 상태로 저장돼 있어, `TripMapView.Awake()`가 최초로 패널이 열릴 때(`TripPanel.Open()`)까지 지연된다. 그런데 `TripMapInteractionCoordinator.Bind()`는 그보다 훨씬 이른 `RegisterTripUI`(앱 시작 시 1회) 시점에 실행된다. 처음엔 `mapView.Content`/`Viewport` 값을 `Bind()` 시점에 미리 꺼내 생성자에 캐시했는데, 이 시점엔 항상 `null`이라 드래그 미리보기 선이 엉뚱한 곳에 생기고, 도시 이동 판정이 항상 "지도 밖"으로 오판돼 경로가 있는 도시를 옮기면 도시+경로가 통째로 사라지는 버그로 이어졌다. **교훈**: 이런 지연-활성화 패널 하위에서 `TripMapView`(또는 유사한, Awake에서 초기화되는 컴포넌트)의 값을 다루는 협력 객체는 그 값을 생성자/등록 시점에 캐시하지 말고, `TripMapView` 참조 자체를 들고 있다가 실제 사용 시점(사용자가 상호작용하는 시점 — 이미 패널이 열린 뒤)마다 다시 읽어야 한다.
2. **레이캐스트를 가리는 시각 전용 오브젝트**: 드래그 중 보이는 임시 선(`TripDebugRoadLineView`를 재사용한 미리보기)에 `raycastTarget = true`가 남아있으면, 드롭 순간 그 선 자신이 레이캐스트를 가로채 그 아래 실제 도시 아이콘을 못 찾는다(연결이 생성되지 않는 버그). **교훈**: 드래그 중 커서를 따라다니는 순수 시각 요소(고스트, 미리보기 선 등)는 항상 `raycastTarget = false`로 만들 것 — `FormationUnitIconView`의 드래그 고스트가 이미 이렇게 처리돼 있던 것과 같은 이유.
3. **content 밖 UI 요소는 zoom을 자동으로 물려받지 않음**: 배치된 마커는 지도 `content`의 자식이라 확대/축소(`localScale`)를 자동으로 물려받지만, 루트 캔버스에 직접 붙는 팔레트 드래그 고스트는 그렇지 않다 — 드래그 시작 시점의 `content.localScale.x`를 직접 곱해줘야 화면상 크기가 일치한다.

### 14.3 미검증 범위
이 세션에서는 코드만 작성했고, 실제 Unity Editor 실행/Play 모드 테스트는 전부 사용자가 직접 수행하며 버그를 리포트하는 방식으로 진행했다. 위 3건은 그렇게 확인·수정됐다. 아직 사용자가 명시적으로 테스트했다고 언급하지 않은 것:
- 패널을 닫았다가 다시 여는 시나리오에서 배치/배정 상태가 실제로 유지되는지(C-7 규칙).
- 정보 패널 변경 모드(3.1.1절)의 4가지 케이스 전부(특히 swap, "반대편 대기" 중 실패 후 재시도).
- `상행 시작` 버튼 게이팅이 실제로 출발/도착 모두 배정됐을 때만 활성화되는지.
