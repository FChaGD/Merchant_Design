## 1. 개요

[[06-2026-08-25-Field씬_기획]]의 이동 뷰/전투 전환/결과 처리 흐름을 기존 매니저 구조(§01) 위에 배선한다. 새 매니저는 추가하지 않는다 — `GameManager`(세션 진행 상태), `EncounterManager`(인카운터 판정), `BattleManager`(전투 결과), `UIManager`(화면 표시) 네 매니저 산하에 하위 컴포넌트를 채우는 것으로 전부 해결된다.

**핵심 배치 원칙**: "진행 게이지가 얼마나 찼는가"는 게임 상태(`GameManager` 산하 `SessionStateTracker`)이고, "그것을 어떻게 보여주는가"는 UI 상태(`UIManager` 산하 `FieldUIController`)다. 두 책임을 분리해, 인카운터 판정 로직이 나중에 설계되어도 UI 쪽을 다시 손댈 필요가 없게 한다.

## 3. 진행 상태 — `ISessionState` / `SessionStateTracker`

`EncounterManager`는 진행을 멈추는 것(`Pause`) 하나만 필요하고, `FieldUIController`는 진행도 조회·시작·재개까지 전부 필요하다 — 필요 범위가 뚜렷이 다른 두 소비자이므로 인터페이스를 분리한다(ISP, `IFormationReader`/`IFormationRepository` 분리와 동일한 방식).

```csharp
public interface ISessionPauseControl
{
    void Pause();
}

public interface ISessionState : ISessionPauseControl
{
    float Progress { get; }              // 0(출발) ~ 1(도착)
    event Action<float> OnProgressChanged;
    event Action OnArrived;

    void Begin();   // 진행도 0으로 초기화, 진행 시작
    void Resume();
}
```

- `SessionStateTracker`(GameManager 산하, `IManagedComponent` 아님 — §5.1 규칙대로 매니저 산하 컴포넌트는 전역 DI 등록 대상이 아니다. 단, `GameManager`가 `RegisterSelf`에서 이 컴포넌트를 `ISessionState`와 `ISessionPauseControl` 두 타입 모두로 등록해 다른 매니저가 필요한 만큼만 조회할 수 있게 한다)는 `Update()`에서 정지 상태가 아니면 경과 시간을 누적해 진행도를 계산한다.
- **테스트 단계**: 고정 소요시간 상수로 `progress = elapsed / testDurationSeconds` 계산. [[06-2026-08-25-Field씬_기획]] 6절에 기록된 대로, 실제 거리+변수 기반 계산은 후속 설계 대상 — 이 인터페이스는 그대로 유지하고 `SessionStateTracker` 내부 구현만 교체하면 되도록 설계했다.
- `Begin()`은 Field 씬 로드 완료 시점에 `FieldUIController`가 호출한다(§5).

## 4. 인카운터 발생 시 정지 — `EncounterManager` 변경

> **갱신(2026-08-25)**: 아래 `ISessionPauseControl` 단독 의존은 [[05-2026-08-25-인카운터_판정_아키텍처]]에서 `ISessionState` 전체로 확장되며 대체되었다(주기 판정에 `OnProgressChanged` 구독이 추가로 필요해짐). `Pause()` 호출 자체는 그대로 유지된다.
>
> **갱신 2(2026-08-25)**: 아래 `battleController.StartBattle()` 호출은 `EncounterManager`에서 제거되고 `FieldEncounterFlowCoordinator`로 이동했다(§5.2 `TransitionAfterWarning` 참고, Docs/제작/02-2026-08-25-인카운터_전투전환_구현.md). 인카운터 발생과 동시에 전투를 시작시키면 `PlaceholderBattleResultRule`의 1초 판정이 경고창 표시 중에 끝나버려 전투 뷰 진입 즉시 결과가 뜨는 문제가 있었다 — 경고·전투 뷰 전환이 끝난 시점에 시작해야 "전투 뷰 진입 후 결과"라는 체감 순서가 지켜진다.

`EncounterManager.ResolveDependencies`에 `ISessionPauseControl`을 추가로 조회한다(전체 `ISessionState`가 아니라 실제로 쓰는 `Pause()`만 노출하는 좁은 인터페이스 — §3 ISP 참고). "인카운터 발생 = 진행 정지"는 UI 연출이 아니라 게임 규칙이므로, UI가 아니라 `EncounterManager`가 직접 정지시킨다.

```csharp
private void TriggerEncounter()
{
    pauseControl.Pause();
    // TODO: IEncounterRule(랜덤/확정) 판정 - 하위 컴포넌트 설계 후 구현
    OnEncounterTriggered?.Invoke();
    // battleController.StartBattle()은 더 이상 여기서 호출하지 않는다 - 위 "갱신 2" 참고.
}
```

`OnEncounterTriggered` 구독자(`FieldEncounterFlowCoordinator`, §5.2)는 "정지시켜야 한다"는 규칙을 몰라도 된다 — 그저 이미 멈춘 게이지를 보여주고 연출만 담당한다.

**남은 이슈**: ~~인카운터 판정 자체가 언제/얼마나 자주 실행되는지~~ → [[05-2026-08-25-인카운터_판정_아키텍처]]에서 정의 (2026-08-25, `Progress` 구간이 아니라 `OnProgressChanged`를 틱 소스로 쓰는 시간 기반 방식으로 확정).

## 5. Field UI 등록 — `FieldUIController` + `FieldEncounterFlowCoordinator`

`HubUIController`와 동일한 패턴이다: `UIManager` 산하 컴포넌트(같은 GameObject, `GetComponent<IFieldUIController>()`로 조회), `UIManager.HandleSceneLoaded`에 `SceneNames.Field` 분기를 추가해 씬 로드 시점에 등록한다.

`FieldUIController`에 모든 로직을 두면 "뷰 바인딩"과 "인카운터→전환→결과라는 시간 축을 가진 상태 흐름"이 한 클래스에 섞인다. 이 프로젝트는 같은 상황을 이미 두 번 겪었고(`UIManager`→`PanelNavigationStack`, `TripPanel`→`TripMapInteractionCoordinator`) 매번 조율 로직을 별도 협력 객체로 뽑아냈다 — 이번에도 같은 방식을 따른다: **`FieldUIController`는 단순 이벤트→뷰 반영(게이지 갱신, 도착 팝업, 버튼 클릭 배선)만 담당**하고, **인카운터 발생부터 전투 결과 처리까지의 상태 흐름은 `FieldEncounterFlowCoordinator`(SRP)로 분리**한다.

**수명주기 주의점(최적화 점검 반영)**: 상행은 Hub↔Field를 여러 번 왕복하는 핵심 루프라, `SceneLoader.Transition`이 Field 씬을 매번 새로 로드할 때마다 `HandleSceneLoaded` → `RegisterFieldUI(...)`가 다시 실행된다. 하지만 `encounterManager`/`battleResultSource`는 Bootstrap 씬에 상주하는 **영속 객체**다 — `RegisterFieldUI`를 호출할 때마다 `FieldEncounterFlowCoordinator`를 새로 만들어 이 영속 객체들에 `+=` 구독하면, 이전 상행에서 만든 coordinator의 구독이 해제되지 않고 계속 쌓인다(순수 C# 객체라 `OnDestroy`로 자동 해제되지도 않는다). 상행을 반복할수록 인카운터 1건당 과거 coordinator 수만큼 중복 호출되고, 그 coordinator들이 들고 있던 뷰 참조는 이미 언로드된 이전 Field 씬 오브젝트라 예외로 이어질 수 있다.

따라서 `FieldUIController`는 **`FieldEncounterFlowCoordinator`를 최초 1회만 생성**해 필드로 유지하고, 매니저 이벤트 구독(`Bind`)과 씬 뷰 참조 교체(`RebindViews`)를 분리한다 — 전자는 최초 1회만, 후자는 Field 씬을 로드할 때마다 실행한다.

```csharp
private void HandleSceneLoaded(string sceneName)
{
    if (sceneName == SceneNames.Hub) { /* 기존 로직 */ }
    else if (sceneName == SceneNames.Field)
    {
        fieldUIController.RegisterFieldUI(this, gameManager, sessionState, encounterManager, battleResultSource);
    }
}
```

`FieldUIController`가 갖는 의존성과 책임:

| 의존성 | 용도 |
|---|---|
| `IUIManager` | `FieldEncounterFlowCoordinator`에 그대로 전달(정비창/방향성 오버레이 강제 닫기용) |
| `IGameManager` | 도착 시 Hub 전환 요청 (`RequestSceneTransition`) |
| `ISessionState` | 게이지 값 구독(`OnProgressChanged`), 도착 구독(`OnArrived`), 씬 진입 시 `Begin()` 호출. `Resume()`은 `FieldEncounterFlowCoordinator`에 전달해 그쪽에서 호출 |
| `IEncounterManager` / `IBattleResultSource` | 구독하지 않고 `FieldEncounterFlowCoordinator.Bind(...)`에 그대로 넘겨 그쪽이 구독하게 한다 |

### 5.1 등록 시퀀스

1. Field 씬의 `SceneUIRoot`를 찾아 `FieldUIElementIds`로 요소 바인딩 (진행 게이지, 배경, 정비창/방향성 재호출 버튼, 인카운터 경고창, 결과 팝업, 카메라 전환용 두 앵커)
2. `formationButton.onClick` → `uiManager.Open(UIPanelIds.Formation)` (방향성 지시 버튼은 `TacticsPanel` 구현 전까지 보류)
3. `sessionState.OnProgressChanged` → 게이지 뷰 갱신, `OnArrived` → `HandleArrived`(§5.3, `FieldUIController`가 직접 처리 — 흐름 상태가 없는 단발성 반응이라 coordinator로 뺄 이유가 없다)
4. `flowCoordinator ??= new FieldEncounterFlowCoordinator();`(`FieldUIController`의 필드 — Field 씬을 다시 방문해도 재생성하지 않는다)
   - `flowCoordinator.Bind(uiManager, sessionState, encounterManager, battleResultSource);` — 내부적으로 최초 1회만 실제 구독을 수행(§5.2)
   - `flowCoordinator.RebindViews(cameraController, encounterWarningView, resultPopupView);` — 매번 새로 바인딩된 이번 Field 씬의 뷰 참조로 교체
5. `sessionState.Begin()` 호출

### 5.2 `FieldEncounterFlowCoordinator` — 인카운터→전투 전환→결과 처리 (2026-09-01, 코드 기준 재작성)

최초 설계 이후 결과 판정 종류가 2종(승리/패배)에서 4종(사망/도주/궤주/포로, §6·설계08 참고)으로 늘고 씬 전환 연출(설계10)이 커튼을 얹으면서 실제 의존성/흐름이 초안보다 훨씬 늘었다. 실제 소스는 `Core/UI/Field/FieldEncounterFlowCoordinator.cs`.

```csharp
internal class FieldEncounterFlowCoordinator
{
    private bool eventsBound;

    // Bootstrap 상주 객체 - Field 씬을 다시 방문해도 매번 같은 인스턴스이므로 Bind에서 값만 갱신
    private IUIManager uiManager;
    private ISessionState sessionState;
    private IBattleController battleController;
    private IDefeatConsequenceSource defeatConsequenceSource;   // 설계08 - 4종 결과 판정 조회
    private IGameManager gameManager;                            // 궤주 시 Hub 귀환 요청

    // Field 씬 로드마다 갈아끼워지는 뷰/카메라/코루틴 실행자 참조
    private MonoBehaviour coroutineRunner;
    private FieldCameraController cameraController;
    private FieldEncounterWarningView warningView;
    private FieldResultPopupView resultPopupView;
    private FieldTransitionCurtainView transitionCurtain;        // 설계10 - Hub↔Field 전환과 같은 커튼 재사용

    private bool isTransitioning;
    private BattleResult? pendingResult;

    // 매니저 이벤트 구독 - 최초 1회만 실행한다(이유는 최초 설계와 동일, §5 참고).
    public void Bind(IUIManager uiManager, ISessionState sessionState, IEncounterManager encounterManager,
        IBattleController battleController, IBattleResultSource battleResultSource,
        IDefeatConsequenceSource defeatConsequenceSource, IGameManager gameManager)
    {
        this.uiManager = uiManager;
        this.sessionState = sessionState;
        this.battleController = battleController;
        this.defeatConsequenceSource = defeatConsequenceSource;
        this.gameManager = gameManager;

        if (eventsBound) return;
        encounterManager.OnEncounterTriggered += HandleEncounterTriggered;
        battleResultSource.OnBattleEnded += HandleBattleEnded;
        eventsBound = true;
    }

    public void RebindViews(MonoBehaviour coroutineRunner, FieldCameraController cameraController,
        FieldEncounterWarningView warningView, FieldResultPopupView resultPopupView, FieldTransitionCurtainView transitionCurtain)
    {
        this.coroutineRunner = coroutineRunner;
        this.cameraController = cameraController;
        this.warningView = warningView;
        this.resultPopupView = resultPopupView;
        this.transitionCurtain = transitionCurtain;
    }

    private void HandleEncounterTriggered()
    {
        uiManager.Close(UIPanelIds.Formation);   // Close는 멱등, 미적용 변경은 FormationPanel 규칙대로 자동 폐기
        uiManager.Close(UIPanelIds.Tactics);     // TacticsPanel은 Apply 버튼이 없어(즉시 반영) 닫아도 버려지는 변경이 없다
        isTransitioning = true;
        warningView.Show();
        coroutineRunner.StartCoroutine(TransitionAfterWarning());
    }

    private IEnumerator TransitionAfterWarning()
    {
        yield return new WaitForSeconds(WarningDisplaySeconds);   // 2초
        warningView.Hide();

        cameraController.TransitionToBattle(() =>
        {
            // 전투 시작을 슬라이드 완료 시점으로 미룬 이유는 최초 설계와 동일(§4 "갱신 2" 참고).
            // 다만 실제 시뮬레이션은 일시정지 상태로 시작해(LiveBattleSimulationRule.paused), 커튼
            // 페이드 아웃이 끝난 뒤에만 ResumeSimulation()으로 재개한다 - 반투명 커튼 너머로 이미
            // 움직이는 전투가 비쳐 보이는 문제를 막기 위한 사용자 확정 사항.
            battleController.StartBattle();
            transitionCurtain.FadeOut(coroutineRunner, TransitionCurtainFadeOutSeconds, onComplete: () =>
            {
                battleController.ResumeSimulation();
                isTransitioning = false;
                FlushPendingResultIfAny();
            });
        });
    }

    private void HandleBattleEnded(BattleResult result)
    {
        if (isTransitioning) { pendingResult = result; return; }
        ShowResult(result);
    }

    private void FlushPendingResultIfAny()
    {
        if (!pendingResult.HasValue) return;
        var result = pendingResult.Value;
        pendingResult = null;   // ShowResult 호출 전에 먼저 비운다 - 재진입 시 중복 소비 방지
        ShowResult(result);
    }

    private void ShowResult(BattleResult result)
    {
        switch (result.Outcome)
        {
            case BattleOutcome.Victory:
                resultPopupView.Show("승리", "확인", onConfirm: () =>
                    cameraController.TransitionToMovement(onComplete: sessionState.Resume));
                break;
            case BattleOutcome.Defeat:
                ShowDefeatConsequence(defeatConsequenceSource.ResolveDefeatConsequence());
                break;
        }
    }

    // 기획 §14.4 확정: 사망=플레이 종료, 도주=상행 속행(Victory와 동일 흐름), 궤주=Hub 귀환.
    // 포로는 아직 콘텐츠가 없어(테스트 단계) 사망과 동일하게 임시 처리 - 콘텐츠가 생기면 이 case만 교체.
    private void ShowDefeatConsequence(DefeatConsequence consequence)
    {
        switch (consequence)
        {
            case DefeatConsequence.Death:
                resultPopupView.Show("패배 - 전멸", "플레이 종료", onConfirm: Application.Quit);
                break;
            case DefeatConsequence.Flee:
                resultPopupView.Show("패배 - 도주", "상행 속행", onConfirm: () =>
                    cameraController.TransitionToMovement(onComplete: sessionState.Resume));
                break;
            case DefeatConsequence.Rout:
                resultPopupView.Show("패배 - 궤주", "귀환", onConfirm: () =>
                    gameManager.RequestSceneTransition(ContentSceneId.Hub));
                break;
            case DefeatConsequence.Captured:
            default:
                resultPopupView.Show("패배 - 포로", "플레이 종료", onConfirm: Application.Quit);
                break;
        }
    }
}
```

최초 설계가 예상하지 못했던 것: (1) 판정 종류가 2종에서 4종으로 늘어난 것을 `switch`에 case를 추가하는 정도로 흡수했다 — §9가 우려했던 "3종 이상이면 재검토" 시점이 실제로 왔지만, `Dictionary<T, IPresenter>` 같은 전략 패턴 재분리 없이 `switch`만으로 충분했다(과설계 우려가 기우였음). (2) `IDefeatConsequenceSource`/`IGameManager`는 `Bind(...)`에 인자로 추가됐을 뿐 구조 자체(명령 vs 통지 분리, §4)는 바뀌지 않았다. (3) `TacticsPanel`이 실제로 추가되며 `uiManager.Close(UIPanelIds.Tactics)`가 그대로 반영됐다 — 최초 설계가 이 지점을 정확히 예견했다.

### 5.3 도착 처리 (`FieldUIController`가 직접 처리)

```
HandleArrived()
 └─ resultPopupView.Show("도착 성공", "도시 입장", onConfirm: () =>
        gameManager.RequestSceneTransition(SceneNames.Hub))
```

`FieldResultPopupView`는 승리/패배/도착 세 상황 모두 "메시지 + 버튼 1개" 구조가 동일해 하나의 뷰를 재사용한다(문구·버튼 라벨·콜백만 다름). 인카운터 경고창은 깜빡임 애니메이션과 버튼 없음이라는 다른 형태라 별도 뷰(`FieldEncounterWarningView`)로 둔다. `resultPopupView`는 `FieldUIController`와 `FieldEncounterFlowCoordinator` 양쪽이 공유해야 하므로, `FieldUIController`가 생성/바인딩한 뒤 `Bind(...)` 인자로 coordinator에 전달한다(뷰 소유권은 항상 `FieldUIController`, coordinator는 참조만 받는다).

## 6. 전투 결과 판정 — `IBattleResultRule` (2026-09-01, 코드 기준 재작성)

최초 설계는 `BattleManager` 산하에 `BattleResultEvaluator`(`IBattleResultEvaluator` 계약)라는 중간 컴포넌트를 두고, 그 안에서 `IBattleResultRule`을 다시 위임하는 2단 구조였다. 2026-08-26 리팩토링에서 SOLID 점검 결과 이 중간 계층이 실질적 책임 없이 그저 위임만 한다고 판단해 삭제했다(`Docs/Refactor/2026-08-26-Field.md` 참고) — 지금은 `BattleManager`가 `IBattleResultRule` 구현체를 자기 GameObject에서 직접 `GetComponent`로 조회해 필드로 보유한다.

```csharp
public interface IBattleResultRule
{
    void Evaluate(Action<BattleResult> onResult);
}

public class BattleManager : MonoBehaviour,
    IBattleController, IBattleResultSource, IDefeatConsequenceSource, IBattleSimulationEvents, IManagedComponent
{
    private IBattleResultRule resultRule;
    private IDefeatConsequenceRule consequenceRule;      // 설계08 - 결과 판정 확장(4종)
    private IPausableBattleSimulation pausableSimulation; // §5.2 - 커튼 페이드 종료까지 시뮬레이션 정지

    public void ResolveDependencies(IDependencyRegistrar registrar)
    {
        resultRule = GetComponent<IBattleResultRule>();
        if (resultRule == null)
            throw new InvalidOperationException($"{nameof(BattleManager)}와 같은 GameObject에 {nameof(IBattleResultRule)} 구현체가 없다.");

        consequenceRule = GetComponent<IDefeatConsequenceRule>();
        // resultRule이 IRequiresFormationReader/IRequiresCaravanRoster/IRequiresTacticsReader를
        // 구현하면 registrar.TryResolve로 선택 주입(CLAUDE.md 컨벤션 - 아직 설계 전인 시스템은 선택 조회).
        // IBattleSimulationEvents면 OnSimulationBuilt를 그대로 중계, IPausableBattleSimulation이면 보관.
        pausableSimulation = resultRule as IPausableBattleSimulation;
    }

    public void StartBattle() => resultRule.Evaluate(EndBattle);
    public void ResumeSimulation() => pausableSimulation?.ResumeSimulation();
    public DefeatConsequence ResolveDefeatConsequence() => consequenceRule.Resolve();
}
```

`resultRule`은 지금은 Placeholder가 아니라 `LiveBattleSimulationRule`(설계06 참고)이다 — "전략 인터페이스만 교체하면 매니저는 안 바뀐다"는 최초 설계의 OCP 의도는 그대로 지켜졌다. 다만 예상보다 관심사가 늘면서(결과 판정 확장, 시뮬레이션 생성 이벤트 중계, 일시정지/재개) `BattleManager`에 전용 필드/메서드를 새로 추가하는 대신 `resultRule as IXxx`로 선택적 캐스팅하는 패턴이 반복 적용됐다 — 새 관심사가 생길 때마다 `resultRule` 구현체가 필요한 인터페이스를 얼마나 구현하는지로 자연히 확장되지, 매니저 쪽 코드가 늘어나지 않는다.

## 7. 카메라 전환 — `FieldCameraController` (2026-09-01, 코드 기준 재작성)

실제 Field 씬은 카메라가 아니라 전부 Canvas UI로 구성돼 있어(§01 시점엔 없었던 정보), "카메라가 두 앵커 사이를 이동"하는 설계는 애초에 적용되지 않았다. 실제로는 이동 뷰/전투 뷰 두 `RectTransform`(둘 다 화면 전체를 채우는 stretch 앵커)의 `anchoredPosition.x`를 코루틴으로 함께 움직여 "한쪽이 밀려나고 반대쪽이 들어오는" 슬라이드 효과를 낸다 — 실제 소스는 `Core/UI/Field/FieldCameraController.cs`.

```csharp
internal class FieldCameraController
{
    private readonly MonoBehaviour coroutineRunner;
    private readonly RectTransform movementViewRoot;
    private readonly RectTransform battleViewRoot;
    private readonly GameObject battleWorldRoot;              // 전투 뷰 월드 오브젝트 전환(설계13) 이후 추가
    private readonly FieldTransitionCurtainView transitionCurtain;

    public FieldCameraController(MonoBehaviour coroutineRunner, RectTransform movementViewRoot,
        RectTransform battleViewRoot, GameObject battleWorldRoot, FieldTransitionCurtainView transitionCurtain) { ... }

    public void TransitionToBattle(Action onComplete) => SlideRoutine(toBattle: true, onComplete);
    public void TransitionToMovement(Action onComplete) => SlideRoutine(toBattle: false, onComplete);

    private void SlideRoutine(bool toBattle, Action onComplete)
    {
        // 진입 방향의 시작 위치에서 반대쪽 뷰가 반대 방향으로 밀려나도록 두 RectTransform을 동시에 보간.
        // toBattle=true일 때만 battleWorldRoot를 함께 SetActive(true)하고, 검은 커튼도 같은 시작
        // 위치·같은 속도로 동행시켜(설계10과 공유하는 SlideTransitionTimeline) 이전 전투의 잔여
        // 스프라이트가 두 뷰 사이로 비치는 문제를 가린다. 커튼은 슬라이드가 끝나도 걷지 않고
        // 화면을 덮은 채 유지되며, 실제로 걷는 시점은 FieldEncounterFlowCoordinator가 결정한다(§5.2).
    }
}
```

- **`TransitionToBattle`/`TransitionToMovement` 모두 `onComplete` 하나만 받는다** — 최초 설계의 `onBlackoutReached`(카메라 도착 시점에 페이드아웃 시작) 콜백은 없다. "검은 화면"의 역할은 카메라 이동이 아니라 `FieldTransitionCurtainView`(설계10과 공유)가 전담하고, 그 커튼을 걷는 타이밍도 카메라가 아니라 `FieldEncounterFlowCoordinator`가 전투 상태 재구성 완료 후 직접 결정한다(§5.2) — 최초 설계가 카메라 컨트롤러 하나에 몰아넣었던 "전환 애니메이션 + 페이드 타이밍" 책임이 카메라(슬라이드)·커튼(암전)·코디네이터(타이밍 결정) 셋으로 갈렸다.
- `TransitionToMovement`도 진입과 대칭인 슬라이드 애니메이션을 쓴다(최초 설계가 상정했던 "즉시 전환"은 실플레이 피드백으로 폐기됨, [[06-2026-08-25-Field씬_기획]] §4.1).
- `battleWorldRoot`(설계13, 전투 뷰 월드 오브젝트 전환 이후 추가): 전투 유닛 스프라이트가 UI 패널이 아니라 별도 월드 하이어라키에 있어, `battleViewRoot.SetActive`만으로는 자동으로 켜지고/꺼지지 않는다 — `battleViewRoot`와 정확히 같은 시점에 `battleWorldRoot`도 SetActive한다.
- 별도 씬 전환이 아니므로 `ContentSceneId`/`SceneNames`에 전투용 항목을 추가하지 않는다는 원래 결정은 그대로 유지된다.

## 11. 남은 이슈 / 후속 결정 사항

- **§5.2 타이밍 보장**: `EncounterManager.TriggerEncounter()`가 `battleController.StartBattle()`을 즉시 호출하는 기존 코드(§01에서 이미 확정된 명령 방향)를 그대로 유지했다. 그 결과 `BattleResultEvaluator`의 1초 판정 타이머와 `FieldCameraController`의 전환 애니메이션(경고 2초 + 슬라이드/페이드)이 서로 독립적으로 흐른다. 결과가 화면 전환보다 먼저 나올 수 있으므로 `FieldEncounterFlowCoordinator`가 "전환 완료 전이면 결과를 큐잉"하는 처리를 반드시 넣어야 한다(§5.2에 명시). 실제 전투 로직이 생기면 이 타이밍 문제 자체가 자연히 사라질 가능성이 높다(전투 연출 길이가 곧 결과 확정 시점이 되므로).
- **결과 판정 종류 확장**: 궤주/포로/사망/도주가 추가되면 `FieldEncounterFlowCoordinator.ShowResult`의 `switch`를 수정해야 한다(OCP, §9). 2종(승리/패배)뿐인 지금 전략 패턴으로 미리 분리하는 것은 과설계라 판단해 보류했다 — 3종 이상으로 늘어나는 시점에 재검토.
- **인카운터 메타데이터 확장 여지**: 기존 `IEncounterManager.OnEncounterTriggered`는 매개변수 없는 `event Action`이다. [[06-2026-08-25-Field씬_기획]] 7절에 이미 "경고창이 랜덤/확정 인카운터를 구분해서 보여줄지"가 남아 있는데, 지금 계약으로는 그 정보를 전달할 방법이 없다 — 나중에 필요해지면 `EncounterManager`/`IEncounterManager`/`FieldEncounterFlowCoordinator.HandleEncounterTriggered`까지 시그니처를 함께 바꿔야 하는 파급 변경이 된다. 지금 쓰지 않는 정보를 미리 매개변수로 얹는 것은 과설계라 보류하되, 이 지점이 향후 확장 비용으로 남는다는 점만 기록해둔다.
