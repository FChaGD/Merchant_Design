## 1. 전체 구조 개요

기획 §8의 핵심 난제는 "도착 판정은 Field 씬(정식, 빌드 포함)에서 일어나는데, 도착지를 고르는 클릭 배선은 디버그 전용 코드(`Core/Debug/Trip/`, `#if UNITY_EDITOR`) 안에 있다"는 것이다. 이번 설계는 **상태(현재 위치/도착지)는 정식·전역으로 승격**하고, **그 상태를 채우는 "클릭 판정 로직"은 정식 클래스로 유지하되 여전히 디버그 도구에서만 호출**하는 방식으로 이 난제를 푼다 — 지도 위 도시를 클릭할 방법이 디버그 도구 말고는 아직 없기 때문이다(03/04번 기획, 실제 지역 시스템 부재).

```
[정식, Bootstrap 전역 싱글턴 - Core/UI/Trip/, #if 없음]
  InMemoryTripCurrentLocationRepository  (현재 위치, IManagedComponent)
  TripDestinationAssigner                (도착지 지정 로직, IManagedComponent)
        ↑ 읽기/쓰기                              ↑ 클릭 판정 호출(routeReader는 호출부가 전달)
[TripPanel, 정식이지만 실질 트리거는 디버그뿐]      [Core/Debug/Trip/TripMapInteractionCoordinator, #if UNITY_EDITOR]
  - 출발지 패널에 현재 위치 표시                    - 도시 마커 클릭 → destinationAssigner.HandleCityClicked(cityId, routeRepository)
  - "상행 시작" 게이팅(에디터 한정)                  - 정보 패널/마커 시각 갱신
  - 종료 시 destinationAssigner.Reset()

[FieldUIController, 정식 - Core/UI/Field/]
  HandleArrived(): destinationAssigner.DestinationCityId가 있으면
    currentLocationRepository.SetCurrentCity(그 값) 후 destinationAssigner.Reset()
```

## 2. 신규 인터페이스/클래스 (`Core/UI/Trip/`, 전부 정식 — `#if UNITY_EDITOR` 없음)

### 2.1 "현재 위치"

```csharp
public interface ITripCurrentLocationReader
{
    int CurrentCityId { get; }
    event Action Changed;
}

public interface ITripCurrentLocationRepository : ITripCurrentLocationReader
{
    void SetCurrentCity(int cityId);
}
```

`InMemoryTripCurrentLocationRepository : MonoBehaviour, ITripCurrentLocationRepository, IManagedComponent` — `IUnitConditionRepository`/`InMemoryUnitConditionRepository`와 동일한 패턴(Bootstrap 상주, 앱 재시작 시 소멸 = 세션 내 유지, 기획 §4에서 사용자 확정). `RegisterSelf`에서 `registrar.Register<ITripCurrentLocationRepository>(this)` 하나만 등록한다 — 지금은 읽기 전용으로만 필요한 소비자가 없어 `ITripCurrentLocationReader`를 별도로 이중 등록하지 않는다(YAGNI, 필요해지면 추가).

```csharp
public class InMemoryTripCurrentLocationRepository : MonoBehaviour, ITripCurrentLocationRepository, IManagedComponent
{
    // 임시값 - 실제 홈/시작 도시 결정 방식은 후속 과제(기획 16번 §8, §4).
    private const int InitialHomeCityId = 1;

    private int currentCityId = InitialHomeCityId;

    public int CurrentCityId => currentCityId;
    public event Action Changed;

    public void RegisterSelf(IDependencyRegistrar registrar) => registrar.Register<ITripCurrentLocationRepository>(this);
    public void ResolveDependencies(IDependencyRegistrar registrar) { }

    public void SetCurrentCity(int cityId)
    {
        if (currentCityId == cityId) return;
        currentCityId = cityId;
        Changed?.Invoke();
    }
}
```

### 2.2 "도착지 지정"

```csharp
public interface ITripDestinationReader
{
    int? DestinationCityId { get; }
    bool IsAssigned { get; }
    event Action Changed;
}

public interface ITripDestinationAssigner : ITripDestinationReader
{
    /// <summary>
    /// 도시 클릭 판정(기획 16번 §6). routeReader를 호출부가 매번 넘기는 이유: 이 클래스는 정식/전역
    /// 싱글턴(Bootstrap Awake 시점에 생성)인데, 실제 경로 데이터(ITripRouteReader)는 아직 디버그
    /// 지도 도구(TripMapInteractionCoordinator)가 세션마다 들고 있는 로컬 객체라 생성 시점에 주입할
    /// 전역 인스턴스가 없다. 호출부(=디버그 도구, 현재 유일한 클릭 출처)가 자신이 들고 있는
    /// ITripRouteReader를 그대로 넘기게 하면, 실제 지역/경로 시스템이 생겨 경로 데이터가 전역이
    /// 되더라도 이 메서드 시그니처를 바꿀 필요 없이 그 시점의 전역 인스턴스를 넘기기만 하면 된다.
    /// </summary>
    void HandleCityClicked(int cityId, ITripRouteReader routeReader);

    void HandleCityDeleted(int cityId);

    /// <summary>도착지 배정만 초기화한다(출발지="현재 위치"는 건드리지 않음). 상행 준비 UI 종료 시,
    /// 그리고 도착 판정 성립 시(다음 상행을 위해) 호출한다.</summary>
    void Reset();
}
```

`TripDestinationAssigner : MonoBehaviour, ITripDestinationAssigner, IManagedComponent` — `ITripCurrentLocationReader`에 의존(생성자 대신 `ResolveDependencies`에서 `registrar.Resolve`, MonoBehaviour라 생성자 주입 불가 — 기존 `InMemoryUnitConditionRepository` 등과 동일한 제약/패턴).

```csharp
public class TripDestinationAssigner : MonoBehaviour, ITripDestinationAssigner, IManagedComponent
{
    private ITripCurrentLocationReader currentLocationReader;

    public int? DestinationCityId { get; private set; }
    public bool IsAssigned => DestinationCityId != null;
    public event Action Changed;

    public void RegisterSelf(IDependencyRegistrar registrar) => registrar.Register<ITripDestinationAssigner>(this);
    // ITripCurrentLocationReader 자체는 등록되지 않으므로(위 참고) ITripCurrentLocationRepository로 조회한다.
    public void ResolveDependencies(IDependencyRegistrar registrar) => currentLocationReader = registrar.Resolve<ITripCurrentLocationRepository>();

    public void HandleCityClicked(int cityId, ITripRouteReader routeReader)
    {
        var currentCityId = currentLocationReader.CurrentCityId;
        if (cityId == currentCityId)
        {
            return; // 기획 §5/§6 - 현재 위치는 항상 무효
        }

        if (cityId == DestinationCityId)
        {
            DestinationCityId = null;
            Changed?.Invoke();
            return;
        }

        if (routeReader.IsReachable(currentCityId, cityId))
        {
            DestinationCityId = cityId;
            Changed?.Invoke();
        }
        // 도달 불가 - 무시(상태 변화 없음, 기획 §6)
    }

    public void HandleCityDeleted(int cityId)
    {
        if (DestinationCityId != cityId) return;
        DestinationCityId = null;
        Changed?.Invoke();
    }

    public void Reset()
    {
        if (DestinationCityId == null) return;
        DestinationCityId = null;
        Changed?.Invoke();
    }
}
```

`ITripCurrentLocationReader`는 `registrar.Resolve`(필수)로 조회한다 — `InMemoryTripCurrentLocationRepository`도 항상 함께 등록되는 전역 매니저라 없을 이유가 없다(둘 다 `ManagerHierarchyInstaller`가 같은 방식으로 생성 — §5).

**폐기**: `TripOriginDestinationAssigner.cs`, `ITripOriginDestinationReader.cs`, `ITripOriginDestinationAssigner.cs`, `TripRole` 중 상태 머신 관련 사용부(단, `TripRole` enum 자체는 마커 시각 구분용으로 계속 쓰이므로 파일은 유지 — §4 참고).

## 3. `ITripRouteReader` — 경로 탐색으로 확장

기획 §6.1: 직접 인접(`HasRoute`)이 아니라 경로 탐색 기반 도달 가능 여부로 판정을 바꾼다.

```csharp
public interface ITripRouteReader
{
    /// <summary>fromCityId에서 toCityId까지 경로를 거쳐 도달 가능한가(무방향, 몇 개를 거치든 무관).</summary>
    bool IsReachable(int fromCityId, int toCityId);

    IReadOnlyCollection<int> GetConnectedCityIds(int cityId);
}
```

`HasRoute(int, int)`는 제거한다 — 기존 `TripOriginDestinationAssigner`가 유일한 호출부였고(폐기 대상), 다른 소비자가 없음을 확인했다(프로젝트 전체 검색).

`InMemoryTripRouteRepository`(`Core/Debug/Trip/`)에 BFS로 구현한다 — 이미 갖고 있는 `Dictionary<int, HashSet<int>> adjacency`(도시별 인접 목록, `GetConnectedCityIds`가 이미 쓰던 자료구조)를 그대로 순회하면 되므로 추가 자료구조가 필요 없다. 디버그 지도 규모(도시 수십 개 이하)에서는 성능 고려가 불필요한 수준이다.

```csharp
public bool IsReachable(int fromCityId, int toCityId)
{
    if (fromCityId == toCityId) return true;

    var visited = new HashSet<int> { fromCityId };
    var queue = new Queue<int>();
    queue.Enqueue(fromCityId);

    while (queue.Count > 0)
    {
        foreach (var neighbor in GetConnectedCityIds(queue.Dequeue()))
        {
            if (neighbor == toCityId) return true;
            if (visited.Add(neighbor)) queue.Enqueue(neighbor);
        }
    }
    return false;
}
```

## 5. `Core/Debug/Trip/TripMapInteractionCoordinator.cs` — 배선 변경

- 필드 `private readonly TripOriginDestinationAssigner assigner = ...` 제거. 대신 `Bind(...)`가 `ITripCurrentLocationReader currentLocationReader, ITripDestinationAssigner destinationAssigner` 두 매개변수를 새로 받아 필드에 저장한다(생성 책임이 전역 DI로 넘어갔으므로 이 클래스는 더 이상 `new`하지 않는다).
- `public ITripOriginDestinationReader OriginDestinationReader => assigner;` 프로퍼티, `public void ResetOriginDestination() => assigner.Reset();` 메서드 제거 — `TripPanel`이 `destinationAssigner`를 이제 직접 들고 있어 이 코디네이터를 거칠 필요가 없다(§6).
- `originInfoView.SetPanelClickHandler(...)`/`destinationInfoView.SetPanelClickHandler(...)` 두 줄 제거(§4에 따라 `TripLocationInfoView`에 그 메서드 자체가 없어짐).
- `HandleMarkerClicked`: `assigner.HandleCityClicked(cityId)` → `destinationAssigner.HandleCityClicked(cityId, routeRepository)`(코디네이터가 이미 갖고 있는 `routeRepository` 필드를 그대로 넘긴다 — §2.2의 시그니처 설계 참고).
- `cityRepository.CityRemoved += assigner.HandleCityDeleted;` → `cityRepository.CityRemoved += destinationAssigner.HandleCityDeleted;`(그대로 형태 유지, 대상만 교체).
- `RefreshOriginDestinationDisplay` → `RefreshDestinationDisplay`로 개명, 내용 변경:
  ```csharp
  private void RefreshDestinationDisplay()
  {
      // 출발지 패널은 항상 "현재 위치"를 표시한다(기획 §5) - Clear 분기 없음.
      originInfoView.Show(BuildLocationInfo(currentLocationReader.CurrentCityId));
      ShowOrClear(destinationInfoView, destinationAssigner.DestinationCityId);
      RefreshMarkerRoleVisuals();
  }
  ```
  구독 대상도 `destinationAssigner.Changed += RefreshDestinationDisplay;` + `currentLocationReader.Changed += RefreshDestinationDisplay;`(현재 위치가 바뀌는 경우는 지금은 Field 씬 도착 시점뿐이라 이 패널이 열려 있는 동안 바뀔 일은 없지만, 방어적으로 구독해 둔다 — 비용이 거의 없다).
- `EnsureSavedMapLoaded()` 끝에 `RefreshDestinationDisplay();` 한 줄을 추가한다 — 출발지 패널이 클릭 없이도 최초 진입 시 즉시 "현재 위치"를 보여줘야 하기 때문(기획 §5, §8의 "최초 1회 자동으로 채우는 배선 필요" 항목 해소).
- `RefreshMarkerRoleVisuals`: `pair.Key == assigner.OriginCityId` → `pair.Key == currentLocationReader.CurrentCityId`, `pair.Key == assigner.DestinationCityId` → `pair.Key == destinationAssigner.DestinationCityId`.
- **"현재 위치" 도시가 지도에서 삭제되는 극단적 케이스(기획 §8)**: 별도 처리하지 않기로 확정한다. 이 코디네이터는 디버그 전용이고, 자신이 지금 서 있는 도시를 스스로 지우는 것은 정상 사용 흐름이 아니다(실사용 시나리오 아님) — 마커가 없으면 그 역할 강조만 표시되지 않을 뿐, 정보 패널(문자열 기반 폴백)이나 도달 가능성 판정이 예외를 던지지는 않는다(BFS는 인접 목록이 없는 노드를 그냥 빈 컬렉션으로 처리 — §3).

fieldUIController.RegisterFieldUI(uiManager, sessionState, encounterManager, battleController, battleResultSource, defeatConsequenceSource, battleSimulationEvents, gameManager, sceneRevealSignal, unitConditionRepository, currentLocationRepository, destinationAssigner);

`ITripDestinationAssigner`가 두 Wiring 모두에서 `TryResolve` 되는 건 정상이다 — 같은 전역 싱글턴을 서로 다른 두 소비자(Hub의 TripPanel, Field의 FieldUIController)가 각자의 용도(쓰기 트리거 vs 읽고 초기화)로 조회하는 것뿐이다.
