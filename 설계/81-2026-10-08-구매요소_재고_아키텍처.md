## 1. 현재 구조 (코드 확인)

| 영역 | 구현 | 문제 |
|---|---|---|
| 보유 마차·시설 | `PlaceholderCaravanRosterProvider`: 개체 Id = 카탈로그 Id(`Wagon01`). 시작 보유 종류별 첫 행 1개 | 같은 종류를 두 대 가질 수 없음. 파괴되면 다시 후보가 됨 |
| 마구간 후보 | `PlaceholderCaravanAssetCandidateProvider`: 카탈로그 중 미보유 전부, 마을 무시 | 마을 재고 없음 |
| 무역품 판매 | `PlaceholderTownShopStockProvider`: 테이블의 일반(TradeKind) 품목 전부, 수량 무제한, 마을 무시 | 마을 재고 없음 |
| 용병 후보 | `PlaceholderMercenaryCandidateProvider`: 미고용 캐릭터 전부, 마을 무시 | 사망 기록 개념 없음 |
| 상한 | `MercenaryHiringService.MaxOwnedPerClass = 5`, `CaravanAssetPurchaseService.MaxOwnedPerKind = 5`. 정비창 배치 상한(기획 11)은 별도 코드 없이 보유 수가 곧 상한 | 기획 80 §3-10으로 폐기 |
| 개체 Id → 카탈로그 직접 조회 | `PlaceholderTradeGoodsInventoryRepository.SyncSections`(적재 섹션 모양·이름), `StablePanel.RenderOwned`(보유 목록) | 발급 Id 체계로 바꾸면 조회 실패 |
| 적재 섹션 이름 | `InventorySection.DisplayName`을 생성 시 고정 | 재번호 규칙(기획 80 §4-1)과 충돌 |
| 사망 | `InMemoryUnitConditionRepository`의 사망 플래그. `ResetAllToFull()`이 상행 시작(Field 노출)·정상 도착에서 전원 해제. **궤주 귀환 경로(`FinishStep`)에는 호출 없음** | 영구 제거 경로 없음 |

개체 Id를 받는 나머지 소비자(정비창 배치 `FormationLayout`, 전투 보호 대상, 화물 원장, 정산 `BattleAftermathApplier`)는 Id를 문자열로만 다룬다 — 체계 변경의 영향이 없다.

## 3. 재고 데이터 계층

### 3.1 테이블

`Assets/Table/Town/TownStock.xlsx`, 시트 `TownStock`.

| 열 | 형식 | 참조 |
|---|---|---|
| CityId | 정수 | `City.xlsx` CityData.Id |
| Category | 문자열 `Wagon` / `Facility` / `TradeGoods` | — |
| ItemId | 문자열 | Category별: `Wagon.xlsx` / `Facility.xlsx` / `TradeGoods.xlsx` 의 Id |
| Quantity | 정수 | 1 이상 |

- 행 순서 = 화면 표시 순서(기획 80 §4-3).
- 초기값 = 기획 80 §3.1 디버그 초기 재고.

### 3.2 임포터

- `TownStockTableImporter`(Editor) → `TownStockTableAsset`(SO, 행 목록). 경로 상수는 기존 `TableAssetPaths`에 추가.
- `TableAutoImportOnPlay`와 Import All에 등록.
- 임포트 오류(예외로 중단, 기존 임포터와 같은 방식): 알 수 없는 Category, Category 테이블에 없는 ItemId, CityData에 없는 CityId, Quantity ≤ 0, (CityId, Category, ItemId) 중복.

### 3.3 Category

```csharp
public enum TownStockCategory { Wagon, Facility, TradeGoods }
```

- Category → 판매 시설 매핑은 정적 클래스 `TownStockCategoryFacilities` 한 곳: Wagon·Facility → `TownFacilityIds.Stable`, TradeGoods → `TownFacilityIds.TradeGoodsMarket`.
- 무역품 화면의 TradeKind(일반) 필터는 없앤다 — 판매 여부는 재고 행이 정한다. 특산물 구매 화면이 생기면 Category를 추가한다.

### 3.4 실행 중 재고 저장소 `InMemoryTownStockRepository`

Bootstrap 상주 MonoBehaviour, `IManagedComponent`. 인스펙터 필드: `TownStockTableAsset`.

```csharp
public readonly struct TownStockLine { string ItemId; int Remaining; }

public interface ITownStockReader
{
    // 테이블 행 순서. 남은 수량 0인 행도 포함한다(무역품 품절 표시용).
    IReadOnlyList<TownStockLine> GetLines(int cityId, TownStockCategory category);
    event Action OnStockChanged;
}

public interface ITownStockConsumer
{
    // 남은 수량이 1 이상이면 1 줄이고 true.
    bool TryConsume(int cityId, TownStockCategory category, string itemId);
}
```

- 두 타입을 각각 DI 등록한다(읽기 타입 미등록 방지).
- 마을을 처음 조회할 때 테이블에서 그 마을 행을 복사해 초기화한다. 앱 실행 중 유지(기획 80 §3-9).
- **규모 경고(실행 시점)**: 마을 규모별 시설 배정은 Bootstrap 인스펙터(`TownScaleFacilityAvailabilityProvider`)에 있어 임포터가 모른다. 초기화 시 `ITownFacilityAvailabilityReader`(선택적 DI)로 Category의 판매 시설이 그 마을에 없으면 `Debug.LogWarning` 후 그 행을 제외한다. 조회기가 없으면 검사하지 않는다.
- 늘리는 연산은 두지 않는다(재입고 범위 밖, 기획 80 §3-7).

### 3.5 Placeholder 교체

| 제거 | 신규 | 동작 |
|---|---|---|
| `PlaceholderTownShopStockProvider` | `TownShopStockProvider` : `ITownShopStockReader` | `GetLines(cityId, TradeGoods)`를 무역품 카탈로그와 조인 → `ShopStockEntry`(정의, 가격, **남은 수량**). 시설 Id가 무역품 구매가 아니면 빈 목록 |
| `PlaceholderCaravanAssetCandidateProvider` | `CaravanAssetCandidateProvider` : `ICaravanAssetCandidateReader` | `GetLines(cityId, Wagon)` → `GetLines(cityId, Facility)` 순으로, 남은 수량만큼 프로필을 반복해 펼친다(재고 1대 = 후보 1개) |

- 소비자 인터페이스는 그대로(이미 마을 Id를 받는다). `ShopStockEntry`에 `Remaining`(int)만 추가한다 — 품목 Id는 기존 `Definition.Id`를 쓴다.
- 카탈로그에 없는 ItemId 행은 임포터가 막으므로 실행 중에는 건너뛰기만 한다.

## 4. 상점 화면·구매 서비스

### 4.1 공통 구매 순서

판정 → 재화 차감 → 지급(그리드 배치 / 로스터 추가) → **재고 차감**.

- 지급 실패 시 재화 환급(기존 방식).
- 재고 차감은 판정에서 남은 수량을 확인한 같은 프레임 안이라 실패 경로가 없다. 실패하면 지급은 유지하고 `Debug.LogWarning`만 남긴다 — 되돌림 연산을 만들지 않는다.
- 판정 우선순위: **품절 → 재화 부족 → 공간 부족**(품절은 기다려도 풀리지 않음).

### 4.2 무역품 구매

- `ShopPurchaseCheck`에 `SoldOut` 추가. `ShopPurchaseService` 생성자에 `ITownStockConsumer`와 현재 마을 Id 조회(`ITripCurrentLocationReader`)를 받는다.
- `TradeGoodsMarketPanel`:
  - 행: 이름·크기·가격 + **"남은 수량 n" / "품절"**. 품절 행은 제자리 유지.
  - 사유 문구 `SoldOut` → "품절".
  - `ITownStockReader.OnStockChanged` 구독 → 목록 다시 그림, **선택 유지**(행이 사라지지 않음). Dispose에서 해제.
  - 빈 목록 문구 "판매품 없음" → "판매 품목 없음".
- `ShopStockRowView`에 수량 레이블 필드 추가. `TradeGoodsMarketUIBuilder`가 행 템플릿에 get-or-create로 붙이고 연결한다.

### 4.3 마구간

- `CaravanAssetPurchaseCheck`: `OwnedFull`·`AlreadyOwned` 삭제, `SoldOut` 추가(후보 펼침 후 구매 직전에 다른 경로로 재고가 줄었을 때의 방어).
- `CaravanAssetPurchaseService`: `MaxOwnedPerKind` 삭제. 생성자에 `ITownStockConsumer`, 현재 마을 조회. 구매 = 재화 차감 → `roster.TryAddOwned(종류 Id, out 개체 Id)` → 재고 차감.
- `StablePanel`:
  - 후보 행 = 재고 1대당 1행, 이름 = 종류 이름(번호 없음). 재고 변경 이벤트로 다시 그림 → 산 행이 사라지고 선택 해제(기존 로스터 변경 시와 같은 규칙).
  - 좌측 보유 목록: 제목 "마차 n"(상한 표기 제거), 개체는 보유 순서대로 `n번 이름`(§5.3).
  - 빈 목록 문구 "구매 가능한 마차·시설 없음" → "판매 품목 없음".
  - `ICaravanAssetCatalogReader` 의존은 종류 이름표(`GetKindLabel`)용으로만 남는다.

### 4.4 용병단 접촉

- `MercenaryHireCheck.RosterFull`, `MaxOwnedPerClass`, 상한 문구, 보유 제목의 "/5" 삭제.
- 후보 제외 조건 추가는 §6.

## 5. 마차·시설 개체 체계

### 5.1 발급 Id

`PlaceholderCaravanRosterProvider`가 담당한다.

| 항목 | 규칙 |
|---|---|
| 형식 | `{종류 Id}#{일련번호}` (예 `Wagon01#3`). 형식을 아는 곳은 로스터뿐 — 다른 곳은 불투명 문자열로 다룬다 |
| 일련번호 | 종류별 카운터, 1부터 증가만(제거돼도 재사용 안 함) |
| 매핑 | `Dictionary<string 개체 Id, string 종류 Id>` |
| 시작 보유 | 종류별 첫 행 1대 발급(`Wagon01#1`, `Facility01#1`) — 재고와 무관(기획 80 §4-2) |
| 유닛 객체 | `PlaceholderFormationUnit(개체 Id, 종류명, 아이콘, Kind, 종류 AreaShape)` — DisplayName은 팔레트 카테고리 이름이라 종류명 유지 |
| 로스터 목록 순서 | 용병(캐릭터 테이블 순) → 마차 → 시설, 마차·시설은 **보유 순서**(같은 List를 비우고 다시 채우는 기존 방식 유지) |

### 5.2 계약 변경

```csharp
public readonly struct OwnedCaravanAsset
{
    public string InstanceId { get; }
    public CaravanAssetProfile Profile { get; }   // 종류 정보(이름·모양·적재 모양)
    public int Number { get; }                    // 같은 종류 안 보유 순서 + 1 (조회 시 계산)
}

public interface IOwnedCaravanAssetReader
{
    IReadOnlyList<string> GetOwnedIds(FormationUnitKind kind);   // 기존 — 이제 개체 Id
    bool TryGetOwned(string instanceId, out OwnedCaravanAsset asset); // 신규
    event Action OnOwnedChanged;
}

public interface IOwnedCaravanAssetRoster : IOwnedCaravanAssetReader
{
    int CountOwnedOfKind(FormationUnitKind kind);
    bool TryAddOwned(string kindId, out string instanceId);   // 변경 — 종류 Id를 받고 개체 Id를 돌려준다
    // IsOwned(string) 삭제 — "이미 보유" 개념 없음
}
```

- `IOwnedCaravanAssetRemover.TryRemoveOwned(개체 Id)`는 시그니처 유지, 매핑도 함께 지운다.
- 번호는 저장하지 않고 조회마다 계산한다 → 제거 시 자동으로 당겨짐(기획 80 §4-1).

### 5.3 표시 이름

- 정적 형식 함수 `OwnedCaravanAssetNames.Format(OwnedCaravanAsset)` → `"{Number}번 {Profile.Name}"`. 소비자 모두 이 함수를 쓴다.

| 소비자 | 변경 |
|---|---|
| 상단 물류품 저장소 `PlaceholderTradeGoodsInventoryRepository` | 섹션 생성 시 `TryGetOwned`로 적재 모양·이름. **보유 변경마다 모든 섹션 이름을 다시 계산**해 갱신한다 — `InventoryGrid`에 섹션 이름 변경 연산(`TrySetSectionDisplayName`) 추가, 이름이 바뀌면 기존 변경 이벤트(`OnChanged`) 발생 → 팝업 `이름 (n/N)` 재표시 |
| 마구간 보유 목록 | `GetOwnedIds(kind)` 순회 + `TryGetOwned` + `Format` |
| 정비창 정보 패널 | 마차·시설 유닛을 `CaravanAssetFormationUnit`(`IInstanceNamedUnit.InstanceName` — 조회 시 로스터에서 `Format` 계산)으로 만들고, `FormationInfoPanelView.Show`는 `IInstanceNamedUnit`이면 `InstanceName`, 아니면 `DisplayName`을 쓴다. 정비창 등록 시그니처를 늘리지 않기 위함(제작 계획 수립 시 변경, 2026-10-08) |

### 5.4 기존 한계 (범위 밖, 기록)

- 정비창 팔레트는 마차를 "마차" 한 줄로 묶고 드래그 시 남은 개체 중 첫 번째를 고른다. 종류별 대열 모양·적재 모양이 다르면 원하는 종류를 골라 놓을 수 없다. 캐릭터(직업당 한 줄, 캐릭터 단위 스탯)도 같은 상태. 기획 80 §4-7로 이번엔 유지 — 후속 과제.

## 6. 캐릭터 월드 유일·사망 영구 제거

### 6.1 월드 유일

- 후보 제공자가 마을 무관하게 미고용 캐릭터를 돌려주므로 이미 충족. `PlaceholderMercenaryCandidateProvider`는 유지(마을 소속 확장 시 교체, 기획 80 §5).
- 후보 조건 추가: `!roster.IsHired(id) && !deceased.IsDeceased(id)`. `IDeceasedCharacterReader`는 선택적 DI — 없으면 미고용만 본다.

### 6.2 사망 기록 저장소 `InMemoryDeceasedCharacterRepository`

Bootstrap 상주, `IManagedComponent`.

```csharp
public interface IDeceasedCharacterReader { bool IsDeceased(string characterId); }
public interface IDeceasedCharacterRecorder { void Record(string characterId); }
```

- 두 타입 각각 DI 등록. 앱 실행 중 유지(기획 80 §4-5).
- 로스터에 두지 않는 이유: 로스터는 현재 구성원, 사망 기록은 상단에서 빠진 뒤에도 남는 월드 기록 — 수명·소비자가 다르다.

### 6.3 로스터 제거 계약

```csharp
public interface IHiredCharacterRemover { bool TryRemoveHired(string characterId); }
```

- `PlaceholderCaravanRosterProvider`가 구현·DI 등록. 제거 시 `OnHiredChanged` 발생. 고용 화면 계약(`IHiredCharacterRoster`)에 제거 권한을 넓히지 않는다(ISP, `IOwnedCaravanAssetRemover`와 같은 이유).

### 6.4 상행 종료 처리 `TripEndProcessor`

plain C#. 의존: `ICaravanRosterProvider`, `IUnitConditionRepository`, `IFormationRepository`, `IHiredCharacterRemover`, `IDeceasedCharacterRecorder`(모두 null 허용 — 없으면 해당 단계 생략).

```
Finish():
 1. 로스터의 용병(IMercenaryUnit) 중 IsDead인 Id 수집
 2. 현재 배치를 복제해 그 Id의 칸을 비우고 Apply (캐릭터는 대열 연결과 무관)
 3. 각 Id: remover.TryRemoveHired → recorder.Record
 4. condition.ResetAllToFull()   ← 기존 상행 종료 호출을 이곳으로 옮김
```

- 제거(3)를 초기화(4)보다 먼저 한다 — 초기화가 사망 플래그를 지우기 때문.

| 호출 지점 | 지금 | 변경 |
|---|---|---|
| 정상 도착 `FieldUIController.HandleTripArrived` | `ResetAllToFull()` | `FinishTrip()` |
| 궤주 귀환 `FinishStep`(Rout 분기) | 호출 없음, Hub 전환 | Hub 전환 직전 `fieldUIController.FinishTrip()` |

- 두 곳에서 명시 호출한다("Hub 씬 진입" 훅은 게임 시작 첫 진입과 구분하는 암묵 조건이 생겨 쓰지 않는다).
- 배선: `FieldUIController`가 기존 DI 해결 시점에 의존을 받아 `TripEndProcessor`를 만들어 소유한다. `IFieldUIController`에 `FinishTrip()`을 추가하고, 정상 도착은 내부에서, 궤주는 `FinishStep`이 이미 받는 `IFieldUIController`로 호출한다 — `FinishStep` 생성자는 바뀌지 않는다.
- 사망·포로 패배(플레이 종료)는 대상 아님. 상행 중 표시(팔레트 회색)는 변화 없음.

## 12. 결정 사항 (2026-10-08 사용자 승인)

1. 개체 Id: 발급 Id + 종류 매핑(A안). 번호는 조회 시 계산.
2. 재고 차감은 지급 뒤 마지막, 되돌림 연산 없음. 판정 순서 품절 → 재화 → 공간.
3. 무역품 TradeKind 필터 폐기, 판매 여부 = 재고 행.
4. 규모 경고는 실행 시점(저장소 초기화).
5. 사망 기록은 로스터와 분리된 저장소, 로스터 제거는 별도 계약.
6. 상행 종료 처리는 정상 도착·궤주 귀환 두 곳에서 명시 호출.
7. 팔레트 카테고리 묶음 한계는 범위 밖(후속).
