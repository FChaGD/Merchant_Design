## 0. 범위

- **아군(Ally)에만 적용된다.** 적 행동 성향(§5-6 미착수 주제)은 별도라 `BattleCharacterUnit`의 적 진영 경로는 이번 설계로 건드리지 않는다 — 아군/적 분기가 이미 `isAlly` 플래그와 호출부(`BuildAllies`/`BuildEnemies`)로 나뉘어 있어 자연스럽게 격리된다.
- 개체별 축(기획 §4)은 범위 밖 — 확장 여지만 남긴다.
- 서포터/암살자는 대응 직업이 없어 이번 구현 대상에서 제외(기획 §0에서 이미 확정) — `RoleGroupTacticsCatalogAsset`에 항목이 없으므로 자연히 해당 역할군 유닛도 없다.

## 1. 데이터 흐름 개요

```
ITacticsRepository(파티 설정 + 역할군 override)
  + MercenaryRoleGroupMapAsset(직업→역할군)
  + RoleGroupTacticsCatalogAsset(역할군별 허용 후보 — override 값이 실제로 여기서 옴)
        ↓ LiveBattleSimulationRule.BuildAllies 시점에 유닛별로 "해석"
UnitTacticsProfile (유닛 1기당 1개, 전투 시작 시 확정 — 전투 중 UI에서 값을 바꿔도 이번 전투엔 반영 안 됨)
        ↓ 생성자 주입
BattleCharacterUnit → 6개 전략 협력자에 위임(§3)
```

전투 시작 시점에 한 번 해석해 고정하는 이유는 기존 `fleeTravelDistance`(대형 크기 기반, 전투 시작 시 확정)와 같은 이유다 — 전투 중간에 방향성 지시가 바뀌어도 이미 시작된 전투의 각 유닛 행동이 프레임마다 흔들리면 예측 불가능해진다.

## 2. UnitTacticsProfile (해석된 값, 유닛 생성 시 확정)

```
public readonly struct UnitTacticsProfile
{
    public EnemyRecognitionType RecognitionType;   // 파티 축
    public ActivityRadiusPreset RadiusPreset;      // 파티 축
    public PursuitPreset Pursuit;                  // 파티 축
    public TargetPriority TargetPriority;          // 역할군 축
    public LocalPositioning Positioning;            // 역할군 축
    public SelfPreservation SelfPreservation;       // 역할군 축
```

해석 규칙: 파티 3축은 `ITacticsRepository.GetPartySettings()`를 그대로 쓰고, 역할군 3축은 유닛의 직업을 `MercenaryRoleGroupMapAsset`로 역할군에 매핑한 뒤 `ITacticsRepository.GetRoleGroupOverride(roleGroup)`의 값을 그대로 쓴다(§6-1에 이 규칙의 해석상 애매함을 정리했다).

## 3. 신규 전략 인터페이스 (BattleCharacterUnit의 협력자)

기존 백로그(설계 06번 §10 "`BattleCharacterUnit`이 이동·타겟팅·공격·사기·도주를 전부 맡음 — 전술이 추가되면 상태 패턴 재검토")를 해소하는 지점이다. 6개 협력자로 책임을 나눈다 — 전부 `IUnitSpatialQuery`와 같은 성격의 순수 C# 전략 인터페이스(OCP: enum값→구현체는 팩토리가 매핑, 새 후보가 늘어도 `BattleCharacterUnit` 무변경).

### 3.1 IActivityRadiusZone — "여기가 내 활동 반경 안인가"

```
public interface IActivityRadiusZone
{
    bool Contains(Vector2 worldPosition);
    Vector2 ClampToZone(Vector2 desiredPosition);  // 제작 단계 추가 - HoldPosition 전용, §3.4 참고
}
```

- `Fixed`: `homePosition` 기준 반경 4m.
- `Standard`: 대형 중심(원점) 기준 `IBattleFieldLayout`에 새로 추가할 `ComputeStandardActivityRadius(columnCount)`(= `FormationExtentRadius(columnCount) + 5f`) 반경 — `ComputeFieldRadius`/`ComputeFleeTravelDistance`와 같은 자리에 같은 패턴으로 추가.
- `Wide`: 항상 `true`.
- 이 판정은 §2.1(적 인식의 "근접" 조건)과 §4(추적/복귀 조건)에서 공유해서 쓴다 — 활동 반경이라는 개념이 두 축(파티 인식, 파티 추적)에서 같은 경계선을 참조하기 때문(기획 문서에서도 "근접"의 기준이 활동 반경이라고 명시).
- **제작 단계 반영(5-f)**: `ClampToZone`은 최초 스케치엔 없었다. `Contains`(참/거짓)만으론 `IPursuitPolicy.ClampDestination`(HoldPosition 전용)이 "반경 밖이면 어디로 당겨야 하는지" 알 수 없어 추가했다 — `Fixed`/`Standard`는 경계 위 최근접점으로, `Wide`는 항상 그대로 반환.

### 3.2 IEnemyRecognitionTracker — "이 적이 인식됐는가"

유닛 1기당 1개, 매 틱 갱신되는 상태 객체(적마다 개별 판정 — 기획 §2.1).

```
public interface IEnemyRecognitionTracker
{
    // 상태 갱신과 인식 목록 조회를 한 메서드로 합쳤다(점검 이력 참고 — 최적화 리뷰에서
    // Tick+GetRecognized 별도 순회가 지적됨) - 한 번의 순회로 처리, 반환 리스트는 내부에서
    // 재사용(매 틱 재할당 없음).
    IReadOnlyList<IDamageable> TickAndGetRecognized(float deltaTime, IReadOnlyList<IDamageable> allEnemies, IActivityRadiusZone radiusZone);
    void NotifyAttackedBy(IBattleCombatant attacker);  // §5-1 참고 - TakeDamage 시그니처 변경 필요
}
```

- `OneSecondDelay`/`FiveSecondOrProximity`: 적별 개별 타이머(스폰 시점 기준) + (후자는) `radiusZone.Contains`로 조기 인식.
- `ProximityOrHit`: 타이머 없음. `radiusZone.Contains` 또는 `NotifyAttackedBy`로 들어온 공격자만 개별 인식 처리.

### 3.3 ITargetSelector — "인식된 적 중 누구를 공격할까"

```
public interface ITargetSelector
{
    IDamageable Select(Vector2 selfPosition, IReadOnlyList<IDamageable> recognizedCandidates);
}
```

`Nearest`(기존 `spatialQuery.FindNearest` 위임) / `DeepestPenetration`(원점으로부터 먼 정도 대신 "아군 대형 중심 반대편으로 얼마나 파고들었는지" — 원점 기준 근접도로 근사) / `HighestHpRatio`(§3.3-1) / `HighestAttack` / `LowestHp` 5종. 진영 공유 상태 없이 후보 목록만으로 계산 가능 — `IEngagementLedger` 같은 신규 공유 상태는 필요 없어졌다(아래 참고).

**§3.3-1 HighestHpRatio(구 "미피격 적")**: "아직 공격받지 않은 적을 우선 노린다"는 원래 의도를 유지하되, "누가 이미 타겟 중인지" 같은 진영 공유 상태 없이 **현재HP/최대HP 비율이 가장 높은 적**으로 근사한다(사용자 확정, 2026-08-27) — 공격을 안 받은 적일수록 자연스럽게 HP 비율이 100%에 가까우므로, 비율이 가장 높은 적을 고르면 사실상 "아직 안 맞은 적 우선"과 같은 효과를 낸다. 대신 `IDamageable`에 현재 HP(또는 HP 비율)가 노출돼야 한다(§5-4) — `LowestHp` 선택자도 같은 데이터가 필요해 이 노출 하나로 두 선택자 모두 해결된다.

### 3.4 IPursuitPolicy — "지금 추적을 그만두고 복귀·재타겟해야 하는가"

```
public interface IPursuitPolicy
{
    bool ShouldDisengage(float deltaTime, bool isOutsideRadius, bool justLandedHit);
    // 대부분의 프리셋은 destination을 그대로 반환한다(no-op) - HoldPosition만 zone 경계 안으로
    // clamp한다. "반경 밖으로 안 나간다"는 지식을 이 정책 안에 캡슐화해, BattleCharacterUnit이
    // Pursuit 프리셋별 분기를 직접 갖지 않게 한다(점검 이력 참고 - OCP 위반으로 지적됨).
    Vector2 ClampDestination(Vector2 desiredDestination, IActivityRadiusZone zone);
}
```

**호출 전제**: 이 정책은 "현재 살아있는 타겟을 추적 중"일 때만 매 틱 호출된다 — 타겟이 죽거나 도주해서 없어졌을 때의 재타겟은 기존 `BattleCharacterUnit.Tick`의 널 타겟 분기(`target is not { IsAlive: true }` → `spatialQuery.FindNearest`)가 프리셋과 무관하게 이미 처리한다. 그래서 최초 설계안에 있던 `targetIsAlive` 매개변수는 실제로 항상 true인 채로만 호출되는 죽은 매개변수라 제거했다.

프리셋별 내부 누적 타이머를 각자 들고 있다(기획 §2.3 그대로):
- `Autonomous`: 항상 false — **§6-2에서 정정**: 이 축은 §3.4 자기 자신의 트리거만 무력화할 뿐, `IActivityRadiusZone`/§2.1 인식 판정에는 전혀 영향을 주지 않는다. 즉 "반경 무시"는 "추적을 절대 포기하지 않는다"는 의미로 한정되고, 반경 자체(그리고 그걸 참조하는 인식·포지셔닝)는 파티가 고른 `ActivityRadiusPreset` 그대로 정상 동작한다.
- `HuntToKill`: 항상 false(위 호출 전제와 같은 이유로 사실상 "죽을 때까지 안 그만둠"이 자동으로 성립 — 별도 로직 불필요).
- `OffensiveJudgment`: 반경 밖 & 미명중 누적 5초.
- `NoPursuit`: 반경 밖 누적 3초, 명중 여부 무관.
- `HoldPosition`: `ShouldDisengage`는 "타겟이 반경 밖으로 나간 그 즉시" true. "애초에 반경 밖으로 이동하지 않는다"는 부분은 같은 프리셋의 `ClampDestination` 구현이 담당한다(위 인터페이스 변경, 점검 이력 §OCP 참고) — 다른 4개 프리셋은 `ClampDestination`을 no-op(그대로 반환)으로 둔다.

트리거되면: 인식된 적 중 반경 내의 적이 있으면 그 적으로 재타겟(§3.3 재호출 — 반경 내 필터링은 `BattleCharacterUnit`이 `recognizedCandidates`에 `radiusZone.Contains`를 적용해 만든다, §4), 없으면 `HomePosition`으로 복귀(신규 `Returning` 상태 — §4).

### 3.5 IPositioningStrategy — "반경 안에서 어떻게 움직일까"

```
public interface IPositioningStrategy
{
    Vector2 ComputeMoveTarget(Vector2 selfPosition, IDamageable target, float range, Vector2 homePosition);
}
```

`Charge`(기존 기본 동작 그대로 — 타겟 방향 직진) / `Blocking`(아군 대형 중심과 타겟 사이 지점) / `MaintainRange`(사거리의 일정 비율 이내로 들어오면 뒤로, 벗어나면 앞으로) / `Stationary`(항상 `selfPosition` 반환 — 제자리).

### 3.6 ISelfPreservationModifier — "생존 지향 이동으로 덮어쓸까"

```
public interface ISelfPreservationModifier
{
    void NotifyDamaged(float amount, float currentHpRatio);
    bool TryGetOverrideMovement(float deltaTime, Vector2 selfPosition, IDamageable target, float range, out Vector2 destination);
}
```

**제작 단계 반영(5-e, 2026-08-27)**: `deltaTime`/`range` 매개변수는 최초 스케치엔 없었으나 실제 구현 중 필요해 추가했다 — `FallBackOnHeavyDamage`의 "일시"(시간 기반 지속, `deltaTime` 필요)와 `Kiting`의 사거리 비율 판정(`range` 필요) 때문. `TacticsTuning`에 `FallBackOnHeavyDamageRetreatSeconds`(2초)도 함께 추가.

`Resilient`(항상 false) / `FallBackOnHeavyDamage`(HP 임계치 이하 최초 1회만 일시 후퇴 — 기획에서 확정한 "전투당 1회" 제한을 여기서 내부 플래그로 구현) / `Kiting`(타겟이 사거리 근접 구간 이내면 반대 방향 목적지 반환) / `RetreatOnHit`(피격 시 일정 거리 후퇴 목적지 반환, 거리 도달하면 해제).

## 4. BattleCharacterUnit 리팩터 개요

- `Tick()`은 더 이상 이동/타겟팅을 직접 계산하지 않고 위 협력자에 위임하는 조율자로 축소된다.
- 상태 우선순위: 기존 `Fleeing`(사기 도주) 최우선 유지 → 신규 `Returning`(활동 반경 밖에서 복귀 중, §3.4가 트리거) → 기존 `Engaging` 로직.
- **Engaging 세부 순서(확정, 점검 이력 반영 — 최적화①·SOLID③ 수정안)**:
  1. 매 틱 `IEnemyRecognitionTracker.TickAndGetRecognized(...)`로 인식된 적 목록을 갱신·조회한다(한 번의 순회).
  2. **타겟 선택은 스티키를 유지한다** — `ITargetSelector.Select`는 (a) 현재 타겟이 없거나 죽었을 때(기존 `target is not {IsAlive:true}` 분기, 프리셋과 무관하게 항상 동작), 또는 (b) `IPursuitPolicy.ShouldDisengage`가 이번 틱에 true를 반환했을 때(이때는 후보를 `radiusZone.Contains`로 한 번 더 필터링해 반경 내 후보만 넘긴다)만 호출한다. 살아있고 반경 조건도 문제없는 타겟을 매 틱 다시 고르지 않는다 — 기존 코드의 "타겟 고정" 최적화를 그대로 승계.
  3. 이동 목적지 계산: `ISelfPreservationModifier.TryGetOverrideMovement`를 먼저 물어보고, true면 그 목적지를 그대로 쓴다(자기보호가 포지셔닝을 덮어씀) — false일 때만 `IPositioningStrategy.ComputeMoveTarget`으로 폴백한다(자기보호=Kiting과 포지셔닝=Stationary처럼 서로 반대되는 값을 같은 유닛이 동시에 가질 수 있어, 이 우선순위로 모순을 해소한다).
  4. 위에서 정해진 목적지를 `IPursuitPolicy.ClampDestination(destination, radiusZone)`에 통과시킨 뒤 실제로 적용한다 — `HoldPosition`이면 여기서 반경 경계로 clamp되고, 나머지 프리셋은 그대로 통과한다(`BattleCharacterUnit`은 `Pursuit` 값을 직접 분기하지 않는다).
- **Returning 종료 조건**: `HomePosition` 도달 시 `Returning` 해제 → 통상 `Engaging`으로 복귀. 이 시점의 타겟은 이미 §3.4 트리거 시점에 정리된 상태(반경 내 재타겟 완료 또는 타겟 없음)라 별도 처리 불필요 — 타겟이 없으면 기존 널 타겟 분기가 다음 틱에 자연히 재탐색한다.
- 생성자에 `HomePosition`(정비창 슬롯 좌표)과 `UnitTacticsProfile`(또는 이미 해석된 6개 전략 인스턴스)이 추가된다.
- `ApplySeparation`(같은 진영 반발)은 무변경 — 전술 축과 무관한 저수준 이동 보정이라 그대로 둔다.

## 5. 기존 인터페이스 변경 필요 사항

### 5.1 `IDamageable.TakeDamage` 시그니처

피격 인식(§2.1 "근접 또는 피격")은 "누가 때렸는지"가 있어야 그 공격자만 인식시킬 수 있다. 지금은 `TakeDamage(float amount)`라 공격자 정보가 없다.

```
void TakeDamage(float amount, IBattleCombatant attacker);
```

`BattleCharacterUnit.Tick`의 공격 지점(`target.TakeDamage(...)`)에서 `this`를 넘긴다. `BattleProtectedUnit`(Wagon/Facility)도 같은 시그니처를 구현해야 하지만 이 값을 쓰지 않고 무시하면 된다(LSP — 계약은 지키되 필요 없는 구현체는 무시).

### 5.2 `IBattleFieldLayout` 분리 — `IAllyPositionLayout` / `IBattleFieldGeometry` (점검 이력 반영, SOLID② 수정안)

06번 설계 문서 §10에 이미 "아군 좌표 변환과 스폰/반경 계산 두 책임을 겸함"으로 저우선순위 backlog로 남아있던 항목을, 이번에 활동 반경 계산까지 얹기 전에 실제로 분리한다(사용자 확정, 2026-08-27 — 옵션2).

```
public interface IAllyPositionLayout
{
    Vector2 ComputeAllyPosition(int column, int row, int columnCount);
}

public interface IBattleFieldGeometry
{
    Vector2 ComputeSpawnPoint(int spawnPointIndex, int columnCount);
    float ComputeFieldRadius(int columnCount);
    float ComputeFleeTravelDistance(int columnCount);
    float ComputeStandardActivityRadius(int columnCount);  // 신규 - FormationExtentRadius(columnCount) + StandardRadiusMargin(5f), 나머지 셋과 같은 파생값 패밀리
}
```

`BattleFieldLayout` 클래스 하나가 두 인터페이스를 함께 구현한다(분리는 인터페이스 레벨에서만, 구현 클래스는 그대로 하나 — `FormationExtentRadius` 같은 내부 공유 헬퍼가 있어 억지로 클래스까지 나누면 오히려 손해). 실제 소비자는 `LiveBattleSimulationRule` 한 곳으로 파악돼 파급 범위는 좁다 — 이 클래스가 필요한 인터페이스만 선언해 갖도록(`IAllyPositionLayout fieldPositionLayout; IBattleFieldGeometry fieldGeometry;`) 바꾼다.

### 5.3 `IUnitTacticsProfileResolver` 신규 — 프로필 해석 전담 (점검 이력 반영, SRP①/확장성② 수정안)

"직업→역할군→프로필" 해석 로직을 `LiveBattleSimulationRule.BuildAllies`에 인라인하지 않고 전담 인터페이스로 뺀다 — 이 클래스가 조립 책임(6개 협력자+역할군 해석)을 계속 떠안는 것을 막고, 향후 개체별 방향성이 이 해석 체인에 끼어들 정확한 확장 지점을 마련한다(§6-1에서 이미 "개체별이 상단 지침+역할군별 방향성을 override할 예정"이라고 확정해둔 것과 직결).

```
public interface IUnitTacticsProfileResolver
{
    UnitTacticsProfile Resolve(MercenaryClass mercenaryClass, Vector2 homePosition);
}
```

내부에서 `ITacticsRepository`(파티 설정+역할군 override) + `MercenaryRoleGroupMapAsset` + `RoleGroupTacticsCatalogAsset`를 조회해 조립한다. `LiveBattleSimulationRule.BuildAllies`는 기존에 `statProvider.GetStats(mercenaryClass)`를 호출하던 자리에 `tacticsProfileResolver.Resolve(mercenaryClass, position)`을 나란히 호출만 한다 — 해석 로직 자체는 몰라도 된다.

### 5.4 `IDamageable`에 현재 HP(비율) 노출

`§3.3-1 HighestHpRatio`와 `LowestHp` 선택자 둘 다 "현재 HP"가 필요한데 지금 `IDamageable`엔 `MaxHp`만 있다.

```
float CurrentHp { get; }  // 또는 HpRatio => CurrentHp / MaxHp 를 바로 노출해도 됨
```

`BattleCharacterUnit`/`BattleProtectedUnit` 둘 다 이미 내부에 `currentHp` 필드를 갖고 있어 프로퍼티만 추가하면 된다 — 새로 계산할 값은 없다.

### 5.5 `IDamageable`에 공격력(Attack) 노출 — `HighestAttack` 선택자용

```
float Attack { get; }
```

`BattleUnitStats.Attack`은 이미 있지만 `IDamageable`엔 노출돼 있지 않다(지금은 `BattleCharacterUnit` 내부에서만 씀). `Defense`/`MaxHp`와 같은 자리에 같은 방식으로 추가.

### 5.6 `TacticsTuning` 신규 — 테스트 수치 중앙화 (점검 이력 반영, 확장성① 수정안)

`MoraleTuning`/`ProtectedUnitTuning`과 같은 자리에 이번 축들의 테스트값을 전부 모은다 — 각 전략 구현체는 자기 안에 매직 넘버를 두지 않고 이 클래스만 참조한다.

```
public static class TacticsTuning
{
    public const float FixedRadiusMeters = 4f;
    public const float StandardRadiusMarginMeters = 5f;
    public const float OffensiveJudgmentTimeoutSeconds = 5f;
    public const float NoPursuitTimeoutSeconds = 3f;
    public const float FallBackOnHeavyDamageHpRatioThreshold = 0.5f;   // 예시값 - 실제 밸런싱은 후속
    public const float KitingProximityRangeRatio = 0.4f;               // 예시값
    public const float RetreatOnHitDistanceMeters = 2f;                // 예시값
}
```

수치 자체는 여전히 테스트값(밸런싱 대상)이지만, 최소한 "어디를 고치면 되는지"가 한 곳으로 정리된다.

### 5.7 `RoleGroupTacticsCatalogAsset` 빈 후보 방어 (점검 이력 반영, 확장성④ 수정안)

`MercenaryRoleGroupMapAsset`에 매핑된 역할군인데 `RoleGroupTacticsCatalogAsset`에 해당 역할군 항목(또는 그 안의 축별 후보 목록)이 비어 있으면, override 초기값 규칙("후보 첫 항목")이 성립하지 않는다. 에디터 검증(예: 두 에셋을 함께 참조하는 간단한 `[MenuItem]` 검사 도구, 또는 `OnValidate`)으로 "매핑은 있는데 후보가 없는 역할군"을 `Debug.LogWarning`으로 조기에 드러낸다 — 프로젝트가 이미 쓰는 "요소를 못 찾으면 경고로 조기에 드러낸다" 컨벤션과 같은 방향.

## 6. 설계 중 발견된 해석 (확인/해소 이력)

### 6-1. "파티 따르기" 명칭 및 override 관계 (해소, 2026-08-27)

**확정**: "파티 따르기"라는 명칭을 **"상단 지침"**으로 바꾼다. 상단 지침(파티 축)과 역할군별 방향성(역할군 축)은 애초에 겹치는 축이 없어 서로 override하는 관계가 아니다 — 개체별 방향성이 구현되면 그때 비로소 이 두 계층(상단 지침 + 역할군별 방향성)을 override하는 관계가 생긴다(향후 확장, 이번 범위 밖).

**토글 처리(확정)**: 향후 확장성(개체별 방향성이 이 자리에 실제 override 관계를 붙일 예정)을 고려해, **UI 형태(토글)는 남겨두되 이번 단계에서는 기능을 구현하지 않는다** — `IsOverridden`은 `RoleGroupTacticsOverride`에 필드는 유지하지만 시뮬레이션(`UnitTacticsProfile` 해석)이 값을 참조하지 않는다(항상 override 필드의 실제 값 = 카탈로그 첫 항목을 그대로 씀). 토글은 화면에 존재하되 이번 구현에서는 비활성(disabled) 상태로 렌더링 — 클릭해도 동작이 바뀌지 않는 자리 확보용. 11번 UI 문서 §5 레이아웃은 그대로 유지(수정 불필요).

### 6-2. "자율 행동"이 활동 반경을 무효화하는 범위 (해소, 2026-08-27)

**확정**: 추적 축(자율행동 포함)은 §2.1 적 인식에 전혀 영향을 주지 않는다. "자율 행동"은 §3.4(`IPursuitPolicy.ShouldDisengage`) 하나만 항상 false로 고정할 뿐, `IActivityRadiusZone`은 파티가 고른 `ActivityRadiusPreset` 그대로 정상 동작한다(§3.4에 반영 완료).

### 6-3. "미피격 적" 타겟 선택자의 데이터 요구사항 (해소, 2026-08-27)

**확정**: 신규 공유 상태(`IEngagementLedger`)는 도입하지 않는다. "미피격 적"은 **HP 비율이 가장 높은 적**(`HighestHpRatio`)으로 근사해 구현한다(§3.3-1) — `LowestHp`가 이미 필요로 하는 "현재 HP 노출"(§5.4) 하나로 두 선택자 모두 해결된다.

## 7. 리팩토링 점검 이력 (2026-08-27, `Docs/Refactor/리팩토링_점검_컨벤션.md` 절차 적용)

컴포넌트 구조 초안(§1~§6) 작성 직후, 같은 컨벤션(최적화 → SOLID → 확장성/하드코딩 순, 문제 식별 후 종합 수정)으로 이 설계 자체를 점검했다. 발견 문제와 반영된 수정은 다음과 같다.

**최적화**

**SOLID**

**확장성/하드코딩**
- 테스트 수치가 각 전략 구현체에 흩어질 위험 → `TacticsTuning` 클래스 신설(§5.6).

- 빈 카탈로그 방어 로직 부재 → 에디터 검증 추가(§5.7).
- (허용) no-op 구현 중복은 과설계 방지 차원에서 이번 라운드는 그대로 둠.

통합 점검: 위 수정안 전체가 세 기준과 서로 충돌하지 않음을 확인 — 이후 §1~§6 본문에 전부 반영 완료.

- **SRP**: `BattleCharacterUnit`의 책임을 6개 협력자로 분산(06번 §10 백로그 해소) + `IUnitTacticsProfileResolver`로 프로필 해석을 `LiveBattleSimulationRule`에서 분리 + `IBattleFieldLayout`을 `IAllyPositionLayout`/`IBattleFieldGeometry`로 분리(같은 06번 §10 backlog의 다른 축까지 해소).

- **ISP**: `IActivityRadiusZone`을 별도로 뽑아 `IEnemyRecognitionTracker`/`IPursuitPolicy`가 "판정 방법"이 아니라 "판정 결과"만 참조하게 했다 — 반경 계산 방식이 바뀌어도 이 두 인터페이스는 무변경.

## 10. 제작 완료 후 코드 리뷰에서 발견된 보류 항목 (2026-08-28)

§1~§9 제작 완료 후 `develop..battle` 범위 코드 리뷰(effort: high)에서 나온 중복 코드 지적 중, 동작 버그가 아니라 판단이 필요한 항목 — **지금은 보류, 기록만 해둔다**(사용자 확정, 2026-08-28).

### 10-1. "타겟에서 멀어지는 방향" 공식 4곳 중복

`MaintainRangePositioningStrategy`(§3.5, 사거리 유지형) / `KitingSelfPreservationModifier`(§3.6, 카이팅) / `FallBackOnHeavyDamageSelfPreservationModifier`(§3.6, 중상 시 1회 후퇴) / `RetreatOnHitSelfPreservationModifier`(§3.6, 피격 시 후퇴) 4개 구현체가 전부 다음 3줄을 각자 다시 작성했다:

```csharp
var toTarget = target.Position - selfPosition;
var direction = <가드> ? -toTarget.normalized(또는 /distance) : Vector2.zero;
destination = selfPosition + direction * range;
```

- 가드 방식이 이미 둘로 갈라져 있다 — `MaintainRange`/`Kiting`은 `distance > 0.0001f`(magnitude), `FallBackOnHeavyDamage`/`RetreatOnHit`는 `toTarget.sqrMagnitude > 0.0001f`. 결과는 사실상 같지만 복붙 흔적.
- 엡실런(`0.0001f`)도 4곳에 직접 하드코딩돼 있다 — `TacticsTuning`(§5.6)의 "매직 넘버를 직접 갖지 않는다" 규칙 밖에 있음.
- 이 자리에서 실제로 버그가 한 번 났다(`RetreatOnHitSelfPreservationModifier`의 origin 리셋 오류, 2026-08-28 코드 리뷰에서 발견·수정) — 4곳이 따로 있어 나머지 3곳은 같은 종류 결함이 있어도 서로 눈에 안 띈다.
- **보류 이유**: 지금 당장 기능 결함은 없음(가드 차이는 결과 무해). §4.4(밸런싱, 이 수치들 전부 테스트값)에서 후퇴 방향 공식에 실제 손을 대는 시점에 재검토하는 편이 낫다는 판단.
- 추출한다면: 정적 헬퍼(`TacticsMovementMath.AwayFrom(selfPosition, targetPosition, range)`) 하나로 4개 호출부 교체, 엡실런도 `TacticsTuning`으로 이동 — 작고 리스크 낮은 변경으로 예상.

### 10-2. 타겟선택 4종의 "IsAlive 스킵 + 최고점수 추적" 루프 골격 중복

`HighestAttackTargetSelector`/`HighestHpRatioTargetSelector`/`LowestHpTargetSelector`/`DeepestPenetrationTargetSelector`(§3.3) — 지표(`Attack`/`HpRatio`/`Hp`/침투 깊이)와 비교 방향만 다르고 순회 골격은 동일. 진짜 중요한 공통 규칙은 `IsAlive` 스킵 하나뿐인데 4곳에 복붙돼 있어, 새 셀렉터를 또 복붙으로 추가하면 이 가드를 빼먹기 쉽다.
- **보류 이유**: 추출하려면 제네릭/델리게이트 기반 공통 헬퍼가 필요해 10-1보다 추상화 단계가 하나 더 들어간다 — "지금 규모에선 섣부른 추상화보다 반복이 낫다"는 판단으로 보류.

### 10-3. `TacticsPanel`의 씬 조회 보일러플레이트가 `FormationPanel`/`TripPanel`과 3중 중복

"씬 이름 조회 → 유효성 확인 → 루트 오브젝트 순회하며 `SceneUIRoot` 탐색 → 경고" 블록이 세 패널에 각각 인라인돼 있다.

## 11. 전장 경계 하드 캡 설계 (확정, 2026-08-28 — 제작 미착수)

기획 §2.2-1의 3단 이동 구간 재정의를 반영한 설계. §3.1~§3.4(활동 반경/추적)는 무변경 — ②·③ 구간은 기존 `IActivityRadiusZone`/`IPursuitPolicy` 그대로 담당한다. 새로 필요한 것은 ①(전장 밖 하드 캡) 하나뿐이다.

**핵심 판단**: 새 클래스를 만들지 않는다. `StandardActivityRadiusZone`이 이미 "원점 기준 반경으로 clamp"라는 동일한 수학(§3.5 참고)을 갖고 있으므로, `new StandardActivityRadiusZone(fieldRadius)`를 그대로 "전장 경계 zone"으로 재사용한다 — 기존 것을 확장 재사용 우선(CLAUDE.md 인터페이스 설계 컨벤션).

**데이터 흐름 확장**:
```
LiveBattleSimulationRule.BuildAllies
  standardActivityRadius = FieldGeometry.ComputeStandardActivityRadius(columnCount)  // 기존
  fieldRadius            = FieldGeometry.ComputeFieldRadius(columnCount)             // 신규, 같은 자리에서 계산
        ↓
UnitTacticsBehaviorsFactory.Build(profile, standardActivityRadius, fieldRadius, spatialQuery)  // 인자 추가
        ↓
UnitTacticsBehaviors.FieldBoundaryZone = new StandardActivityRadiusZone(fieldRadius)  // 신규 필드
```

**적용 지점**: `BattleCharacterUnit.MoveTowardTacticalDestination`에서 `PursuitPolicy.ClampDestination(...)` 결과에 이어 무조건 한 번 더 clamp한다:
```csharp
var clampedDestination = tacticsBehaviors.PursuitPolicy.ClampDestination(desiredDestination, tacticsBehaviors.RadiusZone);
clampedDestination = tacticsBehaviors.FieldBoundaryZone.ClampToZone(clampedDestination);  // 신규 - 프리셋 무관 하드 캡
MoveToward(clampedDestination, deltaTime);
```
추적 프리셋 5종 전부(위치 사수뿐 아니라 자율행동/추살/공세판단/추적금지 포함) 이 clamp를 동일하게 통과한다 — §2.2-1 ①이 "추적 프리셋과 무관하게 항상 적용"으로 확정했기 때문에, 프리셋별 분기 없이 `BattleCharacterUnit` 한 곳에서 무조건 적용하는 게 맞다(기존 `IPursuitPolicy.ClampDestination`을 건드리지 않고 그 바깥에 얹는 이유).

**영향받지 않는 경로**: `TickFlee`(사기 도주)는 완전히 별도 코드 경로라 이 clamp를 거치지 않는다 — §2.2-1이 명시한 유일한 예외와 자동으로 일치. `TickReturning`(활동 반경 밖에서 배치 위치로 복귀)도 목적지가 항상 `HomePosition`(활동 반경 안)이라 전장 경계에 닿을 일이 없어 별도 처리 불필요.

**프리셋 명칭 변경(반영 완료, 2026-08-28)**: `TacticsPanel.RadiusOptions` 표시 라벨(대열 유지/상행 전체/전장 전체)뿐 아니라 `ActivityRadiusPreset` enum 값 자체도 `FormationHold`/`TripWide`/`FieldWide`로 함께 바꿨다 — 코드베이스에 이미 있는 용어(대형→`Formation`, 상행→`Trip`, 전장→`Field`)를 그대로 따랐다. Unity는 이 enum을 정수값으로 직렬화해 기존 저장된 값(`InMemoryTacticsRepository` 등 런타임 상태)에는 영향 없음.

**제작 완료(2026-08-28)**: `LiveBattleSimulationRule.BuildSimulation`에서 `fieldRadius`를 `standardActivityRadius`와 같은 자리에 계산해 `BuildAllies`→`UnitTacticsBehaviorsFactory.Build`로 전달, `UnitTacticsBehaviors.FieldBoundaryZone`(=`new StandardActivityRadiusZone(fieldRadius)`)으로 보관, `BattleCharacterUnit.MoveTowardTacticalDestination`이 `PursuitPolicy.ClampDestination` 다음에 무조건 `FieldBoundaryZone.ClampToZone(...)`을 적용하도록 배선 완료. 실전투 검증(전장 경계 밖으로 유닛이 안 나가는지) 대기 중.

## 12. 방진 형성(Blocking) 그룹 재편성 설계 (확정, 2026-08-28 — 제작 미착수)

기획 §3.2-1의 재설계를 반영. 기존 `BlockingPositioningStrategy`(유닛 1기당 독립 계산, 다른 아군 상태를 모름)를 대체해, 전투 1회당 하나만 존재하는 새 조율자가 `LocalPositioning.Blocking`을 고른 전열 유닛 전체를 그룹으로 묶어 매 틱 재편성한다. `Charge`/`MaintainRange`/`Stationary` 등 나머지 전략은 무변경.

### 12.1 인터페이스 확장 (제작 완료, 2026-08-28)

방진선 계산에 필요한 데이터가 기존 `IDamageable`/`IBattleCombatant`에 없어 먼저 확장했다:

- `IDamageable.Range` — "인식한 적의 최대 사거리"를 구하려면 필요. `Attack`(§5.5)과 같은 이유로 `IDamageable`에 둠(인식 목록이 `IReadOnlyList<IDamageable>`이라 캐스팅 없이 읽어야 함). `BattleCharacterUnit.Range => stats.Range`, `BattleProtectedUnit.Range => 0f`(N/A, `Attack`과 같은 패턴).
- `IBattleCombatant.CurrentTarget` — "이 적이 지금 보호대상을 타겟팅 중인지" 판정에 필요. `IsFleeing`과 같은 자리(오직 Tick/공격 능력이 있는 대상만 타겟 개념이 있어 `IDamageable`이 아니라 여기 둠). `BattleCharacterUnit.CurrentTarget => target`(private 필드 노출).

### 12.2 FrontlineFormationCoordinator (신규 클래스, 전투 1회당 1개)

`BattleSimulationLoop`이 필드로 소유한다(`PartyMorale`과 같은 자리 — 전투마다 새로 생성) — 유닛 개별이 아니라 `allies`/`enemies`/`protectedUnits` 전부에 접근 가능한 위치여야 하기 때문(§0에서 확인된 구조적 제약: `BattleCharacterUnit`은 `protectedUnits` 목록에 접근할 방법이 없다).

```
BattleSimulationLoop.Tick(deltaTime)
  1. coordinator.Update(deltaTime, allies, enemies, protectedUnits)   // 신규 - 각 유닛 Tick 전에 실행
  2. 기존 allies/enemies Tick 루프
```

`coordinator`는 `linePoint`/`lineDir`/소속 유닛 리스트(합류 순서 유지)를 담은 "활성 라인" 목록을 틱 간 상태로 들고 있는다. `EnemyRecognitionTrackerBase.recognizedBuffer`(§7 점검 이력)와 같은 이유로, 매 틱 새 `List`/`Dictionary`를 할당하지 않고 재사용 버퍼를 미리 들고 있는다(§12.8 최적화 참고).

### 12.3 보호대상 후보군과 anchorCenter

**후보군**: `IDamageable` 중 `BattleProtectedUnit`(마차/시설) + `RoleGroup.RangedDealer` 아군 유닛 + `RoleGroup.Supporter` 아군 유닛(현재 대응 직업 없어 공집합, 향후 자동 포함).

**클러스터별 anchorCenter**: 그 클러스터에 속한 적들이 (a) `CurrentTarget`이 후보군의 원소이거나(현재 타겟팅 중), (b) 타겟팅 여부와 무관하게 후보군 중 가장 가까운 것 — 이 조건을 만족하는 후보들의 위치 평균. 조건을 만족하는 후보가 하나도 없으면(후보군 전체가 비어있는 극단적 경우) 원점(상행 대열 중심)으로 대체.

### 12.4 매 틱 갱신 순서

```
Update(deltaTime, allies, enemies, protectedUnits):

  1. 기존 라인 재조정
     각 활성 라인에 대해:
       - 사망(!IsAlive) 또는 도주(IsFleeing) 중인 소속 유닛을 즉시 제거(§12.6)
       - recognizedUnion = 남은 소속 유닛들이 인식한 적의 합집합(죽은 적 제외 - 자연히 걸러짐, §5.1 EnemyRecognitionTrackerBase 참고)
       - if recognizedUnion 비어있음: 라인 해체 → 소속 유닛 전원 개별 로직(Returning)으로 복귀
       - else:
           anchorCenter/enemyCenter/axisDir/range/canonicalPoint 재계산(§12.3, §12.5)
           파티 Pursuit 설정 기준 이탈 조건 판정(라인 위치·상행 전체 반경 기준):
             트리거됨 → linePoint = canonicalPoint (즉시 재배치, "당겨오기")
             안 트리거됨 →
               소속 유닛 중 교전 가능 상태(타겟 존재 && 거리<=사거리)가 하나라도 있으면: 정지(linePoint 그대로)
               소속 수 > enemyCount(recognizedUnion 크기)면: linePoint를 enemyCenter 쪽으로 서서히 이동
               그 외: 정지

  2. 미배정 풀 처리 (신규 라인 그리기, 반복)
     pool = 아직 라인에 없는 Blocking 전열 전체(인식 여부 무관, 전부 포함)
     loop:
       recognizingSubset = pool 중 인식한 적이 있는 유닛만
       if recognizingSubset 비어있음: break (남은 pool 전원 "대기")
       (거리 임계값 기반 클러스터링 - §12.7 - 으로 recognizingSubset의 인식한 적들을 군집으로 나눔)
       군집 하나를 골라 anchorCenter/enemyCenter/axisDir/range/canonicalPoint 계산, linePoint=canonicalPoint
       joined = pool 중 슬롯이 상행 전체 반경(standardActivityRadius) 안인 유닛(가장 가까운 빈 슬롯 배정, §12.6)
       if joined 비어있음: break (남은 pool 전원 "대기")
       새 라인 등록(joined)
       pool -= joined
       (군집이 여러 개면 나머지 군집에 대해 loop 계속 - 다른 군집도 각자 라인 후보가 됨)

  3. 라인 간 교차 처리(§12.9)

  4. 각 라인 소속 유닛에게 슬롯을 배정(신규 합류/재배정 발생 시에만, §12.6) → BlockingPositioningStrategy가 그 슬롯을 반환하도록 값 설정
```

### 12.5 라인 위치·방향 계산 (canonicalPoint)

```
axisDir = normalize(enemyCenter - anchorCenter)   // 0벡터면(적이 anchorCenter와 정확히 겹침) axisDir=Vector2.zero로 두고 canonicalPoint=anchorCenter
range = recognizedUnion 중 최댓값(Range)          // 확정 - 최대 사거리 기준(가장 위협적인 적 기준)
canonicalPoint = anchorCenter + axisDir * range
canonicalPoint = StandardActivityRadiusZone(standardActivityRadius).ClampToZone(canonicalPoint)   // 방진선은 최소한 상행 전체 반경 안에 있어야 함(§12 보완 - 사거리가 커서 반경 밖으로 계산되는 경우 방지)
lineDir = axisDir에 수직인 방향(90도 회전)
```

~~`정지` 상태에서는 이 블록 전체를 다시 계산하지 않고(재계산은 "이탈 트리거 여부"/"전진 여부" 판단 재료로만 쓰고), `linePoint`엔 반영하지 않는다 — 그래서 라인이 완전히 고정된다.~~ **(폐기, §12.10 갱신 참고)** 실전투에서 "교전이 시작되면 라인이 전투 내내 완전히 고정된다"는 문제가 확인돼(2026-08-29), 각도(`lineDir`)/위치(`linePoint`)와 "정지/전진/당겨오기" 상태를 분리했다 — 자세한 내용은 §12.10 갱신 참고. 캐릭터 이동 자체는 `MoveToward`가 이미 속도 제한을 걸므로, 매 틱 재계산해도 순간이동처럼 보이지 않는다.

### 12.6 슬롯 배정과 재배치 (라인이 직접 관리)

- 슬롯 위치는 `linePoint`를 중심으로 `lineDir` 방향 1m 간격(`±1, ±2, ...`)으로 정의되는 좌표 집합 — 라인의 기하 형태 자체는 항상 존재.
- **슬롯 소속(어떤 유닛이 어느 슬롯인지)은 이벤트성으로만 결정**한다 — 매 틱 재계산하지 않는다:
  - 유닛이 새로 합류할 때: 그 순간 **가장 가까운 빈 슬롯**에 배정, 이후 그대로 유지.
  - 사망/도주로 소속 유닛이 빠질 때: 그 슬롯만 비우고, 즉시 그 자리에 배정 가능한 다른 소속 유닛(가장 가까운 인접 유닛)을 당겨 채운다(1회성 이벤트).
  - 교차 처리(§12.9)로 슬롯이 제거/생성될 때만 추가 재배정.
- 이렇게 "합류·이탈 이벤트가 있을 때만" 재계산해야, 매 틱 "가장 가까운 슬롯"을 다시 따지다가 좌우로 진동하는 문제(코드 리뷰 §10-2류 문제)를 피할 수 있다.

### 12.7 클러스터링 (거리 임계값 기반, Union-Find)

인식한 적들을 좌표 기준으로 군집화한다 — 신규 상수 `TacticsTuning.ClusterMergeDistanceMeters`(테스트값) 이내에 있는 적끼리 전이적으로 같은 군집으로 묶는다(A-B 가깝고 B-C 가까우면 A/B/C 한 군집). 적 수가 적어(현재 규모 최대 5) O(n²) 쌍 비교로 충분, 별도 라이브러리 불필요. 이 방식은 §12.4의 "미배정 풀 처리"에서 새 라인을 그릴 때만 쓰인다 — 기존 라인의 `recognizedUnion`은 이미 배정된 소속 유닛 기준으로 자연히 갈린다.

군집별로 라인을 하나씩 배정하는 이 방식이 "적이 여러 라인에 중복 카운트되는" 문제(코드 리뷰 §B-8)를 근본적으로 해소한다 — 적 하나는 정확히 하나의 군집에만 속하므로.

### 12.8 최적화

지금 규모(아군 최대 16, 적 최대 5)에서 CPU 비용 자체는 무시할 만하다. 대신 매 틱 클러스터링/라인 갱신용 `List`/`Dictionary`를 새로 할당하지 않고, `EnemyRecognitionTrackerBase.recognizedBuffer`와 같은 패턴으로 `FrontlineFormationCoordinator`가 재사용 버퍼를 미리 들고 있는다 — GC 압박 감소, 기존 프로젝트 컨벤션과 일치.

### 12.9 라인 간 교차 처리 (필렛/곡선 안 폐기, 최종 확정)

**폐기된 대안**: 두 라인이 교차할 때 완만한 곡선(필렛)으로 잇는 안을 검토했으나, 필렛은 정의상 교차점 P를 향해 모서리를 깎는 방식이라 **P가 상대적 배치에 따라 보호대상 쪽에 생길 수 있고, 그러면 방진선이 보호대상 쪽으로 볼록해지는 결함**이 있음을 좌표 계산으로 확인해 폐기했다(대칭 배치에선 P가 적 쪽에 생기지만, 두 적 군집이 서로 엇갈려 접근하는 배치에선 P가 보호대상 쪽에 생기는 반례를 확인).

**최종 확정 3규칙**:
1. **선 긋기 중단**: 각 라인은 `linePoint`에서 양방향으로 슬롯을 늘어놓다가, 다른 라인과 만나는 교차점에 도달하면 그 방향으로는 더 이상 슬롯을 놓지 않는다(교차점 근방 1m 이내 기존 슬롯도 제거). 새로운 곡률을 전혀 추가하지 않으므로 §필렛의 방향 결함이 구조적으로 발생하지 않는다.
2. **교차점 슬롯의 소속**: 교차점에 놓이는 슬롯 하나는 **소속 인원이 더 많은 라인**이 가져간다. 동률이면 **상대하는 적 군집(recognizedUnion) 수가 더 적은 쪽**, 그것도 같으면 랜덤.
3. **손실분 보충**: 잘려나간(제거된) 슬롯 수만큼, 각 라인은 자기 쪽(교차와 무관한 반대편 등)에 새 슬롯을 추가로 만들어 전체 슬롯 수를 유지한다 — 밀려난 유닛이 오갈 데 없어지지 않도록.

### 12.10 정지/전진/당겨오기 요약 (갱신, 사용자 확정 2026-08-29)

**폐기 이력**: 원래 설계는 "정지" 상태에서 `linePoint`/`lineDir`를 완전히 고정했다. 실전투에서 "방진선이 최초 확정된 이후 전투가 진행돼도 이동하지 않고 최초 발생 지점에 고정된다"는 문제가 확인됐다 — 원인은 근접 교전+스티키 타겟팅 특성상 한 번 교전이 시작되면 `hasEngagedMember`(교전 가능 상태)가 전투 내내 거의 계속 true로 유지되어, "정지"만 계속 타고 "전진"/"당겨오기"로 넘어갈 조건(`!hasEngagedMember`, `isOutsideRadius`)이 사실상 열리지 않기 때문이었다.

**재설계 핵심**: "각도/위치"와 "당기기·전진·정지 상태"를 분리한다.
- **각도(`lineDir`)·위치(`linePoint`)**: 상태와 **무관하게 매 틱** `anchorCenter`(보호대상 중심, 실시간)와 `axisDir`(실시간)로 다시 조립한다 — `linePoint = ClampToZone(anchorCenter + axisDir * distanceFromAnchor)`. `anchorCenter`는 마차/시설뿐 아니라 원거리딜러/서포터 아군도 포함하므로(§12.3), 이들이 포위/산개 등으로 전투 중 움직이면 라인도 자동으로 따라간다. 적 군집 중심이 움직이면 `axisDir`(따라서 `lineDir`)도 즉시 그쪽을 향해 돈다.
- **`distanceFromAnchor`(신규 스칼라, `FrontlineFormationLine`에 저장)**: "그 축 위에서 앵커로부터 얼마나 나가 있는지"만 담당 — 당기기/전진/정지는 이제 이 값 하나만 조절하는, 순수하게 "보호대상↔적 군집 중심 거리 비율" 문제로 좁혀졌다.

| 상태 | distanceFromAnchor 갱신 | 트리거 조건 |
|---|---|---|
| 정지 | 안 함(이전 값 유지) — **단, linePoint/lineDir는 위 규칙대로 매 틱 갱신됨** | 소속 유닛 중 교전 가능 상태가 있음, 또는 소속 수 <= enemyCount |
| 전진 | `Vector2.Distance(anchorCenter, enemyCenter)` 쪽으로 서서히(`LineAdvanceSpeedMetersPerSecond`) | 아무도 교전 중이 아니고 소속 수 > enemyCount |
| 당겨오기(복귀) | `geometry.Range`로 즉시 스냅 | 파티 Pursuit 설정 기준 이탈 트리거, recognizedUnion 남아있음(비어있으면 해체) |

세 상태 모두 `distanceFromAnchor`만 바뀔 뿐, 캐릭터 자신의 이동은 항상 `MoveToward`의 속도 제한을 받는다 — "당겨오기"가 즉시 스냅이어도 캐릭터가 순간이동하지 않으므로 별도의 "서서히"가 필요 없다(기존과 동일).

**디버깅**: `FrontlineFormationLine.AnchorCandidates`(신규) — 이 라인의 앵커 계산에 실제로 기여한 보호대상 후보 목록을 코디네이터가 매 틱 채워둔다. `BattleFrontlineGizmoView`가 각 후보→`linePoint`를 초록 선으로 이어 "이 라인이 누구를 지키는지" Scene 뷰에서 바로 보여준다.

### 12.11 대기 상태

`§12.4` 2단계 루프에서 라인에 합류하지 못한 유닛은 "대기" — 이번 틱엔 아무 이동도 하지 않는다. 별도 트리거 없이, 매 틱 2단계 루프가 다시 돌면서 합류 가능한 라인이 생기는 순간 자동으로 편입된다(신규 인식한 적 발생 시 라인이 추가로 그어지는 것도 같은 메커니즘 — 별도 장치 불필요).

2. `FrontlineFormationCoordinator` 뼈대(활성 라인 상태 보관, 재사용 버퍼) + §12.7 클러스터링.

## 13. 원거리딜러 포위/산개 재설계 (확정, 2026-08-28 — 제작 미착수)

기획 §3.2-2 반영. 사거리 유지형(`MaintainRangePositioningStrategy`)이 자기보호 카이팅과 트리거·로직이 동일해 폐기되고, `LocalPositioning` 축의 원거리딜러 후보가 **고정형(기존 유지) / 포위(신규) / 산개(신규)** 3종으로 바뀐다.

### 13.0 범위/전제

- `LocalPositioning` enum에서 `MaintainRange`를 제거하고 `Surround`(포위)·`Disperse`(산개)를 추가한다 — Unity가 enum을 정수로 직렬화하지만 런타임 상태(`InMemoryTacticsRepository`)만 영향받고 저장 파일은 없어 안전하다(§11 프리셋 명칭 변경 때와 같은 판단).
- `RoleGroupTacticsCatalogAsset` 데이터(원거리딜러 항목의 `PositioningOptions`)는 코드가 아니라 에디터 Inspector에서 수동으로 갱신해야 한다(§13.5) — 라벨은 애초에 ScriptableObject 데이터이지 코드에 없다.
- Charge/Blocking/Stationary는 무변경. Blocking과 마찬가지로 포위도 "코디네이터 + 얇은 전략" 패턴을 그대로 재사용한다(§12와 동일한 구조 재사용 — 새 패턴을 만들지 않는다).

### 13.1 `IPositioningStrategy` 인터페이스 확장

```csharp
Vector2 ComputeMoveTarget(
    IBattleCombatant self, Vector2 selfPosition, IDamageable target, float range, Vector2 homePosition,
    IReadOnlyList<IBattleCombatant> sameSideUnits);
```

`sameSideUnits`는 산개 전용이다 — 동료 원거리딜러와의 거리를 계산하려면 "같은 진영 유닛 목록"이 필요한데, 지금 시그니처엔 없다. `BattleCharacterUnit.Tick(deltaTime, targets, sameSideUnits)`이 이미 갖고 있는 값을 그대로 흘려보내면 되므로(`TickEngageWithTactics`/`MoveTowardTacticalDestination` 매개변수에 관통 추가), 새 상태나 새 조회 경로가 필요 없다. 나머지 4개 구현체(Charge/Blocking/Stationary/Surround)는 이 값을 무시한다(OCP — self 매개변수를 추가했을 때와 같은 판단).

### 13.2 산개 — `DispersePositioningStrategy`

**핵심 개념**: "사거리를 확보하되(Charge와 동일한 접근/정지 판단), 동료 원거리딜러가 가까이 있으면 그만큼 밀려난 지점을 목적지로 삼는다." 새 반발 공식을 만들지 않고 `BattleCharacterUnit.ApplySeparation`이 이미 쓰는 `IUnitSpatialQuery.ComputeSeparationPush`를 그대로 재사용한다 — 검증된 로직 재사용이 새 공식 발명보다 우선이라는 기존 컨벤션(§10-1 점검 이력)과 같은 방향.

```
distance = |target.Position - selfPosition|
approachTarget = distance > range ? target.Position : selfPosition   // Charge와 동일

rangedAllies = sameSideUnits 중 RoleGroup == RangedDealer (재사용 버퍼로 필터링)
pushOut = spatialQuery.ComputeSeparationPush(self, selfPosition, TacticsTuning.DisperseRadiusMeters, rangedAllies)

destination = approachTarget + pushOut
```

- `TacticsTuning.DisperseRadiusMeters`(신규 상수, 테스트값) — `ApplySeparation.SeparationRadius`(1m, 단순 겹침 방지)보다 커야 실제로 "퍼지는" 효과가 보인다.
- 생성자 의존성은 `IUnitSpatialQuery` 하나뿐 — `PositioningStrategyFactory.Create`가 이미 `spatialQuery`를 받도록 확장해야 한다(현재는 `frontlineCoordinator`만 받음, `TargetSelectorFactory.Create(priority, spatialQuery)`와 같은 자리에 나란히 추가).
- 필터링 버퍼(`rangedAllies`)는 인스턴스별 재사용 리스트로 둔다(§12.8과 같은 이유 — 매 틱 새로 할당하지 않음).

### 13.3 포위 — 1차 설계(폐기, `CurrentTarget` 기준 개별 각도 배정)

**폐기 이력(2026-08-29)**: 원래 설계는 §12(방진 형성)의 "코디네이터 + 얇은 전략" 패턴을 그대로 가져오되, 그룹화 키를 유닛의 `CurrentTarget` 참조 그 자체로 단순화했다(거리 기반 군집화 불필요하다고 판단). 실전투 검증에서 3차례에 걸쳐 버그가 드러났다:
1. 궤도 좌표를 매 틱 무조건 반환해 이미 공격 가능해도 계속 쫓아가는 잔떨림 → "사거리 안이면 정지" 판단 추가로 1차 수정.
2. 배정 각도가 접근 방향 반대편이면 직선 이동이 적진을 관통 → 각도 배정을 접근 방향 우선으로 바꿨다가 균등 분산이 깨지는 회귀 발생, 원복 후 접근 중 반발(밀어내기)만으로 완화.
3. 그래도 "뭉쳐서 쏘기만 하고 안 둘러쌈" 증상이 재발 → 정지 판단 기준을 "사거리"에서 "배정 궤도 좌표 도달"로 교체해 3차 수정.

3차 수정 후에도 사용자가 근본 원인으로 지목한 것은 **그룹화 키가 `CurrentTarget` 단위라는 구조 자체**였다 — 원거리딜러들이 같은 군집 안에서 서로 다른 개체를 타겟팅하면 "군집 전체를 둘러싸는 하나의 원"이 아니라 "타겟별로 따로 도는 작은 원" 여러 개가 생겨, 애초에 "포위"라는 그림이 나올 수 없는 구조였다. 이 구조적 한계는 각도/정지 판단을 아무리 고쳐도 풀리지 않아 아래 13.3′로 전면 재설계했다.

### 13.3′ 포위 — 재설계 (확정, 2026-08-29 — 제작 미착수)

**핵심 아이디어**: 그룹화 키를 `(적 군집, 사거리 값)` 쌍으로 바꾼다. 포위망("Ring")은 "어떤 적 군집을 감싸는지" + "어떤 사거리의 유닛을 위한 것인지"로 식별되고, 같은 군집이라도 사거리가 다른 원거리딜러는 서로 다른(반지름이 다른) 링에 합류한다. 예: 사거리 3/5/8인 아군이 섞여 있고 적 군집이 2개면, 링은 최대 2×3=6개까지 생길 수 있다.

**군집화(사용자 1번 요구사항)**: `FrontlineFormationCoordinator.ClusterEnemies(IReadOnlyList<IDamageable>)`가 이미 `public`이라 그대로 재사용한다(§12.7과 같은 Union-Find, `TacticsTuning.ClusterMergeDistanceMeters` 공유). 다만 완전히 같은 클러스터 *인스턴스*를 Frontline과 공유하지는 않는다 — Frontline은 "Blocking 유닛들이 인식한 적"의 합집합을, Surround는 "Surround 유닛들이 인식한 적"의 합집합을 각각 같은 알고리즘에 넣는 구조다(역할군마다 인식하는 적 목록 자체가 다를 수 있어서). "로직(알고리즘) 공유"로 해석해 진행 — 완전히 하나의 전역 클러스터 결과를 두 시스템이 공유해야 한다면 더 큰 리팩토링(클러스터링을 `BattleSimulationLoop.Tick`으로 끌어올려 한 번만 계산) 필요.

**군집 선택 기준(사용자 확정)**: 원거리딜러는 자기 `CurrentTarget`이 속한 군집의 링에 합류한다 — 기존 스티키 타겟팅과 자연스럽게 연결되고, 타겟 재선택 시(사망/도주 등) 군집도 함께 자연히 재선택된다.

**상태(`SurroundRing`, `FrontlineFormationLine`과 같은 자리)**:
- `ClusterCenter`(군집 소속 적들의 평균 위치), `ClusterBoundingRadius`(중심에서 가장 먼 소속 적까지 거리) — 매 틱 소속 군집으로부터 재계산.
- `DealerRange`(이 링이 대응하는 사거리 값 — 링 식별의 일부).
- `CurrentRadius`(실제 반지름, 초기값 `ClusterBoundingRadius + DealerRange`, 13.3′-4의 축소 대상, 하한 `ClusterBoundingRadius`).
- `Members`(합류 완료된 유닛 목록 — 이벤트성, 매 틱 재계산 안 함).

**사거리 변동 확장성(사용자 확정 — 이번 구현 범위엔 넣지 않되, 구조는 대비)**: `BattleUnitStats.Range`는 현재 `readonly struct` 필드로 전투 시작 시 고정되고, 전투 중 값을 바꾸는 버프/디버프 시스템이 코드베이스에 없다(확인됨) — 그래서 "Range 변경 이벤트"를 처리하는 코드는 만들지 않는다. 대신 링 그룹화를 **캐시하지 않고 매 틱 살아있는 Surround 유닛들의 실제 `self.Range`를 다시 스캔**해서 구성하도록 만든다 — 이러면 향후 Range가 가변이 되어도(버프/디버프 시스템 도입 시) 별도 이벤트 배선 없이 자동으로 반영된다. 이건 이번 세션의 판단 근거이자 제약이니 다음 세션에서 "왜 매 틱 다시 스캔하나"를 묻지 말고 이 문단을 참고할 것.

**합류 판정(사용자 확정 — 콜리전 대체 구현)**: 전투 시뮬레이션에는 Unity 물리/Collider가 없다(`BattleCharacterUnit`은 MonoBehaviour 아님, 확인됨). "콜리전 접촉"은 "링까지의 거리가 `TacticsTuning.SurroundJoinToleranceMeters` 이내"로 근사한다.

**접근 중(미합류) 이동 목적지 = 세 벡터의 합**:
1. **반지름 접근**: `ClusterCenter + CurrentRadius * normalize(selfPosition - ClusterCenter)` — 자기 현재 위치에서 군집 중심 쪽으로의 반지름 선을 따라 링을 향해 이동(명시적 각도 배정 없음 — 접근 방향이 그대로 최종 각도가 됨).
2. **아군 반발**: `IUnitSpatialQuery.ComputeSeparationPush(self, selfPosition, TacticsTuning.SurroundAllySpacingMeters(2m), sameSideRangedAllies)` — `DispersePositioningStrategy`와 동일한 재사용 패턴, 반경만 2m.
3. **빈 구간 약한 끌어당김(사용자 확정, 1차 설계 회귀 재발 방지 설계)**: 이 링에 이미 합류한 멤버들의 **실제 현재 각도**(`atan2(member.Position - ClusterCenter)`, 캐시 안 함 — 매 틱 실측)를 모아 가장 넓은 빈 구간을 찾고, 그 구간 중심 방향으로 접선(반지름에 수직) 방향 벡터를 `TacticsTuning.SurroundGapPullWeight`(약한 가중치, 0에 가까운 값) 만큼 더한다. **1차 설계의 회귀와 다른 점**: 그때는 "가장 넓은 간격의 중간각"을 유닛당 한 번 계산해 영구 각도로 고정했다(→ 첫 멤버 직후엔 빈 구간이 원 전체라 사실상 무의미했고, 그 결과가 그대로 굳어버림). 이번엔 (a) 하드 배정이 아니라 약한 방향 보정이라 실제 접근 경로를 완전히 결정하지 않고, (b) 매 틱 "합류 완료된 멤버들의 실측 각도"로 다시 계산하므로 상황이 바뀌면 보정 방향도 같이 바뀐다 — 한 번의 잘못된 계산이 영구 고정될 수 없는 구조.

**합류 판정 후(사용자 확정)**: `distanceToRing <= SurroundJoinToleranceMeters`가 되는 순간 `Members`에 추가하고, 그 순간부터 이동 목적지 계산을 하지 않는다(이벤트성 고정, §12.6과 같은 철학). 재갱신 트리거는 오직:
- `ISelfPreservationModifier`가 오버라이드할 때(기존 우선순위 그대로 유지),
- 소속 군집의 적이 죽어 군집 구성이 바뀔 때(→ `ClusterCenter`/`ClusterBoundingRadius` 재계산, 필요시 링 해체),
- 13.3′-4의 반지름 축소를 자신이 추적해야 할 때(공격 불가 상태).

**13.3′-4 반지름 축소(사용자 확정)**: 이 링의 `Members` 중 하나라도 "공격 불가"(`CurrentTarget` 없음, 또는 있어도 실제 거리가 `DealerRange` 밖)면, `CurrentRadius`를 하한(`ClusterBoundingRadius`)까지 서서히 줄인다(`LineAdvanceSpeedMetersPerSecond`류의 신규 상수, `TacticsTuning.SurroundRingShrinkSpeedMetersPerSecond`). 공격 불가 상태가 없으면 `CurrentRadius`를 다시 이상적 반지름(`ClusterBoundingRadius + DealerRange`)까지 서서히 되돌린다(양방향 서서히 - 순간 스냅 없음). **줄어드는 동안 이미 공격 가능한 `Members`는 움직이지 않는다**(합류 후 이벤트성 고정 원칙 그대로 - 이들에게 `CurrentRadius`는 더 이상 의미가 없다). **공격 불가 `Members`만** 매 틱 `ClusterCenter + CurrentRadius * normalize(selfPosition - ClusterCenter)`로 갱신받아 반지름 방향으로 좁혀 들어간다(자기 각도는 유지, 반지름만 축소 추적).

**활동 반경(사용자 확정, Blocking과 동일 패턴)**: 접근 목적지(또는 합류 시점의 위치)가 자기 `RadiusZone` 밖이면 합류하지 않고 대기(제자리) — 다음 틱 조건이 바뀌면 자동 재평가.

**미정(다음 세션 확인 또는 실전투로 확정)**:
- `SurroundJoinToleranceMeters`/`SurroundGapPullWeight`/`SurroundRingShrinkSpeedMetersPerSecond`/`SurroundAllySpacingMeters` 구체 수치 — 전부 신규 테스트값, 플레이테스트 후 조정 대상.
- 사거리 값을 "다르다"고 판단할 부동소수점 허용오차(정확히 같은 `float`가 아니면 별도 링이 되는데, 스탯 자체가 고정값이라 실전 영향은 적을 것으로 예상 — 문제 되면 작은 epsilon 그룹화 추가).
- 군집이 완전히 전멸(모든 소속 적 사망)했을 때 링 처리는 Frontline의 "해체"와 동일하게: 링 제거, 소속 유닛은 다음 틱 미배정 풀에서 재평가.
- 서로 다른 군집의 링이 물리적으로 겹칠 수 있는 문제는 1차 설계와 마찬가지로 이번에도 해결 대상 밖(`ApplySeparation`이 최소 완충).

### 13.4 카탈로그 자산 갱신 (제작 시 필수, 코드로 자동화하지 않음)

`RoleGroupTacticsCatalogAsset`의 `RangedDealer` 항목 `PositioningOptions`에서 "사거리 유지형" 항목을 지우고 "포위"/"산개" 항목(한국어 라벨 포함)을 에디터 Inspector에서 새로 추가해야 한다. 라벨은 ScriptableObject 데이터이지 코드가 아니라서(§2.1 컨벤션) 코드 변경만으로는 반영되지 않는다 — 잊으면 `InMemoryTacticsRepository`의 override 초기값(카탈로그 첫 항목) 계산이 빈 목록을 만나 `TacticsCatalogValidator` 경고가 뜨거나 드롭다운이 비어 보인다. (1차 설계 때 이미 완료됨 — 재설계로 라벨 자체는 안 바뀌므로 다시 할 필요 없음.)

### 13.5 제작 순서 (재설계 반영, 추천)

**이미 완료(1차 설계 잔존분, 재사용)**: `TacticsTuning.DisperseRadiusMeters`, `LocalPositioning` enum(`Surround`/`Disperse`), `IPositioningStrategy.ComputeMoveTarget`의 `self`/`sameSideUnits` 매개변수, `DispersePositioningStrategy`, 카탈로그 자산 라벨(§13.4) — 전부 그대로 유지, 재작업 불필요.

**재설계로 교체 대상**: 기존 `RangedSurroundCoordinator`/`SurroundPositioningStrategy`(§13.3, 1차 설계) 전체를 아래 순서로 다시 작성한다. `groupsByTarget`/`AngleByMember`/`TryGetAngle` 등 1차 설계의 상태·API는 전부 폐기.

1. `TacticsTuning`에 신규 상수 추가: `SurroundJoinToleranceMeters`, `SurroundAllySpacingMeters`(2m), `SurroundGapPullWeight`, `SurroundRingShrinkSpeedMetersPerSecond`. 기존 `SurroundApproachAvoidanceRadiusMeters`/`SurroundArrivalToleranceMeters`(1차 설계 전용)는 삭제 대상.
2. `SurroundRing` 클래스 신설(`FrontlineFormationLine`과 같은 자리) — `ClusterCenter`/`ClusterBoundingRadius`/`DealerRange`/`CurrentRadius`/`Members`, Join/Leave.
3. `RangedSurroundCoordinator` 전면 재작성 — `FrontlineFormationCoordinator.ReconcileExistingLines`/`AssignUnassignedPool` 패턴을 그대로 본떠 `SurroundRing` 버전으로: 기존 링 재조정(사망/도주 제거, 소속 군집 재계산, 없어지면 해체) → 미배정 풀에서 군집×사거리 조합별 신규 링 생성(`FrontlineFormationCoordinator.ClusterEnemies` 재사용, 그룹화는 "자기 CurrentTarget이 속한 군집"). 반지름 축소/복원 로직(§13.3′-4) 포함.
4. `SurroundPositioningStrategy` 재작성 — 미합류 시 (반지름 접근 + 아군 반발 2m + 빈 구간 약한 끌어당김) 합산 벡터 반환, 합류 완료 시 `selfPosition` 고정 반환(코디네이터의 `Members` 조회로 판정, Blocking 패턴과 동일).
5. `PositioningStrategyFactory`/`UnitTacticsBehaviorsFactory`/`LiveBattleSimulationRule`/`BattleSimulationLoop` 배선은 1차 설계와 동일한 자리 그대로 유지(코디네이터 인스턴스 교체만 필요, 배선 구조 자체는 안 바뀜).
6. 실전투 검증: 포위망이 실제로 군집 전체를 둘러싸는지(가장 중요 — 1차 설계가 못 풀었던 문제), 사거리가 다른 아군이 각자 다른 반지름의 링에 정상 합류하는지, 반지름 축소가 과도하게(끝없이) 줄어들지 않는지, 같은 방향에서 접근할 때 "빈 구간 끌어당김"이 실제로 완화 효과가 있는지.
