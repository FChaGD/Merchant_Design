## 1. 영향 범위

반경 값 1개가 흐르는 경로는 두 갈래다. 두 경로 모두 마지막에 영역 계산(`FormationArea`)으로 들어간다.

| 경로 | 거치는 곳 |
|---|---|
| 마차·시설 | 엑셀 → 테이블 임포터 → 테이블 자산(`CaravanAssetEntry`) → 카탈로그(`CaravanAssetProfile`) → 로스터(`PlaceholderCaravanRosterProvider`) → 유닛(`PlaceholderFormationUnit` / `IAreaAnchorUnit`) → 영역 계산, 마을 칸 표시 범위(`HubFormationPanel`) |
| 디버그 핀 | 디버그 패널 입력칸(`FormationGridDebugView`) → 격자 편집기(`FormationGridEditor`) → 편집 핸들러 계약(`IFormationEditingHandler`, 구현 2개: Hub·Field 패널) → 핀 값(`FormationAreaPin`) → 핀 저장소 → 영역 계산 |

## 2. 방향 범위 값 — `FormationAreaSpan` (신규, plain C#)

반경 `int` 1개를 대체하는 불변 값 타입. 마차·시설·핀 세 곳이 같은 값을 쓰므로 한 타입으로 모은다 — 네 개의 `int`를 따로 넘기면 계약 4곳(유닛, 핀, 편집 핸들러, 디버그 입력)의 매개변수 순서가 어긋날 여지가 생긴다.

```csharp
public readonly struct FormationAreaSpan
{
    public int Up { get; }      // 행 감소 방향(격자 화면 위쪽)
    public int Down { get; }    // 행 증가 방향
    public int Left { get; }    // 열 감소 방향
    public int Right { get; }   // 열 증가 방향

    public FormationAreaSpan(int up, int down, int left, int right); // 음수는 0으로 올림
    public static FormationAreaSpan Uniform(int value);
    public int MaxReach { get; } // 네 값 중 최댓값 - 마을 칸 표시 범위용
}
```

- 위치: `Core/UI/Formation/`(`FormationArea.cs`와 같은 폴더).
- **방향 기준**: 정비창 격자는 `GridLayoutGroup`이 위→아래로 행을 놓는다(`FormationGridView` 확인). 따라서 상 = 행 번호 감소, 하 = 행 번호 증가.
- 음수 방어는 생성자에서 한 번만 한다. 입력 경로(테이블·디버그 입력)마다 따로 막지 않아도 영역 계산이 깨지지 않는다. 테이블 오류는 임포터가 별도로 드러낸다(§3).

## 3. 데이터 — 테이블·임포터·카탈로그

- 엑셀: `Wagon`·`Facility` 데이터 시트에서 `Radius` 열을 삭제하고 `Up`, `Down`, `Left`, `Right` 정수 열을 추가한다. 전 행 값은 4. 이름 시트(`...Strings`)는 그대로.
- `CaravanAssetEntry`: `Radius`를 삭제하고 `Up`, `Down`, `Left`, `Right` `int` 필드 4개를 추가한다. 직렬화 필드는 기존 방식(평면 `int`)을 유지한다 — 임포터가 필드 이름으로 값을 써 넣기 때문이다.
- `CaravanAssetProfile`: `Radius`를 `FormationAreaSpan AreaSpan`으로 바꾼다. 카탈로그가 엔트리 4개 필드로 값을 만든다.
- 임포터: 4개 열을 필수 정수로 읽는다. **음수면 `FormatException`**(시트·Id 포함)을 던진다(§7-2). 옛 `Radius` 열이 남아 있어도 읽지 않을 뿐 오류로 보지 않는다.
- 테이블 자산은 Play 시 자동 임포트되므로 별도 임포트 절차는 없다.

## 4. 유닛 계약 — `IAreaAnchorUnit`

- `int AreaRadius`를 `FormationAreaSpan AreaSpan`으로 바꾼다.
- `PlaceholderFormationUnit` 생성자의 `int areaRadius = 0`을 `FormationAreaSpan areaSpan = default`로 바꾼다(기본값 = 네 방향 0 = 1칸, 지금 기본값 0과 같은 의미).
- 로스터는 프로필의 `AreaSpan`을 그대로 넘긴다.

## 5. 영역 계산 — `FormationArea`

- `FormationAreaPin.Radius`를 `FormationAreaSpan Span`으로 바꾼다.
- 정사각형 추가 로직을 직사각형 추가 로직으로 일반화한다. 행 범위는 `row − Up ~ row + Down`, 열 범위는 `column − Left ~ column + Right`이고, 판 밖은 기존처럼 잘린다.
- 내부 목록(`(slot, radius)`)의 반경도 방향 범위로 바꾼다. 그 밖의 계산(대열·자리·연결 칸 집합, 연결 판정, 경계 상자, 마차 중심)은 그대로 둔다.
- 전투 대열 범위(`ToExtent`)는 경계 상자와 마차 중심으로 계산하므로 비대칭 영역도 그대로 처리된다. 반폭은 "중심에서 더 먼 쪽 가장자리까지"라서 비대칭 영역은 전장 반경이 약간 넉넉하게 잡힌다(기존과 같은 규칙).

## 6. 화면·디버그

### 6.1 마을 칸 표시 범위 (`HubFormationPanel`)

- "로스터 마차 반경 최댓값"을 "로스터 마차 방향 범위 최댓값(`MaxReach`)"으로 바꾼다. 여백 = `max(기본 2, 최댓값 + 1)`, 사방에 똑같이 적용(기획 61번 §3.3). 로스터 기준(팔레트 마차 포함)은 설계 60번 §15.3 그대로.

### 6.2 디버그 핀 입력

- `FormationGridDebugView`: 반경 입력칸 1개를 `upInput`/`downInput`/`leftInput`/`rightInput` 4개로 바꾼다. 핀을 놓을 때 네 칸을 파싱해 방향 범위를 만든다. 비었거나 숫자가 아니면 기본 4를 쓰고, 시작할 때 빈 칸을 4로 채운다.
- 전달 계약: 디버그 뷰 콜백, 격자 편집기, `IFormationEditingHandler`의 핀 추가 메서드와 Hub·Field 구현 2곳의 매개변수를 `(int slotIndex, FormationAreaSpan span)`으로 바꾼다.
- `FormationUIBuilder` 디버그 패널: 기존 "핀 반경" 라벨과 입력칸 자리(가로 0.00~0.22)에 `상`/`하`/`좌`/`우` 라벨+입력칸 4쌍을 놓고, 핀 아이콘과 안내문은 오른쪽으로 민다. 옛 `RadiusLabel`/`RadiusInput`은 정리 목록에 넣어 지운다.
- 디버그 패널은 Hub와 Field가 같은 빌더를 쓰므로 **Build Hub Scene, Build Field Scene 둘 다 다시 실행**해야 한다.

## 8. 전투 쪽 영향 (기획 61번 §5 미확인 항목 확인 결과)

- 정비창 행은 전장 x축, 열은 전장 y축으로 옮겨진다(`BattleFieldLayout`: x = (행 − 중심 행) × 행 간격). 따라서 **상(행 감소) = 전장 −x 쪽, 하 = 전장 +x 쪽**이다.
- 적 출현점은 전장 중심을 둘러싼 원 위에 번호순으로 배치된다(`ComputeSpawnPoint`). 전투에는 고정된 전방/후방 개념이 없으므로 상/하 선택이 전투 규칙에 주는 영향은 없다.
- 전투 코드는 수정하지 않는다.
