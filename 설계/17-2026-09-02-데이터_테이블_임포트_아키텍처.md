## 1. 조사 결과 — 배선 전례

`RoleGroupTacticsCatalogAsset`/`MercenaryRoleGroupMapAsset`는 DI로 등록되지 않는다. 소비자마다 `[SerializeField]`로 직접 참조를 들고, 그 배선은 인스톨러가 담당한다 — `LiveBattleSimulationRule`과 `BattleTestSimulationRule`이 각자 `roleGroupMap` 필드를 갖고, `ManagerHierarchyInstaller`/`BattleTestSceneInstaller`가 `AssetDatabase.LoadAssetAtPath` + `SerializedObject`로 각각 채운다.

`IBattleUnitStatProvider`/`IEnemyCompositionProvider`는 DI 대상도 아니다 — `PlaceholderBattleUnitStatProvider`/`PlaceholderEnemyTypeCompositionProvider`가 필드가 전혀 없는 순수 값 조회 클래스라, 소비자 3곳(`LiveBattleSimulationRule`, `BattleTestSimulationRule`, `InMemoryUnitConditionRepository`)이 그냥 `new PlaceholderBattleUnitStatProvider()`로 인라인 생성해 쓴다.

이번 설계는 이 두 전례를 그대로 따른다 — 엑셀에서 값을 채우는 대상이 되는 SO 에셋은 **소비자별 `[SerializeField]` 배선 + 인스톨러가 채움** 방식을 유지하고, 새로 DI 싱글턴을 도입하지 않는다. 기존 구조를 뒤엎지 않는 최소 변경 경로다.

## 2. 파싱 계층

- **라이브러리**: `ExcelDataReader`(MIT, 읽기 전용) — `Assets/Plugins/Editor/ExcelDataReader/`에 DLL 배치. 에디터 전용이므로 빌드에 포함되지 않는다.
- **의존성 정정(제작 단계에서 실제 워크북으로 검증하며 발견)**: 기획 단계에서 "xlsx만 쓰면 추가 의존성 없음"으로 예상했으나 틀렸다 — `ExcelReaderConfiguration`의 기본 생성자가 xlsx/xls 여부와 무관하게 항상 코드페이지 1252로 `FallbackEncoding`을 계산하는데, .NET(코어) 런타임은 이 코드페이지를 기본 내장하지 않아 `System.Text.Encoding.CodePages` 프로바이더를 등록하지 않으면 `NotSupportedException`이 난다. `System.Text.Encoding.CodePages.dll`(MIT, netstandard2.0)도 같은 폴더에 함께 배치하고, `EditorTableReader`가 최초 1회 `Encoding.RegisterProvider(CodePagesEncodingProvider.Instance)`를 호출한다. 이 패키지의 전이 의존성(`System.Memory`, `System.Runtime.CompilerServices.Unsafe`)은 Unity 런타임이 이미 내장 제공하므로 별도 DLL을 추가하지 않는다(중복 어셈블리 충돌 위험을 피하기 위함).
- **공용 유틸리티** `EditorTableReader`(`Assets/Scripts/Editor/EditorTableReader.cs`, `internal static`) — `EditorUIBuilder`와 같은 성격의 저수준 공용 클래스. 워크북 경로 + 시트명을 받아 **헤더 행 기준 `IReadOnlyList<IReadOnlyDictionary<string, string>>`**(컬럼명→셀 문자열)로 변환하는 것까지만 책임진다. 타입 변환(`float.Parse`, enum 매칭)과 도메인 검증은 각 도메인 임포터가 담당 — 한 클래스가 "엑셀 파싱"과 "게임 데이터 해석"을 동시에 갖지 않는다(SRP).

```csharp
internal static class EditorTableReader
{
    public static IReadOnlyList<IReadOnlyDictionary<string, string>> ReadSheet(string workbookPath, string sheetName);
}
```

## 3. 새 ScriptableObject 에셋 (데이터 컨테이너, 로직 없음)

## 4. 임포터 (Editor, get-or-create)

씬 편집 컨벤션과 동일한 원칙을 데이터 에셋에 적용한다 — 재실행해도 안전(항상 엑셀 최신 내용으로 덮어씀), 대상 에셋이 없으면 생성.

```csharp
        // CharacterStats.xlsx → CharacterStatsTableAsset / EnemyStatsTableAsset / EnemyEncounterCompositionTableAsset
        // 각 에셋: AssetDatabase.LoadAssetAtPath 또는 없으면 CreateAsset → SerializedObject로 entries 덮어쓰기
        // → EditorUtility.SetDirty → AssetDatabase.SaveAssets

public static class TacticsTableImporter
{
    [MenuItem("Tools/Game/Table/Import Tactics")]
    public static void Import()
```

에셋 저장 경로는 기존 두 SO 에셋과 같은 폴더(`Assets/Prefabs/ScriptableObejct/`)로 통일한다 — 임포터가 새로 만드는 3종도 이 폴더에 생성.

## 5. Provider 어댑터 — `IBattleUnitStatProvider`/`IEnemyCompositionProvider` 구현 교체

인터페이스는 변경하지 않는다. Placeholder 구현을 대체하는 새 클래스를 추가한다.

```csharp
public class TableBattleUnitStatProvider : IBattleUnitStatProvider
{
    private readonly CharacterStatsTableAsset table;
    public TableBattleUnitStatProvider(CharacterStatsTableAsset table) => this.table = table;

    public BattleUnitStats GetStats(MercenaryClass mercenaryClass)
    {
        if (!table.TryGetEntry(mercenaryClass, out var entry))
            throw new InvalidOperationException($"CharacterStatsTableAsset에 '{mercenaryClass}' 항목이 없다.");
        return new BattleUnitStats(entry.MaxHp, entry.Attack, entry.Defense, entry.MoveSpeed, entry.AttackInterval, entry.Range, entry.MoraleSyncRate);
    }
}
```

```csharp
public class TableEnemyTypeCompositionProvider : IEnemyCompositionProvider

    private readonly EnemyStatsTableAsset statsTable;
    private readonly EnemyEncounterCompositionTableAsset compositionTable;

    // 그대로 옮긴다 - 이번 변경은 "값의 출처"만 바꾸고 확률 로직은 건드리지 않는다.
    public IReadOnlyList<BattleUnitStats> GetEncounterComposition();
```

## 7. 검증기 확장

`TacticsCatalogValidator`와 같은 성격의 검증을 새 테이블에도 적용할 여지가 있다 — 예: `CharacterStatsTableAsset`에 `MercenaryClass` 값 중 누락된 항목이 있는지, `EnemyStatsTableAsset`과 `EnemyEncounterCompositionTableAsset`의 `EnemyType` 집합이 서로 일치하는지. 이번 설계 범위에서는 임포터가 파싱 시점에 "필수 컬럼 누락/enum 값 불일치"를 즉시 에러로 던지는 것으로 최소 방어선을 삼고, `TacticsCatalogValidator`처럼 별도 메뉴로 실행하는 상시 검증기 신설 여부는 제작 단계로 이월한다(§8-3).

## 9. 제작 완료 내역 및 실행 안내 (2026-09-02)

이 설계 문서 §2~§6이 실제 코드로 구현됐다. 새 파일: `EditorTableReader.cs`, `CharacterStatsTableImporter.cs`, `TacticsTableImporter.cs`, `CharacterStatsTableAsset.cs`/`EnemyStatsTableAsset.cs`/`EnemyEncounterCompositionTableAsset.cs`, `TableBattleUnitStatProvider.cs`/`TableEnemyTypeCompositionProvider.cs`. 삭제: `PlaceholderBattleUnitStatProvider.cs`, `PlaceholderEnemyTypeCompositionProvider.cs`. `Assets/Table/CharacterStats.xlsx`/`Tactics.xlsx`도 기존 값 그대로 생성 완료.

`ExcelDataReader.dll`/`System.Text.Encoding.CodePages.dll`을 실제 워크북 파일로 별도 .NET 콘솔 프로젝트에서 파싱까지 검증했다(헤더/로우/한글 라벨/숫자 컬럼 전부 정상 왕복 확인) — `EditorTableReader.ReadSheet`의 파싱 로직 자체는 신뢰할 수 있다. 다만 이 세션은 Unity를 실행할 수 없어 **다음은 미검증**:

1. Unity 컴파일 통과 여부(SerializedProperty 필드명 오탈자 등 C# 자체는 재확인했으나 Unity 컴파일러로 직접 확인하지 않음).
2. `Tools/Game/Build Bootstrap Scene`, `Tools/Game/Table/Import Character Stats`, `Tools/Game/Table/Import Tactics`, `Tools/Game/Debug/Build BattleTest Scene`(또는 해당 인스톨러) 순 실행 후 실제 배선/전투 동작.

**사용자 확인 필요**: `Assets/Table/*.xlsx`는 바이너리라 지금 `git status`에 새 파일로 잡힌다 — 커밋 여부/방침은 아직 사용자 확인 전이라 별도로 커밋하지 않았다.

### 9.1 플레이 진입 시 자동 재임포트 (`TableAutoImportOnPlay.cs`)

수동 메뉴 실행 대신, 에디터에서 플레이 버튼을 누를 때마다 엑셀 최신 내용이 자동 반영되게 했다.
`[InitializeOnLoad]` 정적 생성자가 `EditorApplication.playModeStateChanged`를 구독하고,
`PlayModeStateChange.ExitingEditMode`(에디트 모드를 벗어나는 시점 - 아직 에디터 API를 쓸 수 있는
마지막 타이밍)에 두 임포터를 순서대로 호출한다. 워크북이 없거나 파싱에 실패해도 각 임포터가
`Debug.LogError`만 남기고 조용히 중단하므로 플레이 진입 자체는 막지 않는다(기존 SO 에셋 값 그대로
플레이됨). 수동 메뉴(`Tools/Game/Table/Import ...`)는 그대로 남아 있다 - 에디터 밖(빌드)에서 값을
미리 확정해두고 싶을 때 등에 여전히 유효하다.

## 10. 파티 방침 옵션 카탈로그 확장 (2026-09-02, 기획 14번 §3.6 대응)

### 10.1 새 SO 에셋 — `PartyTacticsPolicyCatalogAsset`

`MercenaryRoleGroupMapAsset`/`RoleGroupTacticsCatalogAsset`과 같은 폴더(`Assets/Scripts/Core/Battle/Tactics/`)에 신설. `RoleGroupTacticsCatalogAsset`처럼 데이터만 담고 로직은 없다 - 다만 역할군 그룹핑이 없어(기획 14번 §3.6) 리스트 3개를 곧바로 갖는다.

```csharp
[Serializable] public struct EnemyRecognitionOption { public EnemyRecognitionType Value; public string DisplayLabel; public int SortOrder; public bool IsDefault; }
[Serializable] public struct ActivityRadiusOption   { public ActivityRadiusPreset Value;   public string DisplayLabel; public int SortOrder; public bool IsDefault; }
[Serializable] public struct PursuitOption          { public PursuitPreset Value;          public string DisplayLabel; public int SortOrder; public bool IsDefault; }

public class PartyTacticsPolicyCatalogAsset : ScriptableObject
{
    [SerializeField] private List<EnemyRecognitionOption> recognitionOptions = new();
    [SerializeField] private List<ActivityRadiusOption> radiusOptions = new();
    [SerializeField] private List<PursuitOption> pursuitOptions = new();

    public IReadOnlyList<EnemyRecognitionOption> RecognitionOptions => recognitionOptions;
    public IReadOnlyList<ActivityRadiusOption> RadiusOptions => radiusOptions;
    public IReadOnlyList<PursuitOption> PursuitOptions => pursuitOptions;
}
```

임포터가 이미 `SortOrder`로 정렬해서 쓰므로(§10.4), 리스트는 항상 표시 순서대로 저장돼 있다 - 소비자가 다시 정렬할 필요 없다.

### 10.2 `TacticsPanel.cs` 변경

`static readonly (TEnum, string)[] RecognitionOptions/RadiusOptions/PursuitOptions` 3개 필드를 제거하고, 기존 `catalog`(RoleGroupTacticsCatalogAsset) 옆에 `[SerializeField] private PartyTacticsPolicyCatalogAsset partyPolicyCatalog;`를 추가한다.

- `BindPartyDropdowns()`: `SetOptions(recognitionDropdown, RecognitionOptions)`(튜플 배열 오버로드) → `SetOptions(recognitionDropdown, partyPolicyCatalog.RecognitionOptions, o => o.DisplayLabel)` - 이미 존재하는 제네릭 `SetOptions<T>(dropdown, IReadOnlyList<T>, Func<T,string>)` 오버로드(L292)를 그대로 재사용한다(RoleGroup 축 드롭다운이 이미 이 오버로드를 쓰고 있어 새로 만들 필요 없음).
- `onValueChanged` 콜백 안의 `RecognitionOptions[index].Value` 등도 `partyPolicyCatalog.RecognitionOptions[index].Value`로 치환.
- `RefreshFromRepository()`의 `IndexOf(RecognitionOptions, party.RecognitionType)`(튜플 배열 전용 제네릭) → `IndexOfOption(partyPolicyCatalog.RecognitionOptions, party.RecognitionType)` - `IndexOfOption(IReadOnlyList<TargetPriorityOption>, TargetPriority)` 등 기존 3개 오버로드와 같은 스타일로 3개(`EnemyRecognitionOption`/`ActivityRadiusOption`/`PursuitOption`용) 추가. 기존 코드가 이미 제네릭 대신 타입별 반복을 선택한 전례를 따른다.
- `RefreshRoleGroupSelection`이 `catalog == null`을 가드하는 것과 같은 이유로, `BindPartyDropdowns`/`RefreshFromRepository`도 `partyPolicyCatalog == null`을 가드하고 `WarnMissing`과 같은 패턴으로 경고 후 스킵한다.

### 10.3 `InMemoryTacticsRepository.cs` 변경

`DefaultPartySettings` 정적 상수(하드코딩 값)를 제거하고, `catalog` 옆에 `[SerializeField] private PartyTacticsPolicyCatalogAsset partyPolicyCatalog;`를 추가한다. `GetPartySettings()`가 저장된 값이 없을 때 호출하는 계산을 `ResolveCatalogDefault(RoleGroup)`(기존, 역할군 override 기본값 계산)와 같은 자리에 나란히 추가한다:

```csharp
private PartyTacticsSettings ResolveDefaultPartySettings()
{
    if (partyPolicyCatalog == null) { Debug.LogWarning(...); return default; }
    return new PartyTacticsSettings(
        FindDefault(partyPolicyCatalog.RecognitionOptions, o => o.IsDefault, o => o.Value),
        FindDefault(partyPolicyCatalog.RadiusOptions, o => o.IsDefault, o => o.Value),
        FindDefault(partyPolicyCatalog.PursuitOptions, o => o.IsDefault, o => o.Value));
}
```

`IsDefault==true` 항목이 하나도 없으면(임포트 전이거나 엑셀에 표기 누락) 경고 로그 후 그 축은 `default(TEnum)`(=enum 0번째 값)로 폴백 - `ResolveCatalogDefault`가 카탈로그 누락 시 `default`로 폴백하는 것과 같은 fail-soft 원칙.

### 10.4 `TacticsTableImporter.cs` 확장

같은 `Import()` 안에서 `TacticsRecognitionOptions`/`TacticsRadiusOptions`/`TacticsPursuitOptions` 3개 시트를 추가로 읽어 `PartyTacticsPolicyCatalogAsset`을 채운다. 각 시트는 `RoleGroup` 그룹핑이 없어 `GroupByRoleGroup<TEnum>`을 재사용하지 않고, `SortOrder`로 정렬만 하는 더 단순한 헬퍼가 필요하다:

```csharp
private static List<(TEnum Value, string Label, bool IsDefault)> ReadOptionsSortedBySortOrder<TEnum>(
    IReadOnlyList<IReadOnlyDictionary<string, string>> rows) where TEnum : struct, Enum
```

`IsDefault` 컬럼 파싱은 `EditorTableReader`에 `bool.TryParse` 기반 `ParseBool(row, column)`을 추가한다(`ParseFloat`/`ParseInt`/`ParseEnum`과 같은 자리). 시트당 `IsDefault==true`가 정확히 1개인지는 임포트 시점에 검증해 0개/2개 이상이면 `Debug.LogError`로 즉시 드러낸다(§10.6과 연결).

`PartyTacticsPolicyCatalogAsset`은 `MercenaryRoleGroupMapAsset`/`RoleGroupTacticsCatalogAsset`과 달리 기존에 존재하던 에셋이 아니라 이번에 처음 생기는 에셋이다 - `CharacterStatsTableImporter`의 `GetOrCreateAsset<T>`와 완전히 같은 로직이 필요하다. 이 시점에 2번째 임포터가 같은 get-or-create 로직을 필요로 하게 되므로, CLAUDE.md 공용 유틸리티 분리 규칙대로 `GetOrCreateAsset<T>`을 `CharacterStatsTableImporter`에서 `EditorTableReader`(공용 유틸리티)로 옮기고, `CharacterStatsTableImporter`도 그 공용 버전을 쓰도록 정리한다(중복 제거, 한 인스톨러가 다른 인스톨러의 private 메서드를 열어 쓰지 않는 원칙 유지).

### 10.5 배선 — 자동 배선(auto-wire)하기로 결정

조사 결과, 기존 `roleGroupMap`/`catalog` 필드는 실제로는 `ManagerHierarchyInstaller`(Bootstrap 실제 게임 경로)가 자동 배선하지 않는다 - `BattleTestSceneInstaller`(테스트 씬)만 자동 배선하고, Bootstrap.unity 쪽은 개발자가 인스펙터에서 한 번 수동으로 끌어다 놓고 그 결과가 씬 파일에 저장되는 방식이었다(과거 세션에서 그렇게 이미 연결됨 - 재생성 대상이 아니라 재사용 대상).

`PartyTacticsPolicyCatalogAsset`은 이번에 처음 생기는 에셋이라 Bootstrap.unity에 수동 연결된 이력이 없다. §6에서 `CharacterStatsTableAsset` 등 3종을 `ManagerHierarchyInstaller`/`BattleTestSceneInstaller`에서 자동 배선하기로 한 것과 같은 이유(첫 배선을 사람이 깜빡하면 조용히 null로 남는다)로, 이번에도 두 인스톨러 모두에서 자동 배선한다 - `roleGroupMap`/`catalog`처럼 수동 연결에 맡기지 않는다.

| 파일 | 변경 |
|---|---|
| `ManagerHierarchyInstaller.cs` | `TacticsPanel`(L79 `EnsureSiblingComponent`)과 `InMemoryTacticsRepository`(L99 근처 `GetOrCreateManager`)에 `partyPolicyCatalog` SerializeField 배선 추가 |
| `Editor/Debug/BattleTestSceneInstaller.cs` | `WireTacticsPanelCatalog`/`WireTacticsCatalog` 옆에 `WirePartyPolicyCatalog` 계열 메서드 추가, 같은 호출부(L60/L100 근처)에서 함께 호출 |
