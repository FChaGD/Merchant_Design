## 1. 문제 요약

- 로스터 클래스 2개가 종류 타입(`MercenaryClass`/`EnemyType`)만 다르고 코드가 같다.
- 그 중복이 `BattleTestSimulationRule`(스폰, 제거, 스탯 덮어쓰기, 기본 스탯 조회, 미리보기 유닛 생성, 전투 유닛 생성, 미리보기 재생)과 `ILiveUnitSpawner`(소환 메서드 2개), 팔레트(진영 분기), 정보 패널(진영 분기 4곳)에 쌍으로 전파돼 있다.
- 진영을 나타내는 bool + 항목 Id는 이미 유닛 추가 이벤트, 클릭 대상 식별에서 통합되어 흐르고 있다. 갈라지는 곳은 "종류 타입이 다르다"는 이유로 종류를 받는 지점뿐이다.

## 2. 설계 결정 (사용자 확정: 4항목 모두 추천안)

| # | 결정 | 내용 |
|---|---|---|
| 1 | 통일 식별자 | 진영 + 정수 종류값을 담은 값 구조체 `BattleTestUnitKind`. enum 타입 검사 손실은 변환 지점을 진영 정의 한 곳에 가둬 완화 |
| 2 | 진영 차이 흡수 | 진영 정의 객체 2개(아군/적)가 공통 인터페이스 `IBattleTestSide`를 구현. 규칙 클래스는 진영 bool로 객체를 골라 쓴다 |
| 3 | 아이콘 직렬화 | 기존 직렬화 필드 3개(진영/직업/적 타입) 유지 + 통일 식별자 조회 프로퍼티 추가. 씬·인스톨러 변경 없음 |
| 4 | 진영 전용 기능 | 적 구성 편집, 스폰 포인트 예약, 적 로스터 비움 이벤트는 범위 제외(동작 그대로) |

추가로 확정한 사항: 로스터는 클래스 1개로 통합하되 **인스턴스는 진영별 2개**를 유지한다 — 항목 Id가 진영마다 0부터 시작하는 현재 방식이 유지되어 클릭 대상(진영+항목 Id)과 유닛 추가 이벤트 시그니처를 바꾸지 않는다.

## 3. 구조

### 3.1 통일 식별자 `BattleTestUnitKind`
- readonly struct: `IsAlly`(bool), `Value`(int).
- 생성: 정적 팩토리 `Ally(MercenaryClass)`, `Enemy(EnemyType)` — enum→int 변환은 여기서만 한다.
- 역변환: `ToMercenaryClass()`, `ToEnemyType()` — 진영 정의 객체만 호출한다. 진영이 맞지 않으면 예외로 조기 실패(잘못된 진영 정의에 종류가 넘어가는 실수 차단).
- 항목 Id(`EntryId`)와는 별개다: Kind는 "종류", EntryId는 "배치된 개체 하나".

### 3.2 로스터 `BattleTestRoster` (기존 2개 대체)
- 기존 코드 그대로(항목 목록, Id 채번, 추가/조회/제거/전체 삭제), `Entry`는 `Id`, `Kind`(`BattleTestUnitKind`), `Position`, `StatsOverride`.
- `Entry`가 클래스인 이유(Id로 식별해 나중에 변경)와 "전투 리셋은 목록을 지우지 않는다"는 주석은 그대로 승계.
- 삭제: `BattleTestAllyRoster.cs`, `BattleTestEnemyRoster.cs` (MonoBehaviour가 아닌 순수 클래스라 씬 참조 없음 — 확인됨).

### 3.3 진영 정의 `IBattleTestSide`

| 멤버 | 책임 |
|---|---|
| `IsAlly` | 진영 구분 |
| `Roster` | 이 진영의 `BattleTestRoster` |
| `Morale`, `WaveCoordinator` | 이 진영의 사기/파동 인스턴스. `BeginBattle(fieldRadius)`마다 새로 만들고, 전투 중 소환 유닛은 같은 인스턴스를 재사용(현행 규칙 유지). 첫 전투 전에는 null |
| `GetDefaultStats(BattleTestUnitKind)` | 진영별 기본 스탯 조회 (아군: 직업 스탯 공급자, 적: 타입 구성 공급자) |
| `CreatePreviewUnit(Entry)` | 세팅 단계 미리보기 유닛 (더미 사기/파동, 이동거리 0, 전술 행동 없음 — 현행과 동일) |
| `CreateBattleUnit(Entry, BattleTestBattleContext)` | 전투용 유닛 (아군: 전술 행동 부여, 적: 타입별 아이콘) |

구현체: `BattleTestAllySide`, `BattleTestEnemySide`(신규). 진영 차이(전술 행동 부여 여부, 아이콘, 스탯 공급자)는 각 구현체에만 남는다.

`BattleTestBattleContext`: 전투 유닛 생성에 필요한, `BuildSimulation` 시점에 정해지는 값(도주 이동 거리, 표준 활동 반경, 전장 반지름, 전열/원거리 포위 조율자, 전술 프로필 해석기)을 묶은 값 묶음. 피해 공식과 공간 질의는 미리보기 생성(전투 전, 컨텍스트 없음)에도 필요하므로 컨텍스트가 아니라 진영 객체 생성자로 주입한다(제작 중 조정). 규칙 클래스가 `BuildSimulation` 때 채운다 — 진영 객체가 규칙 클래스를 역참조하지 않게 하는 용도.

### 3.4 소환 인터페이스
`ILiveUnitSpawner`: `SpawnAlly`/`SpawnEnemy` → `Spawn(BattleTestUnitKind, Vector2)` 1개. `IsRunning`은 유지.

### 3.5 규칙 클래스 `BattleTestSimulationRule`

| 현재 (쌍) | 변경 후 |
|---|---|
| 로스터 필드 2, 프로퍼티 2, 사기/파동 필드 4 | 진영 객체 2개 보유 |
| `SpawnAlly`/`SpawnEnemy` | `Spawn(kind, pos)` 1개 — 진영 객체 선택 후 공통 절차(로스터 추가 → 실행 중이면 전투 유닛 생성+등록, 아니면 미리보기 생성 → `OnUnitAdded` 발행) |
| `RemoveAlly`/`RemoveEnemy` | `RemoveUnit(isAlly, entryId)` |
| `SetAllyStatsOverride`/`SetEnemyStatsOverride` | `SetStatsOverride(isAlly, entryId, stats)` |
| `GetAllyDefaultStats`/`GetEnemyDefaultStats` + 정보 패널의 현재 스탯 조회 | `TryGetCurrentStats(isAlly, entryId, out stats)` (덮어쓰기 ?? 기본값) |
| `BuildPreviewAlly`/`BuildPreviewEnemy` | 진영 객체의 `CreatePreviewUnit` |
| `BuildAllies`/`BuildEnemies` | 진영 객체를 순회하는 공통 빌더 1개 |
| `ReplayRosterAsPreview`의 반복문 2개 | 진영 순회 1개 (순서: 아군 → 적, 현행과 동일) |

- 공개 프로퍼티 `AllyRoster`/`EnemyRoster`는 삭제한다(외부 소비자는 정보 패널 1곳뿐이고 `TryGetCurrentStats`로 대체됨).
- `AllyMoraleValue`/`EnemyMoraleValue`는 유지(진영 객체의 사기 값 위임, 첫 전투 전에는 0).
- **유지(범위 제외)**: `ReplaceEnemyComposition`, `SyncReservationsIntoRoster`, 적 로스터 비움 이벤트는 적 진영 객체의 로스터를 직접 사용하도록 참조만 바꾼다. 동작 변화 없음.

## 5. 동작 동일성 (리팩토링 불변 조건)

- 항목 Id는 진영별로 0부터 채번한다. 리셋해도 로스터를 지우지 않는다.
- 전투 유닛 생성 인자와 순서는 현행과 같다. 아군은 전술 행동을 부여하고, 적은 타입별 아이콘을 쓰고 전술 행동이 없다.
- 미리보기 유닛은 더미 사기/파동, 이동 거리 0을 쓴다.
- 사기/파동은 `BuildSimulation`마다 새로 만들고, 전투 중 소환은 같은 인스턴스를 재사용한다.
- `OnUnitAdded`는 (유닛, 진영, 항목 Id)를 실행 중 여부와 무관하게 발행한다. `OnReset`, `OnEnemyRosterCleared`는 현행 그대로다.
- 리셋 후 미리보기는 아군 → 적 순서로 복원한다.
- 스탯 덮어쓰기는 다음 미리보기 재생/전투 시작부터 반영된다(현행 그대로).

## 6. 위험과 완화

| 위험 | 완화 |
|---|---|
| enum↔정수 변환 실수(엉뚱한 종류로 스폰) | 변환은 `BattleTestUnitKind` 팩토리/역변환 두 곳에만 존재, 진영이 맞지 않으면 예외 |
| 진영 객체가 사기/파동을 소유하면서 수명 관리 실수(전투 중 소환이 다른 인스턴스 사용) | `BeginBattle`에서만 생성, 소환은 읽기만 함 — 실전투 검증 항목에 포함 |
| 규칙 클래스 대량 수정으로 인한 회귀 | 동작 동일성 목록(§5)을 기준으로 전 기능 순환 검증 |
| 미확인 | 사기 게이지 등 `AllyMoraleValue`/`EnemyMoraleValue` 소비자 목록은 검색 시 확인 필요(시그니처 유지로 영향 없을 것으로 예상) |

## 7. 검증 계획 (제작 후 사용자 확인)

1. 컴파일 오류 없음.
2. 세팅 단계: 팔레트에서 아군 3종/적 3종을 드래그 배치 → 미리보기 표시.
3. 배치된 유닛 클릭 → 정보 패널 조회/스탯 적용/배치 취소를 아군·적 각각.
4. 적 구성 편집 패널 적용, 스폰 포인트 예약 → 전투 시작 시 반영.
5. 전투 시작 → 전투 중 팔레트로 아군/적 소환 → 사기 게이지, 승패 팝업.
6. 리셋 → 배치했던 유닛이 미리보기로 그대로 복원(아군 → 적), 스탯 덮어쓴 값 유지.
