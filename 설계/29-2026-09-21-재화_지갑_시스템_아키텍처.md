## 1. 범위

23번/26번 문서가 정의한 재화는 "기본 소지 재화"(항상 휴대, 마차 무관) + "적재 재화"(골드 상자류 아이템형, 마차 슬롯 소비) 이원 구조다. 후자는 마차/인벤토리 시스템이 아직 설계되지 않아 구현할 대상 자체가 없다(26번 문서 §4 명시). 이번 설계는 사용자 지시("일단 재화를 관리하는 시스템 기반을 구축하는 것에 집중")에 따라 **기본 소지 재화만 관리하는 지갑 시스템**을 만들고, 적재 재화는 나중에 붙일 수 있는 확장 지점만 남긴다(§5).

26번 문서 §3.4(인터페이스 분리 방향)에 따라, 지략/행정력 계열과는 별도의 인터페이스 집합으로 설계한다 — 22번 문서 §5가 제안했던 통합 `IPlayerResourceProvider`/`IPlayerResourceRepository`는 채택하지 않는다.

## 2. 새 인터페이스 — `IPlayerCurrencyReader` / `IPlayerCurrencyWallet`

위치: `Core/Player/`(신규 폴더 — 재화는 특정 씬/도메인 소유가 아니라 Hub/Field 양쪽에서 조회·소모돼야 하는 플레이어 전역 상태라 `Core/Game`도 `Core/UI`도 아닌 별도 도메인으로 분리한다. 22번 문서 §5가 예상했던 지점).

`IFormationReader`/`IFormationRepository` 분리(ISP)와 동일한 패턴 — 표시만 필요한 소비자(향후 재화 표시 UI)는 `IPlayerCurrencyReader`만 의존해 증감 조작 권한을 아예 갖지 않는다.

```csharp
namespace Game.Core
{
    /// <summary>
    /// 재화 조회 전용 계약. 표시만 하는 소비자(재화 계열 UI 표시 영역, 26번 §3.3)는
    /// 이 인터페이스만 의존해 IPlayerCurrencyWallet의 증감 조작에 접근하지 못하게 한다.
    /// </summary>
    public interface IPlayerCurrencyReader
    {
        int CurrentAmount { get; }
        int Capacity { get; }
        event Action<int> OnAmountChanged; // 변경 후 값을 전달 — 폴링 대신 이벤트로 UI 갱신
    }
}
```

```csharp
namespace Game.Core
{
    /// <summary>
    /// 캐릭터 고용, 마차/시설 구매, 상품 구매 등 재화를 소모/획득시키는 소비자를 위한 계약
    /// (23번 §3.1 용도). Apply류 저장이 아니라 즉시 반영되는 지갑 모델이다.
    /// </summary>
    public interface IPlayerCurrencyWallet : IPlayerCurrencyReader
    {
        // 상한을 넘는 만큼은 손실된다(23번 §3.1 "상한 초과 시 처리") — 실제로 반영된 양을 반환해
        // 호출자가 손실분을 알 수 있게 한다.
        int Add(int amount);

        // 부족하면 아무 것도 차감하지 않고 false. 소요시간 증가 등 대체 페널티는 두지 않는다(23번과
        // 같은 계열인 22번 §3.3 소진 처리 원칙 재사용).
        bool TrySpend(int amount);
    }
}
```

## 3. 구현체 — `InMemoryPlayerCurrencyWallet`

`InMemoryFormationRepository`와 같은 성격(MonoBehaviour, `IManagedComponent`, Bootstrap 상주, 세이브 연동 없이 앱 실행 중에만 유지 — 재화 영속화는 세이브 시스템이 생긴 뒤의 범위 밖 과제).

```csharp
using System;
using UnityEngine;

namespace Game.Core
{
    /// <summary>
    /// 기본 소지 재화만 관리한다(26번 §4) — 적재 재화(마차 연동)는 마차/인벤토리 시스템
    /// 설계 후 Capacity 계산에 합산 지점을 추가한다(§5 확장 지점).
    /// </summary>
    public class InMemoryPlayerCurrencyWallet : MonoBehaviour, IPlayerCurrencyWallet, IManagedComponent
    {
        // 23번 §3.1 기본 수치(잠정) — 가격 체계 정의 후 재검토 대상.
        [SerializeField] private int basicCapacity = 1000;

        private int currentAmount;

        public int CurrentAmount => currentAmount;
        public int Capacity => basicCapacity;
        public event Action<int> OnAmountChanged;

        public void RegisterSelf(IDependencyRegistrar registrar) => registrar.Register<IPlayerCurrencyWallet>(this);

        // 게임 시작 시 상한만큼 가득 채운 상태로 시작(23번 §3.1).
        public void ResolveDependencies(IDependencyResolver registrar) => currentAmount = basicCapacity;

        public int Add(int amount)
        {
            var applied = Mathf.Clamp(amount, 0, Capacity - currentAmount);
            if (applied <= 0) return 0;
            currentAmount += applied;
            OnAmountChanged?.Invoke(currentAmount);
            return applied;
        }

        public bool TrySpend(int amount)
        {
            if (amount > currentAmount) return false;
            currentAmount -= amount;
            OnAmountChanged?.Invoke(currentAmount);
            return true;
        }
    }
}
```

`IPlayerCurrencyReader`는 별도 구현체를 두지 않는다 — `IPlayerCurrencyWallet`이 이미 그 계약을 포함하므로, 표시 전용 소비자는 DI에서 같은 인스턴스를 `IPlayerCurrencyReader` 타입으로만 `TryResolve`하면 조작 메서드에 접근할 수 없다(인터페이스 타입이 접근 범위를 결정 — `IFormationReader`/`IFormationRepository` 사례와 동일).

## 4. DI 등록 — 기존 데이터 저장소 그룹에 합류

`ManagerHierarchyInstaller.BuildUIManagerDataRepositories`가 관리하는 8개 저장소(`PlaceholderCaravanRosterProvider`, `InMemoryFormationRepository` 등)와 같은 자리에 `InMemoryPlayerCurrencyWallet`을 9번째로 추가한다. 재화의 실제 주 소비자도 결국 UI(마을 시설 구매/고용 패널)가 될 것으로 예상되므로, 기존 저장소들과 같은 이유(주 소비자가 UIManager 산하 UI)로 같은 위치에 둔다.

- `DataRepositoryNames` 배열에 `nameof(InMemoryPlayerCurrencyWallet)` 추가.
- `BuildUIManagerDataRepositories`에서 `EditorUIBuilder.GetOrAddComponent<InMemoryPlayerCurrencyWallet>(...)` 추가, 반환 배열에 포함.

다른 저장소와 마찬가지로 소비자는 `registrar.TryResolve<IPlayerCurrencyWallet>(out var wallet)` 또는 `TryResolve<IPlayerCurrencyReader>(...)`로 선택 조회한다(인스톨러 미실행 방어).

이번 지갑은 다른 저장소를 참조하지 않으므로(`ResolveDependencies`가 아무것도 `TryResolve`하지 않음) DI 등록 순서 의존성이 없다.

## 5. 확장 지점 — 적재 재화(마차 연동)는 범위 밖으로 명시

26번 문서의 이원 구조를 나중에 통합할 때 건드릴 지점만 미리 표시해둔다(지금 코드를 추가하지 않는다):

- `Capacity`는 현재 `basicCapacity` 고정값이다. 마차 시스템이 생기면 "적재 슬롯 칸 수 → 적재 재화 상한" 계산 결과를 여기에 합산해야 한다 — 그 시점에 마차 스탯 조회 인터페이스를 `TryResolve`해 더하는 방식이 될 가능성이 높지만, 아직 대상 인터페이스가 없어 지금 훅을 만들지 않는다(과도한 사전 설계 방지).
- `Add`/`TrySpend`도 마차 연동 시점에 "기본 소지분 우선 소모/적재분 우선 소모" 같은 우선순위 규칙이 필요해질 수 있다 — 26번 문서 §4가 이 환산 비율/우선순위를 아직 미정으로 남겨뒀으므로 지금은 단일 합계로만 다룬다.
- 골드 상자(적재 재화)가 25번 문서의 교역품/전리품 인벤토리와 같은 저장 구현체를 쓸지도 미정 — 인벤토리 시스템 설계 시 결정.

## 6. 이 설계가 건드리지 않는 것

- 지략/행정력(22번 문서) — 별도 인터페이스 집합으로 후속 설계.
- 평판(23번 §3.2) — 소진되지 않는 척도라 지갑과 성격이 달라 이번 설계에 포함하지 않음.
- 재화 계열 UI 표시 영역(26번 §3.3)의 실제 화면/배치 — 이번 설계는 그 UI가 바인딩할 데이터 소스(`IPlayerCurrencyReader`)만 제공한다.
- 재화 획득/소비를 트리거하는 구체 행위(캐릭터 고용, 상품 구매 등)의 UI/로직 — 아직 해당 시스템 자체가 없다(23번 §4). `IPlayerCurrencyWallet.Add`/`TrySpend`는 그 시스템들이 나중에 호출할 진입점만 제공한다.
- 재화 영속화(세이브/로드) — 세이브 시스템 자체가 없어 범위 밖.

## 7. 제작 체크리스트

1. `Core/Player/IPlayerCurrencyReader.cs`, `IPlayerCurrencyWallet.cs`, `InMemoryPlayerCurrencyWallet.cs` 신설(§2, §3).
2. `ManagerHierarchyInstaller`의 `DataRepositoryNames` 배열 + `BuildUIManagerDataRepositories`에 `InMemoryPlayerCurrencyWallet` 추가(§4).
3. Unity 컴파일 확인 후 `Tools > Game > Build Bootstrap Scene` 재실행 → Ctrl+S로 씬 저장.
4. (검증) 임시 디버그 호출(또는 콘솔 테스트)로 `Add`/`TrySpend`가 상한 클램프·부족 시 실패를 올바르게 반환하는지 확인 — 실제 UI가 없으므로 자동화 테스트(`Tests/EditMode`)로 검증하는 편이 낫다.
