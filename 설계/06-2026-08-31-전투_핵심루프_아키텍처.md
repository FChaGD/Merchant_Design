## 1. 개요 및 범위

08번 기획 문서는 사기·정비창 영향·전술·보호 목표·판정 확장·연출까지 다루지만, 이번 설계는 그중 **가장 근본이 되는 "유닛이 실제로 어떻게 이동·타겟팅·공격·피해를 주고받는가"**만 다룬다. 나머지(사기, 보호 목표 파괴 판정, 결과 확장, 연출)는 이 루프 위에 얹히는 후속 설계로 남긴다(§10).

**핵심 배치 원칙**: 작성 당시엔 `BattleManager → IBattleResultEvaluator → IBattleResultRule`(`PlaceholderBattleResultRule`) 구조를 그대로 유지한다고 서술했으나, **2026-09-01 갱신**: `IBattleResultEvaluator`는 2026-08-26 리팩토링에서 삭제됐다(설계01/설계04 §6, `Docs/Refactor/2026-08-26-Field.md` 참고) — 지금은 `BattleManager`가 `IBattleResultRule`을 직접 `GetComponent`로 조회해 보유한다. 이번 절이 다루는 핵심 논지(OCP — [[05-2026-08-25-인카운터_판정_아키텍처]]와 동일하게 이미 설계된 확장점을 재사용, `PlaceholderBattleResultRule`을 `LiveBattleSimulationRule`로 교체, `BattleManager`가 "규칙이 `IFormationReader`를 필요로 하면 주입한다"는 **일반적 지원 코드를 1회**만 추가하는 것(§7.1))은 중간 계층 유무와 무관하게 그대로 유효하다 — 이후 같은 방식으로 데이터가 필요한 새 규칙이 추가돼도 `BattleManager`는 다시 바뀌지 않는다.

이번 설계 범위의 승패 조건은 "한쪽 진영의 Character 유닛이 전부 사망하면 그 진영이 진다"는 **단순화된 전멸전**이다. 기획 §7.4의 정식 조건(사기로 인한 도주 포함)과 §9(보호 목표 파괴)는 후속 설계에서 이 승패 판정에 조건을 추가하는 형태로 확장한다(§10) — 이번 설계가 만드는 시뮬레이션 루프 자체는 바뀌지 않는다.

## 3. 유닛 스탯 데이터 모델 (기획 §3/§4/§12)

```csharp
public enum MercenaryClass
{
    Warrior,
    Archer,
    ShieldBearer,
}

public readonly struct BattleUnitStats
{
    public float MaxHp { get; }
    public float Attack { get; }
    public float Defense { get; }
    public float MoveSpeed { get; }
    public float AttackInterval { get; }
    public float Range { get; }

    public BattleUnitStats(float maxHp, float attack, float defense, float moveSpeed, float attackInterval, float range)
    {
        MaxHp = maxHp; Attack = attack; Defense = defense;
        MoveSpeed = moveSpeed; AttackInterval = attackInterval; Range = range;
    }
}

public interface IBattleUnitStatProvider
{
    BattleUnitStats GetStats(MercenaryClass mercenaryClass);
}

/// <summary>
/// 기획 08번 문서 §12 표를 그대로 반영한 테스트 수치. 용병 밸런싱 시스템이 설계되면 대체/제거 대상.
/// </summary>
public class PlaceholderBattleUnitStatProvider : IBattleUnitStatProvider
{
    private static readonly Dictionary<MercenaryClass, BattleUnitStats> Table = new()
    {
        [MercenaryClass.Warrior] = new BattleUnitStats(100, 20, 10, 3.0f, 1.0f, 1.5f),
        [MercenaryClass.Archer] = new BattleUnitStats(70, 15, 5, 3.0f, 1.2f, 6.0f),
        [MercenaryClass.ShieldBearer] = new BattleUnitStats(150, 8, 20, 2.5f, 1.5f, 1.2f),
    };

    public BattleUnitStats GetStats(MercenaryClass mercenaryClass) => Table[mercenaryClass];
```

### 3.1 직업(Class) 배정 — 로스터 미완성에 대한 임시 처리

`ICaravanRosterProvider`(`PlaceholderCaravanRosterProvider`)는 현재 `Character` 유닛을 1종("character-01")만 제공하고, 직업 개념 자체가 없다. 실제 용병 개체가 직업을 가지는 정식 데이터 모델은 아직 설계되지 않았다 — 이번 설계에서 `IFormationUnit`을 확장하지 않는다(ISP: Formation UI 소비자에게 불필요한 전투 전용 필드를 얹지 않기 위함).

대신 **배치 슬롯 인덱스로 직업을 순환 배정**하는 Placeholder를 둔다.

```csharp
public interface IMercenaryClassAssigner
{
    MercenaryClass GetClass(int slotIndex);
}

/// <summary>
/// 용병 개체별 직업 데이터가 없어, 배치 슬롯 순서(occupied 슬롯 등장 순)로 3직업을 순환 배정한다.
/// 실제 로스터/직업 데이터 시스템이 설계되면 슬롯 기반이 아니라 유닛 Id 기반 조회로 교체 대상.
/// </summary>
public class RoundRobinMercenaryClassAssigner : IMercenaryClassAssigner
{
    private static readonly MercenaryClass[] Cycle =
    {
        MercenaryClass.Warrior, MercenaryClass.Archer, MercenaryClass.ShieldBearer,
    };

    public MercenaryClass GetClass(int slotIndex) => Cycle[slotIndex % Cycle.Length];
}
```

## 4. 전장 좌표 / 스폰 지점 (기획 §2)

`BattleFieldLayout`은 MonoBehaviour가 아니라 `LiveBattleSimulationRule`이 `new`로 직접 소유하는 순수 C# 객체다(§7, `RandomEncounterRule`과 같은 이유). `[SerializeField]`는 MonoBehaviour/ScriptableObject(또는 그 안에 중첩된 `[System.Serializable]` 필드)에만 적용되므로, 이 클래스에 붙여도 인스펙터에 노출되지 않는다 — `PlaceholderBattleResultRule`이 이미 쓰고 있는 방식(`private const`)으로 통일한다. 값 조정은 코드 수정으로 하고, 정말 인스펙터 노출이 필요해지면 이 값들을 `LiveBattleSimulationRule`(MonoBehaviour) 쪽 `[SerializeField]`로 옮기고 생성자로 주입하는 형태로 바꾼다.

"스폰 지점 12개"라는 수치를 두 클래스가 각자 상수로 들고 있으면 하나만 바뀌었을 때 조용히 어긋난다 — 공유 상수로 단일화한다.

```csharp
// 전장 기하 상수의 단일 출처. BattleFieldLayout과 IEncounterSpawnPointSelector 구현체가 공유한다.
public static class BattleFieldGeometry
{
    public const int SpawnPointCount = 12;
}

public interface IBattleFieldLayout
{
    Vector2 ComputeAllyPosition(int column, int row, int columnCount);
    Vector2 ComputeSpawnPoint(int spawnPointIndex);
}

public class BattleFieldLayout : IBattleFieldLayout
{
    // 설계 확정 전 임시값 - Field 전투 뷰 크기에 맞춰 제작 단계에서 조정 대상(코드 수정으로 튜닝)
    private const float SpawnRadius = 10f;
    private const float ColumnSpacing = 1f;
    private const float RowSpacing = 1.5f;

    // 열(0~columnCount-1) → 세로축(Y), 전방(열 인덱스가 클수록) 쪽이 +Y (기획 §2 회전 규칙)
    // 행(0~1) → 가로축(X). 어느 쪽이 좌/우인지는 의미 없음(대형 폭 표현일 뿐)
    public Vector2 ComputeAllyPosition(int column, int row, int columnCount)
    {
        float y = (column - (columnCount - 1) / 2f) * ColumnSpacing;
        float x = (row - 0.5f) * RowSpacing;
        return new Vector2(x, y);
    }

    public Vector2 ComputeSpawnPoint(int spawnPointIndex)
    {
        float angleRad = spawnPointIndex * (360f / BattleFieldGeometry.SpawnPointCount) * Mathf.Deg2Rad;
        return new Vector2(Mathf.Cos(angleRad), Mathf.Sin(angleRad)) * SpawnRadius;
    }
}

public interface IEncounterSpawnPointSelector
{
    int SelectSpawnPointIndex(); // 0~11
}

/// <summary>
/// 기획 §2 — 이번 세션은 균등 랜덤. 인카운터 종류별 스폰 지점 고정(매복 등)은 이 인터페이스의
/// 다른 구현체로 교체하는 것으로 확장한다(OCP) — EncounterManager/BattleManager 쪽 변경 불필요.
/// </summary>
public class UniformRandomSpawnPointSelector : IEncounterSpawnPointSelector
{
    public int SelectSpawnPointIndex() => UnityEngine.Random.Range(0, BattleFieldGeometry.SpawnPointCount);
}
```

`FormationLayout.GetUnitId(slotIndex)`의 `slotIndex`를 `row = slotIndex / columnCount`, `column = slotIndex % columnCount`로 환원해 `ComputeAllyPosition`에 넘긴다(`FormationGridView`가 이미 같은 row-major 규칙을 쓰고 있다, `FormationGridView.cs` 133행 주석 참고).

## 5. 적 진영 구성 (기획 §13)

```csharp
public interface IEnemyCompositionProvider
{
    IReadOnlyList<BattleUnitStats> GetEncounterComposition();
}

/// <summary>
/// 기획 08번 문서 §13 — 도적/산적 단일 유형, 인카운터당 3~5마리 무작위.
/// 적 진영 다양성(두목급, 다른 세력)이 설계되면 대체 대상.
/// </summary>
public class PlaceholderBanditCompositionProvider : IEnemyCompositionProvider
{
    private static readonly BattleUnitStats BanditStats =
        new(maxHp: 60, attack: 12, defense: 5, moveSpeed: 3.0f, attackInterval: 1.0f, range: 1.5f);

    public IReadOnlyList<BattleUnitStats> GetEncounterComposition()
    {
        int count = UnityEngine.Random.Range(3, 6); // 3~5 (Range의 max는 배타적)
        var result = new List<BattleUnitStats>(count);
        for (var i = 0; i < count; i++)
        {
            result.Add(BanditStats);
        }
        return result;
    }
}
```

### 5.1 적 유형 다양화 재설계 (2026-08-31, 기획 08번 §13.1 반영)

약탈자 단일 유형을 약탈자/괴수/적대자 3개 "적 타입"으로 확장하는 기획이 확정됨에 따라 위 코드를 아래처럼 재설계한다. `IEnemyCompositionProvider` 인터페이스 자체는 무변경 — 소비 측(`LiveBattleSimulationRule.BuildEnemies`)은 여전히 "이번 인카운터에 스폰할 `BattleUnitStats` 목록"만 받으면 되고, "타입이 몇 종류인지·어떻게 고르는지"는 구현체 내부 관심사다.

**① `BattleUnitStats`에 재생 필드 추가 — 기존 호출부 무변경**

```csharp
public readonly struct BattleUnitStats
{
    // ...기존 6개 프로퍼티...
    public float HpRegenPerSecond { get; }

    public BattleUnitStats(
        float maxHp, float attack, float defense, float moveSpeed, float attackInterval, float range,
        float hpRegenPerSecond = 0f)
    {
        // ...기존 대입...
        HpRegenPerSecond = hpRegenPerSecond;
    }
}
```

기본값 0f인 선택적 매개변수로 추가해 `PlaceholderBattleUnitStatProvider`(용병 3직업)의 기존 6-인자 호출부가 전부 그대로 컴파일된다 — 재생은 괴수 전용 특성이고 나머지 모든 유닛(용병 3직업 + 약탈자/적대자)은 값을 안 주면 자연히 0(재생 없음)이 된다(§13.1 "괴수만의 특징").

**② 재생 적용 — `BattleCharacterUnit.Tick` 최상단, 상태 무관**

```csharp
public void Tick(...)
{
    if (!IsAlive) return;
    ApplyRegen(deltaTime);   // 신규 - 교전/도주/복귀 상태와 무관하게 항상 적용
    TickMorale(deltaTime, targets);
    ...
}

private void ApplyRegen(float deltaTime)
{
    if (stats.HpRegenPerSecond <= 0f) return; // 0이면 즉시 반환 - 나머지 타입엔 비용 없음
    currentHp = Mathf.Min(stats.MaxHp, currentHp + stats.HpRegenPerSecond * deltaTime);
}
```

별도 전략 인터페이스로 뽑지 않는다 — §12번 문서의 6개 전략 협력자는 "방향성 지시(전술)가 있는 아군에서만 갈리는 행동"을 분리한 것인데, 재생은 방향성 지시와 무관하게 스탯 값 하나로만 결정되는 단순 파생 동작이라 굳이 협력자를 만들 이유가 없다(§5.1-1 재탐색 플래그와 같은 판단 - 기존 것을 확장).

```csharp
/// 두목급 변형·타입 선택 가중치·난이도 스케일링(§14.7 잔여 미정)이 설계되면 대체 대상.

    // Random.Range의 max는 배타적 - (3,6)=3~5, (2,5)=2~4, (1,3)=1~2 (기획 08번 §13.1 표 그대로).

    public IReadOnlyList<BattleUnitStats> GetEncounterComposition()
    {
        var type = (EnemyType)Random.Range(0, 3); // 3개 타입 균등 무작위 - §13.1 확정
        var stats = StatsByType[type];
        var countRange = CountRangeByType[type];
        var count = Random.Range(countRange.x, countRange.y);

        var result = new List<BattleUnitStats>(count);
        for (var i = 0; i < count; i++) result.Add(stats);
        return result;
    }
}
```

`UniformRandomSpawnPointSelector`(§2 스폰 지점 선택)와 같은 패턴으로 타입도 `Random.Range(0, 3)` 균등 무작위 — 가중치 조정(§14.7 잔여 미정)이 필요해지면 이 한 줄만 바뀔 대체 대상이다. 여전히 `Placeholder` 접두사를 유지한다 — 두목급 변형/타입별 가중치/난이도 스케일링을 다루는 "진짜" 인카운터 콘텐츠 시스템은 아직 없고, 지금은 그 자리를 채우는 하드코딩된 3타입 테이블이기 때문이다(CLAUDE.md Placeholder 컨벤션).

**⑤ 배선 변경**: `LiveBattleSimulationRule.enemyProvider` 필드의 `new PlaceholderBanditCompositionProvider()`를 `new PlaceholderEnemyTypeCompositionProvider()`로 교체. 그 외 `BuildEnemies`/`BattleCharacterUnit` 생성 경로는 무변경 — `IEnemyCompositionProvider` 인터페이스가 그대로라 소비 측이 타입 개념 자체를 몰라도 된다(OCP).

**적대자 "개별 패턴"의 향후 스킬 확장 여지(기획 §13.1)**: 이번 설계는 스탯만으로 표현하고 스킬 관련 구조는 추가하지 않는다 — `BattleUnitStats`/`BattleCharacterUnit`에 스킬 훅을 미리 만들어두는 것은 아직 근거 없는 선제 설계(YAGNI)라 하지 않는다. 다만 `BattleUnitStats`가 이미 순수 데이터 구조체이고 `BattleCharacterUnit.Tick`이 전략 협력자(공간 탐색/방향성 지시)에 위임하는 구조라, 실제로 스킬을 붙이게 되면 "적 전용 전략 협력자를 하나 더 추가"하는 형태로 확장 가능한 여지는 이미 있다 — 별도 준비 작업 불필요.

## 6. 유닛 인스턴스 및 시뮬레이션 루프 (기획 §5)

### 6.1 데미지 공식 — 별도 전략으로 분리

기획 단계에서 §5.3 공식은 세 번 바뀌었다(가산 고정값 → 비율 → 구간별 곡선). 그 정도로 자주 바뀌는 로직을 유닛 행동 클래스에 박아두면 수정 때마다 `BattleCharacterUnit`을 건드려야 한다 — `IBattleResultRule`에 이미 적용한 것과 같은 논리(OCP 확장점)를 여기도 적용한다.

```csharp
public interface IDamageFormula
{
    float ComputeDamage(float attack, float defense);
}

/// <summary>
/// 기획 08번 문서 §5.3 — 방어력이 공격력의 0.7배를 넘으면 반비례 곡선 구간으로 전환.
/// </summary>
public class PlaceholderDamageFormula : IDamageFormula
{
    public float ComputeDamage(float attack, float defense)
    {
        var breakpoint = attack * 0.7f;
        return defense <= breakpoint
            ? attack - defense
            : 0.21f * attack * attack / defense;
    }
}
```

### 6.2 타겟 계약 분리 — `IDamageable` / `IBattleCombatant`

피격 대상(맞고 죽을 수 있는 것)과 능동 전투 유닛(이동·타겟팅·공격하는 것)을 분리한다. §9의 Wagon/Facility는 이동도, 공격도 하지 않지만 피해는 받는다 — `IBattleCombatant`(Tick 포함)를 구현하면 아무 의미 없는 `Tick`을 억지로 채워야 하므로(LSP 위반 소지), 최소 계약인 `IDamageable`만 구현하게 한다.

```csharp
public interface IDamageable
{
    Vector2 Position { get; }
    bool IsAlive { get; }
    float Defense { get; }
    event Action OnDied;   // HP가 0을 넘어 처음 죽는 순간 1회만 발행 (§6.3 BattleSimulationLoop가 구독)
    void TakeDamage(float amount);
}

public interface IBattleCombatant : IDamageable
{
    bool IsAlly { get; }
    void Tick(float deltaTime, IReadOnlyList<IDamageable> targets);
}
```

`Defense`를 `IDamageable`에 둔 이유: `Tick`(이동/공격 능력)과 달리 "피해를 얼마나 경감하는가"는 Wagon/Facility에도 의미가 있는 값이다(기획 §4: 방어력 등은 "해당 없음(N/A)" — 즉 0으로 취급해도 자연스럽다). `Tick`처럼 억지로 빈 구현을 채워야 하는 경우가 아니라서 `IDamageable`에 둬도 ISP를 어기지 않는다.

`OnDied`를 둔 이유: §6.3에서 `BattleSimulationLoop`가 전멸 여부를 매 프레임 리스트 전체 스캔 없이(`TrueForAll`) 판단하려면, "몇 명이 죽었는지"를 이벤트로 통지받아 카운터만 감소시키는 편이 낫다.

`IBattleCombatant`는 전투 중에만 존재하는 순수 데이터+행동 객체다. Unity 생명주기가 필요 없으므로 MonoBehaviour가 아니다 — `RandomEncounterRule`과 같은 이유([[05-2026-08-25-인카운터_판정_아키텍처]] §4).

```csharp
/// <summary>
/// 기획 §5.1(최근접 타겟팅)·§5.2(이동-공격 사이클)을 구현한다. 데미지 계산은 IDamageFormula에 위임한다.
/// </summary>
public class BattleCharacterUnit : IBattleCombatant
{
    public Vector2 Position { get; private set; }
    public bool IsAlly { get; }
    public bool IsAlive => currentHp > 0f;
    public float Defense => stats.Defense;
    public event Action OnDied;

    private readonly BattleUnitStats stats;
    private readonly IDamageFormula damageFormula;
    private float currentHp;
    private IDamageable target;
    private float attackCooldown;

    public BattleCharacterUnit(Vector2 startPosition, bool isAlly, BattleUnitStats stats, IDamageFormula damageFormula)
    {
        Position = startPosition;
        IsAlly = isAlly;
        this.stats = stats;
        this.damageFormula = damageFormula;
        currentHp = stats.MaxHp;
    }

    // 타겟 고정(sticky targeting): 살아있는 타겟이 있는 동안은 재탐색하지 않는다. 매 프레임 전체
    // 재탐색(O(n))을 피하기 위한 의도된 선택이며, 기획 §5.1 "가장 가까운 적"은 엄밀히는 "타겟 획득
    // 시점 기준 최근접"으로 완화되어 적용된다 - 도중에 더 가까운 적이 나타나도 갈아타지 않는다.
    public void Tick(float deltaTime, IReadOnlyList<IDamageable> targets)
    {
        if (!IsAlive) return;

        if (target is not { IsAlive: true })
        {
            target = FindNearestTarget(targets);   // §5.1
            if (target == null) return;
        }

        var toTarget = target.Position - Position;
        var distance = toTarget.magnitude;

        if (distance > stats.Range)               // §5.2 1번
        {
            Position += toTarget.normalized * stats.MoveSpeed * deltaTime;
            return;
        }

        attackCooldown -= deltaTime;               // §5.2 2~3번
        if (attackCooldown <= 0f)
        {
            target.TakeDamage(damageFormula.ComputeDamage(stats.Attack, target.Defense));
            attackCooldown = stats.AttackInterval;
        }
    }

    public void TakeDamage(float amount)
    {
        if (!IsAlive) return;   // 이미 죽은 대상은 무시 - OnDied가 두 번 발행되지 않도록
        currentHp = Mathf.Max(0f, currentHp - amount);
        if (!IsAlive) OnDied?.Invoke();
    }

    private IDamageable FindNearestTarget(IReadOnlyList<IDamageable> targets)
    {
        IDamageable nearest = null;
        var nearestSqrDist = float.MaxValue;
        foreach (var candidate in targets)
        {
            if (!candidate.IsAlive) continue;
            var sqrDist = (candidate.Position - Position).sqrMagnitude;
            if (sqrDist < nearestSqrDist)
            {
                nearestSqrDist = sqrDist;
                nearest = candidate;
            }
        }
        return nearest;
    }
}
```

### 6.3 시뮬레이션 루프 — 생존 카운터

```csharp
/// <summary>
/// 순수 C# 합성 객체. 아군/적 리스트를 들고 매 틱 각 유닛의 Tick을 돌리고, 전멸 여부를 노출한다.
/// 사기로 인한 도주(기획 §7)나 보호 목표 파괴(§9)는 포함하지 않는다 — 이번 설계는 "전멸전"만 다룬다.
/// 생존 수는 매 프레임 리스트를 다시 스캔(TrueForAll)하지 않고, OnDied 이벤트로 카운터를 유지한다.
/// </summary>
public class BattleSimulationLoop
{
    private readonly List<IBattleCombatant> allies;
    private readonly List<IBattleCombatant> enemies;
    private int aliveAllyCount;
    private int aliveEnemyCount;

    public BattleSimulationLoop(List<IBattleCombatant> allies, List<IBattleCombatant> enemies)
    {
        this.allies = allies;
        this.enemies = enemies;
        aliveAllyCount = allies.Count;
        aliveEnemyCount = enemies.Count;

        foreach (var ally in allies) ally.OnDied += () => aliveAllyCount--;
        foreach (var enemy in enemies) enemy.OnDied += () => aliveEnemyCount--;
    }

    public bool IsAllyWiped => aliveAllyCount <= 0;
    public bool IsEnemyWiped => aliveEnemyCount <= 0;

    public void Tick(float deltaTime)
    {
        foreach (var unit in allies)
        {
            if (unit.IsAlive) unit.Tick(deltaTime, enemies);
        }
        foreach (var unit in enemies)
        {
            if (unit.IsAlive) unit.Tick(deltaTime, allies);
        }
    }
}
```

## 7. `IBattleResultRule` 통합 — `LiveBattleSimulationRule`

`BattleResultEvaluator`는 `GetComponent<IBattleResultRule>()`로 규칙 구현체를 찾는다(변경 없음, [[BattleResultEvaluator.cs]] 참고). `PlaceholderBattleResultRule` 대신 이 컴포넌트를 붙이면 교체가 끝난다.

```csharp
public class LiveBattleSimulationRule : MonoBehaviour, IBattleResultRule, IRequiresFormationReader
{
    private readonly IBattleUnitStatProvider statProvider = new PlaceholderBattleUnitStatProvider();
    private readonly IMercenaryClassAssigner classAssigner = new RoundRobinMercenaryClassAssigner();
    private readonly IEncounterSpawnPointSelector spawnSelector = new UniformRandomSpawnPointSelector();
    private readonly IEnemyCompositionProvider enemyProvider = new PlaceholderBanditCompositionProvider();
    private readonly IBattleFieldLayout fieldLayout = new BattleFieldLayout();
    private readonly IDamageFormula damageFormula = new PlaceholderDamageFormula();

    private IFormationReader formationReader;   // BattleManager가 주입 (§7.1)
    private BattleSimulationLoop simulation;
    private Action<BattleResult> onResult;
    private bool resultReported;

    // BattleManager.ResolveDependencies가 IRequiresFormationReader로 캐스팅해 호출한다(§7.1).
    public void SetFormationReader(IFormationReader reader) => formationReader = reader;

    public void Evaluate(Action<BattleResult> onResult)
    {
        this.onResult = onResult;
        resultReported = false;
        simulation = BuildSimulation();
    }

    private void Update()
    {
        if (simulation == null || resultReported) return;

        simulation.Tick(Time.deltaTime);

        if (simulation.IsEnemyWiped) Report(BattleOutcome.Victory);
        else if (simulation.IsAllyWiped) Report(BattleOutcome.Defeat);
    }

    private void Report(BattleOutcome outcome)
    {
        resultReported = true;
        onResult(new BattleResult(outcome));
    }

    // 아군/적 구성을 따로 뽑아둔다 - §9(보호 목표), §7(사기)가 이미 다음 설계 대상으로 예정돼 있어
    // 이 두 메서드가 각자 더 커질 걸 알고 있다. 한 메서드에 몰아두면 다음 확장 때 더 번거로워진다.
    private BattleSimulationLoop BuildSimulation() => new(BuildAllies(), BuildEnemies());

    private List<IBattleCombatant> BuildAllies()
    {
        var allies = new List<IBattleCombatant>();
        if (formationReader == null || !formationReader.TryLoadCurrent(out var layout))
        {
            return allies;
        }

        for (var slotIndex = 0; slotIndex < layout.SlotCount; slotIndex++)
        {
            var unitId = layout.GetUnitId(slotIndex);
            if (unitId == null) continue;   // Wagon/Facility는 §9에서 별도 처리 - 이번 루프는 Character만

            var column = slotIndex % layout.ColumnCount;
            var row = slotIndex / layout.ColumnCount;
            var position = fieldLayout.ComputeAllyPosition(column, row, layout.ColumnCount);
            var stats = statProvider.GetStats(classAssigner.GetClass(slotIndex));
            allies.Add(new BattleCharacterUnit(position, isAlly: true, stats, damageFormula));
        }
        return allies;
    }

    private List<IBattleCombatant> BuildEnemies()
    {
        var spawnCenter = fieldLayout.ComputeSpawnPoint(spawnSelector.SelectSpawnPointIndex());
        return enemyProvider.GetEncounterComposition()
            .Select(enemyStats => (IBattleCombatant)new BattleCharacterUnit(spawnCenter, isAlly: false, enemyStats, damageFormula))
            .ToList();
    }
}
```

### 7.1 `BattleManager` 쪽 변경 — 마커 인터페이스로 `IFormationReader` 주입

`IBattleResultRule` 자체에 `SetFormationReader`를 얹으면 `PlaceholderBattleResultRule`류의 단순 규칙까지 불필요한 메서드를 갖게 된다(ISP 위반). 그렇다고 `BattleManager`가 `LiveBattleSimulationRule`을 구체 타입으로 알면 새 규칙이 추가/교체될 때마다 `BattleManager`를 다시 고쳐야 한다(OCP 위반, §1). 이 둘을 동시에 지키기 위해 "이 정보가 필요하다"는 것만 표시하는 좁은 마커 인터페이스를 따로 둔다.

```csharp
// IFormationReader가 필요한 IBattleResultRule 구현체만 선택적으로 구현하는 마커 인터페이스.
public interface IRequiresFormationReader
{
    void SetFormationReader(IFormationReader reader);
}
```

**2026-09-01 갱신**: 아래 스니펫은 작성 당시(`IBattleResultEvaluator` 존재 시점) 기준이다. 2026-08-26 리팩토링으로 그 계층이 삭제된 지금은 `resultEvaluator` 필드 자체가 없고, `GetComponent<IBattleResultRule>()`을 바로 호출한다 — 이후 로직(마커 인터페이스로 `IFormationReader` 선택 주입)은 동일하다.

```csharp
public void ResolveDependencies(IDependencyRegistrar registrar)
{
    resultRule = GetComponent<IBattleResultRule>();
    if (resultRule == null)
        throw new InvalidOperationException(...);

    // 어떤 규칙이 붙어있든 상관없다 - IRequiresFormationReader를 구현했을 때만 주입한다.
    // LiveBattleSimulationRule을 이름으로 알 필요가 없으므로, 이후 같은 인터페이스를 구현하는
    // 새 규칙이 추가/교체돼도 이 코드는 다시 바뀌지 않는다(OCP).
    // IFormationReader 자체는 DI에 등록되지 않는다 - InMemoryFormationRepository는
    // IFormationRepository로만 등록하므로(제네릭 타입 키라 상위 인터페이스로는 조회 불가),
    // IFormationRepository로 조회해 업캐스트한다(UIManager의 기존 패턴과 동일, 제작 단계에서
    // Resolve<IFormationReader>()로 잘못 작성했다가 DependencyNotRegisteredException으로 발견됨).
    // 상행 관리 데이터 시스템이 아직 없는 동안은 CLAUDE.md 컨벤션대로 TryResolve로 선택 조회한다.
    if (GetComponent<IBattleResultRule>() is IRequiresFormationReader formationConsumer
        && registrar.TryResolve<IFormationRepository>(out var formationRepository))
    {
        formationConsumer.SetFormationReader(formationRepository);
    }
}
```

이번 설계에서 `BattleManager`가 받는 유일한 변경은 위 마커 인터페이스 확인 + 주입 블록이다 — `IRequiresFormationReader`라는 "개념"을 처음 지원하는 데 1회 필요한 비용이며, 이후 이 인터페이스를 구현하는 규칙이 몇 개가 되고 서로 교체되어도 `BattleManager`는 무변경이다.

## 9. 최적화 요약

- `BattleSimulationLoop.Tick`은 `foreach` 1회 순회만 수행. 유닛별 최근접 탐색(`FindNearestTarget`, O(n))은 **타겟이 없거나 죽었을 때만** 호출된다(타겟 고정/sticky targeting, §6.2) — 매 프레임 재탐색하지 않는 대신, 더 가까운 적이 새로 나타나도 갈아타지 않는다는 트레이드오프를 감수한다. 유닛 수가 적어(아군 최대 16, 적 3~5) 지금은 재탐색 비용 자체도 무시할 만하다. **2026-08-30**: "타겟이 사거리 밖 + 피격당함"도 재탐색 트리거에 추가됐다(§10-9) — 매 프레임이 아니라 피격 이벤트 빈도(공격주기 단위)로만 추가 호출되므로 이 트레이드오프의 성격 자체는 유지된다.
- `IsAllyWiped`/`IsEnemyWiped`는 매 프레임 리스트를 다시 스캔하지 않는다 — `OnDied` 이벤트로 생존 카운터(`aliveAllyCount`/`aliveEnemyCount`)를 유지하고 프로퍼티는 정수 비교만 한다(§6.3).
- 유닛 오브젝트(`BattleCharacterUnit`)는 전투 시작 시 1회만 생성하고 전투 종료까지 재사용 — 매 프레임 할당 없음.
- 유닛 수가 크게 늘어나는 인카운터가 생기면 `FindNearestTarget`의 O(n) 탐색이 병목이 될 수 있다 — 공간 분할(그리드/쿼드트리) 재검토 대상(§10).

(변경 없음, 계속 유효 — sticky 자체는 그대로지만, **2026-08-26**: 탐색 로직(`FindNearestTarget`)과 근접 반발 계산이 `IUnitSpatialQuery`(신규 확장점)로 분리됐다. `BattleCharacterUnit`은 "누가 이웃/최근접인지 어떻게 찾을지"를 몰라도 되고, 현재 구현체는 여전히 O(n) 선형 탐색(`LinearScanUnitSpatialQuery`)이다 — 실제 공간 분할 구현체는 아직 없이 교체 가능한 구조만 마련해 둔 상태.)

   **2026-08-30 설계 (기획 08번 §5.1-1 확정에 따른 해소)** — 실전투에서 "타겟을 전투 내내 절대 안 바꾼다"는 문제로 확인되어(주기적 재탐색이 아니라) 이벤트 기반 재탐색 조건 하나를 추가하기로 확정. "누구로" 재탐색할지(§5.1의 최근접/`TargetSelector`)는 그대로 두고, "언제" 재탐색을 트리거할지만 확장하는 것이라 새 전략 인터페이스는 만들지 않는다 — `IPursuitPolicy`(추적을 포기하고 복귀할지 판정, 결이 다른 개념)나 `ITargetSelector`(이미 "누구로"를 맡고 있음) 어느 쪽에도 끼워 넣지 않고, 기존 스티키 타겟팅 자체의 정의를 고치는 것이므로 `BattleCharacterUnit` 내부 상태로 처리한다(기존 것을 확장 — 새 협력자 불필요).
   - `BattleCharacterUnit`에 `private bool retargetRequested` 필드 추가.
   - `TakeDamage`에서 `target is { IsAlive: true }`이고 현재 타겟과의 거리가 `stats.Range`보다 크면(§5.2 1단계, 접근 중 — 이미 사거리 안에서 교전 중이면 조건 불성립이라 자동으로 무시됨, §5.1-1의 "교전 중엔 무시" 요구사항이 별도 분기 없이 이 거리 비교 자체로 충족된다) `retargetRequested = true`로 세팅.
   - `TickEngageWithoutTactics`/`TickEngageWithTactics` 진입부의 기존 `target is not { IsAlive: true }` 재탐색 분기 조건을 `target is not { IsAlive: true } || retargetRequested`로 확장하고, 그 분기에 실제로 들어가면 플래그를 소비해 `false`로 되돌린다. 재탐색 결과를 만드는 호출(`spatialQuery.FindNearest`/`tacticsBehaviors.TargetSelector.Select`)은 그대로 재사용 — 알고리즘 자체는 무변경.
   - 적용 범위(아군+적 모두, §5.1-1 3번)는 두 메서드 각각에 동일한 조건을 넣는 것만으로 자연히 충족된다 — 별도 분기·플래그 공유 불필요.
   - **타이밍 판단(설계 단계에서 새로 채움)**: 피격은 공격자 쪽 Tick 도중 임의 시점에 발생하므로 "피격당한 그 즉시" 별도 콜백으로 재탐색하지 않고, 플래그만 세워 **이 유닛의 다음 Tick 진입 시점**에 소비한다 — 최대 한 프레임 지연이라 체감 차이가 없고, 기존 Tick 흐름 밖에 새 콜백 경로를 만들 필요가 없다.
